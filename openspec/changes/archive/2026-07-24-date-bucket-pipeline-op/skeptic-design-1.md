## Skeptic Report — design gate (round 1)

### What I verified (with evidence)

- Read `ticket.md`, `proposal.md`, `design.md`, `tasks.md`, `specs/pipeline-date-bucket-op/spec.md` in full.
- **Flyway V-number claim (design.md Decision 7 / tasks.md 1.1).** `ls backend/src/main/resources/db/migration/ | sort -t V -k2 -n | tail` shows the current max is `V63__pipeline_run_trigger_source.sql`, and `V52__add_chunkbytokencount_op.sql` is the most recent `pipeline_steps_op_check` migration. `V64` is correct and free as of this review. `V52`'s op list (`rename, filter, join, compute, groupby, cast, select, limit, sort, aggregate, splittext, extractheadings, chunkbytokencount` — 13 values) matches `PipelineStep.Registry` in `backend/src/main/scala/com/helio/domain/PipelineStep.scala:101-115` exactly (13 entries), confirming the "14th kind" framing in design.md and the "13 → 14" framing in tasks.md 4.4.
- **`jsonFormat3` vs `jsonFormat6` self-correction (design.md Planner Notes).** Verified against `backend/src/main/scala/com/helio/api/protocols/PipelineStepProtocol.scala:149-161` and `PipelineAnalyzeProtocol.scala:140-145`: every `*StepResponse` / `*AnalyzeStepResponse` wrapper (id/pipelineId/position/createdAt/updatedAt/config, or id/position/config/inputSchema/outputSchema/validationError) is 6 fields → `jsonFormat6`, while each `*Config` itself uses its own field-count-derived formatter (e.g. `ComputeConfig` → `jsonFormat3` for 3 fields). Design's self-approved correction is accurate.
- **Epoch/flooring math (spec.md scenarios).** `date -d 2026-03-19 +%A` → Thursday; `date -d 2026-03-16 +%A` → Monday — matches the "Floor to week" scenario. `date -u -d @1771286400` → `2026-02-17`, a valid date, consistent with the epoch-seconds scenario (10-digit threshold correctly classifies 1771286400 as seconds, not millis). Quarter arithmetic `((month-1)/3)*3+1` for month=8 → 7 (July), matches the "Floor to quarter" scenario (2026-08-05 → 2026-07-01).
- **Cast/Compute analog claims (design.md Context, Decision 6).** Read `CastStep.scala`, `ComputeStep.scala`. Confirmed `cast`'s `"date"` target type is already represented on the wire as a plain string (`CastStep.scala:72`, `case "date" => str`) — design's claim that `date` fields are plain ISO strings, not a distinct runtime type, is accurate. Confirmed the frontend wiring claim (`cast` reads `inputSchema` via `analyzeColumns`, `compute` does not) against `StepCard.tsx:147-162` and `CastFieldsConfig.tsx`.
- **`inferCompute` append-or-replace claim — FALSIFIED.** Design.md Decision 4 states `inferDateBucket` "mirrors `inferCompute`'s append-or-replace shape." Read `PipelineAnalyzeService.scala:114-136`: `inferCompute` unconditionally does `inputSchema :+ SchemaField(name = column, ...)` with **no** existence/collision check — it always appends, never replaces (a compute step whose `column` collides with an existing field name would produce a duplicate-named field, a pre-existing quirk of `compute`, not "replace" behavior). The actual append-or-replace pattern (`filterNot` on the target name, then `:+`) lives in `inferSplitText` (`PipelineAnalyzeService.scala:182-183`), `inferExtractHeadings` (216-217), and `inferChunkByTokenCount` (253-254) — those three explicitly document "replacing any existing field of the same name." Design's own Decision 4 *behavior spec* for `datebucket` (replace-in-place if the name exists, else append) is itself correct and matches spec.md's two analyze scenarios — but the cited precedent is the wrong file.
- **Frontend types surface (design.md Decision 6 / tasks.md 2.1).** Read `frontend/src/features/pipelines/types/pipelineStep.ts` in full. Each existing op requires **four** additions to this one file: the `*Config` interface, a `*Step extends BasePipelineStep` interface (+ entry in the `PipelineStep` and `PipelineStepConfig` unions), and a `*AnalyzeStep extends BaseAnalyzeStep` interface (+ entry in the `AnalyzeStepResult` union) — see e.g. `CastConfig`/`CastStep`/`CastAnalyzeStep` at lines 35-37, 111-114, 211-214, plus the two union entries at 150 and 250. `AnalyzeStepResult` and `PipelineStepConfig` are consumed widely (`StepCard.tsx`, `useStepCardState.ts`, `PipelineRiverView.tsx`, `pipelineService.ts`, `PipelineDetailPage.tsx`, `stepNarrowing.ts` — confirmed via grep). Tasks.md 2.1 says only "add `DateBucketConfig` wire type," understating the file's actual scope by 3 of 4 required additions.
- **Frontend test coverage gap.** `CONTRIBUTING.md:38` — "Write Jest tests for components, hooks, selectors, and reducers" (binding). `find frontend/src/features/pipelines -iname "*.test.tsx"` shows **every** existing per-op editor component has a co-located test: `CastFieldsConfig.test.tsx`, `ComputeFieldConfig.test.tsx`, `SplitTextConfig.test.tsx`, `ExtractHeadingsConfig.test.tsx`, `ChunkByTokenCountConfig.test.tsx`, `FilterConfig.test.tsx`, `LimitConfig.test.tsx`, `RenameFieldsConfig.test.tsx`, `SelectFieldsConfig.test.tsx`, `SortConfig.test.tsx` — no exceptions. Tasks.md section 4 ("Tests") lists four backend-only test tasks (4.1-4.4: `InProcessPipelineEngineSpec`, analyze-schema test, codec round-trip, `PipelineStepSpec` kind-parity) and has **no** task for a `DateBucketConfig.test.tsx`. AC 4 ("Frontend StepCard renders a working editor; config PATCHes round-trip") and AC 6 (the test-coverage AC) have no automated-test hook on the frontend side as currently planned — this is a real, unclaimed acceptance-criterion gap, not just a nit, given the 100%-consistent codebase convention and the binding CONTRIBUTING.md instruction.
- **MCP op-list terminology.** `helio-mcp/src/tools/write.ts:152-169`: `add_pipeline_step`'s `type` field is `z.string().min(1)` (free text), not a `z.enum`, and the field is literally named `type`, not `op`. Ticket/spec/tasks all describe this as "the `op` enum" — a pre-existing terminology looseness inherited from the ticket, not introduced by design. Self-correcting on read (non-blocking, noted only).
- **Backward-compat / additive claim.** Registry-driven `PipelineStepKind.All` (`PipelineStep.scala:150`) and the `Map`-registration pattern mean a new `Registry` entry is genuinely additive; the migration's drop/re-add pattern (`V52` reviewed) only widens the CHECK set. No contradiction found.

### Verdict: REFUTE

### Change Requests

1. **Add a frontend Jest test task for the new editor component.** `tasks.md` section 2 (or 4) needs an explicit task to add `frontend/src/features/pipelines/ui/DateBucketConfig.test.tsx`, mirroring the sibling `*Config.test.tsx` files (e.g. `CastFieldsConfig.test.tsx`, `ChunkByTokenCountConfig.test.tsx`). Every existing per-op editor component has one; `CONTRIBUTING.md:38` binds this ("Write Jest tests for components, hooks, selectors, and reducers"). Without this task, AC 4 and the test-coverage bullet in AC 6 have no frontend enforcement and are likely to ship unverified.

2. **Correct design.md Decision 4's cited precedent.** `inferCompute` (`PipelineAnalyzeService.scala:114-136`) does not do append-or-replace — it unconditionally appends via `inputSchema :+ SchemaField(...)` with no name-collision check. Update Decision 4 to cite the actual append-or-replace pattern used by `inferSplitText`/`inferExtractHeadings`/`inferChunkByTokenCount` (`filterNot` on the resolved name, then `:+`) instead, so the executor copies the correct existing code shape rather than looking at `inferCompute` for a "replace" branch that doesn't exist there. (The behavior described for `inferDateBucket` itself is correct and need not change — only the citation.)

3. **Expand tasks.md 2.1's scope for `types/pipelineStep.ts`.** The task currently says only "add `DateBucketConfig` wire type." Ground truth shows each existing op needs four additions to this file: the `*Config` interface, a `DateBucketStep extends BasePipelineStep` interface (+ entry in the `PipelineStep` and `PipelineStepConfig` unions), and a `DateBucketAnalyzeStep extends BaseAnalyzeStep` interface (+ entry in the `AnalyzeStepResult` union). Spell these out explicitly (as the task already does correctly for the backend's four-file surface) so the scope isn't discovered piecemeal via TypeScript compile errors during implementation.
