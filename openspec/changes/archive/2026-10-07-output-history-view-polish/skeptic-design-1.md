### Verdict: REFUTE

The design is substantially sound, and D1's deviation from §5 is correct in substance. Two verification specifications need fixing before execution, because as written they cannot prove what they claim.

### Change Requests

1. **D4 and task 3.2: the long-table check cannot exercise the path D4 itself flags as at risk.** D4 says "the virtualised path needs a bounded scroll container — verify it is still bounded", but tells the executor to verify with "a >20-row payload". Windowing only engages above `VIRTUALIZATION_ROW_THRESHOLD = 150` (`frontend/src/shared/ui/DataGrid.tsx:205,635`). A 20–150-row table renders every row without windowing, so it passes whether or not `useVirtualRows`' scroll container is bounded. This is the HEL-1060 trap that `DataGrid.tsx`'s own comment names: a fixture below the threshold passes regardless. Revise D4 and task 3.2 to require three running-app sizes:
   - a 2-row payload: the note sits directly under the rows;
   - a non-virtualised overflowing payload (roughly 20–150 rows): it scrolls inside 360px;
   - a payload above 150 rows: the table is virtualised, the scroll container's rendered height is at most 360px, and scrolling to the bottom renders the final rows, with no blank spacer gap and no unbounded growth.

   For each size, record the measured `.output-history__table` and `.ui-data-grid` `getBoundingClientRect().height`.
2. **D1 and task 4.2: replace "differs in both themes" with a measured contrast acceptance signal.** DESIGN.md's HEL-866 note says the arbiter is a rendered contrast measurement against the real backdrop, and that "non-identical but not measurably different" (1.04) was rejected. My computation gives 1.122 dark and 1.179 light against the guard's 1.10 threshold, which passes, but with little margin in dark. D1 should record these figures and the 1.10 threshold. Task 4.2 should sample the rendered hovered-button pixel against the hovered-card pixel in both themes and state the ratio. Only that sample proves the hover is visible: the stylesheet values alone do not, because transitions and opacity can change what actually renders. Also state in the D1 comment which backdrop this is (`--app-surface-soft`, the hovered card). HEL-866's three-row table does not list that backdrop, so the next reader cannot look it up there.

### Non-blocking notes

- D2 does not say what `formatCapturePair` (or the header) does when there is no comparison point (the oldest point is selected). Today the header falls back to minute precision through `formatCaptureTime(selected, false)`. Keeping exactly that is the obvious reading, but the executor should state it in the helper's signature (e.g. `comparisonIso: string | null`) or keep `formatCaptureTime` for that branch.
- The `fractionalSecondDigits` output from `toLocaleString(undefined, …)` depends on the locale and ICU build. The RTL and unit tests in 2.1/2.3 should assert relationships (header differs from the "vs" label; the label contains the ms digits "900"/"100"; the suffix is present), not exact localized strings, so the tests are not tied to Node's default locale.
- `HistoryScrubber`'s per-point accessible names stay at minute precision, so two same-minute points still share an accessible name on the range control. D2 excludes this as a non-goal, which is acceptable for this ticket. It is a candidate follow-up, because the same "which point is which" problem exists for screen-reader users.
- Task 1.1's guard extension should also assert the hover stays `--app-surface-raised`. Otherwise a future well-meaning "fix to §5 literal" reintroduces the invisible hover and nothing goes red.
