## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

1. **AiStepClient seam / wiring.** Read `backend/src/main/scala/com/helio/domain/model/PipelineStep.scala:99-125` — `PipelineExecutionContext` already carries exactly this pattern for `writeBackSink` (HEL-1100, defaulted field, threaded through `InProcessPipelineEngine.makeContext`). Adding `aiClient: AiStepClient = AiStepClient.Unavailable` is a direct extension of an established, working precedent, not a novel mechanism.
   - `grep -rn "new InProcessPipelineEngine("` (`backend/src/main`) → exactly **one** production construction site: `PipelineRunService.scala:108`. `grep -n "new PipelineRunService"` in `ApiRoutes.scala` → exactly one site, `ApiRoutes.scala:315`. Design's claim that the engine is built in exactly one place, reused by both `execute`/`executeTree` (and hence preview, since preview goes through the same `PipelineRunService`/engine instance — no separate preview-only engine construction found) is correct. Every construction path is a single chokepoint; the design's DI story is sound.
   - `ApiRoutes.scala:580,588,604,612,625,626,631` — confirmed **three** existing `ClaudeConfig.fromEnv()`-gated `ClaudeClient`/`HttpClaudeTransport` construction sites (`dashboardAuthoringServiceOpt`/`refinementServiceOpt`/`assistantServiceOpt`), each following the identical Left/Right + log-warn convention design.md describes as the pattern for the new `AiStepClient` wiring. Grounded, not invented.

2. **No-API-key degrade path.** `AiStepClient.Unavailable` as the context default (mirrors `writeBackSink = new WriteBackSink` default) means a run with no key still boots and fails only at step-evaluation time with a named `ai-unavailable` reason — consistent with the existing `StepExecutionException.from` `IllegalArgumentException`-message-verbatim allowlist (`InProcessPipelineEngine.scala:41-51`). Sound.

3. **Single HEL-1108 call point / ownerUserId.** `ClaudeError` (`backend/src/main/scala/com/helio/ai/ClaudeModels.scala:48-63`) has exactly three variants: `ApiError`, `TransportFailure`, `GuardrailExceeded`. Design's D2 says `ClaudeAiStepClient` maps `ClaudeError`s to `AiStepFailure(Unavailable, Guardrail, Api, Transport)` — `Unavailable` is not itself a `ClaudeError` variant (it's the context-level default, never produced by `ClaudeAiStepClient` itself). This is loose wording but not a functional defect — non-blocking.
   - `ownerUserId` availability at the engine: not independently traced end-to-end (no current caller passes user identity into `PipelineExecutionContext`), but the design only requires it be `Option[String]`, populated "when the engine knows it and otherwise `None`" — a deliberately deferred, non-blocking commitment for HEL-1108, not a gap in this ticket's own scope.

4. **CLAUDE_MAX_TOKENS / CLAUDE_MAX_INPUT_TOKENS enforcement.** `backend/src/main/scala/com/helio/ai/ClaudeClient.scala:27-34` — `send` estimates input tokens and rejects over `config.maxInputTokens` as `GuardrailExceeded` before any network call, and clamps `maxTokens` to `config.maxOutputTokens`. Ticket's premise-validation claim is correct.

5. **Registration-site line references.** `rowToDomain` at `PipelineStepRepository.scala:1286` and `PipelineService.scala:1711` (`toAnalyzeStepResponse` op dispatch) — both exact matches to design.md's cited line numbers. `PipelineCostEstimator.AiOps` (`PipelineCostEstimator.scala:24`) already contains `"analyzewithai"`. `grep -rln "analyzewithai" src/test` confirms it is used as an unregistered stand-in in exactly `PipelineCostEstimatorSpec`, `PipelineStepsOpCheckSeededRowsSpec`, `PipelineAnalyzeRoutesSpec`, and `PipelineCreateTransactionalSpec` — matches D8's claim precisely.

6. **Completeness of registration sites — REFUTE finding.** Task 2.6 says: "Update schemas/OpenAPI and helio-mcp `write.ts` op docs **wherever `convertformat` is enumerated**." I checked this literally:
   - `grep -rln "convertformat" schemas/` → **zero hits**.
   - `grep -n "convertformat" helio-mcp/src/tools/write.ts` → **zero hits**.
   - `convertformat` is enumerated **only** in `openspec/specs/*.md` and backend source — never in `schemas/` or `helio-mcp/src/tools/write.ts`.
   - Yet `helio-mcp/src/tools/write.ts:376-378` (the `add_pipeline_step` tool's own docstring) contains an explicit, hand-maintained op-name list: `"rename/filter/join/compute/groupBy/cast/select/limit/sort/aggregate/datebucket/pivot/window/unpivot/dedupe/fillnull/stringops/union/lookup/assert/upsertsource"`. This list is missing `convertformat` (a pre-existing HEL-1105 gap this ticket doesn't own) **and will therefore also omit `analyzewithai`** if the implementer follows task 2.6's literal instruction ("wherever convertformat is enumerated") — because convertformat isn't enumerated there at all, that search will never surface this file as a site needing an update.
   - Functionally the MCP tool's `type` field is `z.string().min(1)` (not a hard enum, `write.ts:503`), so `analyzewithai` would still be *accepted* by the tool — but it would be silently **undocumented and undiscoverable** to any agent reading the tool description, directly undercutting the ticket's own stated goal ("Full registration... helio-mcp docs" per the driver brief) and proposal.md's "Full registration" claim, which doesn't even list `helio-mcp` as an impacted surface (only tasks.md 2.6 does) — an internal inconsistency between proposal.md's Impact section and tasks.md's own task list.

### Verdict: REFUTE

### Change Requests

1. **tasks.md §2.6 / helio-mcp registration.** Do not use "wherever `convertformat` is enumerated" as the search key for `helio-mcp/src/tools/write.ts` — it is a dead trail there (`convertformat` was never added to that file's op docs, a pre-existing HEL-1105 gap). Explicitly task the executor to add an `analyzewithai` entry to the `add_pipeline_step` tool's op-name list and per-op config-shape docstring at `helio-mcp/src/tools/write.ts:376-378` (and any sibling analyze/list-op-kinds doc in the same file), independent of whether `convertformat` is fixed in the same change. If fixing the pre-existing `convertformat` omission is out of scope, say so explicitly in a Non-Goal rather than leaving it to be silently skipped by an unreliable grep-based instruction.
2. **proposal.md "Impact" section.** Add `helio-mcp` to the Impact list (currently only lists `domain/steps`, `PipelineStep.scala`, engine context, `PipelineRunService`, `ApiRoutes`, codec, repository, analyze service/protocol, JSON schemas) so it matches tasks.md 2.6's actual scope — the proposal and tasks currently disagree on what "Full registration" covers.

### Non-blocking notes

- D2's "maps `ClaudeError`s to `AiStepFailure` (`Unavailable`, `Guardrail`, `Api`, `Transport`)" is imprecise: `Unavailable` is never produced by the `ClaudeError` mapping (there are only 3 `ClaudeError` variants); it's the context-level default. Worth a one-word fix in design.md ("plus the context default `Unavailable`") so a future reader doesn't go looking for a 4th `ClaudeError` case.
- Confirm during implementation that `schemas/` actually needs a change for `analyzewithai` at all — since `schemas/pipelines/create-pipeline-step-request.schema.json`'s `type` field is a bare `string` (no enum), and no schema file enumerates op names by string match today (only `convertformat`-free structural schemas exist). If no schema file needs edits, task 2.6's "Update schemas/OpenAPI" clause should be revisited too — verify this doesn't hide a second dead-trail identical to the helio-mcp one.
