## Standing Constraints

- [C1] HEL-1080's grid keyboard/a11y support is built by extending `frontend/src/shared/ui/DataGrid.tsx` with default-off, opt-in grid/a11y props (grid role, roving tabindex, cell-level focus) — never a purpose-built replacement grid. A regression check (DOM snapshot/role assertions per the 5 real named consumers — `TableRenderer`, `SourceDetailPanel`, `SqlTab`, `ConnectorsPage`, `StepCard` — captured from `main` before the change, not just "tests pass") must prove all 5 render unchanged with the new props left off. `DatasetRowGrid` always uses `variant="preview"` (never `"full"`) — virtualization is full-variant-only (verified, `DataGrid.tsx:598`), so this structurally avoids the virtualization/focus interaction rather than merely staying under a row-count threshold. General `gridMode` + `"full"`-variant virtualization support is a named, out-of-scope gap for any future consumer. Owner ruling, 2026-09-11.

## 3. Frontend: schema + rows data layer

- [x] 3.1 `datasetRowsSlice` (Redux, `createAsyncThunk`): `fetchDatasetSchema`, `fetchDatasetRowsPage`, `patchDatasetRow`, `deleteDatasetRow`, `appendDatasetRow`. State: `schema` (by source id), `rows` (by source id + page), `cursorStack` (by source id — design.md Decision 0a), `pending` edits (by row id), `conflicts` (by row id, holding the refetched current row).
- [x] 3.2 Service layer functions for the new schema route + existing paged rows/write/patch/delete routes. Page size is the named constant `DATASET_GRID_PAGE_SIZE = 100`, always passed explicitly (never the API's own default).
- [x] 3.3 `useDatasetFieldEditor` hook mapping each `DataFieldType` to a concrete editor (design.md Decision 6): `StringType` → text, `IntegerType`/`FloatType` → numeric input, `BooleanType` → checkbox, `TimestampType` → date/time input, `StringBodyType` → multi-line text, `BinaryRefType` → read-only display cell (excluded from editable tab order but still a focus stop).
- [x] 3.4 Conflict recovery (design.md Decision 3): on a `409` from `patchDatasetRow`/`deleteDatasetRow`, re-fetch the row's current page (using the cursor currently on top of `cursorStack`), locate the row by id. If present: store it in `conflicts[rowId]`, and a retry re-applies only the user's edited cell(s) on top of that current row (never the user's full stale row) with its `updatedAt` as the new precondition. If absent (deleted concurrently): mark the row "already deleted", discard-only.
- [x] 3.5 400 validation-error parsing (design.md Decision 3a): parse the three known `DatasetRowValidator` message templates (`field '<name>' is required`, `field '<name>' — <reason>`, `expected <n> fields, got <m>`) via a `field '([^']+)'` match to attach an error to the offending cell (row-length errors always render as a grid-level banner); on an unparseable message, fall back to the same grid-level banner (tested, not silent). Emptying any editor (backspacing text to `""`, clearing numeric/timestamp) is uniformly treated as a clear attempt submitting JSON `null` — **never `""`** — client-side-blocked (validation error, no submit) only when the field is `required` with no declared `default`; allowed (submits `null`) for a required field with a default or any non-required field.
- [x] 3.6 Add-row pagination: after a successful `appendDatasetRow`, page forward (following `nextCursor` until `None`, pushing each onto `cursorStack`) so the user lands on the last page and sees the row they just added.

## 4. Frontend: grid UI

- [x] 4.1 `DatasetRowGrid` component wrapping `DataGrid` with `gridMode` enabled and **`variant="preview"`** (never `"full"` — avoids the full-variant's resize-handle/pin-toggle tab stops, which would break the roving-tabindex invariant and let `Shift+Tab` land on a header control instead of leaving the grid). Per-column `render` returns either static text or, for the active editable cell, an inline editor from `useDatasetFieldEditor`. Mounts on `/sources/:id` (`SourceDetailPanel`) for `dataset`-kind sources, replacing that panel's existing read-only Preview grid for this kind only (design.md Decision 7) — non-dataset kinds keep Preview unchanged. Add a test asserting exactly one element inside the grid has `tabindex="0"` at any time.
- [x] 4.2 Keyboard interaction: `Enter`/`F2` (not editing) enters edit mode on the active cell; `Enter` (editing) commits and moves the active cell down one row; `Escape` cancels and restores the pre-edit value; `Delete`/`Backspace` on a focused row triggers delete (behind confirm) **only when no cell is in edit mode** (while editing, these keys edit the cell's text normally); `ArrowUp` on the first row / `ArrowDown` on the last row of the current page holds the active cell in place (no wrap, no cross-page navigation via arrow keys — only the pager control changes page); a dedicated "Add row" button (not a keyboard shortcut) appends a row.
- [x] 4.2a Tab/Shift+Tab and blur while editing: attach a `keydown` handler to the active cell's **editor element itself** (not just the grid body) intercepting `Tab`/`Shift+Tab` — commit the in-progress edit, then programmatically `.focus()` the resolved next/previous focusable element outside the grid (never rely on the browser's default Tab traversal from inside the editor, which would land back on the same `<td>` or an unintended DOM-order element). A `blur` handler on the editor commits the in-progress edit the same way for any other focus-loss cause (e.g. a mouse click elsewhere).
- [x] 4.3 Pager control (Prev/Next + 1-based page indicator from `cursorStack.length`) — no infinite scroll. `DatasetRowGrid` always passes `variant="preview"` to `DataGrid`, which never virtualizes (virtualization is `"full"`-variant-only), so the wrapper never has to interact with `useVirtualRows` regardless of page size.
- [x] 4.3a **(Skeptic round-5 finding, required, not optional)** Guard against double-commit on Tab/Enter/blur: the wrapper's programmatic `.focus()` (on Tab) triggers the editor's own `blur` handler, which also commits — without a guard this fires the commit twice, and the second (stale) submission gets misread as a `409` conflict from someone else. End the edit (clear the "currently editing" state) synchronously on the FIRST commit or cancel, and have the blur handler no-op if the edit has already ended. Escape must not commit at all. Tests: exactly one save fires per Tab/Enter; zero saves fire on Escape.
- [x] 4.3b **(Skeptic round-5 finding)** Tab from the grid's last focusable page element (no next focusable target) falls back to default browser tab order rather than doing nothing or throwing. A field declared with `default: null` (JSON null as the literal default value) is treated as "no usable default" for the client-side required-emptying check — the field still blocks emptying, since a null default doesn't give the user anything different than emptying it directly. Committing an edit where the value is unchanged (e.g. already `""` or already at its committed value) is a no-op — it does not raise the "cannot be emptied" validation error for a field whose stored value already happens to need no submission.
- [x] 4.4 Inline cell edit with client-side validation (required/type, per 3.5's default-aware required check) before submit; **pessimistic apply** (amended design.md Decision 4, skeptic-final-1.md CR6) — the cell shows a `pending` state while the PATCH is in flight and updates only once the server confirms; a `409`/`400` failure never applied anything to roll back in the first place.
- [x] 4.5 Field-level validation error rendering on the offending cell (client-side and server-parsed per 3.5), announced via `aria-live`/`role="alert"`.
- [x] 4.6 Stale-conflict UI (edit and delete paths per the spec's conflict scenarios): show current server value inline, retry (re-applying only edited cells)/discard actions; "row already deleted" state with discard only; "delete anyway" action for a delete-path conflict where the row still exists.
- [x] 4.7 Row delete action (pessimistic) and add-row action (pessimistic, see 3.6 for post-add paging).
- [x] 4.8 Explicit "Refresh" control (design.md Decision 8) re-running `fetchDatasetRowsPage` (using the current top of `cursorStack`) + `fetchDatasetSchema` — this is what satisfies the "reflects a concurrent change on refresh" AC, not implicit browser refresh.
