## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- Insert sites (grep of `table += `/`PanelTable` in backend main): PanelRepository.insert (user ctx = panel.ownerId), PanelMutationRepository.insertBatch + duplicate (system ctx), DashboardContentsOps.replaceContents (system ctx, writes layout in one tx, no FOR UPDATE), DashboardSnapshotRepository.duplicate and .importSnapshot (system ctx). Service callers: DashboardProposalService (per-panel create + PATCH), PatchSet apply/undo/rollback via create. MCP only calls the HTTP routes. So the design's list misses exactly two inserters: dashboard duplicate and dashboard import.
- placeDefaultLayout writes via dashboardRepo.update, which runs `withUserContext(dashboard.ownerId)` (DashboardRepository.scala:163-174) and rewrites name/appearance/layout from a stale read. So "the existing Output path already writes the layout for an editor" is NOT evidence an editor-context write works: it runs as the dashboard OWNER. V36 `dashboards_update` does admit owner or editor grantee, so FOR UPDATE under the editor's context is plausible, but unproven.
- RLS never runs in the standard backend harness (MISTAKES.md "RLS policies never run in dev or CI"). The only real-RLS harness is ProductTelemetryDbHarness (telemetry-specific). Task 3.5 "RLS harness: editor-grantee create ... under the RLS-enforcing role" names no mechanism and HelioRouteTest cannot do it.
- D5 / resolveDashboardLayout (dashboardLayout.ts:139-199): for a breakpoint that passes isLayoutValid, anchorsFor returns liveEntries verbatim (first entry per id, sanitize is identity on valid items), missing panels go through placeAround/createBaseLayoutAround without moving anchors. Append-only claim holds for valid breakpoints; empty breakpoint and all-missing cases yield all-derived items (nothing to preserve); duplicate ids are deduped to the first entry, matching the planned server check. Server DashboardLayoutRepair.plan today only acts on stored-bad, and its `dropped`/`unknown`/dup/validity checks are reusable. Soundly implementable.
- D3 apply: ProposalLayoutSupport.buildLayout currently omits unauthored panels; `applyLayout` skips when `lg.isEmpty`; with D1 appended items the PATCH replaces all four breakpoints with a valid layout. Sound.
- useLayoutSave.ts header (lines 24-50) and layoutPlacement.detectPlacementExtension: class 3 requires, in EVERY breakpoint, prev as exact prefix + appended ids unknown to every breakpoint of prev.
- repair reducer (dashboardsSlice.ts:352-361) adopts the server layout only if the store layout still equals expectedLayout.
- Client orphan sizes (dashboardLayout.ts defaultItemWidth): lg 4, md(10 cols) 4, sm(6) 3, xs(2) 2. Server D1 scaling round(4*cols/12): md 3, sm 2, xs 1.
- schemas/panels/panel.schema.json:57 describes `layouts` as output-only on POST /api/panels; helio-mcp/src has no `layouts` modelling (1.8 is conditional, fine).

### Verdict: REFUTE

### Change Requests
1. D2 leaves the transaction's DB context undecided and mis-cites precedent. Decide and write down: either (a) one `withSystemContext` transaction after the service ACL check (precedent: insertBatch, duplicate, replaceContents) or (b) `withUserContext(caller)` with FOR UPDATE + layout UPDATE under the editor's RLS. State which, and why the panel INSERT's current user-context `panels_insert` WITH CHECK defence is kept or knowingly dropped. Remove the claim that the Output path proves editor writability (it runs as dashboard owner). Also specify the layout write is layout(+lastUpdated)-only, not `dashboardRepo.update` (which clobbers a concurrent rename/appearance from the stale read).
2. Task 3.5 is unexecutable as written. Name the mechanism (e.g. extend the ProductTelemetryDbHarness non-superuser/NOBYPASSRLS pattern to dashboards/panels with an editor grant and run create/batch/duplicate through it), or, if option (a) is chosen in 1, state that RLS is bypassed by design and drop 3.5 in favour of an ACL test (viewer 403, editor 200).
3. Enumerate dashboard duplicate and dashboard import (DashboardSnapshotRepository.duplicate/importSnapshot) in D3. Today they copy/remap whatever layout the source/payload has, so an orphaned source or hand-built/old export yields orphans in a brand-new dashboard. Decide: place unplaced panels there (preferred: it is a create site, AC1) or explicitly declare them covered only by the owner repair, and add a test either way.
4. The useLayoutSave.ts class-4 justification becomes false: an append-only repair response can satisfy detectPlacementExtension (panel orphaned in all four breakpoints -> prev is an exact prefix, appended ids unknown) and be classified class 3; a panel present in lg only (hel1023 A_lg_only) is not (ids known) -> class 4; stale-entry drops -> class 4. Specify the intended classification, update the header paragraph (task 2.4 only mentions class 3 wording), and add a unit test pinning pending=false / no history entry / baseline correctness for both outcomes (and when a local edit is pending).
5. DashboardLayoutRepair.plan: state precedence when a breakpoint is both stored-bad and incomplete (it must take the stored-bad rules; append-only cannot apply). Add a route-spec case.
6. D1 rationale "looks the same size as before the fix" is true only at lg: client orphan widths are 4/4/3/2 (lg/md/sm/xs) vs server 4/3/2/1. Either correct the claim and accept/document the narrower md/sm/xs size (xs becomes half width on a 2-col phone grid), or choose per-breakpoint widths that match the client default. Add the md/sm/xs expectation to the spec scenario so tests pin it.
7. Qualify the Goals' "no lost update": FOR UPDATE serialises creates only; the layout PATCH (DashboardService.update read-modify-write) and replaceContents take no row lock and can still overwrite a freshly appended item. Say so (and whether the PATCH path should also lock) rather than claiming it globally; update the schema description at panel.schema.json:57 (task 1.8) which currently says output-only.

### Non-blocking notes
- Red-first plan (D6) and seam plan (D7) are adequate in shape; add the pending-edit-then-create case to the seam since server bottom is computed from the server layout.
- Tasks 3.7/3.8 correctly anticipate the hel1023 stub; confirm A_lg_only seeding still produces lg-only after creates now place all four.
