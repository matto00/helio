### Verdict: REFUTE

### Change Requests

1. **D2's "post-pipeline rows are flat" is false, and D6 breaks on it.** `PipelineRowJson.anyToJsValue` (`domain/engine/PipelineRowJson.scala:47`) has an explicit `case m: Map[String, Any] => JsObject(...)` case, added by HEL-216 precisely because the image connector's `content` field is a nested `BinaryRef` map (`storageKey`/`mimeType`/`filename`/`sizeBytes`). `PipelineRunService.extractBinaryRefs` (:713-731) exists solely to harvest those nested maps *from `resultRows` on this very call path*. So nested objects demonstrably DO reach pipeline output today.
   Consequence of the planned change: `JsonFlattener.leaves` recurses into that object, so the schema stops carrying a `content` column (today: one field, type `"string"` via `inferFieldType`'s catch-all, which IS canonical and IS reported by capabilities) and instead carries four dotted fields `content.filename`, `content.mimeType`, `content.sizeBytes`, `content.storageKey` — none of which match the stored row key `content` (`overwriteRows` writes `jsRows` un-flattened). That is (a) a column disappearing from the capability report, refuting D6, and (b) schema/row disagreement, the exact defect class HEL-599 exists to prevent. It also silently breaks `WorkspaceContextService`, which looks up `row.fields.get(field.name)`.
   Required: decide and document explicitly whether output rows are flattened (`JsonFlattener.flattenJsObject` applied to `jsRows` before `overwriteRows`, keeping schema and rows consistent — but note that changes the persisted row shape and the `content` read path / `binary_refs` index) or whether inference must NOT recurse for this path. Either way the choice must be stated in design.md, and a test must pin a binary-ref-shaped nested column end-to-end (persisted fields + persisted rows + capability report agreeing).

2. **D6's "cannot remove a column from the capability report / an already-numeric column stays eligible" is false for type widening.** `SchemaInferenceEngine.widenJson` has a catch-all `case _ => StringType`. So a column whose row 0 is a number but which holds a boolean or a non-numeric string (`"N/A"`, `"-"`) on any later row infers `integer` today and `string` after. `SlotEligibility.accepts` (`domain/panels/PanelBindingSpec.scala:19-21`) accepts only `IntegerType`/`FloatType` for `Numeric`, so that column loses `metric.value` / `chart.yAxis` eligibility, and if it was the only numeric column the whole panel type flips `bindable: true` → `false`. This is precisely the heterogeneous, messy-row data the ticket is about, so it is not a hypothetical. Required: correct D6 to state the real invariant (the *key set* is additive; the *type* may widen to `string` and that can remove eligibility), state whether that is accepted, and add a test pinning the mixed number/string case. Task 3.4's "verify the additive claim" must be re-specified accordingly — as written it invites the executor to confirm a false claim.

3. **D5's consumer audit is scoped to `"double"`→`"float"` only, but the change produces two further transitions.** (a) `integer`→`string` per CR2; (b) `string`→`timestamp`: the engine's `inferJsonType` calls `isTimestamp` and emits `TimestampType` for ISO-date/`MM/dd/yyyy` strings, which `inferFieldType` never emitted (every string was `"string"`). Every existing pipeline-output date-like string column changes wire type on its next run. Re-run the audit over all three transitions (frontend type-conditional UI, MCP surface, assistant/workspace-context, `BoundPanelService`'s pre-write `PanelBindingSpec.evaluate` gate — confirm whether a re-save of an existing panel can now be rejected) and state the result. Also fix the two wrong file paths for the `NUMERIC_TYPES` rows (`features/pipelines/ui/stepConfigs/`, not `features/panels/ui/editors/`).

4. **`displayName` is undecided and is wire-visible.** Today `DataField(name, name, ...)` — displayName equals the raw name. `InferredField` carries `SchemaInferenceEngine.displayName(path)` (`rec_yd` → `"Rec Yd"`). Task 2.1 says only "mapping each `InferredField` to a `DataField`" and does not say which displayName is written. Pick one, state it in design.md with the reason, and assert it in a test.

5. **Tasks 1.1-1.7 cannot fail on the defects above.** The fixture is specified only as sparse + fractional. Add to task 1.1 an explicitly enumerated fixture covering: a nested (binary-ref-shaped) column, a column mixing numeric and non-numeric-string values, and a date-like string column — and add the corresponding assertions. Task 1.8's "record the red" should also require confirming each red is for the specific defect, which it does for 1.4 only; extend that requirement to every new test.
