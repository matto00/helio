### Change Requests
1. **D1/D9 omit the two `usePanelData(panel)` call sites (PanelCard.tsx:387, MobilePanelStack.tsx:47).** `refresh()` (manual button, `usePanelPolling`, HEL-1094 SSE fan-out) calls `fetchPanelPage` with `filter: undefined` and replaces `paginationState`. Under server mode with the client filter gated off (task 3.2), any refresh/poll would silently drop the cross-filter and show unfiltered rows for a panel that still claims to be filtered - a regression vs today (client filter survives refresh). Design must state how refresh/mount fetches in these two hosts carry the composed ops (e.g. thread `[...control, ...cross]` into `usePanelData` at these sites, which also resolves D8's mount double-read for cross-filter), and add a test: cross-filtered panel + refresh keeps the `eq` op. The D9 survey list must name these two sites explicitly, not leave it to the executor.
2. **`mode` threading to `OutputPanelContent` is unspecified for the detail modal / fullscreen.** D3 says one decision computed in PanelCardBody and threaded down, but `PanelDetailModal` renders `PanelContent` without `output`, outside PanelCardBody, with its own `usePanelData`. Define: the prop's default when absent, and which component computes mode for the modal. Otherwise the modal either double-filters (server ops + client filter still on) or loses filtering. Add a test for the modal.
3. **Capabilities hook cost/staleness.** (a) State it fetches lazily - only when a cross-filter is active and this panel is a candidate target (never eagerly per panel on dashboard load; `buildContract` is an O(columns x rows) scan per call). (b) The module-scope cache by outputId never invalidates, but cardinality can change after a pipeline re-run; a stale "eq allowed" makes `/rows` return 400 and the panel error out. Specify handling: on a 400 for a cross-filter `eq`, invalidate the cache entry and fall back to client mode (and a test), or bound the cache (e.g. clear on run-status refresh).
4. **Spec vs server semantic conflict on numeric strings.** The spec scenario "A numeric selection matches a differently-formatted sibling column" (SHALL narrow "3" to "3.0") is not true on the server path for string-typed columns (exact-text eq). Decide now, not in task 5.4: either restrict the server path to columns whose capability/schema type is numeric/timestamp-safe or exact-match-safe and otherwise use fallback, or amend the scenario to scope it to numeric-typed columns / the fallback path. Also state timestamp-column behavior (server casts; client compared strings).
