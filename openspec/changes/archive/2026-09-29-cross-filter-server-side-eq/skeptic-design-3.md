### Verdict: REFUTE

### Change Requests
1. **`lastQuery` is not scoped to an Output (stale replay).** `paginationState` is keyed by panelId only and is NOT reset when a panel's bound Output changes (`resetPanelPagination` has no non-test caller; grep). `usePanelData`'s key includes outputId, so an Output change dispatches a page-0 fetch; under D9a that fetch replays the OLD Output's `{sort, filter}` (old sort column, table column filters, control ops, cross-filter eq) against the NEW Output, giving 400s or wrongly filtered data. Design must store `outputId` inside `lastQuery` and replay only when it equals the current outputId (test: rebind panel to another Output, assert unfiltered/unsorted fetch).
2. **Replay makes stale-eq possible on remount with no corrective fetch.** The corrective mount fetch in `usePanelSortFilter` (line ~211) fires only if sort/filter/controls are active. If the cross-filter state differs between the stored `lastQuery` and current state at remount (e.g. cleared/changed while the panel was unmounted), the parent's replay of the stale `eq` is the latest dispatch and nothing corrects it. D9a must state the replay is reconciled against current cross-filter state (e.g. replay only the `eq` op for the CURRENT crossFilter, i.e. strip any cross-filter eq op from `lastQuery` and re-derive it from current state, or compare and drop when mismatched) and add a test for clear-while-unmounted.
3. **D3a's 400 handling does not cover the mount/refresh replay path.** D3a only makes `usePanelSortFilter`'s toast catch skip `cross-filter-eq-rejected`. `usePanelData`'s `.catch` (usePanelData.ts:~125) unconditionally sets `errorForKey`, and that error is cleared only by a success under the SAME key; a 400 on a replayed/refreshed eq would leave the panel in an error state after the mode flip refetch succeeds via the other hook. Specify that `usePanelData` also ignores that code (and does not set errorForKey), and add a test for the mount/refresh class (design currently lists tests for only page-0 effect and load-more).
4. **`lastQuery` lifecycle in reducers unspecified.** `.fulfilled` and `.rejected` rebuild/spread the entry (`panelsSlice.ts:313-350`); `.fulfilled` builds a fresh object with no `lastQuery`, so it would be dropped before any refresh. Also page>0 (load-more) pending must NOT overwrite `lastQuery`. State: fulfilled carries `existing.lastQuery` forward; only page-0 pending writes it. Note `panelsSlice.test.ts:253` deep-equals the entry shape and will need a legitimate update (state it explicitly so it is not read as a fixture-massage symptom).

### Non-blocking notes

- D3a: detection must read the HTTP status from the raw Axios error before `classifyRequestError` (`classifyRequestError.ts` only maps 403/404 to kinds, 400 is not preserved in the rejectValue today).
