## Context

Today two client-side call sites filter loaded rows: `useCrossFilteredPanelData` (feeds `PanelInspectView`) and `OutputPanelContent` in `PanelContent.tsx` (main content, mobile, fullscreen). HEL-1190 composes viewer-control filters into every server fetch via `controlFilterOps` -> `composeOutputRowsFilter` (`usePanelSortFilter`, `PanelCard.handleLoadMore`, `usePanelData` for the detail modal). HEL-1027's `latestFetchRequestId` reducer guard drops stale responses.

## Decisions

**D0 - Owner rulings (not re-decided).** (a) Cross-filter state stays in Redux (`panelsSlice.crossFilter`) only, NOT in the URL: recorded by the owner on the HEL-1191 comment thread, 2026-09-29 ("Owner ruling (2026-09-29), answered before dispatch"). A cross-filter not surviving reload while HEL-1190 controls do is this ruling, not a bug. (b) HEL-588 "Action in Inspect": only `PanelInspectView` dispatches `setCrossFilter`; trigger behaviour is untouched and a test asserts it.

**D1 - Compose through the one existing composer, no third path.** A new hook `useCrossFilterServerOps(panel, output)` returns `OutputRowsFilterOp[]` (`[{column: dimension, op: "eq", value}]` or `[]`). SUPERSEDED by D9a-i (single mechanism): the cross op travels as its own `crossFilterEq?: {column, value}` parameter, NEVER concatenated into `controlFilterOps`. `useCrossFilterServerOps` therefore returns `{ crossFilterEq: {column,value} | null, mode }` (not an ops array). The parameter is passed to `usePanelSortFilter(panelId, outputId, output, controlFilterOps, crossFilterEq)`, `usePanelData(panel, controlFilterOps, crossFilterEq)`, `handleLoadMore`, and the `fetchPanelPage` arg; the thunk folds it into `filter.ops` through `composeOutputRowsFilter`. `composeOutputRowsFilter` is reused unmodified; no new request-building code. The hook's array is memoized on (crossFilter, eligibility) so the existing `controlFilterOpsKey` effect re-dispatches exactly when it changes.

**D2 - Precedence when a cross-filter and a control target the same column: AND (intersection), no override.** Server ops are ANDed by construction; both are visibly surfaced (control bar shows its value, `CrossFilterIndicator` shows the cross-filter) so an empty result is explainable and the table's own empty state applies. Rejected: cross-filter overriding the control (silently discards a viewer's visible selection) and control overriding cross-filter (silently discards a dashboard-level action).

**D2a - Same-column precedence, corrected after evaluation-1.md (cycle 1).** The backend rejects two ops with the same `(column, op)` (`400 duplicate filter op`, `OutputRowsQueryParsing.scala:76`), so a server-side AND of a cross `eq` with a control `eq` on the SAME column is impossible. Rule: intersection semantics are unchanged (no override in either direction), but when the panel's control ops already contain an op with the same `(column, op)` as the cross-filter's `eq`, the panel deterministically takes `client-fallback` (mode derivation, no request that could 400, no capabilities-cache invalidation): the control stays a server filter and the cross-filter narrows the loaded (already control-filtered) rows client-side, with the loaded-scope disclosure. A different-op control on the same column (`gte`/`lte`/`in`) still composes server-side. The announcement for that panel must state a count consistent with what is displayed (empty intersection announces 0 results).

**D3 - Eligibility.** A target panel gets the server `eq` only when ALL hold: (1) a cross-filter is active and `crossFilter.panelId !== panel.id` (origin always renders full data, as today); (2) `isPanelFilterableByDimension(...)` passes (today's field-mapping criterion, unchanged); (3) the column's schema type is any non-timestamp type (server `eq` compares numeric-typed columns via `safe_numeric` on both sides, so "3" matches "3.0" exactly as the client does; string/boolean columns compare exact text - see D10); (4) the Output's filter-capabilities (`getFilterCapabilities`, fetched once per Output per panel via a small hook `useOutputFilterCapabilities(outputId)`, cached in module scope by outputId) list `eq` for the dimension.
- Fails (1) or (2): panel unaffected - identical to today (unfiltered). This covers "Output lacks the column".
- Passes (1)+(2) but (3) or (4) fails (timestamp column, or contract disallows `eq`, e.g. the cardinality cap of 50 from HEL-1188, or capabilities failed to load): KEEP TODAY'S BEHAVIOUR - the existing client-side loaded-rows filter (`filterRowsByDimension` / `filterRecordRowsByDimension`) plus the existing "loaded scope" truncation disclosure. `crossFilterRows.ts` therefore stays, now reachable only on this fallback.
- While capabilities are still loading for a panel, the fallback behaviour (today's) applies until they resolve, then the panel switches to the server path; the sequencing guard resolves the resulting refetch. `PanelContent`'s client-side filter and the hook must consume the SAME eligibility result (one decision, computed once in `PanelCardBody`/`PanelCard` and threaded down), so a panel is never filtered by both paths (double-filter would still be correct but would corrupt `isCrossFiltered`/loaded-count disclosure).

**D4 - Counts and hasMore.** On the server path the panel's `paginationState` (`total`, `hasMore`, `rows`) already describes the filtered set, because the same `fetchPanelPage` response replaces them. The client-side "loaded scope" disclosure is shown only on the fallback path (`isCrossFiltered` client-side true). The server path must not render it.

**D5 - Clearing / staleness.** Clearing sets `crossFilter` to null, the ops key changes, `usePanelSortFilter`'s existing effect re-dispatches page 0 without the `eq` op, and `latestFetchRequestId` discards any still-in-flight filtered response. `handleLoadMore` carries the composed ops so an appended page belongs to the same filtered set. Tests: a delayed filtered response resolving after clear must not win.

**D6 - Public dashboards.** Cross-filter is NOT reachable on public dashboards: `PublicDashboardViewerPage` renders neither `PanelCard`, `PanelInspectView` nor `CrossFilterIndicator` (verified by grep), so nothing can dispatch `setCrossFilter` there. The public rows route's allowed-column set (HEL-1190 C11, a security boundary) is NOT widened and no backend file changes. A test pins that the public content path emits only control-scoped filters.

**D7 - Announcement.** `PanelCardBody`'s existing live region (already shared by desktop grid and mobile stack) announces on a server-applied cross-filter: "N results match the dashboard filter, <dimension> = <value>." (deliberately not the `CrossFilterIndicator`'s own "Filtered by ..." wording, to avoid a duplicate announcement) and on clear: "Cross-filter cleared: N results." (N = the panel's `paginationEntry.total`, after the fetch settles - never announced from a loading state). Only panels the filter actually applies to (server path) announce; the origin and unaffected panels stay silent. This composes with, and takes precedence over, the HEL-1190 control-count text when a cross-filter is the most recent change.

**D8 - HEL-1198 (chart panels do an unfiltered read before the filtered one).** Not folded in. This change does not alter the mount fetch in `usePanelData`; a panel mounted while a cross-filter is active still does its unfiltered first read then the corrective filtered read, exactly like a control at mount. Stated so a reviewer does not expect it fixed.

**D9 - Other render paths.** Detail modal, fullscreen overlay and mobile stack: whichever of them already composes HEL-1190 control ops must also receive the cross-filter ops through the separate `crossFilterEq` parameter (D9a-i; D1 concatenation is superseded) (the executor surveys them: PanelCardBody, PanelDetailModal, PanelFullscreenOverlay, MobilePanelStack); none gets its own composition code.

**D9a - Refresh/mount hosts (skeptic rounds 1-2, CR1).** `usePanelData(panel)` is also called with no ops at `PanelCard.tsx` (~387, BEFORE `useOutputMeta` ~406) and `MobilePanelStack.tsx` (~47, whose `MobileStackPanelBody` deliberately has NO Output - a second `useOutputMeta` there was probe-confirmed to cause a transient-unfiltered-sibling race after a breakpoint remount and was removed). Its mount fetch and `refresh()` (manual, `usePanelPolling`, HEL-1094 SSE fan-out) dispatch `fetchPanelPage` with `filter: undefined`, replacing `paginationState` and silently dropping a server-side cross-filter. So hosts are NOT given an Output and NOT reordered. Instead the query travels with the data: `fetchPanelPage`'s pending reducer records the page-0 request's `{sort, filter}` on the panel's `paginationState` entry as `lastQuery`; `usePanelData`'s mount dispatch and `refresh()` reuse `paginationState[panel.id].lastQuery` (an explicit `controlFilterOps` argument, as the detail modal passes, still takes precedence). The only producers of ops stay `PanelCardBody` (has its Output) and the detail modal; the two ops-less hosts just replay the last query. Consequences: (a) a remount (breakpoint change) replays the filtered query instead of dispatching an unfiltered one, so a mobile-stack sibling never renders unfiltered rows in the remount window; test for exactly that; (b) refresh/poll/SSE keep the cross-filter `eq` op (test on the desktop host and the mobile host); (c) as a natural side effect refresh also stops dropping HEL-1190 control ops and HEL-1027 sort/filter - the executor verifies whether that was a real pre-existing defect and states so in evidence (if refresh already preserved them through another mechanism, reuse that mechanism instead of `lastQuery`). HEL-1198's unfiltered-then-filtered chart read is NOT touched (D8).

**D9a-ii - Plumbing (skeptic round 4).** `crossFilterEq` is a first-class input to each hook that owns an ops key: in `usePanelSortFilter` it joins `dispatchFetch`'s args (read via ref like `controlFilterOps`), the corrective-mount condition (`controlFilterOps.length > 0 || crossFilterEq !== null`), and the change-detection key (`JSON.stringify([controlFilterOps, crossFilterEq])`); in `usePanelData` it joins `currentFetchKey` and every dispatch; `handleLoadMore` passes it; `PanelDetailModal` passes it to its own `usePanelData`. So set/change/clear re-dispatches page 0 on every path.

**D9a-i - `lastQuery` shape and lifecycle (skeptic round 3).** `fetchPanelPage` gains an optional arg `crossFilterEq?: {column, value}`; the thunk itself folds it into `filter.ops` (the single compose point, still via `composeOutputRowsFilter`), and callers pass the cross op separately instead of concatenating into `controlFilterOps` at each site (D1's concatenation becomes this arg; same one composition path). `lastQuery = {outputId, sort, filter /* excluding the cross op */, crossFilterEq}` is written ONLY by a page-0 `pending` (load-more never overwrites it); `fulfilled` and `rejected` carry `existing.lastQuery` forward explicitly (they rebuild the entry object today). `panelsSlice.test.ts`'s entry-shape deep-equal (~:253) is updated for the new field - a legitimate shape change stated here, not fixture massaging. Replay rules in `usePanelData` mount/`refresh()`: (1) replay only when `lastQuery.outputId === current outputId` (paginationState is keyed by panelId and not reset on rebind; a rebind dispatches an unfiltered, unsorted fetch; test: rebind); (2) replay `crossFilterEq` only when it equals the CURRENT `state.panels.crossFilter` (same dimension and value, and `crossFilter.panelId !== panel.id`), otherwise drop it - so clear-or-change while unmounted can never replay a stale `eq` (test: clear-while-unmounted); when the cross-filter is newly active with no replayable match, `PanelCardBody`'s existing corrective mount fetch fires because the current ops are non-empty. (3) The corrective fetch when it fires intentionally overrides the replay.

**D9b - Mode threading (skeptic CR2 rounds 1-2).** `mode` is a pure function of (crossFilter, output, schema type, capabilities). `OutputPanelContent`/`PanelContent` take a REQUIRED `crossFilterMode` prop (`"server" | "client-fallback" | "none"`), so an omitting caller is a type error. Producers: `PanelCardBody` (has Output; also passes to the mobile path, which reuses it) and `PanelDetailModal` (owns its `usePanelData` and Output) call `useCrossFilterServerOps`. `PanelFullscreenOverlay` never resolves an Output by design: it receives `crossFilterMode` as a prop threaded from `PanelCard`, computed there with the same hook from the Output `PanelCard` already resolves. Tests: modal server mode (ops in fetch, no client filter) and fallback mode (client filter + disclosure); overlay renders the threaded mode.

**D3a - Capabilities hook cost and staleness (skeptic CR3).** Lazy: `useOutputFilterCapabilities` performs no request unless a cross-filter is active AND the panel is a candidate (passes criteria 1-2), so no eager per-panel fetch on dashboard load (the backend contract build is O(columns x rows) per call). Cached per outputId with a 5-minute TTL. If a `/rows` request carrying the cross-filter `eq` returns 400 (cardinality grew past the cap after a pipeline re-run), the cache entry is invalidated, the hook reports `client-fallback` for that Output, and the panel refetches without the `eq` op (no error toast for that specific self-healing case). Wiring (single detection point): all three dispatch classes (mount replay, `usePanelSortFilter`'s sort/filter/control effect, `handleLoadMore`) go through the `fetchPanelPage` thunk. In that thunk's failure path, when the response is HTTP 400 AND `arg.crossFilterEq != null` (the trigger is the explicit arg, never an inference from `filter.ops`, so a same-column HEL-1190 control `eq` that 400s is not misread as a cap rejection), the thunk (1) invalidates the capabilities cache entry for that outputId (a tiny module store the hook subscribes to via `useSyncExternalStore`, so every host re-derives `client-fallback`) and (2) rejects with a distinguishable `code: "cross-filter-eq-rejected"`; both `usePanelSortFilter`'s toast catch AND `usePanelData`'s `.catch` (which would otherwise set `errorForKey` on a 400 from a mount/refresh replay and leave the panel in an error state until a same-key success) ignore that code. The HTTP status is read from the raw Axios error inside the thunk BEFORE `classifyRequestError` (which maps only 403/404 and drops 400). The mode flip empties the ops, the existing ops-key effect refetches without the `eq`, and the client filter takes over. One test per dispatch class (page-0 effect, load-more, mount/refresh replay) plus a thunk-level test.

**D10 - Value semantics (skeptic CR4).** Server path is used only for numeric-typed columns (parity with the client's numeric-equality: server casts both sides) and string/boolean columns (exact text: for a string column "3" and "3.0" are distinct labels, and that is the defined server-path behaviour; the spec scenario is scoped to numeric-typed columns and to the fallback path). Timestamp-typed columns are NOT sent server-side (server casts via `safe_timestamptz`, client compared strings); they take the client fallback, which is today's behaviour. Cardinality note: the 50-value cap means high-cardinality dimensions (scatter numerics, ids) always take the fallback and keep the loaded-window inaccuracy; the red-first AC test uses a low-cardinality dimension, and the PR body says so.

## Risks

- Capabilities fetch adds one request per target panel per Output (cached module-level); acceptable, same cost model as HEL-1189/1190.
- Server/client value parity is settled by D10; the executor verifies numeric-typed parity with a real request and records it.
