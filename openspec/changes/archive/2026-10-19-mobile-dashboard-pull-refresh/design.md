## Context

- The phone dashboard is `PanelList` -> `PanelGrid` -> `MobilePanelStack` (`frontend/src/features/panels/ui/grid/`). `PanelGrid` picks the stack by measured CONTAINER width (`width < panelGridConfig.breakpoints.sm`), not viewport, so the stack also mounts on desktop viewports whose content column is narrow (rail + context list). Viewport gating is therefore needed separately.
- The page scrolls inside `.app-content` (`App.css`, `overflow-y: auto`); the shell is `100dvh`, the document never scrolls. Nothing sets `overscroll-behavior` except `BottomSheet.css`. On Chrome Android, an at-top overscroll of `.app-content` chains to the viewport and can fire native pull-to-refresh (a full reload).
- `useSheetSwipe` (HEL-1582) uses pointer capture with `touch-action: none` on a non-scrolling header. On a scrolling body the browser claims the touch for panning and sends `pointercancel`, so that approach cannot drive a pull on `.app-content`. Its velocity window (last 100 ms of samples) and `sheetMotion`'s token-timed settle + `afterTransition` fallback timer do transfer.
- Refresh: there is no dashboard-level refresh. Each panel's single `usePanelData(panel)` call (in `MobileStackPanelBody`) exposes `refresh()` (no-op while `inFlightRef` is set) and `isRefreshing`. The stack renders no Refresh control.
- Motion levels resolve through tokens: under Subtle/Off/reduced motion `--motion-duration-move` is instant (`isInstant(readMotionDuration(...))`).
- Owner ruling `suppress-on-phone-dashboard` (see ticket.md).

## Goals / Non-Goals

**Goals:** a pull-to-refresh on the authenticated phone dashboard per ticket.md AC 1-8; reuse the shared motion helpers rather than copying them; no extra request volume beyond one refresh per output-bound panel.

**Non-Goals:** public/shared dashboard routes (they do not render through `PanelList`/AppShell's `.app-content`); a visible dashboard-level Refresh button (a follow-up candidate); sheet swipe (HEL-565); pipeline runs; any desktop change; tablets above 768px.

## Decisions

**D1. Touch events on `.app-content`, not pointer capture.** New `frontend/src/shared/motion/usePullToRefresh.ts`. Listeners: `touchstart` (passive), `touchmove` (`{ passive: false }`), `touchend`, `touchcancel`, attached to the scroller element found via `closest(".app-content")` from the stack's root ref. Engagement rules, decided on the first `touchmove` that moves >= 6px (the "slop"):
- exactly one touch (`touches.length === 1`) for the whole gesture; a second finger cancels (settle, no refresh);
- `scroller.scrollTop <= 0` at touchstart and at engagement;
- downward and vertical-dominant (`dy > 0 && |dy| > |dx|`);
- the touch target is inside the stack root, and no element between the target and the scroller is a vertical scroller with `scrollTop > 0` (a table panel scrolled inside itself keeps its own scroll);
- not starting on a form control (`input, select, textarea, [contenteditable="true"]`). Buttons/links ARE allowed as start points (a pull starting on a card must work; the click is suppressed naturally because a moved touch never fires `click` once `preventDefault` has run on `touchmove`).
Once engaged, every `touchmove` calls `preventDefault()`; if the slop decision is "not engaged", the gesture is ignored until the next `touchstart` and never prevented. Pull distance is `max(0, dy)` damped: `pull = dy * 0.5`, capped at `PULL_MAX_PX = 112`; threshold `PULL_THRESHOLD_PX = 64` (on the damped value). Pointer types: touch events only fire for touch, so mouse/pen never engage (AC3).

**D2. Shared helpers extracted, not duplicated.** Move the velocity-sample window and `velocityOf` into `frontend/src/shared/motion/dragVelocity.ts`, used by both `useSheetSwipe` and `usePullToRefresh` (behaviour-preserving for the sheet; its existing tests stay green). Generalise `sheetMotion.ts`'s private `afterTransition` into an exported helper (same file or `motionTransition.ts`) and add `settleOffset(element, offsetPx, toRest, attribute, done)` that `settleSheet` delegates to. A fast flick (velocity > 0.5 px/ms downward) with `pull >= PULL_THRESHOLD_PX * 0.75` also counts as past the threshold.

**D3. What moves.** The stack root gets an inline `translateY(pull)` during a Full-motion drag (no transition while dragging), and the indicator sits in a slot above the first stack child, revealed by the same translate (absolutely positioned at `top: -<indicator height>` inside the translated wrapper, so no layout shift at rest; at rest there is NO inline transform, the same contract as the sheet so portalled `position: fixed` popovers are unaffected). On release: past threshold -> settle to `PULL_HOLD_PX = 48` (indicator visible, busy) and refresh; when all refreshes settle -> settle to 0 and clear the transform. Short -> settle to 0. Settles use `--motion-duration-move` and its easing via the D2 helper.
Under Subtle/Off/reduced motion (`isInstant(--motion-duration-move)`): no transform at any time and no layout shift. The visual indicator is an absolutely positioned overlay pinned to the top of the stack (over the first card's top edge, `pointer-events: none`), shown only while a pull is engaged or busy, and it snaps between `pulling` (arrow, "Pull to refresh"), `ready` ("Release to refresh") and `busy` (Spinner, "Refreshing") with no transition. Inserting a row was rejected because it shifts the panel list. This is the "snaps with no movement" reading; it is a reversible UI choice (listed in the PR body).

**Rest state (both levels).** At rest the visual indicator is not rendered at all (`null`), so nothing sits at `top: -height` above the stack and nothing can bleed into the chip row or be hit-tested. Under Full it mounts on engagement inside the translated wrapper (revealed by the translate) and unmounts when the settle to 0 completes.

**D4. Indicator and status region (separate).** Visual: `PullRefreshIndicator` in `frontend/src/features/panels/ui/grid/` with the `RotateCw` icon (lucide, `ICON_SIZE.sm`) rotating proportionally to pull under Full only, and the shared `Spinner` when busy. It is `aria-hidden="true"`. Text uses existing type tokens, colour `--app-text-muted`; no new tokens; light/dark via existing tokens only. Announcements: a separate, ALWAYS-mounted visually-hidden `role="status"` `aria-live="polite"` element in `MobilePanelStack` (existing visually-hidden utility class), whose text is set to "Refreshing" on a qualifying release and to "Refreshed" when busy ends (cleared on the next engagement). It is never unmounted with the visual indicator, so the "Refreshed" announcement is not lost. A short pull announces nothing.

**D5. Refresh fan-out registry and busy tracking.** A small context in `MobilePanelStack`: `PullRefreshRegistry` holding `Map<panelId, { refresh, isRefreshing }>` in a ref. `MobileStackPanelBody` registers only when `outputId !== null` and deletes its entry on unmount. It writes its entry's `isRefreshing` in an effect keyed on `isRefreshing` and notifies the registry ONLY when that value changes (never on every render: no render loop).
On a qualifying release the stack snapshots the current entries into a "round" map `panelId -> seenTrue`, where `seenTrue` starts as the entry's current `isRefreshing` (a panel already in flight counts as seen). Then it calls each entry's `refresh()` once (the hook's own `inFlightRef` makes an already-in-flight panel a no-op, so the count is <= one rows request per output-bound panel, the same as tapping each panel's refresh once). Background: `isRefreshing` is `paginationEntry.isLoadingMore`, which turns true only in the `fetchPanelPage.pending` reducer, dispatched from an effect after the render `refresh()` triggers. So a false read right after `refresh()` means "not started yet", not "done".
On each change notification: an entry reporting `true` sets `seenTrue`; busy ends when every round entry has `seenTrue === true` and now reports `false`, or the entry unmounted. Safety ceiling: `PULL_REFRESH_TIMEOUT_MS = 15000` is a request-timeout constant (not a motion timing), defined in `features/panels/ui/grid/pullRefreshRegistry.ts` (outside `shared/motion`), after which busy clears anyway. A hung request must not pin the indicator; the panel keeps its own spinner and error. An in-progress table "Load more" on a panel keeps busy until it settles, which is accepted. A second pull while busy is ignored (no re-fire). No pipeline-run code path is imported.

**D6. Overscroll containment scope.** The hook sets `data-pull-refresh` on the scroller while it is attached and removes it on detach/unmount. CSS (in `MobilePanelStack.css`): `@media (max-width: 768px) { .app-content[data-pull-refresh] { overscroll-behavior-y: contain; } }`. The hook attaches only when `useIsNarrowerThan(769)` is true AND the stack is mounted, so a narrow-container desktop stack never gets it. Viewport crossing 768 detaches live.

**D7. Tests.**
- jest: `usePullToRefresh` with synthetic `TouchEvent`s on a jsdom scroller: engages at top/downward; not when scrollTop > 0, upward, horizontal-dominant, two-finger, nested scrolled container, form control; `preventDefault` called only when engaged; threshold/flick/short release; attribute set/removed. Registry: release refreshes each output-bound entry once and skips non-output panels; busy does NOT end while a mocked rows request is held open (pending dispatched, not yet fulfilled) and ends after it resolves, each with a recorded red mutation (e.g. ending busy on first false read). `dragVelocity`: unit tests. Each guard paired with a recorded mutation that turns it red (MISTAKES.md).
- Playwright `e2e/hel1656-pull-to-refresh.spec.ts`: `hasTouch: true, isMobile: true`, 375x812 and 390x844 (430 in the screenshot pass), dispatching real touch input via CDP `Input.dispatchTouchEvent` (`page.touchscreen` only taps). Cases: pull at top past threshold -> count rows requests (= output-bound panels) and zero `/runs` POSTs; short pull -> zero requests; scrolled page -> native scroll moves, no indicator; computed `overscroll-behavior-y` contain on the phone dashboard and auto on Home and at 1280; Motion Off -> stack has no transform mid-pull (sampled, state-waited per HEL-1658) and refresh still fires; desktop 1280 -> no indicator in the DOM; an engaged touchmove is actually cancelable in Chromium (assert `event.cancelable` and `defaultPrevented` via a page-side listener) so the native scroll does not move during a pull. Workers <= 2.
- Native browser PTR cannot be emulated headless; containment is proven by the computed style, stated as such in the PR.

## Risks / Trade-offs

- Containment removes Chrome's native pull-to-refresh and overscroll glow on the phone dashboard only (owner-approved). Other pages keep native behaviour.
- iOS Safari: `.app-content` rubber-band is suppressed by `contain`; on old iOS (< 16) `overscroll-behavior` is ignored, but `preventDefault` on the engaged `touchmove` still stops the bounce during a pull.
- Non-passive `touchmove` costs scroll performance only if it blocks; the handler returns immediately when not engaged and never reads layout except `scrollTop` (one read at engagement).
- WCAG 2.5.1: the pull is a path gesture with no single-pointer alternative on the phone stack (panels still refresh on run completion via SSE). A visible refresh control is a follow-up candidate, not in scope.
- Touch on a card that started a pull: suppressed click relies on the browser not firing `click` after a prevented `touchmove`; covered by the e2e (the detail modal must not open after a pull).
