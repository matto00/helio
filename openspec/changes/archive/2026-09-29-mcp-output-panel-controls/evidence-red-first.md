## Findings / premise corrections (verified, not assumed)
1. Raw `update_panel({config:{controls:[...]}})` ALREADY persists controls on main, and an ineligible one already returns the defined 400 `control not eligible: column 'region', kind 'date-range'`. The gap is ergonomics/discoverability, not raw capability: an agent has no tool telling it which columns/kinds are eligible (`filter-capabilities` returns only `operators`, no MCP tool wraps it, `get_output_capabilities` is the unrelated pipeline step shape), must hand-mint UUIDs and replace the whole list, and `get_workspace_context` never shows controls (0 hits after a real control was written).
2. `propose_dashboard` (MCP) is CLIENT-SIDE ONLY (`proposal.ts` + `computeProposalWarnings`); it never calls backend `DashboardProposalService.validate` (that is used only by the in-app authoring/assistant paths). A top-level `controls` key on a proposal panel is silently DROPPED (Zod strips it; backend ProposalPanel would ignore it too: PUT contents returned 200) with applyReady=true; `config.controls` with an ineligible column passes propose with applyReady=true. So propose-time rejection needs a change in the MCP tool itself as well as backend validate.
3. `apply_proposal` and `PUT /dashboards/:id/contents` ALREADY reject an ineligible control with 400 (via panelService.create), i.e. apply time. The gap is propose time (authoring/assistant `validate`, MCP `propose_dashboard`).
4. Backend defects observed (out of scope, spinoff candidates): PATCH with a control missing `id`, or `controls` not an array, or an array element that is not an object, returns HTTP 500 "Internal server error" (not a defined 4xx); duplicate control ids are accepted (200) and persisted; a text panel PATCH with `config.controls` is 200 and silently ignores controls.
