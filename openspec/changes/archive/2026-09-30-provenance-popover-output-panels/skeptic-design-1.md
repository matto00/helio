### Verdict: REFUTE

### Change Requests
1. **Zero-rows vs never-run claim is false on the wire.** design.md Context and spec ("ran with zero rows (lastRun present, rowCount 0)", scenario "Never run versus zero rows") assume `rowCount: 0`. The backend emits `rowCount: null` for BOTH an empty snapshot and an absent one (ProvenanceService.scala:84; schema description). Specify the actual mapping: lastRun null -> never run; lastRun.status succeeded + rowCount null -> "no rows" (cannot distinguish empty vs absent; word it accordingly, e.g. "produced no rows"); fix the spec scenario and the test plan. Do not plan a backend change (Non-goal) unless you deliberately amend scope.
2. **Public path omits the share token.** Design decision 8 says the public path uses dashboardId from the `usePublicPanelData` context. The public endpoint authorizes via `?token=` (anonymous viewers are denied without it), and `PublicOutputPanelBody` receives `token` as a prop. Specify that the public service takes `(dashboardId, panelId, token)`, the cache key stays `public:<dashboardId>:<panelId>` (state explicitly whether token is part of it), and the trigger variant prop carries token. Add a test that the request includes the token.
3. **Trigger location per path is deferred, not designed.** "Executor places it at each path's equivalent footer/header" is the ambiguity the gate exists to catch: the mobile stack and public viewer have NO footer (verified above), the fullscreen overlay and detail modal are `Modal` headers. Name the concrete location for each of the five paths (e.g. mobile: in `mobile-panel-stack__header` beside the title; public: a small header/row above `PanelContent` in `PublicOutputPanelBody`; fullscreen/detail: modal header/actions slot) and the touch-target/size at phone width. Also state the detail modal already renders an "open pipeline" link (PanelDetailModal.tsx:~103) and how the provenance trigger relates (no duplicate authenticated link confusion).
4. **Portal event bubbling / nested-modal interactions unaddressed.** React synthetic events bubble through portals: a click on non-button popover text inside a card bubbles to `handleCardClick`/`handleItemClick` (closest("button,input,a") on the portal target does not match) and would open the detail modal. Require `stopPropagation` (or equivalent) on the popover root and on the trigger, with a test on desktop and mobile stack. Separately, inside `Modal` (fullscreen, detail) the popover's document-level Escape (usePortalPopover) fires alongside the Modal's own Escape and would close both, and the Modal's focus trap/inert handling may fight a portalled dialog. State the required behaviour (Escape closes only the popover first) and how it is achieved.
5. **Focus trap is claimed but the host does not provide one.** Decision 3 says "focus trapped while open ... Tab cycles" using usePortalPopover with panelRef; that hook closes on focus-out rather than trapping (no Tab cycling exists). Choose one explicitly: add a small trap inside ProvenancePopover (Tab/Shift+Tab wrap) and omit panelRef, or accept close-on-focus-out and amend the spec's "trap focus" wording and the AC mapping. The ticket AC requires "focus trapped and returned"; the design must say how.
6. **Badge/assertion-status dedupe is left to the executor with a semantic gap.** The badge reads `status.invalid`; provenance gives counts (`failed`, `warned` by severity). Specify the mapping (badge shown iff `failed > 0`? does `rootBound`/warned matter?) and the concrete dedupe mechanism (e.g. one module-level per-output promise cache shared by `getAssertionStatus` consumers and/or prefetch), since on initial paint the provenance cache is empty by design (lazy) so the badge fetch must remain. Note the badge trigger needs an actual button (currently a `<span>`) with keyboard operability and a label.
7. **Label mapping detail.** Decision 5 is fine (reuse `OP_TYPES`), but name the module and the fallback, and note nodePath is `step.kind` (trunk-first, primary parent chain only) so root-bound outputs have an empty path: specify the empty-path rendering.

### Non-blocking notes
- Tasks lack an explicit acceptance signal for the "lazy, no request until opened" AC beyond 3.1; add a network-count assertion per path.
- Public variant must not show the pipeline id/link; already specified, keep a test asserting absence of link and ids.
- Design claim on telemetry hook, file layout, and "no backend/migration" are sound.
