### Change Requests
1. **D3 hand-rolls a shared primitive (DESIGN.md §6, "use these; do not hand-roll equivalents", mechanical + judgment).** DESIGN.md §6 lists `useScrollEdges` as the canonical "scroll-shadow edge state for overflowing lists/grids". `frontend/src/shared/ui/useScrollEdges.ts` already computes `bottom: maxScrollTop - scrollTop > 1` and wires scroll, window resize and a `ResizeObserver` on the container and its children. D3 specifies a private reimplementation of exactly this. Revise D3 (and task 2.3) so `ToastRowList` uses `useScrollEdges<HTMLUListElement>()` on the `ul` and drives `data-overflow-below` from `edges.bottom`. Note how the hook's observation works: it observes the `li`s that exist at mount. A row whose action is removed shrinks an observed `li`, so a re-measure fires. If the design needs a re-measure on `items` change beyond that, say how it gets one through the hook rather than forking it. Update D4's `ToastRowList` test plan to match, and model it on `useScrollEdges.test.tsx` / `PanelDetailModal.editScrollFade.test.tsx`.
2. **D1's rationale for keeping the message in id order rests on a misreading.** "Byte-identical" is this module's own term for the coalescing invariant. The doc comment in `deniedPipelinesToast.ts` reads: "a burst of writes against an unchanged verdict produces byte-identical messages, and `toastsSlice`'s own variant+message dedup coalesces them". HEL-1844's AC is literally "the **coalescing** message stays byte-identical". That is a determinism-across-writes requirement, not a freeze of today's bytes. Name-then-id is a total order (ids are unique), so a name-ordered message is just as byte-identical across a burst, whatever order the input arrives in. Nothing else consumes the message bytes; the only callers are `FormPanelView.tsx` and the tests. Keeping id order buys nothing, and the live region keeps announcing in the arbitrary UUID order that HEL-1844 calls the defect, while sighted users see name order. Revise D1, the proposal, the spec delta and the "Multi-denial rows are ordered…" scenario: build `message` from the same name-then-id order as `items`. Replace the "equals the id-ordered string" test with one where the same denial set pushed in two different input orders yields byte-identical messages and one coalesced toast. If the planner still holds that HEL-1844 means "unchanged from today's bytes", that is a product question to raise as an ESCALATION, not an assumption to build on.
3. **D2's stated technique fails its own guard by arithmetic, and D4 has no check for that failure.** A `margin-block-start` of `-var(--space-4)` (16px) puts the list's top edge 16px above the body. Only 13px is available above the body (12px `.toast` padding plus the 1px border). The list's padding box is a scroll container's paint area, so once the list is scrolled, row text slides up through that band, over the toast's top border and about 3px outside the toast. D2 names this risk, but D4 has no test or screenshot that would catch it. The flaw only shows in the scrolled state. Revise:
   (a) Record the arithmetic in D2: the expanders overhang 13.6px, against 13px available.
   (b) State the precedence when the 1px criterion, the 44px expander (guarded by the existing `bisectHitExtent` test) and "no paint over or outside the toast border" cannot all hold.
   (c) Add to D4/task 1.3 and 3.2 a 390px overflowing-and-mid-scrolled check in both themes, as a screenshot plus a measurement, showing no row content painted at or above the toast's top border.
   Since D3 adds a `.toast__list-frame` wrapper, also say which element carries the D2 margin. The frame is now the flex item, and a negative top margin on the `ul` collapses through a padding-less block frame.
4. **`tasks.md` has an empty `## Standing Constraints` section** (a placeholder). Either restate the run constraints that bind execution, or remove the heading. Those constraints are: lane DB `helio_hel1840` exported with every server, Playwright, jest and hook run; `ANTHROPIC_API_KEY` empty; servers only through `start-servers.sh`/`stop-servers.sh`; jest at 3 workers, Playwright at 2; red output committed as `.txt`; evidence in `.concertino/runs/HEL-1840/evidence/`.

### Non-blocking notes
- D3's visual approach is a gradient to `--app-surface-strong`. The established scroll-cue vocabulary is the HEL-1449 owner-ruled scroll-fade (an inset shadow in `color-mix(--app-text 35%)`) and the DataGrid inset edges. A surface gradient is a reasonable fit for a small toast, and the ticket itself suggests "a fade". Still, record in D3 why it departs from the sibling pattern, so the final gate can judge cohesion against a stated intent.
- The full-width `::after` will paint over the bottom of a classic desktop scrollbar (Linux). Consider insetting it by the scrollbar gutter (`scrollbar-gutter: stable`, or `right` set from `offsetWidth - clientWidth`), or accept it explicitly.
- D2 measurement: the link is a blockified flex item, so its rect is its line box and compares like-for-like with `.toast__message`. Keep it that way, or measure both with a `Range` on the first text node.
- D1: `Intl.Collator("en", { numeric: true })` has default sensitivity `variant`, so ties fall through to id only for canonically equal names. That matches the spec scenario.
