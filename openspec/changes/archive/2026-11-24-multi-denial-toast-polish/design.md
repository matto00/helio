## Context

`buildDeniedPipelinesToast` (`frontend/src/features/pipelines/services/deniedPipelinesToast.ts`) sorts denied pipelines by `pipelineId.localeCompare` and uses that order for both the toast `message` and the `items` rows. `ToastRowList` (`frontend/src/shared/ui/ToastRowList.tsx`) renders the rows in a `ul.toast__list` that scrolls at `max-height: min(40vh, 16rem)` (`frontend/src/shared/ui/toast.css`). When rows are present `Toast.tsx` hides the `.toast__message` paragraph, so the list is the first thing in `.toast__body`. At `(max-width: 768px), (pointer: coarse)` the list gets `padding-block: var(--space-4)` so the 44px touch expanders of the first/last link are not clipped by the scroll container; that padding is what pushes the first row ~16px below the icon on a phone (to be measured red-first, not assumed). The live region in `ToastViewport` announces `toast.message`.

## Goals / Non-Goals

**Goals:** rows in name order (HEL-1840 item 1 + HEL-1844); first-row alignment with the icon at 390px; an overflow cue while more rows are below.

**Non-Goals:** changing the toast `message`'s line text (only its line order changes, D1); changing desktop toast layout beyond the cue and D2's icon offset in multi-row toasts; changing the single-pipeline toast; backend changes.

## Decisions

**D1 — Order (rows and message).** One sorted array drives both `items` and `message`: a module-level `new Intl.Collator("en", { numeric: true })` comparing `name`, and when the collator returns 0, `pipelineId.localeCompare` as today. A fixed locale keeps jsdom and browsers in the same order; numeric collation puts "Pipeline 2" before "Pipeline 10"; ids are unique, so name-then-id is a total order. HEL-1844's "the coalescing message stays byte-identical" is this module's own coalescing invariant (the function's doc comment: "a burst of writes against an unchanged verdict produces byte-identical messages, and `toastsSlice`'s own variant+message dedup coalesces them"), not a freeze of today's bytes — so the message is built in the same name-then-id order, and the live-region announcement matches the visible rows (skeptic-design-1 CR2). Nothing else consumes the message bytes (callers: `FormPanelView.tsx`, tests). The doc comment is updated.

**D2 — First-row alignment at phone width.** Criterion (measurable, used by the e2e test): the vertical offset between the variant icon's top and the first row link's top (the link is a blockified flex item, so its rect is its line box) equals the offset between the icon top and `.toast__message`'s top in a single-message toast at the same viewport and theme, within 1px.

Arithmetic (skeptic-design-1 CR3): at `(max-width: 768px), (pointer: coarse)` the list's `padding-block: var(--space-4)` (16px) pushes the first link 16px down; on desktop `padding: var(--space-1)` pushes it 4px. The 44px touch expanders overhang a ~17px control by ~13.6px each side, and the scroll container clips at its padding box, so that padding is what keeps the first/last expander hittable. Only 13px (12px `.toast` padding + 1px border) is available above `.toast__body`, so pulling the list up with a `-var(--space-4)` margin would let scrolled row text paint ~3px above/over the toast's top border. That technique is rejected.

Chosen technique: move the icon, not the list. A multi-row toast gets a modifier class (`toast--rows`, set by `Toast.tsx` when `hasItems`), and `.toast--rows .toast__icon` takes a `margin-top` equal to the list's block-start padding plus today's 1px (`calc(var(--space-1) + 1px)` on desktop, `calc(var(--space-4) + 1px)` in the phone/coarse block), so the icon lines up with the first row while the list keeps its clipping-safe padding. Precedence when the three cannot all hold: (1) 44px expander hit extent (the existing `bisectHitExtent` y-axis test at 390px) is never traded away; (2) no row content painted at or outside the toast border, in any scroll position; (3) the 1px alignment criterion. Tokens only (DESIGN.md), no raw px beyond the existing 1px icon nudge. The close button and the single-message toast are unchanged.

**D3 — Overflow cue.** `ToastRowList` uses the shared `useScrollEdges<HTMLUListElement>()` hook (DESIGN.md §6 primitive; skeptic-design-1 CR1) on the `ul` and drives `data-overflow-below={edges.bottom ? "true" : undefined}` on a new wrapper `div.toast__list-frame` (position: relative; the frame, not the `ul`, is now the body's flex item; it has no margin/padding so nothing collapses). Re-measure: the hook observes the `ul` and the `li`s present at mount and listens to scroll and window resize. Rows are never added to or removed from a mounted toast (a run action's removal shrinks an observed `li`, which re-measures; a different denial set is a different toast and remounts), so no fork of the hook is needed. The fade is the frame's `::after`: absolute, bottom 0, left 0, right 0, height `var(--space-6)`, `linear-gradient(to bottom, transparent, var(--app-surface-strong))`, `pointer-events: none`, shown only under `[data-overflow-below="true"]`. `--app-surface-strong` is the toast's own opaque background in both themes (`#262320` / `#ffffff`), so the fade reads as content dissolving into the card in light and dark. Departure from the sibling scroll cue (HEL-1449's inset `color-mix(--app-text 35%)` shadow in `PanelDetailModal.css`) is deliberate: a shadow line inside a 340px toast competes with the toast's own border and intent stripe, and the ticket asks for a fade; recorded here so the final gate can judge cohesion against it. Accepted: on a classic (non-overlay) scrollbar platform the fade also tints the bottom of the scrollbar track. A list that fits never gets the attribute; scrolled to the end drops it. The fade is decorative; AT users meet every row through the list.

**D4 — Tests.** Unit (`deniedPipelinesToast.test.ts`): names whose id order differs from name order, with case and numeric mix and two equal names broken by id — rows and message in name-then-id order (mutation: comparator reverted to id → red); the same denial set in two input orders yields byte-identical messages and pushing both through `toastsSlice` holds one toast. `ToastRowList` test modeled on `useScrollEdges.test.tsx` / `PanelDetailModal.editScrollFade.test.tsx`: stubbed `scrollHeight`/`clientHeight`/`scrollTop` for overflowing, fits, and scrolled-to-end (mutation: attribute wiring removed → red). e2e (`e2e/hel1172-multi-denial-toast.spec.ts`, full file): Tab order expects name order (derived from the name sort, never the id sort); at 390px in both themes the D2 criterion and the existing `bisectHitExtent` check; an overflowing case (enough pipelines to exceed the max height) asserting the frame attribute and the `::after` computed `background-image` is not `none`, and, mid-scrolled at 390px in both themes, that no row's rect is above the toast's top border inner edge (`toast.top + 1`) — as a measurement plus a screenshot; a two-row case asserting no attribute. Screenshots at 390px in light and dark, before (unmodified code) and after, plus the overflowing mid-scroll state, go to `/home/matt/Development/helio/.concertino/runs/HEL-1840/evidence/` (not committed).

## Risks / Trade-offs

- Moving the icon adds space above it in a multi-row toast on phone width → judged in the before/after screenshots; precedence in D2 if it conflicts.
- The fade covers part of the last visible row's text → it is short (`--space-6`), transparent at the top, and disappears at scroll end.
