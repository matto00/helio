### Verdict: REFUTE

D1 and the overall approach are sound and the geometry is right. D2 has one lever that cannot be built as written, and a threshold two people would read differently, with visible consequences at 1280px. The design also cites a verification that does not exist. All three are cheap to fix now.

### Change Requests

1. **D2 lever (e) cannot be built as written.** A rule inside `@container spine-column (…)` matches only descendants of `.spine-body__spine`, never the container itself, so "spine column inline padding tightens" cannot be expressed under that query. Revise (e) to a mechanism that works. One option is a page-width container query in `PipelineSpineLayout.css` (an unnamed `@container` resolves to `.pipeline-detail-page--spine`) at the page width where D1 gives a track under the compaction threshold. Another is a negative inline margin, or reduced padding, on the child `.pipeline-spine`. Keep the "grip stays inside the column" invariant: `.spine-row__grip` sits at `left: -12px`. Or drop (e), since (a)–(d) reach about 79px on lane rows at a 180px track.
2. **D2's `max-width: 259px` threshold is ambiguous by about 33px.** A container size query measures the container's **content box**: track − 32px padding − 1px border. As written, compaction applies up to a track of about 292px, not the "below ~260px" the proposal states. Consequence: at 1280 with the list at 400, the page is 824, the track 280 and the content box 247, so the selected row's ⋮ becomes hover-only at 1280. State the threshold explicitly in one unit, e.g. "content box ≤ 226px (≈ 260px track)". Or deliberately accept the about-292px track boundary, and say in proposal.md and design.md which one applies and that compaction may apply at 1280 with the list at max.
3. **The Risks section claims a check that does not exist.** "`container-type` on the spine column changes its min-content to 0 … verified by the 1280×800 test": that test (spec :120-153) never measures the spine's width, and AC3's 270–340px is otherwise backed only by task 2.1's one-off measurement. Make it a committed assertion. C3 allows edits to the sweep test only, and the sweep already sets the viewport to 1280 before each pass. With the list at default, assert the `.spine-body__spine` width is 270–340. Then correct the Risks line to name that assertion, and add it to task 2.1 and the spec scenario evidence.

### Non-blocking notes

- Add to the Risks section that `container-type` brings layout containment: the column becomes the containing block for fixed and absolute descendants. It is safe today because `ActionsMenu` portals to `<body>`. The executor should re-check that nothing new in the spine relies on `position: fixed`.
- D1's rationale says cycle 4's 270px floor "took the room the header/editor needed". The header spans the full page grid row, not the spine/main tracks, so the spine track cannot have taken header width. The cycle-4 header clipping had another cause. The ≥320px main floor is still well justified by the editor action row.
- `PipelineSpineHeader.css:295` ("Below 1100px the page has little room…") introduces the `max-width: 800px` block. It is defensible as a viewport approximation with the default list, but consider rewording it alongside the :331 fix.
- D3's occlusion probe sits at the title's left end, so it would not catch an overlay over the title's right end. The Risks line "the occlusion probe would catch a permanently visible overlay" overstates it. Since the ⋮ in (d) sits at the right end, either probe the right end of the visible span too, or reword the claim.
- The levers hide the ⋮ while not hovered, but it stays in the hit area over the title or count end. That is fine for a mouse, because row hover reveals it. On touch devices in this width band, a tap at the row's right end opens the menu instead of selecting the step. Acceptable, but say so.
