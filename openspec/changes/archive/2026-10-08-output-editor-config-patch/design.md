## Context

`PATCH /api/outputs/:id` shallow-merges `config` (`OutputConfigValidation.mergeConfig = existing.fields ++ patch.fields`): an omitted top-level key is kept, a present key replaces wholesale (so `fieldMapping` is replaced as a whole object), and an explicit `null` is stored as JSON `null` (not deleted). `OutputConfigValidation.validate` tolerates a known key re-sent with `null`; renderer-side reads (`readMetricConfig`, `readTableConfig`, ...) already treat `null` as absent. So the server already supports everything needed; the defects are all in the client's edit-mode Save (`buildOutputConfig.ts` + `OutputEditorSheet.tsx`). See proposal.md for the three symptoms.

HEL-1394 (Inspect grid column order follows `columnOrder`, else schema order) is Backlog and unimplemented: today `PanelInspectView` never reads `columnOrder`, and both the Inspect grid (`usePanelData.ts:215`) and `TableRenderer` (absent `columnOrder`) use row-key order. This change cannot regress HEL-1394; a cleared `columnOrder` simply renders like an Output that never had one. Schema-order fallback remains HEL-1394's job.

## Goals / Non-Goals

**Goals:** edit-mode Save sends only changed top-level keys (+ explicit `null` clears); untouched stored keys preserved byte-for-byte; the three named symptoms each fixed with a red-first test.

**Non-Goals:** no backend behavior change; no UI for collection `layout` / timeline `sort` (the editor simply stops owning them in edit mode); no change to create-mode payloads or to "Add as tail with aggregate"; HEL-1388 (Kind select in edit mode) — if kind changes in edit mode the diff logic below should still behave sanely, but fixing/locking the Kind select is not part of this ticket.

## Decisions

**D1 — Edit-mode Save = diff against an open-time baseline, per top-level key.** Compute the kind config via the existing builder for the current state (`built`), and the same builder for the state the sheet opened with (`baseline`, i.e. the builder fed from the stored config's read-back values). Send key `k` iff `built[k]` is not deep-equal to `baseline[k]` (`undefined` and `null` compare equal; otherwise deep-equal). This is literally "fields the user changed": a stored legacy shape the builder would re-normalize (e.g. a metric aggregation stored as `{agg}`) is not re-sent unless the user touched it. Alternative considered: diff `built` against the raw stored config — rejected, because every read-default (e.g. `chartType: "line"` for an absent key, normalized aggregation shapes) would then be written on an untouched save, violating byte-for-byte preservation. Alternative: per-field dirty flags in the sheet — rejected as more state and more ways to miss a field; the builder already is the single source of the wire shape. The baseline must be computed from the same inputs the sheet seeded its state from (and, for table `columnOrder`, from the same capabilities-dependent hook output — see D3) so an untouched open/save produces an empty diff.

If the resulting patch is empty, `config` is omitted from the PATCH body (`UpdateOutputRequest.config` is `Option[JsObject]`); tests assert the absence.

**D2 — Collection `layout` / timeline `sort` are not owned in edit mode.** The builder keeps writing `"grid"`/`"asc"` for create; on edit they are equal in `built` and `baseline` and so never sent. (Implementation may also pass the stored value through; either way the test is: stored `"list"`/`"desc"` survives a save.)

**D3 — Clears are explicit `null`.**
- Metric `label`/`unit`: the user-visible lost clear is literal→field: today the literal key is sent `undefined` (omitted) and the stored literal keeps rendering. Builder emits `null` for the literal key whenever the slot is in field mode, and `null` (not `""`) for an emptied literal — matching `useBoundOrLiteralState.patchValue`'s convention. Red-first tests target the literal→field path (an emptied literal sending `""` already renders nothing; changing it to `null` is a secondary consistency fix and does not count as the red test for bullet 2).
- Table `columnOrder`: the hook's current "natural" test (`natural = fieldKeys.filter(k => visible.includes(k))`) is true for ANY visible subset in natural relative order, hidden columns included, and `TableRenderer` treats `columnOrder` as the visible set — so mapping it to `null` would un-hide columns. New rule: `columnOrder` is "default" (`undefined` in the hook output → `null` on the wire in edit when it differs from baseline) only when every field key is visible AND in natural order; otherwise it is the explicit visible array. This applies to create too (today hiding a column without reordering is never persisted — fixed). While capabilities have not loaded (`fieldKeys` empty) the hook returns the stored `columnOrder` as-is, so baseline and built agree and an untouched save sends nothing.
- Chart `annotation` literal emptied → `null` (already so).

**D4 — Bound-slot keys in `fieldMapping` come only from editor state; already-damaged rows are repaired (deliberate exception).** The chart base mapping seeded from the stored config drops `annotation`; the metric mapping is already rebuilt from state. A slot (`annotation`, `label`, `unit`) is (re)added only when its state is field mode with a field chosen. `fieldMapping` is sent when EITHER (i) `built.fieldMapping` differs from the baseline (ordinary D1 rule), OR (ii) the RAW stored `fieldMapping` contains a slot key (`annotation` for chart; `label`/`unit` for metric) with a non-empty string value that `built.fieldMapping` does not carry with the same value — i.e. a stale slot. (A stored `null`/empty-string slot is not treated as stale, so it never triggers a one-off write.) The raw comparison is ONLY this stale-slot detection, never whole-object equality, so a healthy Output whose stored mapping merely differs in shape from the builder's output is not rewritten. When (ii) fires on an untouched save, the request carries the repaired `fieldMapping` (plus whatever D4a requires) and nothing else. This is a narrow, deliberate exception to "untouched keys byte-for-byte" for a key the editor owns, applied only to rows this bug already damaged.

**D4a — Metric `fieldMapping.value` and `aggregation` are kept consistent after the merge.** The server's canonical aggregated metric shape is `{fieldMapping:{value:"amt"}, aggregation:{agg:"sum"}}` (`OutputConfigValidation.scala:46`, also what AI authoring writes), and `validateAggregation` only runs when `aggregation` itself is written. Today's builder omits `value` from `fieldMapping` whenever the metric is aggregated (`buildOutputConfig.ts:100`) and relies on always re-sending `aggregation: {value, agg}`; under D1 that stops being re-sent, so sending a `fieldMapping` without `value` would silently unbind the metric. Rule: the metric builder ALWAYS includes `fieldMapping.value = metricField` when a field is chosen (aggregated or not — the server accepts equal values in both places, `:148`), AND for the metric kind `fieldMapping` and `aggregation` are sent together whenever either is sent. Consequently an edit that only binds a label sends `{fieldMapping:{value, label}, aggregation:{value, agg}}`, which is a self-consistent pair, and a D4 stale-slot repair of a metric sends the repaired `fieldMapping` together with `aggregation`. Accepted departures from byte-for-byte preservation, both confined to a metric whose `fieldMapping` is being written anyway: the re-sent `aggregation` may be normalized from `{agg}` to `{value, agg}` (semantically identical), and a metric with no stored `aggregation` key gets an explicit `aggregation: null` (semantically identical to absent).

**D5 — `historyPayloads` and `name` keep their existing handling** (`withHistoryPayloads` already only sends on change). Create mode unchanged: full `buildOutputConfig` output.

**D6 — Seam proof.** (a) Frontend tests assert the exact `updateOutput` payload per symptom, red first against current code for the user-visible defect (standing constraint C1). (b) A backend route/service GUARD test pins the merge semantics the client relies on: PATCH with `{label: null}` stores `null`, an omitted `layout` is preserved, a `fieldMapping` without `annotation` replaces the stored one; it cannot be red-first (pins existing behaviour), so it is labelled a guard and shown to fail under a mutation (e.g. `mergeConfig` dropping `JsNull`-valued keys, or deep-merging `fieldMapping`), then the mutation reverted. (c) Live DB `outputs.config` rows before/after a real edit-mode save through the running app for: collection `layout: "list"` (bullet 1), metric literal→field label clear and table `columnOrder` reset (bullet 2), chart annotation removal (bullet 3).

**D7 — Markdown.** `buildOutputConfig` keeps emitting `fieldMapping: {}` for markdown; under D1 an untouched markdown save no longer drops a stored legacy `fieldMapping.content`. Consistent with the AC; update the stale comment in `OutputEditorSheet.tsx` accordingly.

## Risks / Trade-offs

- [Baseline drift: sheet state seeded asynchronously (capabilities) differs from baseline → spurious key sent] → baseline uses identical seeding; test "open + save untouched sends no config keys" for every kind, including table before/after capabilities load.
- [Kind change in edit mode (HEL-1388 still open) → baseline for old kind vs built for new kind] → if `kind !== output.kind`, send the full built config (today's behavior); note in final report as overlap with HEL-1388.
- [`null` vs absent for `columnOrder`] → reads already treat non-array as absent; a cleared Output renders like one with no `columnOrder` (row-key order today; schema order is HEL-1394, unimplemented). Covered by the table reset test.
- [D4 raw-compare for `fieldMapping` causing spurious writes on healthy Outputs] → raw compare is stale-slot detection only; untouched-save tests for each kind (incl. an aggregated metric in the canonical `{agg}` + `fieldMapping.value` shape, and a chart with a bound annotation) assert no `config`.
- [Aggregated metric unbound by a partial write] → D4a pairs `fieldMapping`/`aggregation` and always carries `value`; tested on the `{agg}` shape.

## Migration Plan

Client-only change; no data migration. Rollback = revert the PR.
