### Change Requests
1. **Server panel list is unspecified and unwired (D2 step 3).** `DashboardService`'s constructor (`DashboardService.scala`) has `dashboardRepo, accessChecker, auditService, outputRepo` and no panel access. `PanelRepository.findAllByDashboardId` is paged (`Page`, `MaxLimit`). The design says "server panel list, not paged" but names no mechanism, no constructor/ApiRoutes wiring (`ApiRoutes.scala:355`), and no handling for the ~20 test fixtures that build `new DashboardService(repo, checker)`. Specify: a dedicated repo method returning all panel ids for the dashboard (not paged, not user-context dependent beyond the already-made owner check), where it lives (DashboardRepository vs injected PanelRepository with the null-default convention), what a `null`/absent collaborator does, and add the task + Impact entry.
2. **The write path clobbers concurrent edits (D2 step 4).** `dashboardRepo.update(dashboard)` writes name, appearance, last_updated and layout from the stale pre-read row. A rename or appearance change landing between the read and the write is silently reverted, and a layout PATCH in that window is lost. The repair fires automatically on open so this is not hypothetical. Require a layout-column-only update (new repo method) that does not rewrite name/appearance/last_updated, ideally guarded `WHERE layout = <the layout read>` so a concurrent change makes it a no-op rather than an overwrite. Add a test for it.
3. **HEL-301 hazard 4.1 is not honoured explicitly.** `PanelGrid.tsx`'s header and `notes/mobile-pwa-handoff.md` 4.1 (called the binding spec) state that no layout-write path exists below `sm`, and `PanelGrid.test.tsx:426-480` pins it. D4 mounts the repair in `PanelGrid` at every width and waves this off in one sentence; task 3.7 only says "re-check". Either decide and document that the repair is the single deliberate exception (update the `PanelGrid` header, the test's contract text, and `features/layout/README.md`; add a phone-width test proving the ONLY write is the repair POST, only for stored-bad and only for the owner, and that `updateDashboardLayout`/`setLayoutPending` stay unreachable), or restrict. As written the structural guarantee in the code comments becomes false.
4. **RLS proof plan (D3) does not prove what it claims.** The repository `update` runs under the owner's user context regardless of caller, and the editor refusal is a service-level check, so a NOBYPASSRLS "editor refused" test only exercises Scala code, not RLS, and the "owner check mutated away" red would go red for a non-RLS reason. State what RLS actually gates here: the sharing-aware `findById` read, the new panel-id read (system context), and the layout-only owner-context write; build the spec to exercise exactly those under `helio_app_test`, with a named mutation per piece. Without this the "non-BYPASSRLS proof" the ticket demands is vacuous.
5. **Task 1.2 hand-waves the contract.** "JSON Schema under `schemas/` if the repo's schema-drift check requires it" leaves a decision to the executor. Resolve it now by checking the drift script and stating the file(s). Also add `"dashboard.layout.repair"` to `frontend/src/features/audit/ui/actionLabels.ts` (or state the fail-open raw string is intended).
