## Standing Constraints

- [C1] Authoritative value = dataset aggregate (sum of the field's delta across dataset_rows), refetched right after the submit itself succeeds — decoupled entirely from any downstream pipeline. This DELIBERATELY reinterprets the AC's "on run success" as "on write/submit success" (owner ruling, HEL-1095 escalation sub-1); stated plainly in proposal.md and the PR body.
- [C2] Only a failed submit request (rejected/network) rolls back the optimistic value with a visible error. A downstream pipeline run failing, or the auto-run guard/cheapness gate denying, must NOT roll back a write that actually persisted (owner ruling, HEL-1095 escalation sub-2).
- [C3] The new aggregate endpoint is ACL-scoped exactly like the existing dataset row routes (findByIdOwned + per-user RLS-respecting query context, never DbContext.withSystemContext), and documented in schemas/ + openspec/ in this same change (schema-drift gate).
- [C4] Ten rapid increments during one pending window accumulate optimistically; the displayed value must never snap back below the in-flight optimistic sum. Achieved by NOT reconciling mid-burst at all (design.md D9, design-gate round 2 fix): the aggregate is fetched only once the whole burst quiesces (the pending-delta map empties), at which point it equals the true total with nothing left to reconcile against — an earlier "reconcile against pending deltas on every success" mechanism was found racy and replaced by this quiesce-gated one; the never-snap-back outcome is unchanged.
- [C5] Concurrent writers' increments legitimately appear in the refetched aggregate — this is correct, expected behavior, stated explicitly in design.md, not a race to guard against.
- [C6] Pending/rollback state is exposed via COMPUTED ARIA state only — aria-busy while pending, aria-invalid + aria-describedby on rollback error — asserted by computed accessibility state in tests, never DOM presence. Compared against the running app in both light and dark themes.
- [C7] Show the red (a failing probe/test) for both the reconcile path and the rollback path before treating either as verified — no green-only evidence.
- [C8] `handleImmediateStep`'s single-value `submitState` reentrancy guard is replaced by a per-click pending-delta map (design.md D9, design-gate rounds 1–4 fixes) — every burst click fires its own request; on success, its own token is removed, `reconcileGeneration` is unconditionally incremented, and the aggregate is fetched and dispatched ONLY if that empties the pending map (never on every success — found racy in round 2); a fetch's own resolution is applied to the displayed value ONLY if no settle of ANY kind (success or failure) has happened since it was dispatched (the `reconcileGeneration` check) AND the pending map is still empty at that moment (found racy in round 3 for a new pending click, and round 4 for a sibling's success that didn't itself empty the map followed by a failure that did); on failure, `reconcileGeneration` is also unconditionally incremented, and only that click's own delta is subtracted from the current displayed value (a relative adjustment, never an absolute revert-to-snapshot).
