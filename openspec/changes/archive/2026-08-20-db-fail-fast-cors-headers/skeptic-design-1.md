## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

1. **`connectionTimeout` is genuinely absent today.** `grep -n "connectionTimeout\|maximumPoolSize\|..." backend/src/main/resources/application.conf` shows `helio.db` (lines 72-75) and `helio.db.privileged` (lines 111-115) set `numThreads`/`maximumPoolSize`/`minimumIdle`/`idleTimeout`/`maxLifetime` but no `connectionTimeout` key anywhere — confirms the design's premise that both pools fall back to HikariCP's built-in 30 000 ms default.

2. **Both pools are actually built via HikariCP through Slick's `forConfig`.** `backend/src/main/scala/com/helio/infrastructure/Database.scala:30,44` calls `JdbcBackend.Database.forConfig("helio.db", config)` / `forConfig("helio.db.privileged", config)`. Slick's HikariCP data source reads standard Hikari property names directly off the config stanza (this is how `maximumPoolSize`/`minimumIdle`/etc. already take effect today), so adding `connectionTimeout = 5000` to both stanzas is a mechanically sound, minimal change — no code change required for task 1, matching tasks.md.

3. **The CORS/`cors()` wrapping location matches design.md's claimed line numbers.** `ApiRoutes.scala:451-456`: `corsSettings` is built via `CorsSettings.defaultSettings...`, and `val routes: Route = cors(corsSettings) { traceContext.withTraceContext { ... } }` — exactly as design.md/Context describes, confirming D2's proposed insertion point (`handleExceptions`/`handleRejections` immediately inside `cors()`, before `traceContext.withTraceContext`) is a real, addressable location, not hand-waved.

4. **No existing `ExceptionHandler`/`RejectionHandler` registration anywhere in the backend.** `grep -rn "ExceptionHandler\|RejectionHandler" backend/src/main/scala/` returns exactly one hit — an unrelated Scaladoc comment in `PipelineService.scala:296` — matching design.md's "confirmed by grep" claim verbatim (including which file the false-positive comment lives in).

5. **`Http().bindAndHandle`-equivalent binding passes a bare `Route` to `.bind`.** `backend/src/main/scala/com/helio/app/HttpServer.scala:12`: `Http()(...).newServerAt(host, port).bind(routes)`. Passing a `Route` (not a pre-sealed `Flow`) to `.bind` relies on Pekko HTTP's implicit `route2HandlerFlow` conversion, which calls `Route.seal` with Pekko's *default* `ExceptionHandler`/`RejectionHandler` applied outside the entire route tree — i.e., outside whatever is inside `cors()`. This substantiates D2's stated rejection of the "top-level `bindAndHandle` exceptionHandler" alternative and confirms the root-cause mechanism (today, an exception unhandled inside the route tree bubbles past `cors()`'s header-attachment logic to this outer seal) is real, not speculative.

6. **`ErrorResponse` shape and existing call sites match design.md D3 exactly.** `ResourceProtocol.scala:10`: `final case class ErrorResponse(message: String)`. `ApiRoutes.scala:515,520,555` show the exact existing `ErrorResponse("Unauthorized")` / `ErrorResponse("Internal server error")` call sites design.md cites by line number — accurate, not approximated.

7. **Precedent for the planned unhandled-exception test (task 3.1/3.2) already exists.** `ApiRoutesSpec.scala:3912-3954` (HEL-311) shows the established pattern of subclassing a repository to return `Future.failed(new RuntimeException(secret))` and asserting the response neither leaks the secret nor includes it in the logged appender — directly reusable for the new top-level-handler test. `JsonProtocols` (mixed into `ApiRoutes`, `ApiRoutes.scala:125`) already provides the `ErrorResponse` marshaller the new handler needs, at zero new-import cost.

8. **Spec deltas are minimal, additive, and match the current base specs verbatim except for the stated addition.** Diffed `openspec/specs/hikaricp-pool-config/spec.md` (base) against the change's `specs/hikaricp-pool-config/spec.md` (delta): every existing requirement sentence and scenario is preserved unchanged; only "and connection timeout of 5 000 ms" is added to each requirement plus one new fail-fast scenario per pool. `error-response-safety` (base spec, unmodified by this change) already states the exact invariant ("no raw exception text... full exception logged server-side... generic curated message") the new `cors-error-handling` capability explicitly builds on without duplicating.

9. **Structural validation.** `openspec validate db-fail-fast-cors-headers --strict` → `Change 'db-fail-fast-cors-headers' is valid`.

10. **Auth's 401 paths complete directly, not via rejection**, so they are provably unaffected by the planned `RejectionHandler` change regardless of D4's "rejection" framing: `AuthDirectives.scala:77-81,96-97` — `case Success(None) | Failure(_) => complete(StatusCodes.Unauthorized, ErrorResponse("Unauthorized"))`. (Non-blocking note below.)

11. **No deploy-time env var overrides pool tuning** — `grep -rn "connectionTimeout\|HIKARI\|maximumPoolSize" infra/` finds nothing besides an unrelated comment, confirming `application.conf` is the sole source of truth for this change, consistent with the design's Impact section.

### Verdict: CONFIRM

The design correctly diagnoses two distinct, real defects, grounds every material claim (line numbers, grep results, library behavior) in the actual codebase rather than assertion, stays within the ticket's stated scope (no pool-sizing retune, no frontend change), and the spec deltas are precise, additive, and pass `openspec validate --strict`. Tasks map cleanly onto the two ticket scope items plus a reasonable test plan that has direct precedent in the existing test suite (including an explicit fallback for the one task — 3.5 — that may not be feasibly testable in-process). Decisions are justified with correct technical reasoning (Pekko's `route2HandlerFlow` auto-seal placement, HikariCP's `connectionTimeout` bounding the caller's wait regardless of how long physical connection establishment takes) rather than hand-waved.

### Non-blocking notes

- D4 in design.md characterizes `authenticate`'s 401 as "existing per-route rejection behavior," but `AuthDirectives.scala:77-81/96-97` shows these paths `complete()` directly rather than reject — the *conclusion* (unaffected by the new `RejectionHandler`) is still correct, just for a slightly different reason (direct completion is orthogonal to rejection handling entirely, not merely "more specific" rejection handling that out-prioritizes the new fallback). Worth a one-line correction at execution time so a future reader isn't misled about the actual mechanism, but it changes no required behavior and blocks nothing.
- Task 2.2's exact construction (`RejectionHandler.newBuilder().withFallback(RejectionHandler.default)...`) is implied rather than spelled out verbatim; a competent Pekko-HTTP implementer has enough here (D4's prose + the stated goal of only touching the "terminal/unhandled case") to build it correctly, but the executor should be explicit in its own PR description about which specific rejection case(s) it overrides (e.g., the no-matching-route/empty-rejection-list case) so the evaluator can verify scenario 2 precisely.
