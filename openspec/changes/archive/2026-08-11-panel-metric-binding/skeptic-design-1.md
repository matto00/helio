  - `schemas/panel.schema.json` — confirmed `MetricConfig`/`ChartConfig`/`TableConfig` are `additionalProperties: false` objects without a `metricId` property today, and `schemas/create-panel-request.schema.json` only `$ref`s these `$defs` (no direct edit needed) — both proposal claims verified.

- **D4's Chart/Table materialization scoping** — read `ChartConfig.fieldMapping`'s schema description (`{xAxis, yAxis, series?}` axis-keyed) vs. `MetricConfig`'s single-slot `{value: ...}` convention referenced from `panel-viz-aggregation`'s spec — the "no unambiguous slot" reasoning is real, not hand-waved, and is explicitly and consistently documented in proposal.md's Non-goals, design.md D4, and the spec delta's final requirement/scenario ("Chart panel with metricId set does not materialize a field mapping"). This is a defensible, clearly-flagged scope decision, not a silent gap — traces cleanly to AC1 (`MetricPanel` case) while explicitly deferring Chart/Table with a stated reason, and proposal.md's "Non-goals" section names it explicitly rather than omitting it.

- **Precedence rule (metricId authoritative default, raw fields override)** — consistent across proposal.md ("`fieldMapping`/`aggregation` become optional overrides"), design.md D4/D5, and the spec delta's dedicated requirement + two scenarios (metric-derived default, explicit override wins). Ticket.md's own scope-bullet wording ("A panel may set `metricId` OR the raw `dataTypeId` trio, not conflicting values") is internally ambiguous against ticket AC4 ("raw `fieldMapping`/`aggregation` act only as overrides" — implying co-existence, not exclusivity); design.md correctly resolves this in favor of the AC's literal language and documents the resolution in Planner Notes as a self-approved decision. Not a defect — a stale/ambiguous ticket sentence correctly disambiguated by the AC itself.

- **`/query`-route wiring gap correctly identified.** Read `backend/src/main/scala/com/helio/api/routes/PanelRoutes.scala:71-79` — confirmed `GET /api/panels/:id/query` calls `panelService.findById` then `panel.buildQuery` directly, with **no** `resolveSingleBinding` call today (even for the existing `dataTypeId` cross-user clearing). Tasks.md 5.3 explicitly flags this as needing to "confirm and wire this call site explicitly since `findById` today calls `panelRepo.findById` directly with no resolution step" — accurate ground truth, and necessary: without this wiring, a `MetricPanel` bound only via `metricId` would resolve to `dataTypeId/fieldMapping = None` on `/query` and silently fail to query at all, defeating AC1.

### Change Requests

1. **proposal.md contradicts design.md/tasks.md/spec.md on "non-deprecated" metric validation — must be reconciled before implementation.** `proposal.md:14` states: *"`PanelService.create`/`update` validate a supplied `metricId` resolves to a caller-owned, **non-deprecated** metric whose `dataTypeId` still satisfies the V41 pipeline-output rule; reject (400) otherwise."* I grepped every planning artifact (`grep -rn "deprecated" openspec/changes/panel-metric-binding/`) and this is the **only** occurrence of "deprecated" in the entire change — it does not appear in:
   - `design.md` D5's concrete algorithm for `rejectUnresolvableMetric` (`None (foreign/nonexistent) → 400; Some(m) → re-validate m.dataTypeId against V41` — no deprecated check anywhere in the described steps),
   - `tasks.md` 4.2 (same omission — describes exactly the same two checks, no deprecated branch),
   - `specs/panel-datatype-binding/spec.md`'s "create/update reject an unresolvable or non-pipeline-output metricId" requirement or its three scenarios (foreign, nonexistent, re-bind-to-foreign — no deprecated scenario), or
   - `tasks.md` T.2's test list (foreign/nonexistent rejected, owned/pipeline-output accepted — no deprecated case).

   `MetricDefinition.deprecated: Boolean` is a real field (`backend/src/main/scala/com/helio/domain/model.scala:843`) and `MetricRepository.findByIdOwned` does not filter on it, so this isn't implicitly covered. As written, an executor building strictly from design.md/tasks.md (the operative implementation-level artifacts) would **not** reject a deprecated-metric `metricId` at create/update — silently diverging from proposal.md's stated behavior, with zero test coverage either way. Resolve by either (a) removing the "non-deprecated" clause from proposal.md if it's not actually wanted (design.md's omission looks intentional/consistent everywhere else it appears), or (b) adding the `deprecated` check + a rejection scenario to design.md D5, tasks.md 4.2/T.2, and the spec delta if it is wanted. Either is fine — but the four artifacts must agree before an executor starts.

### Non-blocking notes

- Tasks.md 4.3's "add `metricRepo: MetricRepository` to `PanelService`'s constructor and its call site" undersells the blast radius — I found ~10 real call sites (`ApiRoutes.scala` + `BoundPanelRoutesSpec`, `PanelServiceResolveBindingsSpec` ×3, `PanelServiceScatterAggregationSpec` ×3, `PanelServiceCompanionBindingGuardSpec`, `PanelServiceBuildAllForCreateSpec`, `PanelServiceBatchUpdateErrorSpec`). Purely mechanical (compile errors make it impossible to miss), but worth the executor budgeting for it up front rather than discovering it mid-implementation.
- D3/D4's read-path per-field `metricId` clearing/materialization (as opposed to `withBindingCleared`'s existing whole-config wipe) has no `Panel`-trait-level accessor proposed (unlike `dataTypeId`, which is a trait method every subtype implements). Neither design.md nor tasks.md's Impact list touches `Panel.scala`, implying the intended implementation is a local 3-way `case mp: MetricPanel | cp: ChartPanel | tp: TablePanel` match inside `PanelService` (consistent with existing precedent in `PanelRowMapper.domainToRow`/`PanelConfigCodec.encodeConfig`, which already do exactly this). Workable and consistent with the codebase's established pattern — flagging only because it's implicit rather than spelled out.
- `PanelService.batchUpdate` (`PATCH /api/panels/batch`, used by the live-edit UI) never calls `rejectCompanionBinding` for `dataTypeId` today, and the design doesn't wire `rejectUnresolvableMetric` into it either — a foreign/nonexistent `metricId` set via that path would bypass create/update-time rejection and only get cleared on next read. This exactly mirrors the pre-existing `dataTypeId` gap in the same path (not a regression this ticket introduces), and AC3's "rejected at create/update" is written against `PanelService.create`/`update` specifically, so this is in-scope-as-written — just noting the precedent so it isn't mistaken for new scope during implementation.
- Design.md D5's framing ("mirrors `PanelService.rejectCompanionBinding`'s existing shape") is a little imprecise: `rejectCompanionBinding`'s own doc comment says a foreign/nonexistent `dataTypeId` **passes through unchanged** (deferred to read-time clearing), whereas `rejectUnresolvableMetric`'s actual described algorithm **rejects** foreign/nonexistent at create/update (per AC3) — the opposite behavior for that case. The concrete algorithm text is correct and matches AC3; only the "mirrors the shape" summary sentence could mislead a skimming reader. Worth a one-line tweak but not blocking.
