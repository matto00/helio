### Verdict: REFUTE

D1/D2 (server-owned state, `conversationId`-only request surface) is, on its own, a defensible and even preferable divergence from the ticket's illustrative `history[]`/`workingProposal` sketch — it's simpler, and the RLS-forgery argument in design.md is real and correct. That part of the design is sound. But combined with D6 and tasks.md 4.1/5.1, it silently drops a requirement the ticket explicitly asks for (AC2's "survive a reload"), and the frontend task breakdown doesn't reckon with a real, load-bearing behavior change in the existing shipped component. Both are fixable at the design-doc level without re-architecting; requesting revision before implementation starts is cheaper than discovering this mid-execution.

### Change Requests

1. **AC2's "survive a reload" is not actually deliverable by this design, and the gap is unacknowledged.** The ticket's Persistence bullet says conversations are stored server-side "so a session survives a reload," and AC2 says "Conversations persist server-side (owner-scoped, RLS) and survive a reload." As specced:
   - Task 4.1 explicitly rules out any new route ("no new route, additive request/response fields only") — there is no `GET` to fetch a persisted conversation's turns.
   - Task 5.1 says the frontend's `conversationId` lives in "local hook state... within the drawer's open lifetime" — not `sessionStorage`/`localStorage`/a URL param.
   - `DashboardAuthoringResponse`/`AuthoringStreamEvent.Result` per the request-shape spec (`{ proposal, warnings, conversationId }`) never return the turn history either — so even a client that *did* keep a stale `conversationId` around has nothing to hydrate the visible thread with.
   - Verified in real code: `AuthoringChatDrawer` is opened via plain `useState` in `DashboardList.tsx` (`isAuthoringOpen`, no persistence) — a browser reload destroys this state today, and nothing in this design changes that.

   The net effect: the DB row for a conversation trivially "persists" across a reload (any DB row does), but the user-facing "session" the ticket is actually motivated by does not survive one — there's no way for a reloaded page to know which `conversationId` to resume, and no route to fetch its turns if it did. Design.md's own Non-Goals/Risks sections don't mention this at all, so it reads as an unnoticed gap, not a reasoned scope cut. **Required:** either (a) add a minimal hydration path — persist `conversationId` client-side (e.g. `sessionStorage`, keyed per-drawer-session) and a `GET` conversation-by-id route/response that returns enough to re-render the thread — or (b) explicitly add "resuming a conversation after a page reload" to Non-Goals with a rationale, and get sign-off that this is an acceptable reduction of AC2's literal text before implementation starts.

2. **tasks.md 5.2 underspecifies a real behavior change to the shipped `AuthoringChatDrawer`.** Read `AuthoringChatDrawer.tsx` lines 75-81: today, the terminal `useEffect` on `result` unconditionally calls `navigate("/proposals/review", ...)` **and** `handleClose()` — which closes the entire drawer — the instant *any* turn's result arrives. For multi-turn support to work at all, this auto-navigate-and-close-on-first-result behavior has to become a manual, explicit "review & apply" action (per spec.md's new scenario "Review & apply hands off the latest working proposal unchanged," which frames it as something "the user activates... at any point"), while a completed turn instead reopens the input for a follow-up message. Neither design.md nor tasks.md 5.2 says this existing effect must be removed/reworked — it only says to "keep 'review & apply' navigating," which reads as if that's already a distinct, existing affordance, when today it's an automatic side effect of the very first result. Design.md's D6 also punts entirely on what content a turn's entry in the "read-only progress log" actually displays, which matters here: `useDashboardAuthoringStream.ts`'s own doc comment says the raw streamed `progressText` is explicitly "not meant to be rendered verbatim... raw, incomplete proposal JSON, not conversational prose" — so the model's response per turn isn't natural-language chat content, and neither design.md nor tasks.md specifies what a turn's thread entry shows instead (the user's own message? a generated one-line proposal diff/summary? just a status marker?). **Required:** tasks.md 5.2 should explicitly call out (a) that the existing terminal `useEffect`'s auto-navigate-and-close behavior must be replaced with an explicit "review & apply" control reachable after any turn, and (b) what data model/content each turn's thread entry renders.

### Non-blocking notes

- D3's JSONB-blob storage choice (`turns`/`latest_proposal` as whole-row JSONB, no per-turn table) is well-justified by the "no per-turn query need" rationale and matches `metrics.allowed_dimensions`/`format`'s existing precedent — no objection.
- D4/D5's self-approved numeric constants (20,000 history-token budget, 200,000 conversation-token ceiling) are reasonable given `ClaudeConfig.DefaultMaxInputTokens = 100000`, and are explicitly flagged as self-approved/tunable per the Planner Notes convention already used elsewhere in this codebase (e.g. `WorkspaceContextBudget.DefaultBudgetBytes`).
- `id TEXT PK` generation strategy (presumably `UUID.randomUUID().toString`, the ubiquitous convention already used by `DataTypeId`/`AlertRuleId`/`ApiTokenId`/`UserId` elsewhere in this codebase) isn't spelled out in design.md, but the convention is unambiguous enough codebase-wide that this is not worth blocking on.
