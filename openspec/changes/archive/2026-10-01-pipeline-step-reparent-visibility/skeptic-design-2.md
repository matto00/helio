### Verdict: REFUTE

### Change Requests
1. Hole in "attachAsTail:true moves nothing" (AC1). In persistNewStep, `attachAsTail` is honored ONLY in the `(Some(parentStepId), None)` branch. With `rootId` (handled by design) OR with NEITHER anchor (the `(None, None)` branch, PipelineService ~L1996-2020), attachAsTail is ignored and the step is spliced after trunk-last, silently re-parenting its tails. The design only rejects rootId + attachAsTail:true; MCP `add_pipeline_step {attachAsTail:true}` with no parentStepId/rootId sends no guard flag (flag only sent when attachAsTail is omitted) and silently splices. This also makes the backend spec line "attachAsTail:true inserts never re-parent and SHALL never be rejected by this flag" false for those shapes. Required: (a) the MCP tool rejects attachAsTail:true unless parentStepId is given (covers rootId and no-anchor), or alternatively sends rejectIfReparents:true for every case except an explicit attachAsTail:false / honored tail; (b) restate the backend spec so the flag is evaluated on the actual placement path (attachAsTail is only honored with parentStepId); (c) add a test for `attachAsTail:true` with no anchor.

### Non-blocking notes

Implement as a new service method (e.g. addStepReporting returning (resp, ids)) with addStep delegating and discarding; state this in design.md/tasks 1.2.

A filter legitimately yielding 0 rows will also warn; acceptable as a "warning", say so in the tool description.
