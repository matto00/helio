## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (against code, HEAD 677db0a8)
- Root cause confirmed: PipelineService.persistNewStep (L1910-2060) default path calls spliceInsertAtInternal, which reads all existing children of the anchor, inserts the new row, and reparents every child under it (PipelineStepRepository L656-720). attachTailInternal (L760+) is the no-move sibling path. write.ts L548-554 / assertSchemas.ts L100-131 never forward attachAsTail. Probe report matches code.
- Backend reparentedStepIds is feasible: `existingChildren` is already computed inside spliceInsertAtInternal's DBIO; it can return (step, ids). Five call sites need threading (rootId L1942, parentStepId L1972, no-position L2016, position L2044, duplicateStep L2303).
- stepRowCounts exists in RunResultResponse (PipelineProtocol L267) and helio-mcp types.ts L623; helioApi.runPipeline (L787-806) drops it.

### Verdict: REFUTE

### Change Requests
1. AC1 is not satisfied by the stated guard: two more MCP paths splice with no guard.
   a. `add_outputs_from_shape` (pipelinesHandlers.ts L234-243) calls api.addPipelineStep with `parentStepId = input.stepId` and no attachAsTail. If `stepId` already has children (the normal case when adding a second output off a shared node), the first expanded step splices in and silently reparents them: the exact bug. If `stepId` is absent, it falls to persistNewStep's (None,None) branch (trunk-last splice). The design is silent. Required: decide and specify (e.g. first expanded step sent with attachAsTail:true when stepId given and it has children, or the same loud guard), with a test. Its tool description says "branching off stepId", which is sibling semantics, so attachAsTail:true is the evident intent.
   b. add_pipeline_step with NEITHER parentStepId nor rootId on a single-root pipeline (explicitly allowed by the tool description) takes the (None,None) branch: anchor = trunkOf(current).last, and spliceInsertAtInternal reparents that step's existing children, which are its tails (trunk-last has no trunk child but can have attachAsTail tails, which the design's own recommended lanes create). The guard defined in Decision 1 only covers parentStepId and rootId. Required: extend the guard to resolve the effective anchor in the no-anchor case (trunk-last's children) or require an explicit anchor.
2. Decision 2 / spec inconsistent on rootId. Design says rootId + attachAsTail:true is an error; the spec's attachAsTail:true requirement/scenario is written only for parentStepId and never states this. Also guard "children of rootId" must be defined precisely: parentless steps with that root_id (spliceInsert uses stepsTable parentStepId.isEmpty && rootId===rid). Add the rootId error to the spec delta and a test. Note a consequence to document: rootId on any non-empty root always trips the guard, so "append to trunk end" must use parentStepId=<last step> (childless, unguarded).
3. Zero-row warning rule has unspecified/incorrect data sources:
   a. Disabled steps get no stepRowCounts entry (InProcessPipelineEngine L335 doc). Define: parent disabled or absent from the map means walk up to the nearest counted ancestor or skip; never treat missing as 0 or as a warning.
   b. "Primary source row count for a root-level step" is only right for the primary root. Under multi-root, a root-level step on another root has a different source whose count is not in the run result. Define: warn only for root-level steps of the primary root, else skip.
   c. Spark path returns stepCounts = Map.empty (SparkJobSubmitter L166): warnings would be silently [] and indistinguishable from healthy. Specify behaviour (e.g. warnings omitted/unavailable marker when stepRowCounts is empty on a non-empty run).
   d. Join lane refs: specify they come from step.config.secondaryInput {kind:"lane", stepId} for join/union/lookup (SecondaryInput.scala L30), and `join` source-kind secondary has no count. Spec says "for a join, any of its inputs" but the lane/parent mapping and the union/lookup cases are unstated. Also the MCP "config: unknown" typing means the handler must narrow it defensively (add a test with malformed config).
4. Schema/doc sites incomplete or wrong target. Task 1.2 says update "schemas/pipelines (create-step response)", but no step-response or run-result schema exists in schemas/pipelines (only create-pipeline-step-request.schema.json carries attachAsTail; update its description too). Name the real sites: that request schema description; openspec/specs/pipeline-run-execution/spec.md (mentions stepRowCounts) and patch-set-lane-edits (attachAsTail); docs/agent-native.md; helio-mcp/README.md; the frontend PipelineStepResponse type if it models the response. State explicitly there is no response schema to update, or add one.
5. PipelineStepResponse is a sealed trait with ~14 case classes (PipelineStepProtocol L17-111). "Adds reparentedStepIds defaulting to []" means a field on every case class and formatter, and it would then appear as `[]` on every GET/PATCH/duplicate response. Specify the mechanism (e.g. a thin wrapper/extra field injected only on the create response) and that the spec's "possibly empty" applies to POST only; add a protocol round-trip test. Also say whether duplicateStep (which also splices) reports it.
