I1 analysis. The two rules together are: the reducer moves the store version from s to s+1 only when the response is s+1, and the hook adopts only when the store version changed this render to persisted+1. These imply s == persisted == response-1. The response being exactly one more proves that the server layout before the create was at version p. So server@p+1 = server@p + the placed items, and the extended baseline equals server@p+1. I traced each interleaving:
- **In-flight PATCH (sent at p), server ran the PATCH first.** The create response is p+2. If it arrives before the PATCH response, the store is at p, so nothing is adopted. If the PATCH response arrived first and was adopted (store and baseline at p+1), then p+2 is adopted. That is correct, because server@p+2 = L1 + the new item. This removes the existing "redundant PATCH" race.
- **In-flight PATCH, server ran the create first.** The create response p+1 is adopted. The PATCH, sent with p, gets a 409, rebases and retries. The retry response is not adopted because the store has the item, so `rebased && !adopted` keeps (B+item, p+1). The next save 409s and rebases. Safe.
- **Two own creates.** In order, both are adopted. Out of order, D5 holds: the baseline includes both items under p+1, so the version is older than the content, which I1 allows.
- **409 retry while the user edits.** The 409 means the server was already past p because of another writer, so every create response is at least p+2 and is never adopted. The exception is when the 409 was caused by our own create, which is the case above.
- **Classification leaks.** If the adoption render lands in class 4 (for example, batched with another store change), the hook re-baselines from the store pair (layout+X, s+1). That pair is valid by the reducer's +1 proof. Any unsaved edit discarded by that re-baseline is today's class-4 behaviour, not new.

### Non-blocking notes
1. **Follow-up not yet filed.** design.md says the DELETE follow-up is "filed", but Linear shows no relation from HEL-1525 other than HEL-1457, and tasks.md has no task to file it. Before delivery, file it (Follow-up label, relatedTo HEL-1525) or reword the claim.
2. **Where the previous-version ref is written.** The ref must be written inside the layout effect, like `prevLayoutRef`. It must not be written in an every-render effect declared before the layout effect: that effect runs first, so the ref would always equal the current version and adoption would never fire. Test 3.3 would catch this, but it is cheap to state.
3. **The in-flight PATCH interleaving is untested.** Task 3.5 relies on the existing `inflightResponse` test, but those mocks carry no `layoutVersion`, so the new code never runs in it. Consider one test: the create response (p+1) arrives while a PATCH sent at p is in flight, the PATCH 409s and is retried, and no item is lost.
4. **Size of the carrier change.** Changing the return type of `PanelService.create` ripples into the five non-route callers and roughly 20 backend test files that pattern-match `(panel, placed)`. Choose the carrier so this ripple stays mechanical.
5. **Reducer guard.** The reducer could also require that `adoptPlacedLayouts` actually appended an item in every breakpoint before it bumps the version. Today `withPanel` skips a breakpoint that already holds the id. The +1 proof still keeps the pair valid in that case, so this is optional belt-and-braces.
