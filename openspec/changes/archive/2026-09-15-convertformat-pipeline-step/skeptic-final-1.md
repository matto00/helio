  - Empty-string CSV → `"[]"`, header-only CSV → `"[]"`, `json->csv` on `[]` → `""`: all three are **documented, deliberate** lossy conversions (design.md D4), not silent failures of an otherwise-convertible input — and critically, the *step* still emits exactly one row per input row (`D2`'s 1:1 contract is about row count, not cell content).   - Lone `\r` — handled by `parseCsvRows`'s CR branch, documented CRLF/CR-agnostic row separator; produces the same `rowHasContent`/`endRow` semantics as `\n`. No silent-empty case found.

This does not produce empty rows (round-trip is still byte-identical since both directions treat it the same way), but it is an undocumented rough edge worth a non-blocking note, not an AC2 violation.

### Verdict: CONFIRM

### Non-blocking notes

1. The D5 Markdown hard-break-join rule (`\` + `\n` when both adjacent lines are non-empty) is real, matches design.md, and is exercised correctly by `textToMarkdown` — but it is presently **unverifiable by any test in the suite**, because the only tests touching text↔markdown assert the round-tripped-back-to-text value, and `markdownToText`'s generic fallback happens to decode a bare `\n` identically to an escaped hard break. A future refactor that silently drops the hard-break escaping would ship green. Recommend (not blocking this gate, since the round-trip AC itself is genuinely met and the code is correct) adding at least one assertion on the intermediate Markdown string for a two-non-empty-line input (e.g. `textToMarkdown("a\nb") shouldBe "a\\\nb"`), so the capability spec's own "text->markdown output SHALL render as the literal text" requirement has a real test behind it.
2. `PipelineAnalyzeConvertFormatSpec` (the embedded-Postgres integration test) confirms analyze returns 200 and the step response is correct, but stops short of asserting `costVerdict.reasons` contains `content-conversion` for that persisted pipeline — the estimator unit test proves the classification logic and I independently read the mapping code proving it reaches the HTTP response, but no single test proves both facts together end-to-end.
3. BOM-prefixed CSV input is not special-cased (a leading U+FEFF becomes part of the first field/header literally); harmless (round-trip stays consistent) but undocumented — worth a note in design.md D4 if BOM-bearing uploads are a realistic input source.

None of the above rises to a Change Request: AC1-AC8 are each traced to real, independently-verified code and passing tests; the owner scope ruling (deterministic-only, no ClaudeClient, CSV<->JSON + text<->Markdown only) is honored exactly; the two mutations I ran independently (beyond the executor's own C6 list) found one genuine coverage gap (note 1) but no functional defect — the shipped behavior is correct, only its regression protection is thinner than ideal for that one rule.
