### Verdict: REFUTE

Round 1's four items are substantively addressed (one textual leftover aside) and Decisions 6/7/8 check out against the code. But the same class of defect round 1 flagged — call sites the design does not enumerate, and composite mutations whose row cardinality is unsettled — is still present in the panel and dashboard-snapshot paths, and Decision 2's success-detection rule does not fit the actual signature of the very first method it will be applied to.

### Change Requests

1. **design.md Non-Goals still names the non-existent `AuditSource.Api`.** The bullet reads "every call site passes `AuditSource.Api` (or whatever the existing default/system source is; see Decision 3)". Decision 3 resolved this to `AuditSource.Ui`; the Non-Goals text was not updated and now contradicts it, leaving the executor two conflicting instructions in one document. Replace the Non-Goals wording with `AuditSource.Ui` (pointing at Decision 3), so no reference to `Api` remains anywhere in the artifacts.

2. **Decision 2's "fire only on the `Right` branch" does not apply to `DashboardService.create`, which is not `Either`-returning.** `DashboardService.scala:69` returns `Future[(Dashboard, Boolean)]`, and the `ifExists: "return"` path (`:72-76`) returns `(existing, false)` when an existing dashboard matched — **nothing was created**. Instrumenting per Decision 2 as written would emit `dashboard.create` for a call that created nothing, violating the ticket AC ("writes exactly one audit row with correct action") and the spec's `dashboard.create` scenario. State in design.md (and task 2.1) that `dashboard.create` fires only when the returned `created` flag is `true`, and add a spec.md scenario for the `ifExists: "return"` match writing no audit row. Also generalize Decision 2 so it covers non-`Either` success signals rather than only `Right`.

3. **`PanelService.batchCreate` and `batchUpdate` are uninstrumented, unenumerated live mutation endpoints with unresolved cardinality.** `PanelRoutes.scala:45` → `batchCreate` (`PanelService.scala:379`) and `PanelRoutes.scala:33` → `batchUpdate` (`:315`) are `POST` routes that create/update N panels per call. Tasks §3 lists only create/update/delete/duplicate, so these will be missed. This is exactly the Decision 7 question: decide and record whether a batch call emits one row (e.g. `panel.batch_create` with a count in metadata) or one `panel.create` per panel — the "one row per actor-initiated API call" principle Decision 7 already adopts argues for the former, but it must be stated, not inferred. Add tasks and a spec.md scenario.

4. **`DashboardContentsService.replaceContents` and `DashboardService.importSnapshot` are unenumerated composite mutations.** `DashboardContentsRoutes.scala:31` (`PUT`, `DashboardContentsService.scala:42` — the service's only public method, and a panel-set replacement that bypasses `PanelService.create/update/delete`) and `DashboardSnapshotRoutes.scala:35` (`POST /api/dashboards/import` → `DashboardService.scala:231` `importSnapshot`, creating a dashboard plus panels). design.md refers to `DashboardContentsService` only as a conditional aside and never mentions `importSnapshot`. Name both explicitly with their action and row cardinality (per Decision 7), and add tasks under §2/§3.

5. **Decide explicitly on the remaining source-adjacent mutation routes, including the one round 1 already named.** `sources/UploadRoutes.scala:42/62` (`POST` → `imageUploadService.upload`), `panels/BoundPanelRoutes.scala:30` (`POST` → `boundPanelService.create` — a panel-creating path distinct from `PanelService.create`), and `panels/AutoLayoutRoutes.scala:31` (`POST` → `autoLayoutService.autoLayout`, which mutates dashboard layout). Each needs a one-line in/out decision recorded in design.md Decision 8 (or a new decision) with its action name if in scope. `UploadRoutes` in particular was named in round-1 CR4 and the revision dropped it silently rather than ruling on it.

6. **Task 7.5 currently guarantees these gaps will not be caught.** It states "the §2-6 enumeration is the source of truth; grepping the diff is a final cross-check, not how call sites are discovered" — a sound principle, but it means an incomplete §2-6 (CRs 3-5 above) is never recovered from. Once CRs 3-5 are folded in, rewrite 7.5 as an explicit route-file-by-route-file audit that enumerates *every* `post`/`put`/`patch`/`delete` directive under `backend/src/main/scala/com/helio/api/routes/` and records, for each, either its audit action or an explicit out-of-scope reason. That is a bounded, checkable task; "confirm no method was missed" is not.
