## Context

See `proposal.md` (Why) and `ticket.md` (root cause from CI logs). Facts about zonky embedded-postgres 2.0.7 that shape this design, read from its source jar (`~/.cache/coursier/.../embedded-postgres-2.0.7-sources.jar`). The executor re-verifies each one:

- `Builder.start()` **mutates the builder**. When unset, it assigns `builderPort = detectPort()` and `builderDataDirectory = Files.createTempDirectory("epg")`. Calling `start()` twice on the same builder therefore reuses the same port and data directory.
- `detectPort()` binds `ServerSocket(0)`, reads the port, then closes the socket. That opens the TOCTOU window.
- `startPostmaster()` runs `pg_ctl ... -w start` and never checks its exit status. `waitForServerStartup()`/`verifyReady()` only check that *something* on `localhost:port` accepts a connection and answers `SELECT 1`.
- `EmbeddedPostgres` exposes no data-directory getter. `Builder.setDataDirectory(...)` and `Builder.setPort(int)` exist; `setPort(0)` restores port auto-detection.
- `cleanDataDirectory` defaults to `true`: `close()` stops the postmaster with `pg_ctl -D <own dir> stop` and deletes the data directory.

There are 226 `EmbeddedPostgres.builder()` call sites in 221 files under `backend/src/test/scala`: 223 `.setConnectConfig("stringtype", "unspecified").start()`, 2 bare `.start()` (`PipelineRunCrossInstanceSpec`, `LegacyOutputConfigKeysParitySpec`) and 1 multi-line chain with `setServerConfig` SSL options (`SqlConnectorTlsSpec`). No call site uses `setPort` or `setDataDirectory` (the executor re-verifies this by grep).

## Goals / Non-Goals

**Goals:** close the port-steal at its source for every embedded-Postgres start in the backend suite. Keep the diff mechanical outside two new files plus one regression spec. Make any regression fail loudly.

**Non-Goals:**
- Changing role names, grants, `SET ROLE`, BYPASSRLS properties, Flyway usage or any spec's assertions.
- Removing the existing `IF NOT EXISTS` role DO-blocks (`ApplyProposalSpecBase`, `CombinedApplyProposalSpecBase`, `PipelineApplyProposalSpecBase`, `ApiTokenAuthSpec`, `AssistantConversationRoutesSpec`, ...). They are harmless once every cluster is guaranteed fresh, but removing them is not provably safe within this change's evidence budget, so they stay (owner ruling: keep unless provably safe).
- Patching or upgrading zonky.
- Changing `build.sbt` test grouping or concurrency (HEL-1468's lane owns `build.sbt`).
- Retrying on start failures other than a cluster mismatch.

## Decisions

### D1. Helper API: `com.helio.testkit.VerifiedEmbeddedPostgres.start(builder: => EmbeddedPostgres.Builder): EmbeddedPostgres`
The parameter is by-name, so each attempt evaluates a **fresh** builder: zonky's `Builder.start()` mutates port and data dir, so reusing one builder would retry the same stolen port. The return type is the unchanged `EmbeddedPostgres`, so no downstream line at any call site changes. It lives in `com.helio.testkit` next to `HelioRouteTest`/`TempDirectorySupport`, the existing home for shared test infrastructure that a guard enforces.
*Alternatives:* a `() => Builder` factory (noisier call sites, same semantics); a trait mixin (cannot reach the field-initialiser and `object` call sites); a builder-configuring function `Builder => Builder` (call sites would need rewriting into lambda form, which is less mechanical).

### D2. Ownership check: compare the server-reported `data_directory` with the attempt's own data directory
For each attempt the helper creates its own data directory and passes it via `setDataDirectory`. After `start()` returns, it runs `SHOW data_directory` over `getPostgresDatabase` (the superuser connection, so the setting is readable). It closes that connection on every path (success, mismatch, or throw; a discarded attempt must not leave an open connection on a foreign cluster), and compares the reported string, normalised with `Paths.get(reported).toAbsolutePath.normalize` (**never** `toRealPath`, because the foreign directory may already be gone), against the helper's **own** directory canonicalised once with `toRealPath` at creation time. Equal means the cluster is ours: return the instance. The owner ruling specifies this check.

**Every outcome other than a verified match is "unverified"** and is discarded and retried within the D4 bound:
- the reported path differs (a steal);
- `SHOW` throws, e.g. the foreign cluster is shutting down (the HEL-1470 shape): connection refused, "terminating connection", "This connection has been closed";
- obtaining the connection throws.
The check's own `SQLException`/`IOException` is never propagated as-is. It is recorded in the attempt log that the exhaustion error carries. Every code path that does not return the instance closes it first (D3), via a `try`/`finally`-style structure, so no exit path skips the discard.

Tmp-symlink safety: if `/tmp` were a symlink, the server reports the `-D` path made absolute but not symlink-resolved. Our side is therefore compared in **both** forms (`toRealPath` and `toAbsolutePath.normalize` of the dir as passed to `setDataDirectory`), and a match on either counts as verified. A foreign directory can never match either form, because each attempt's dir is unique.
*Alternatives:* pg_ctl exit status (zonky does not expose it); reading `postmaster.pid` from our own dir (that file is also absent when the postmaster dies for other reasons, which conflates failure modes, and it still needs the dir); a marker row (requires a write against a possibly foreign cluster, which is exactly what must never happen).
The data directory is created with a raw `Files.createTempDirectory("epg")`. That is the same call and lifecycle zonky uses today, and zonky's `cleanDataDirectory=true` `close()` deletes it. The line therefore carries the `// temp-dir-hygiene: reviewed — <reason>` escape hatch required by `scripts/check-test-temp-dir-hygiene.mjs`. A discarded attempt's dir is deleted by the helper itself (see D3).

### D3. Discarding a stolen attempt must never touch the foreign cluster
On an unverified attempt the helper does **not** run any SQL beyond the read-only `SHOW`. It calls the attempt's `close()`, which runs `pg_ctl -D <our own dir> stop` (confirmed by the design-gate skeptic from source: by data dir, never by port; it catches the stop failure and deletes the dir). That addresses only our own data dir. Our own postmaster has normally already died, but if it is somehow still alive (e.g. an unverified-because-`SHOW`-threw case), it is stopped, which is also correct. Any exception from that `close()` is caught and logged, and the attempt's data dir is deleted. The regression spec (D6) must prove that the foreign cluster is still alive and unchanged after a discard. If zonky's `close()` turns out to signal anything by port rather than by data dir, that is a design-gate-level finding: stop and escalate rather than work around it silently.
A discarded attempt leaves zonky's registered JVM shutdown hook behind (one per attempt, only on a steal, which is rare). That hook calls `close()` again on our dead instance, which is harmless. This is accepted.

### D4. Retry policy: bounded, on mismatch only
At most 5 attempts. Attempt 1 uses the builder as the caller configured it, except that the helper always supplies its own data directory. Attempts 2 and later evaluate a fresh builder and force `setPort(nextPort())` (production `nextPort = () => 0`, i.e. zonky's fresh port detection; see D6 step 4) plus a fresh data dir, so a builder that pins a port (only the regression spec does) is un-pinned onto a freshly detected port. Once attempts are exhausted, the helper throws an `IllegalStateException` naming the expected and observed data directories for every attempt. Every exception thrown by zonky's own `start()` itself (e.g. "Gave up waiting for server to start") propagates unchanged; only failures of the helper's ownership check (D2) are retried. That keeps genuine startup failures as fast and as visible as before, and keeps this change behaviour-preserving for everything except the steal.

### D5. Mechanical migration via a committed codemod and an independent verifier
- `migrate-embedded-postgres.py` lives in this change's directory, so it is archived with the change and the reviewer can re-run it. It rewrites `EmbeddedPostgres.builder()<chain>.start()` into `VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder()<chain>)`, finding the end of the chain by balanced-paren scanning so the multi-line SSL chain is handled. The chain text, including its newlines and indentation, is copied byte-for-byte. For files outside package `com.helio.testkit`, it inserts `import com.helio.testkit.VerifiedEmbeddedPostgres` on the line directly after the existing `import io.zonky.test.db.postgres.embedded.EmbeddedPostgres`, at the same indentation. It refuses (exits non-zero, naming the file) on any occurrence it cannot transform.
- **Exact output rule.** Both scripts implement this independently from this text:
  1. The token `EmbeddedPostgres.builder()` becomes `VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder()`.
  2. The chain's terminal `.start()` (exactly those 8 characters, located as the first `.start()` at paren-depth 0 after the `builder()` token) becomes `)`. Any whitespace or newlines **before** it are kept as-is.
  3. Nothing else changes.

  For the 225 single-line sites this yields `VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder().setConnectConfig("stringtype", "unspecified"))` (or `...builder())`). For `SqlConnectorTlsSpec`'s multi-line chain it yields:
  ```
          VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder()
            .setServerConfig("ssl", "on")
            .setServerConfig("ssl_cert_file", cert.toString)
            .setServerConfig("ssl_key_file", key.toString)
            )
  ```
  The lone `)` on its own line keeps the transform exactly invertible: the inverse replaces the balancing `)` with `.start()`. It is deliberately not hand-tidied (C1).
- `verify-embedded-postgres-migration.py` is a separate script that does not import the codemod. For every changed file in `git diff <base>...HEAD`, other than the allow-listed new files and the change dir, it applies the **inverse** transform to the new content (unwrap the call; drop exactly the one inserted import line) and asserts byte-equality with the base version. It also asserts:
  - that the set of changed files equals exactly the set of files containing `EmbeddedPostgres.builder()` at base, plus the allow-list;
  - **completeness:** for every migrated file, the count of `VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder` in the new content equals the count of `EmbeddedPostgres.builder()` at base, and the count of `EmbeddedPostgres.builder` occurrences **not** immediately wrapped is zero. The totals across all files are 226 wrapped and 0 unwrapped, which catches a partial migration that the inverse byte-check alone would pass;
  - exactly one inserted import line per file outside `com.helio.testkit` (and none inside it).
  Its transcript is the "verified by a script, not by hand" evidence.
- Line length: wrapping adds about 30 characters to each call line. If any repo check (scala-quality, scalafmt if configured) rejects a resulting line, that is a gate finding to report, not a cue to hand-reformat. Hand formatting would break the verifier's byte-equality. Fix it by adjusting the codemod's deterministic output rule and the verifier together.

### D6. Deterministic port-steal regression spec (`VerifiedEmbeddedPostgresSpec`, in `com.helio.testkit`)
1. Start cluster A through the helper and create a marker role/table in it.
2. **Old path:** start `EmbeddedPostgres.builder().setPort(A.getPort).start()` directly and assert its `SHOW data_directory` equals **A's** directory. This is the silent attach, reproduced deterministically. The spec carries a scoped guard exemption (see D7).
3. **Helper:** call `VerifiedEmbeddedPostgres.start(EmbeddedPostgres.builder().setPort(A.getPort))`. Assert it returns an instance on a different port whose `data_directory` is its own and that does not contain A's marker. Assert that A still answers and still holds its marker afterwards.
4. **Exhaustion:** the helper's public `start(builder)` delegates to `private[testkit] def startWith(builder: => EmbeddedPostgres.Builder, maxAttempts: Int, nextPort: () => Int, observeDataDirectory: EmbeddedPostgres => String): EmbeddedPostgres`. Production passes `maxAttempts = 5`, `nextPort = () => 0` (0 means zonky auto-detects) and `observeDataDirectory = <run SHOW data_directory over getPostgresDatabase>`. The spec calls `VerifiedEmbeddedPostgres.startWith(EmbeddedPostgres.builder().setPort(A.getPort), maxAttempts = 2, nextPort = () => A.getPort, observeDataDirectory = <the production observer>)` so every attempt collides with A. It asserts an `IllegalStateException` whose message names both A's directory and each attempt's own directory, and that A is still alive with its marker afterwards.
5. **Failed ownership check (the HEL-1470 shape):** call `VerifiedEmbeddedPostgres.startWith(EmbeddedPostgres.builder(), maxAttempts = 2, nextPort = () => 0, observeDataDirectory = <throws SQLException("This connection has been closed.") on the first call, real SHOW afterwards>)`. Assert that it returns an instance whose real `SHOW data_directory` is its own, and that the first attempt's own data dir no longer exists. There is no data-dir getter, so the test observer first runs the real `SHOW data_directory` on the instance it is handed, records that path, and only then throws; the assertion checks that recorded path no longer exists. With `maxAttempts = 1` and an always-throwing observer, assert an `IllegalStateException` whose message carries the recorded `SQLException` text. Mutation proof (transcript only): let the observer's exception propagate, and this step goes red.
Mutation proof (recorded in the executor transcript, not committed): disable the ownership comparison and step 3 goes red.
Every instance the spec starts, including the step-2 old-path instance, is closed explicitly in a `finally`, and A is closed in `afterAll`.

### D7. Guard spec (`EmbeddedPostgresStartGuardSpec`, in `com.helio.testkit`): a closed allowlist
Superseded by the final-gate rounds: a regex blocklist of bad spellings was bypassable (renames with odd whitespace, static-member imports `EmbeddedPostgres._` / `.{builder => b}` / `.start`, a nested `import EmbeddedPostgres._`, backticks, zonky's other entry points). The guard now scans `src/test/scala` (the test JVM's cwd is `backend/`) and, outside the two exempt **exact paths** (`com/helio/testkit/VerifiedEmbeddedPostgres.scala`, and `.../VerifiedEmbeddedPostgresSpec.scala` for marked lines only), treats every standalone `EmbeddedPostgres` token (word-bounded, so `VerifiedEmbeddedPostgres` never counts) as an offender unless it is exactly one of:
- **(a)** a plain import of the class from `io.zonky.test.db.postgres.embedded`, alone or as an unrenamed item of a `{...}` selector (whitespace and newlines tolerated), not followed by `.`;
- **(b)** a type position: preceded by `:` or `[` (or `,` closed by `]`), and not followed by `.` or `(`;
- **(c)** the builder reference directly wrapped by `VerifiedEmbeddedPostgres.start(` or `.startWith(`.

Also rejected by name: `PreparedDbProvider`, the `*Rule` and `*Extension` classes of zonky's `junit` and `junit5` packages, any import from those packages, a wildcard import of the embedded package, and a wrapped builder argument that still starts the cluster (`.start()` or a paren-less `.start`, e.g. `.tap(_.start)`; for `startWith(` only the first argument, up to the first comma at paren-depth 0). The `// embedded-pg-guard: deliberate unverified start (port-steal repro)` marker is honoured per line, only in `VerifiedEmbeddedPostgresSpec`.

**Comment handling.** Comments are blanked before the scan, because several existing specs mention the class in prose and code in a comment is not executable. The stripper is a small lexer that recognises comments only in code positions: it lexes single- and triple-quoted strings, interpolated strings (`id"..."`, `id"""..."""`, `raw"..."` without escapes), `$$`, and `${...}` splices as nested code (with brace depth, nested strings, nested interpolations, nested comments and char literals such as `'"'`). String contents are never stripped. On any unbalanced or unterminated construct the lexer gives up and that file is scanned RAW with no stripping (fail closed). The spec reports the count in its log (`STATS ... raw-fallback-files=N`); in the real tree it is 0 of 501 files (`proof/c5-whole-tree-dump.txt`, which also lists, per file, whether it has a splice literal, whether it fell back, and whether the stripped text kept the original length).
**Non-vacuity:** `enumerate-embedded-postgres-tokens.py` (an independent python classifier with its own port of the lexer) classifies every token in the real tree: 670 tokens, 223 plain imports + 216 type positions + 231 wrapped builders, 0 unclassified, 0 raw fallbacks (`proof/c5-token-classification.txt`). The spec has reject cases (B1 to B6, junit, fully-qualified, other-package import, all rename spellings, direct starts hidden behind `"*/*"`, a glob, `//`, a triple-quoted string, a nested splice and a char literal inside splices, and the paren-less `.tap(_.start)`), accept cases (plain import, `{EmbeddedPostgres, Other}`, type ascriptions, the wrapped call, comments, a splice-literal file with a prose doc-comment mention), and exact-path exemption cases. They are built by concatenation so the file does not flag itself.
**What the guard does not catch (accepted gaps):**
1. A start through reflection, `classOf`/`Class.forName`, a different zonky entry point added in a later version, or code in a non-`.scala` source (there are no Java test sources today; `git grep io.zonky` outside `backend/src/test/scala` hits only `build.sbt`).
2. A deliberately obfuscated start that never spells the class token, for example a type alias declared in main sources or built from strings. None exists today.
3. A lexer defect that the fail-closed fallback cannot see: the lexer only fails closed on unbalanced or unterminated input, so an input it lexes confidently but wrongly would pass. The mitigation is that the whole tree is dumped and compared (`lenPreserved`), and the guard's own accept and reject cases cover each construct.
4. No runtime backstop: counting clusters started outside the helper would need instrumenting zonky, which is not cheap and would sit outside the helper and guard files (C1). The allowlist already makes every textual route to the class a failure.
**Red-first:** before the migration the guard failed and named 221 files (`proof/3.1-guard-red.txt`); the allowlist cases and the splice cases were each shown red against the previous guard (`proof/c3-guard-red-green.txt`, `proof/c5-guard-red-green.txt`).

### D8. Proof plan (evidence, all judged by LOG per HEL-1468)
- **Parity:** run `testFull` on base (`origin/main` at the merge base, in a scratch checkout namespaced `hel1445-*`) and on the branch. sbt 2 logs only one aggregate `Tests:` line per run, so per-suite results come from each run's fresh JUnit XML (suite name, `tests`, `failures`, `errors`, `skipped`). Aborted suites (`*** ABORTED`, which may produce no XML) and the aggregate `Tests:`/`Suites:` lines come from the log. Diff base vs branch on that combined table. Record `show Global/concurrentRestrictions` before each parity run, and also run the cross-group overlap computation on each parity run's XML. Cross-check the XML suite set against the log's suite headers. The only allowed delta is the two new specs. Run with `-J-Xmx3g`, under `nice -n 19`, using the repo's local caps.
- **RLS mutation:** temporarily add `BYPASSRLS` to `OutputHistoryApiHarness`'s role creation and show that `assertAppPoolEnforcesRls` (via one OutputHistory spec) goes red; revert and it goes green. This is transcript only.
- **Concurrency is mandatory for the loop and parity runs (C5).** Locally, `build.sbt:187-199` keeps sbt's default of one forked group at a time unless `HEL924_TEST_GROUP_CONCURRENCY` is set, and suites inside one forked group run one at a time (`Test / testForkedParallel := false`, build.sbt:119). A default-settings loop therefore never starts two suites' clusters at once and proves nothing about this race. Every loop and parity run sets `HEL924_TEST_GROUP_CONCURRENCY=2` and `HEL924_TEST_GROUP_COUNT=4` (CI's values, `.github/workflows/ci.yml`) with no shard env vars, so grouping is `floorMod(fqcn.hashCode, 4)` (build.sbt). Each run is **one** sbt invocation, so "≤4 workers" means at most 4 concurrent forked JVMs within one sbt, never several sbt processes in one directory. Each run uses `nice -n 19` and `-J-Xmx3g`.
- **Fresh sbt JVM per run.** Every loop iteration and both parity runs are a fresh sbt JVM: `sbt -batch -Dsbt.server.autostart=false ...` (log lines must name this worktree's project path), never a reused sbt server. A reused server may lack the C5 env vars (MISTAKES.md) or serve cached results. Before the loop, record `show Global/concurrentRestrictions` under the C5 env and require it to contain `Limit forked-test-group to 2`.
- **Report location and freshness.** sbt 2 writes JUnit XML to `backend/target/out/jvm/scala-2.13.15/helio-backend/test-reports/` (the executor confirms the path; `backend/target/test-reports/` holds stale sbt-1 files and is never read). Before each iteration and each parity run, that report dir is emptied (it is a build output inside the worktree; the main checkout's is never touched), so every XML read was written by that run.
- **Overlap evidence is between suites of *different* groups.** Overlapping embedded-postgres instances are **not** acceptable evidence, because `VerifiedEmbeddedPostgresSpec` overlaps its own instances in a single JVM regardless of concurrency. In sbt 2.0.9 forked mode, a `<testsuite>`'s `timestamp` is the suite's **end**, to whole-second resolution, and `time` is the sum of its test durations, which excludes `beforeAll`/`afterAll`. Verified by the design-gate skeptic on 481 real reports: the end-based window gave 0 impossible same-group overlaps, the start-based window gave 8. Each suite's window is therefore `[timestamp − time, timestamp]`. Group is Java `String.hashCode` `floorMod 4` of the fully-qualified class name. A pair counts as overlap only when the two suites are in **different** groups and their windows overlap by **more than 1 s**, which absorbs the whole-second resolution. The same computation must give 0 overlaps >1 s for same-group pairs in that iteration, and a non-zero count there invalidates the method for that iteration. Every iteration must have ≥1 cross-group overlap, or it does not count toward the 30. Before the loop, check that the suite set spans at least 2 groups (adjust only by adding suites, never by dropping any).
- **Positive evidence per iteration (not just absence of failure strings).** Each iteration's log must show `Suites: completed 15` (or the exact count of the D8 set) and every suite's header line, and the fresh report dir must hold exactly that many XML files, each with `failures="0" errors="0"`. An iteration that ran nothing (filter matched nothing, cached, wrong server) fails this check. It also requires zero `TESTS FAILED` / `*** FAILED` / `RUN ABORTED` / `*** ABORTED` lines. A stray postmaster log line from a discarded attempt is not itself a failure.
- **Loop suite set (fully qualified, verified by the executor with `grep` before use):** `com.helio.testkit.VerifiedEmbeddedPostgresSpec`, `com.helio.testkit.EmbeddedPostgresStartGuardSpec`, `com.helio.api.OutputHistoryPayloadsAvailableSpec`, `com.helio.api.routes.pipelines.OutputHistoryPayloadRoutesSpec`, `com.helio.api.routes.pipelines.JoinStepConfigSeamSpec`, plus the 10 classes mixing in `OutputHistoryApiHarness`: `ApiRoutesAlertHistoryWiringSpec`, `OutputCompareWriteValidationSpec`, `OutputConfigKeyValidationSpec`, `OutputFilteredMetricMeasurementSpec`, `OutputFilteredMetricRoutesSpec`, `OutputHistoryMetricIdentityRoutesSpec`, `OutputHistoryPublicRoutesSpec`, `OutputHistoryQueryCountSpec`, `OutputHistoryRoutesSpec`, `PayloadOptInWriteValidationSpec` (the executor resolves each to its package). 30 iterations. Grep each iteration's log for `TESTS FAILED`, `*** FAILED`, `RUN ABORTED` and `*** ABORTED`. Because the natural race is probabilistic, D6's deterministic repro is the primary proof of the fix; the loop proves no regression under real overlap.
- **RLS mutation suites:** `com.helio.api.routes.pipelines.OutputHistoryRoutesSpec` and `OutputHistoryPayloadRoutesSpec` (both call `assertAppPoolEnforcesRls`).
- **Parity flake handling (decided in advance):** if a suite fails in the base or branch `testFull` run, re-run only that suite 3 times on **both** base and branch with the same env. It counts as pre-existing/flaky (not a regression) only if it fails on base too, or matches a known flake (HEL-1470, HEL-1471, HEL-1439); otherwise it is a regression. Report every such case explicitly. Never drop a suite from the comparison silently.

## Risks / Trade-offs

- [The large mechanical diff hides a non-mechanical edit] → The D5 verifier proves byte-equality under the inverse transform for every changed file.
- [zonky's `close()` on a discarded attempt affects the foreign cluster] → Proven otherwise by D6 step 3 (A still alive with its marker). If it does affect it, stop and escalate (D3).
- [`toRealPath` mismatches on symlinked tmp] → Both sides are canonicalised. D6's positive case would catch a false mismatch, and an exhausted-retry error names both paths.
- [The concurrent HEL-1435 lane adds a new direct start] → The guard fails loudly on whichever branch merges second.
- [The helper adds one `SHOW` round-trip per start] → Negligible (one query on an already-open-and-verified connection, about 226 per full run).
- [A steal where the foreign cluster dies before our readiness poll] → It surfaces as zonky's existing "Gave up waiting" IOException, as today (D4). Accepted; it is not the observed failure mode.

## Migration Plan

Test-only. Rollback is reverting the PR. No deploy impact.
