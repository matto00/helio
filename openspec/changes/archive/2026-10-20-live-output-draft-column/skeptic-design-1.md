### Change Requests
1. **D2 column-order claim is false; fix the claim and close the gap.** Saved-panel `headers` come from JSONB plus spray `JsObject` key order, not "what the run serializer writes". Revise D2 to say so. Then do one of these: (a) make `recordsToPanelRows`, or the live path, order columns deterministically in a way both paths share; or (b) state the order-dependent cases as a listed divergence: chart with no `xAxis` mapping (`resolveDataColumns` uses `headers[0]`), pie or no-`yAxis` first-numeric fallback, table column order. Add a parity-test case with no `xAxis` mapping so whichever choice is made is pinned. As written, a parity test that feeds "the same records" to both paths passes, yet it does not prove what the AC claims.
2. **D3 table is missing states that the existing view model produces.** Add a row and outcome for each of these, and cover each in `liveOutputSource` tests:
   - (a) A draft view `ok` with `rows === null` and `frameStale === false`. This is a non-focused server-resolved node with no last-good rows (`draftStepView.ts:121-129`), or an unknown node (line 84). Today this falls into the "live" row with nothing to render, which also breaks the §11 rule. It should resolve to saved rows (D5) or the "Select this step" hint, never "live".
   - (b) No sample available, as distinct from "still loading": sample status `error`, an image source, or a caller with no sample entry (a viewer/non-owner without `canSampleShared`). The "skeleton" row would never resolve. It should fall back to saved rows (D5) with the neutral "Showing the last run." caption.
   - (c) An Output bound to a root (`rootId`) while a draft exists. Root frames are not recomputed by the draft, so state which marker shows. Per §11 it should probably not be "live".
3. **Protect the owner's latency budget with the column present.** C2 is vacuous for this change (hel1631 has no Output). In `e2e/hel1632-live-output.spec.ts`, run the same 10-edit `timedFilterEdit`-style burst on the seeded pipeline with a chart Output displayed at 1280. Assert the same budget on the step count/preview update (edit 1 < 100 ms, edits 2-10 < 50 ms). Keep 5.2's input-to-column measurement as reported-only. Update D6 "Latency" and tasks 5.1/5.2 to match.
4. **D4 must not fetch with a "minimal limit" under the shared key.** `outputHistoryKey` ignores the limit, so a short fetch cached under `output:<id>` would serve a truncated history to a dashboard panel's sparkline/compare later in the same SPA session. Use `fetchOutputHistory(outputId)` with the default limit, exactly as `useOutputHistory.ts:45` does, so the entry is shared and not poisoned. A separate key is the alternative, but it costs a second request when both views are visited.
