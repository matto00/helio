## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Base: `82026d58` (matches brief). Worktree clean apart from the untracked change dir.

### What I verified (with evidence)

**1. `validate` is strict, `evaluate` is legacy-tolerant — CONFIRMED.**
`ExpressionEvaluator.scala:385` `def validate(expr, fieldNames) = parse(expr).flatMap(ast => checkRefs(ast, fieldNames))` — no fallback. `:473` `evaluate` has the `case Left(msg) if isDollarPrefixError(msg) => parseLegacy(expr)` arm. The class doc (`:44-57`) states `parse()`/`validate()` is "STRICT-ONLY and never falls back: a bare identifier ... is always a parse error". `openspec/specs/pipeline-compute-op/spec.md` carries this as a shipped requirement ("This legacy fallback applies only to row-execution (`evaluate`) — schema-inference and live validation use the strict grammar only"). So Decision 1's premise — gating the write path on `validate` would 422 bare-identifier expressions (`price * qty`) that still evaluate — is **true**, and Decision 1 is correctly reasoned. Traced `price * qty`: tokenizer letter-branch emits `Ident`/`Star`/`Ident`, `StrictParser` yields `DollarPrefixRequiredMsg`, `isDollarPrefixError` is true, `parseLegacy` parses it. Confirms the regression Decision 1 avoids is real.

**2. The production expression fails both grammars — CONCLUSION correct, STATED MECHANISM wrong.**
Traced `"stats.adp_ppr - stats.pts_ppr"` through the shared `tokenize` (`:345-...`):
- `stats` hits the bare-identifier branch (`case l if l.isLetter || l == '_'`), which the HEL-867 comment explicitly says "intentionally does NOT admit dots"; next char is `.` not `(`, so it emits `Token.Ident("stats")`.
- `.` then hits `case d if d.isDigit || d == '.'`; the scan consumes only the `.` (next char `a` is neither digit nor dot), giving `numStr = "."`, `toDoubleOption == None`. The HEL-867 dotted-reference message is gated on `buf.lastOption.exists(_.isInstanceOf[Token.Ref])` — the last token here is `Token.Ident`, **not** `Token.Ref` — so it returns `Left("Invalid number literal: .")`.

Tokenization fails, so `parse` returns that message; `isDollarPrefixError("Invalid number literal: .")` is `false` (`:354`, exact string equality against `"Column references require a '$' prefix"`), so **`evaluate` never calls `parseLegacy` at all** — it goes straight to the final `case Left(msg) => Left(ParseError(msg))`. `parseLegacy` would fail identically anyway, since `tokenize` is shared by both parsers (`:346-352`).

So `parseProblem` returns `Some("Invalid number literal: .")` and Decision 1's predicate holds. But design.md:57's stated mechanism — "fails strict parse with a `$`-prefix error, then fails `parseLegacy` too, because `parseLegacy` is frozen and HEL-867 added dotted references to the strict lexer only" — is **false in both clauses**: the failure is a tokenizer failure that precedes any parser, the error is not a `$`-prefix error, and the legacy arm is never entered. HEL-867's dotted-ref support is in the shared tokenizer's `$`-branch, not in "the strict lexer" as distinct from a legacy one; there is only one lexer.

**3. Hook wiring — derived by enumeration, list is INCOMPLETE.**
`grep -rn "validateRawConfig\|requiredConfigProblems" backend/src/main/scala` (excluding the step definitions and the base trait) returns exactly:
- `validateRawConfig`: `PipelineService.scala:494`, `PipelineService.scala:670`, `PipelineProposalService.scala:187`, `PatchSetApplyResolvers.scala:240`, **and `PipelineAnalyzeService.scala:128`**.
- `requiredConfigProblems`: `InProcessPipelineEngine.scala:145` (via helper at `:171`), `PipelineAnalyzeService.scala:141`.

All five/two line numbers in the design table are correct as far as they go, but the table and Decision 4 both omit the fifth `validateRawConfig` call site. It is not cosmetic: at `PipelineAnalyzeService.scala:128-133`, `shapeRejection` short-circuits — `if (shapeRejection.nonEmpty) shapeRejection else { ...requiredConfigProblems... }`. Once Decision 3 lands, an unparseable expression is caught by `validateRawConfig` at analyze and the `requiredConfigProblems` branch is **never evaluated there**. Decision 4's claim that "`PipelineAnalyzeService:141` reads the same predicate, so analyze reports it as a `validationError`" is wrong about the route (the reported string will be Decision 3's `"compute: invalid expression: ..."`, not Decision 4's `"invalid expression: ..."`), and task 3.5 is aimed at the wrong mechanism.

**4. Read-path hazard — correctly identified and correctly avoided.** `ComputeConfig.decode` (`ComputeStep.scala:19-25`) uses `StepCodecUtil.str(obj, "expression", "")` and never inspects the expression; Decision 5 leaves it untouched. Both new checks take `raw`, and every call site enumerated in (3) is a write/run/analyze surface — none is `rowToDomain`. Task 4.3 asserts it.

**5. Empty-expression hazard — correctly handled.** `StepCodecUtil.missingRequired` (`:177-181`) already collects any field that is `null` or `.trim.isEmpty`, and `ComputeStep.companion.requiredConfigProblems` already passes `"expression" -> cfg.expression`. So empty is a run-time problem today, and Decision 3's `expr.trim.isEmpty => None` short-circuit plus Decision 4's `if (base.nonEmpty) base` ordering preserve save-ability. Additionally verified the un-flagged sibling hazard: `PipelineService.scala:657-670`'s `req.config match { case None => updateInternal(...) }` means reorder/enable/disable of a pre-existing bad step does not run `validateRawConfig`, so such a step stays movable and deletable. Good.

**6. Evidence discipline in tasks.md — mostly enforced, one mislabel.** Tasks 1.2, 2.1, 2.2, 3.1, 3.2 name the specific red and how to produce it ("today it returns `None`", "today it 200s", "today the run succeeds"); 1.3, 2.6, 3.5 are labelled guards; 5.2 requires reporting the observed split and forbids adopting a count asserted in the ticket. That is enforcement, not recitation. However 2.4, 2.5, 3.4 and 4.3 are labelled **"Proof test"** while their redness is explicitly produced by *mutation* ("under a deliberately naive implementation", "under an implementation that gates on `validate`", "by swapping the two branches", "by adding a `parseProblem` check to `ComputeConfig.decode`"). Under the ticket's own evidence rule those are guards, and pre-labelling them as proof pre-loads the 5.2 count with four miscategorised entries.

### Verdict: REFUTE

The design is sound in substance — Decision 1 is right, the two-tier reuse is right, both hazards are real and correctly handled, and I found no scope drift or uncovered AC. The revisions below are corrections of load-bearing prose and of one test that is currently aimed at the wrong mechanism. Each is cheap.

### Change Requests

1. **design.md:57 — replace the false mechanism for the production expression.** It currently reads "fails strict parse with a `$`-prefix error, then fails `parseLegacy` too, because `parseLegacy` is frozen and HEL-867 added dotted references to the strict lexer only." Ground truth: `"stats.adp_ppr - stats.pts_ppr"` fails in the **shared tokenizer** with `Invalid number literal: .` — `stats` lexes as `Token.Ident` (the bare-identifier scan admits no dots), the following `.` enters the number branch and fails, and HEL-867's dotted-reference message is skipped because it is gated on the previous token being a `Token.Ref`. Since that message is not `DollarPrefixRequiredMsg`, `isDollarPrefixError` is false and **`parseLegacy` is never invoked**. Rewrite the paragraph to say this (and note `tokenize` is shared, so the legacy grammar could not have accepted it either). Keep task 1.2's measurement requirement.

2. **design.md:9-10 (hook table) and Decision 4 — add the fifth `validateRawConfig` call site and fix the analyze claim.** `validateRawConfig` is also wired at `PipelineAnalyzeService.scala:128`, where `shapeRejection` **short-circuits** `requiredConfigProblems` (`:130-132`). State that once Decision 3 lands, analyze surfaces the parse problem through the *write-path* override, not through `requiredConfigProblems`, and that the message therefore carries Decision 3's `"compute: invalid expression: "` prefix rather than Decision 4's `"invalid expression: "`. Adjust the Decision 4 sentence that currently claims `:141` is the route for analyze. (The two overrides producing two different prefixes for the same defect is acceptable, but decide it deliberately and record it — do not let it surface as a surprise at test time.)

3. **tasks.md 3.5 — retarget the analyze assertion.** As written it asserts analyze reports "the same problem ... free from the shared hook", which per (2) is not the mechanism. Assert instead that analyze's `validationError` **contains the parser's message** (substring), and note it arrives via `shapeRejection`. The preview half of 3.5 is correct as written (`previewStep` → `executeWithStepCounts` → `InProcessPipelineEngine:145`) — keep it.

4. **tasks.md 2.4, 2.5, 3.4, 4.3 — relabel from "Proof test" to "Guard test".** Each of these produces its red by *mutating the implementation*, not by running against un-fixed `main`. The ticket's evidence rule makes mutation-failable tests guards, not proof. Relabel them so task 5.2's proof/guard split is not pre-loaded with four miscategorised entries. (2.5's red is genuinely valuable and must still be demonstrated — it just counts as a guard.)

### Non-blocking notes

- Decision 6's fallback ("drop the performance half if the AST entry point widens the surface") is a well-scoped escape hatch, and task 4.2 mirrors it. No objection. Note that the spec delta `pipeline-compute-op` states "The expression SHALL be parsed once per step evaluation rather than once per row" as a SHALL — if 4.2's fallback is taken, that spec sentence must be removed in the same breath, or the delta ships un-met. Worth calling out in 4.2.
- Decision 4's "the naming is admittedly a stretch" trade-off is recorded honestly and I agree with the resolution (a third hook is worse).
- `PipelineService.scala:657-670`: a config-less update (`req.config == None`) skips `validateRawConfig` entirely, so pre-existing bad steps remain reorderable/toggleable/deletable. This is the right behaviour and is not currently written down anywhere in the change — a sentence in Risks would pre-empt the "did we brick existing steps?" question.
