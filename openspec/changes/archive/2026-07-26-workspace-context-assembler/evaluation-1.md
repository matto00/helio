### Phase 2: Code Review — FAIL
Issues:

1. **`schemas/workspace-context.schema.json` does not validate the real response shape — AC1 is not actually met.** Every `Option[T]` field in the new protocol (`WorkspaceContextDataSource.tag`, `WorkspaceContextDataType.sourceId`/`tag`, `WorkspaceContextPipeline.lastRunStatus`/`lastRunAt`/`lastRunRowCount`/`tag`/`stepsError`, `WorkspaceContextPipelineStep.validationError`) is serialized through the plain spray-json `jsonFormatN` macro. Per spray-json's `ProductFormats.productElement2Field` (confirmed by reading `spray-json_2.13-1.3.6` sources), a `None` `Option` field is **omitted from the JSON object entirely**, not written as `null`. The schema, however, lists every one of these fields in each `$defs` object's `required` array (e.g. `schemas/workspace-context.schema.json:47` `DataSourceEntry.tag`, `:87` `DataTypeEntry.sourceId`/`tag`, `:128-141` `PipelineEntry.lastRunStatus`/`lastRunAt`/`lastRunRowCount`/`tag`/`stepsError`, `:114` `PipelineStep.validationError`).

   Verified live: started the backend via `scripts/concertino/start-servers.sh`, logged in as the dev account, called `GET /api/workspace/context`, and validated the real response against the schema with `ajv-2020` (`strict: false`). Result: **invalid** — every `dataSources[]` entry fails with `must have required property 'tag'` (34/34 sources have no tag), and the same class of failure occurs for `dataTypes[].sourceId`/`tag` (pipeline-output types) and `pipelines[].stepsError` (the *successful*-analyze / happy-path case — `stepsError` is `None` whenever a pipeline analyzes cleanly, so essentially every real pipeline entry fails validation). Confirmed by inspecting the raw JSON: a sampled pipeline entry has keys `['id','lastRunAt','lastRunStatus','name','outputDataTypeId','outputDataTypeName','sourceDataSourceId','sourceDataSourceName','steps']` — no `tag`, no `stepsError` key at all — and a sampled `dataTypes[]` entry has keys `['columns','computedColumns','id','name','pipelineOutput','version']` — no `sourceId`, no `tag`.

   This is not caught by `npm run check:schemas` (confirmed by reading `scripts/check-schema-drift.mjs`) — that script only diffs field *names* between the schema and the Scala case class, not JSON Schema `required`-vs-actual-wire-presence semantics. So the AC1 claim ("returns 200 with a body validating against schemas/workspace-context.schema.json") is untested by any existing gate, and demonstrably false against a live response.

   Fix: either (a) drop the affected Optional fields from each `$defs` object's `required` array (matching the existing repo pattern in `schemas/panel.schema.json` (`dataAsOf` optional) and `schemas/panel-appearance-patch.schema.json`, rather than the also-present-but-equally-broken `required`-list pattern in `pipeline-schedule.schema.json`/`alert-event.schema.json`), or (b) mix `spray.json.NullOptions` into `WorkspaceContextProtocol` so `None` is actually written as `JsON null` on the wire, matching the schema as written. Either is a small, scoped fix; (a) requires no Scala change.

2. (Related, no separate action needed beyond #1) The task 4.6 route-level test (`WorkspaceContextServiceSpec.scala:288-304`) only checks `status shouldBe StatusCodes.OK` and that the Scala round-trip deserializes — it does not perform actual JSON Schema validation, so it did not (and structurally cannot, as written) catch #1. Recommend adding an ajv-based (or equivalent) schema-validation assertion to this test once #1 is fixed, so a future regression is caught mechanically rather than by manual live-testing.
