**D1. On the rail-shell dashboard view the meta row replaces the command bar (owner answer 1).** `App.tsx` renders `<DashboardMetaRow>` instead of `<CommandBar>` when `usesDashboardMetaRow(pathname, isPhoneShell)` is true, and `<CommandBar>` otherwise (other pages, and the phone shell everywhere, keep the command bar unchanged).
- `usesDashboardMetaRow` is one new shared predicate in `app/hidesBreadcrumbItemName.ts`'s neighbourhood (`app/dashboardChrome.ts`), defined as `!isPhoneShell && isDashboardViewPath(pathname)`: it composes the existing `isDashboardViewPath` (so HEL-1578's move of the dashboard view to `/dashboards` flows through automatically) and adds no route literal of its own. It is the only place this decision is expressed; `App.tsx` and any test read it.
- **Grid slot.** The meta row's root is `<header className="app-command-bar app-command-bar--dashboard-meta">`: it takes the command bar's grid slot, safe-area padding, height (`--app-top-chrome-height`), opaque `--app-surface` background, hairline bottom border and stacking, so the shell grid, its row count, and HEL-1575's `app-shell--tabs` row move (which targets `.app-command-bar`) all apply to it without any grid edit here; page content does not shift when switching between a dashboard and another page. `DashboardMetaRow.css` only adds the row's internal layout under the `--dashboard-meta` modifier.
- **What it absorbs from the command bar on that view:** the save-state indicator (in the facts group, after the facts), `DashboardAppearanceEditor`, the assistant quick-launcher `IconButton` (same `aria-label`/`title`, same `onOpenQuickLauncher`), and the "Dashboard actions" kebab, which keeps "Refine with AI" (Add panel is the meta row's primary, so the kebab drops it on the rail shell; the phone CommandBar kebab keeps it). The section breadcrumb is not shown (the tab, list and ⌘K carry identity, DESIGN.md §9). `App.tsx` passes the meta row the same `onOpenRefinement`/`onOpenQuickLauncher`/`setDraftAppearance` callbacks it passes `CommandBar`.
- **Shortcuts survive the swap.** `useLayoutUndoRedo` is currently called only inside `CommandBar`; it is also called in `DashboardMetaRow` (the two never mount together, so exactly one listener exists at a time). A test proves ⌘Z/⇧⌘Z undo/redo with the meta row mounted and the command bar absent.
- **No dashboard selected** (dashboard view, nothing open, e.g. after closing the last tab): the meta row still renders (stable chrome height) with no facts and no dashboard actions, only the assistant button.
- **HEL-1575 coordination (unmerged, in a fix cycle).** Its `hideDashboardBreadcrumb` becomes unreachable on the rail-shell dashboard view, because `CommandBar` no longer renders there; whichever lane merges second removes that dead branch and folds the rule into `hidesBreadcrumbItemName`/`usesDashboardMetaRow` rather than keeping two conditionals. Its tab bar renders above the `.app-command-bar` slot, so the meta row lands directly under the tab strip as DESIGN.md §9 and the board require. HEL-1583 reuses `useDashboardMeta` for its phone "refreshed" line.

**D2. Meta row facts, derived in one pure, reusable unit.** A hook `useDashboardMeta(dashboardId, panels)` (pure derivation function underneath, unit-tested) returns `{ panelCount, refreshedAt, refreshIntent, sources }`:
- `panelCount` = number of panels on the dashboard (every kind, dividers included, matching what the grid renders). Copy: "1 panel" / "N panels".
- Feeding pipelines = the distinct `pipelineId`s of the dashboard's output panels' Outputs. Panels without an Output contribute nothing: text/markdown/image/divider panels, an output panel whose `outputId` is the empty unbound default (skipped, no fetch), and form panels, which bind a dataset directly with no pipeline. When the hook is mounted (task 3.2) it is not mounted on the public shared-dashboard route.
- `refreshedAt` = the most recent `lastRunAt` among feeding pipelines that the client has a `PipelineSummary` for. Copy: "refreshed 9h ago" using the app's existing relative-time formatter (re-rendered on the formatter's existing tick if one exists; otherwise once per minute), with the absolute timestamp in a `title`/`<time dateTime>`. If no feeding pipeline has run: "not refreshed yet". If none is known (no output panels, or a viewer without access to the pipelines): the refresh item is omitted entirely, never a fabricated time.
- `refreshIntent`: a `--app-success` dot when the most recent run's `lastRunStatus` is `succeeded`; `--app-danger` dot with copy "last run failed 9h ago" when it is `failed`. The dot is decorative (`aria-hidden`); the text carries the meaning.
- `sources` = distinct `roots[].dataSourceName` of the feeding pipelines, in first-seen panel order. Copy: "source · A" (one), "sources · A, B" (two), "sources · A, B +N" (more). Omitted when none is known.
- **Live update (skeptic CR3, round 2 item 1): the hook keeps its own summaries.** The pipelines slice is not a reliable source here: `fetchPipelines` skips itself once loaded (its `condition` guard), so `items` can be session-old, and `fetchPipelineById.fulfilled` writes only `currentPipeline` and the HEL-1483 latest-request slot (it would also hijack the pipeline detail page's slot). So `useDashboardMeta` holds its own `Map<pipelineId, PipelineSummary>` in local state, filled by calling the service function `getPipelineById` directly (no Redux dispatch): (1) on mount, (2) whenever the feeding pipeline set changes (only the newly added ids), and (3) for a pipeline whenever `subscribeToPipelineTerminal` fires for it. The terminal listener carries no payload, and the first connect of a page's lifetime sets a baseline without firing, so (1) is what corrects a run that finished before mount. Responses that arrive after unmount, or for an id no longer in the feeding set, or older than a later request for the same id (per-id request sequence), are dropped. A failed or 403/404 read omits that pipeline's contribution (a viewer without pipeline access sees no refresh/source facts). The pipelines slice is neither read nor written by the hook. Cost: one `GET /api/pipelines/:id` per feeding pipeline per dashboard open plus one per terminal event, which is bounded by the dashboard's pipeline count.
- **Output metadata (skeptic CR3).** `outputMetaCache` is a module Map that triggers no re-render, so the hook resolves each output panel's Output with `fetchOutputMeta(outputId)` into local React state (seeded synchronously from `getOutputMetaCached` when held), keyed by outputId, ignoring results that arrive after unmount or after the panel set changed. A failed fetch omits that panel's contribution.

**D3. Meta row presentation (DESIGN.md §9).** Facts: `--font-mono`, `--text-xs`, `--app-text-muted`, groups separated by spacing ("source · name" inside the source group, as on the board), then the save-state indicator. Actions trail on the right in this order: edit tools (only in edit mode: Undo, Redo, Tidy layout), Edit layout / Done, Share, **Add panel**, then the appearance editor trigger, the assistant icon button and the overflow kebab. **Chrome button rule (skeptic r4 CR3):** the row reuses `.app-command-bar`, where DESIGN.md §5's [mechanical] rule makes every trigger borderless (`App.css` strips the hairline from `.cmd-btn`, `.ui-icon-btn`, `.actions-menu__trigger` inside it). So every non-primary control is the borderless chrome recipe (`.cmd-btn` / `IconButton variant="secondary"`), including Share, Undo, Redo and Tidy layout; "Done" is a neutral pressed state (`aria-pressed`, background `--app-surface-soft` (light) / `--app-surface-strong` (dark), the pair `.cmd-btn:hover` uses on `--app-surface`, with `--app-text` text; `--app-surface-raised` is white on near-white in light), never accent; **Add panel** uses `.cmd-btn--primary` (`App.css`), the one accent control. This departs from the B2 board's bordered Share (the board is illustration; DESIGN.md wins) and is listed in ui-decisions.md. The facts are a `<p>` of inline items; the actions a `role="group"` labelled "Dashboard actions"; no heading, no dashboard name. Tokens only.
- **Narrow widths.** The row is a size container. Actions never wrap and never truncate. Ladder as the row narrows (thresholds measured live and recorded in `measurements.md`): (i) the facts shrink first (single line, ellipsis, full text in `title`); (ii) edit tools, Edit layout/Done and Share become icon-only `IconButton`s keeping accessible names and `title`; (iii) Share and the assistant move into the overflow kebab (same handlers, same names); the appearance editor trigger stays in the row at every tier (a popover trigger inside a menu would need a second popover host for no width gain). With no dashboard selected the assistant button stays in the row at every tier; (iv) the facts collapse to the panel count only. Add panel keeps its label at every rail-shell width. Verified live at 1280 and 820 with the context list at default, 400px and collapsed, in and out of edit mode, dark and light.
- **Contrast.** The row is chrome (`--app-surface`), never on the user's tinted dashboard background, so muted-on-surface is the token pair's contrast; measured in both themes with a non-default dashboard background set.

**D4. Edit mode gates drag and resize (owner answer 2).** The meta row (shell) and the grid (routed page) are in different subtrees, so edit mode is session UI state in Redux: `editingLayoutDashboardId: string | null` in the layout-history slice (not persisted, not sent to the server). Edit mode is on iff it equals the selected dashboard id, so switching dashboards turns it off with no effect to write; selectors `selectIsEditingLayout(dashboardId)`. `DesktopPanelGrid` reads it which sets RGL's drag/resize enabled flags from it (the RGL v2 equivalents of `isDraggable`/`isResizable`; the executor confirms the exact prop names against the installed `react-grid-layout`), and adds a modifier class that hides the drag handle and resize handles outside edit mode. Everything else on a panel (title edit, detail, delete confirm, interactions) is unchanged in both modes. Edit layout is an `aria-pressed` toggle labelled "Edit layout" / "Done". Escape while editing (focus not in an editable element, no dialog or popover open, no drag or resize in progress, and the event not already `defaultPrevented` by an inner handler such as a menu closing) leaves edit mode. Leaving edit mode does not flush or discard anything: staged changes keep using the existing 30s auto-save / Save now / unmount flush. Alternative: keep drag always on and make Edit layout only reveal undo/redo. Rejected: a mode that changes nothing about what can be dragged is not an edit mode, and the board's "Edit layout" implies the grid is stable while reading. Owner-approved (answer 2).

**D5. **D8. Tidy layout (owner answer 3).** An edit-mode-only "Tidy layout" button compacts panels upward.
- **Algorithm:** a pure function `tidyLayout(items, cols)`, a thin wrapper over the existing `compactLayout` (`breakpointLayout.ts`, already property-tested), never a second compactor. It performs vertical compaction: items sorted by (y, x) are each moved to the lowest y ≥ 0 where they overlap nothing already placed, never changing x, w or h, so relative order is preserved and nothing overlaps. Unit-tested on gaps, stacked columns, already-tidy layouts (identity) and full-width rows.
- **Scope:** all four breakpoints of the dashboard's layout (lg, md, sm, xs) in one action, so the dashboard is tidy at every width; xs order is preserved because compaction keeps (y, x) order. A breakpoint with no gap is left byte-identical.
- **Which layout (skeptic r4 CR2).** Tidy runs on the AUTHORED store layout (`dashboard.layout`), never on `resolveDashboardLayout`'s output. Per breakpoint: an *unauthored* breakpoint (empty, or one the HEL-1023 resolver treats as unauthored because an entry is out of bounds) is left byte-identical; a *partial* breakpoint (some live panels have no stored entry) has only its stored entries compacted and gains no entries, so derived positions are never written into it (the resolver keeps deriving the missing panels from the tidied entries as it does today); a *complete* breakpoint is compacted fully. Only entries for live panels are considered; stored entries for panels this tab has not loaded are kept unchanged, as the drag path does under HEL-1457. "Nothing to tidy" is computed on exactly this basis (no stored entry would move). The spec (dashboard-layout-edit-toggle) states the same rule with unauthored and partial scenarios. Unit cases cover unauthored, partial and complete breakpoints. Recorded in ui-decisions.md.
- **History and persistence (skeptic r4 CR1).** `useLayoutSave`'s HEL-1230 classifier treats a store-layout change as a history traversal (class 2: pending, PATCHed) only when the history slice's `revision` changed and the layout equals `applied`; `pushLayoutSnapshot` + `setDashboardLayoutLocally` alone would land in class 4 (re-baselined as if server-sent, never PATCHed). So the layout-history slice gains a reducer `recordLayoutTidy({dashboardId, before, after})` that pushes `before` onto the past stack, clears `future`, sets `applied = after` and bumps `revision`, and the thunk `applyLayoutTidy(dashboardId)` dispatches it together with the same local layout apply `applyTraversal` uses. The classification comment in `useLayoutSave.ts` is updated so class 2 names tidy. Persisted only by the existing auto-save / Save now / unmount flush. ⌘Z restores the pre-tidy layout exactly (it is an ordinary history entry).
- **Availability:** disabled (with `title` "Nothing to tidy") when every breakpoint is already tidy. Never runs on load, on open, or on a timer (constraint C1).
- **Demonstration (AC4):** on the dev account's "Helio Roadmap (copy)" (18 empty `lg` rows measured at planning) and on a dashboard built with a form panel above a gap like the ticket's "Workouts": before/after screenshots and the DB row's `layout` unchanged until the click (queried before and after opening the dashboard).

## Risks / Trade-offs

- [Users who dragged panels directly must now click Edit layout first] → Owner-approved (answer 2); one click on the always-visible row.
- [e2e specs that read the command bar on the dashboard view (breadcrumb, save state, kebab, undo buttons) or drag by handle] → Re-pointed, never deleted; the FULL e2e suite runs locally before Delivery (C5).
- [Tidy on a breakpoint the user is not looking at] → Order-preserving, one undo entry restores all four.
- [The meta row's facts depend on pipeline summaries a viewer may not have] → Omit unknown facts rather than show wrong ones; tested.
- [Tighter gutter changes every dashboard's look at once] → Ticketed and approved on the board; grid units unchanged, so reverting is one constant.
- [Merge conflicts with HEL-1575 in App.tsx/CommandBar.tsx] → App.tsx diff is the one swap; CommandBar diff is deleting the undo/redo block. Re-check against HEL-1575's worktree before each merge.
