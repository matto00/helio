### Verdict: REFUTE

Two findings. CR-1 is a false enumeration in design.md that also makes an acceptance criterion unsignable as written; CR-2 is a prose/spec claim that no observable behaviour satisfies, and is exactly the "green test over the wrong input" trap standing requirement 3 exists to prevent.

### Change Requests

1. **Decision 6's sweep is not an enumeration and its result is false — at least 13 more files match the pattern as design.md itself defines it.** Decision 6 defines the pattern as "a `*Config.decode` reducing a supplied-but-unrecognised value to an empty default" and then asserts it "exists in exactly `CastStep.scala:22-26` and `RenameStep.scala:22-26`. The ticket's count is confirmed." I ran the enumeration over all 23 step files. The identical shape appears in the *config decoders* of, at minimum:
   - `SelectStep.scala:19-22` — `{"fields":"amount"}` (string, not array) → `Vector.empty`; and `items.collect { case JsString(s) => s }` silently drops non-string elements.
   - `GroupByStep.scala:22-25` — `{"groupBy":"region"}` → `Vector.empty`, i.e. a group-by that silently collapses every row into one group. Same file line 27: `StepCodecUtil.stringOr(obj, "aggFunction", "sum")` silently substitutes `"sum"` for a non-string `aggFunction`. This is the wrong-numbers-reported-green failure shape the ticket opens with.
   - `AggregateStep.scala:36-46` — `items.flatMap(it => Try(it.convertTo[...]).toOption)`, the same `Try(...)`-swallow the ticket quotes from `CastStep`, applied per element.
   - Also `PivotStep.scala:27`, `DedupeStep.scala:29`, `LookupStep.scala:32`, `WindowStep.scala:39,43`, `UnpivotStep.scala:31,35`, `FillNullStep.scala:30`, `FilterStep.scala:37`, `SortStep.scala:31`, `AssertStep.scala:53`.
   Decision 6's exclusion list addresses none of these — it excludes only execution-time row-value handling (`ExtractHeadings`/`SplitText`/`ChunkByTokenCount`), `StringOpsStep`'s declared-optional field, and the `StepCodecUtil` helpers. Required revisions:
   (a) Rewrite Decision 6 with the actual enumeration output and classify every hit above explicitly.
   (b) Decide and state the criterion that distinguishes cast/rename from the rest. "Only these two were seen in the field report" is a legitimate scoping criterion; "the pattern exists in exactly two files" is a false statement of fact and must go.
   (c) AC4 ("a re-run of the sweep across `domain/steps/` finds **no remaining instances**") cannot be truthfully signed off under the current non-goal ("no strict rejection beyond cast/rename"). Per standing requirement 4, correct AC4 inline to something signable — e.g. "the sweep is re-run by enumeration, every hit is classified, and the unaddressed hits are recorded as known-remaining with a follow-up ticket" — rather than leaving an AC that can only be closed by mis-stating the sweep.
   (d) Task 5.1 must require the raw enumeration output for **all** 23 files in the PR, not a confirmation of the expected count.

2. **The spec delta and AC7 attribute the raw-config observation to the wrong component; no observable behaviour satisfies the scenario as written.** `specs/pipeline-step-config-validation/spec.md` states "The validation hook SHALL receive the step's RAW configuration text ... so that it observes configuration keys which a step's tolerant persistence decoder would silently reduce", with the scenario "WHEN that configuration is passed through the analyze-time validation hook THEN the hook observes the supplied key". Against the code:
   - `validateStepConfig` (`PipelineAnalyzeService.scala:99-127`) has **no `cast` or `rename` case** — it returns `Vector.empty` for both. It receives the raw string and does not observe the key. Nothing it emits can satisfy the scenario.
   - Every validator it *does* dispatch to immediately re-applies the tolerant decoder (`StringOpsConfig.decode(config)`, `WindowConfig.decode(config)`, …). So for the existing eight kinds the raw-string parameter confers no observation benefit today at all — the requirement's stated rationale does not describe the shipped code.
   - The only component that actually observes the dropped key is `inferOutputSchema` → `inferCast`/`parseConfig`, whose observable output is `validationError == "cast config error"`.
   Required revisions: (a) reword the spec requirement and scenario to bind to the **analyze surface's observable `validationError`** for a config the typed decoder reduces to empty, not to "the validation hook"; (b) state plainly in design.md Decision 5 that `validateStepConfig` has no cast/rename case and that the existing validators re-decode tolerantly, so the reader is not left with the false impression that the hook itself inspects raw keys; (c) re-specify task 2.1's assertion in terms of the route response (`GET /api/pipelines/:id/analyze` returning `validationError` non-empty for a raw config whose `CastConfig.decode(raw).casts.isEmpty`), since an assertion against a `private` method is not a tripwire anyone will trip. Note the executor will need a raw SQL config insert to seed such a step — the typed `pipelineStepRepo.insert` path cannot express it, and after task 3 the API path cannot either. Say so in the task.

### Non-blocking notes

- Judgments I checked and **agree with**: Decision 7's two deferrals are correct calls. The `groupby`/`join` `inferOutputSchema` gap needs real schema semantics (join in particular is unresolvable in a layer with no repo access) and is properly a follow-up; the `MatchError` seam is unreachable today (each kind guards with a preceding `IllegalArgumentException` check) and this change touches none of those sites. Both are documented rather than silently absorbed, as the ticket requires.
- Ordering (coverage debt before building on the join) is right, and the 400-vs-422 split is coherent: unknown *type* and malformed JSON stay 400, well-formed-but-unrepresentable *config* is 422. No existing status code moves.
- Decision 3's accept-absent/reject-present rule is correct and I found no hole: `Try(o.convertTo[Map[String,String]]).getOrElse(Map.empty)` swallows exactly the "object with a non-string value" case, and `case _` swallows exactly the "not an object" case — the two rejection clauses cover both. The frontend picker seeds `{casts:{}}` (`frontend/src/features/pipelines/state/stepNarrowing.ts:136`), which is a present-and-valid empty object, so it passes; design.md's "the picker seeds a new step with `{}`" is imprecise but the rule is right either way.
- Minor line-reference drift in design.md: `PipelineAnalyzeService` is at `backend/src/main/scala/com/helio/domain/engine/`, not `services/pipelines/`; the multi-failure join is line **126**, not 127; the window test is line **695**, not 694.
- There is a *second* `problems.mkString("; ")` at `PipelineAnalyzeService.scala:619`. Task 1.3 should name line 126's join explicitly so the executor does not cover the wrong one.
- design.md's Impact/Risks name only the direct HTTP callers. `addStep`'s four indirect callers all handle the new `Left` safely (verified above), but the design should say so in one line rather than leave it unexamined — `create_bound_panel` and proposal-apply are agent-facing paths that will now fail-with-rollback where they previously produced a silent no-op pipeline. That is an improvement, but an unstated one.
