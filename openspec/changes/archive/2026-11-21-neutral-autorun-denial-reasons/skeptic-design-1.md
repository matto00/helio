## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed at HEAD 0fac82ce38ee0c391f8473fb4b3bb58d87fb5c7a (planning artifacts untracked in the change dir).

### What I verified (with evidence)

- **Single construction point.** `grep -rn "EvaluatedPipeline.Denied\|DeniedPipelineResponse" backend/src/main` finds `Denied` built only in `AutoRunTriggerService.handleDenied` (AutoRunTriggerService.scala:142,145,146), with all three branches passing `verdict.reasons` verbatim. `DeniedPipelineResponse.fromDomain` (DataSourceProtocol.scala:307) is used by `RowWriteResponse` (:327), `RowResponse` (:348) and `FormSubmitResponse` (FormSubmitProtocol.scala:23). D1 is sound.
- **The list of responses is complete.** `triggerAutoRun` is called only from `DataSourceService` (lines 116 and 128). The awaited calls are at 844 (`appendRows`), 887 (`appendFormRow`, which gets `writer`), 911 (`replaceRows`) and 939 (`patchRow`). `deleteRow` is fire-and-forget (965), so its 204 has no body and carries no denial. `appendFormRow` is reached from `PanelService.scala:130` (JSON) and `PanelFormFileSubmission.scala:62` (multipart), both passing the HTTP caller. Routes are at DataSourceRoutes.scala:196/201/224. `evaluateAtFire` feeds only the scheduler's skip `error_log`, which the design lists as a non-goal. The design's table matches the code.
- **The client never reads `detail`.** `deniedPipelinesToast.ts:30` renders `p.reasons.map(denyReasonCopy)`, and `denyReasonCopy.ts` maps by `code` through `DENY_REASON_COPY`. No non-test `frontend/src` file reads a reason's `.detail` (the `.detail` hits were in ConfirmInline, PipelineListTable and SourceListTable, which are unrelated). helio-mcp has no `deniedPipelines` consumer. The schema types `detail` as a string (`denied-pipeline-response.schema.json:24,42`), so a text-only change does not change the shape. D4 holds.
- **The HEL-1661 table covers every code.** The codes emitted in `domain/engine/PipelineCostEstimator.scala` are exactly ai-step, content-conversion, no-roots, remote-fetch, row-estimate-unavailable, rows-above-threshold, steps-above-bound, unclassified-op, unclassified-source and writeback-step. All ten are keys of `PipelineAnalyzeReads.NeutralReasonDetail` (PipelineAnalyzeReads.scala:329-340). The table is `private[pipelines]` in the same package as `AutoRunTriggerService`, and `GenericReasonDetail` (:342) is the fallback. No new wording is needed, so there is no product question.
- **The `step-config-invalid` pass-through matches analyze.** `RunConfigGate.stepConfigReasons` uses only `PipelineAnalyzeService.stepConfigProblem(kind, config)`, the same schema-independent text analyze gives non-owners (`nonOwnerValidationError`, PipelineAnalyzeReads.scala:233). D3 holds.
- **Existing tests do not pin the raw grantee detail.** In `AutoRunTriggerServiceSpec` and `DataSourceServiceDeniedPipelinesSpec`, grantee assertions check `reasons.map(_.code)` or `nonEmpty`, never `detail`. `RowWriteResponseDenyReasonCoverageSpec` tests `fromDomain` pass-through only. Task 3.1's "still pass" claim is plausible.
- **There is a trap in where 1.1 would run.** `FormSubmitEditorRoutesSpec` mixes in `FormPanelRouteFixture`, whose `new ApiRoutes(...)` (FormPanelRouteFixture.scala:108-116) passes no `autoRunDebounceRepo`. So `autoRunTriggerServiceOpt` is `None` (ApiRoutes.scala:281-283), `dataSourceService` gets `autoRunTriggerService = null`, and `triggerAutoRunAwaited` always returns `Vector.empty`. In that fixture `deniedPipelines` is always empty, before and after the fix. `FormSubmitEditorRlsSpec` (services/panels, lines 124/128) does wire `autoRunDebounceRepo` and a trigger.

### Verdict: REFUTE

The design is sound: one boundary, a correct and complete enumeration, a verified table and no shape change. Only task 1.1 needs revising before execution. As written, it points the AC's red test at a fixture where auto-run is switched off. That red would fail for the wrong reason (no denial at all), and the "no digit appears in the denial" half of the assertion passes trivially when there is no denial. That is the kind of red that proves nothing which the red-first constraint (C12) exists to prevent.

### Change Requests

1. **tasks.md 1.1: name a host where auto-run is actually wired.** Either use `FormSubmitEditorRlsSpec` (or a new spec built the same way), or explicitly add wiring of `autoRunDebounceRepo` into the new spec's `ApiRoutes`. Do not plain-extend `FormSubmitEditorRoutesSpec` / `FormPanelRouteFixture`, which passes none (FormPanelRouteFixture.scala:108-116), so `deniedPipelines` is always `[]` there.
2. **tasks.md 1.1: state the setup and require a non-vacuous red.** Setup: a pipeline owned by the form owner, rooted at the form's bound source, with the editor holding a pipeline grant, forced over the threshold (for example `last_run_row_count` above `MaxAutoRunRows` = 10000, or more than 20 enabled steps for `steps-above-bound`). The test must assert `deniedPipelines` is non-empty with the expected code before the no-digit assertion runs. The recorded red output must show the current code returning the raw `Estimated N rows exceeds the auto-run threshold of 10000` detail to the editor, not an index or empty-array failure.

### Non-blocking notes

- Task 1.3's "unknown code falls back to generic (unit, if reachable)" cannot be reached through `handleDenied` without stubbing the estimator. Either factor the reason mapping into a small pure function that can be tested directly, or drop that sub-item explicitly rather than leaving it hedged.
- D1's mapping sits next to `hasConfigReason`, which is computed from the un-neutralized reasons. That is fine, since codes are unchanged, but keep the `canRun` computation reading `verdict.reasons`, as now.
- After HEL-1799 merges, recheck that `NeutralReasonDetail` and `GenericReasonDetail` keep their names and their `private[pipelines]` visibility.
