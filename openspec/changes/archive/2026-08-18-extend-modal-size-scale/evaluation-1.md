## Evaluation Report — Cycle 1 (evaluation-1.md)

### Phase 1: Spec Review — FAIL

Issues:

1. **PanelCreationModal now renders a new, previously-invisible, redundant header title ("Create panel") stacked directly above the wizard's own step eyebrow + step heading.** Pre-migration, the old `<dialog aria-label="Create panel">` used "Create panel" only as a screen-reader label — the *visible* header was exclusively the "Step N of M" eyebrow + per-step `<h2>` (e.g. "Choose panel type"). Post-migration, `Modal`'s required `title` prop is passed the literal string `"Create panel"` (`PanelCreationModal.tsx:431`), which renders as a real, visible `<h2 class="ui-modal__title">` in `Modal`'s own header — stacked directly on top of the (unchanged) step eyebrow/heading block that was moved into the body. Confirmed live via Playwright screenshot at 1440/1100/375px: every load of the modal shows two headings ("Create panel" then "Step 1 of 2 / Choose panel type") with no visual relationship communicated between them. This contradicts `proposal.md`'s Non-Goal "No visual redesign — footprints, spacing, and animation timing stay pixel-equivalent" (new visible content = a footprint change) and is inconsistent with the codebase's own established multi-step-wizard pattern: `AddSourceModal` (also `Modal`-based, also multi-step) sets `Modal`'s `title` prop *dynamically per step* (`const title = step === "configure" ? "Add data source" : "Preview schema"` — `AddSourceModal.tsx:286`) rather than pairing a static generic title with a separate step heading. `design.md` Decision 4 anticipated moving the step heading into the body but never examined the resulting visual double-heading, and neither skeptic design round caught it (both rounds focused on height ownership and lost focus-trap coverage). Not a subjective/judgment call — it's new, objectively observable, previously-absent visible content.

2. **`PanelDetailModal`'s ✕-button/discard-behavior change is a real, deliberate, and correctly-flagged consequence of Design Decision 2 — assessed as acceptable — but the planning artifacts were never updated to reflect it.** Verified live via Playwright: pre-migration, clicking the ✕ button always fully closed the modal (both the edit-mode-clean case and the edit-mode-dirty-then-confirmed-discard case), while Escape/backdrop-click/the footer Cancel button instead returned to view mode in both of those cases. Post-migration, all four vectors (✕, Escape, backdrop, Cancel) now consistently return to view mode — verified with screenshots showing the modal remaining open in view mode after clicking ✕ in both the clean and dirty+confirmed cases. This is the necessary and correct consequence of Design Decision 2 (unifying `Modal`'s onClose across its own three dismiss vectors), which is itself required to satisfy ticket AC1 ("Both modals open/close/animate/trap-focus identically to every other Modal-based surface in the app") — reverting it would mean re-introducing component-level dismiss-vector-specific hand-rolling that the ticket explicitly asks to retire. I assess this as an acceptable trade-off, not a regression to revert. However: `proposal.md`'s Non-Goals still literally states "No change to... save/discard semantics" (now false), and `openspec/specs/panel-detail-modal/spec.md`'s "Modal dismisses on Escape, backdrop click, and Cancel" requirement (declared "Modified Capabilities: none" in `proposal.md`, so no delta was filed) still documents the old ✕-always-closes distinction, which no longer holds. Planning artifacts must reflect final implemented behavior — this is a required documentation fix, not a code revert.

Everything else in Phase 1 passes: all ticket ACs are addressed (AC2 — "no hand-rolled `<dialog>` outside `shared/ui/Modal.tsx`" — independently verified via `grep -rn "<dialog" frontend/src --include="*.tsx"`, only `Modal.tsx` matches); all `tasks.md` items are done and match the diff; the two deviations from the original task list (1.6 focus-trap relocation, the ✕-button behavior collapse) were transparently flagged by the executor rather than silently absorbed, which is exactly right; no unrelated scope creep (the shared focus-trap fix in `Modal.tsx` is in-scope per `proposal.md`'s own Impact list and is required by the still-binding `modal-dismiss-interactions` spec, not a drive-by change); no regressions found in any of the other 11 `Modal` consumers (see Phase 3).

Issues:

1. **The new shared Tab/Shift+Tab focus-trap effect added to `Modal.tsx` (task 1.6) has zero jsdom/unit test coverage, even though it is straightforwardly testable in jsdom.** `design.md`'s Risk 4 and the executor's own reasoning ("jsdom stubs `showModal` and cannot exercise native `<dialog>` focus containment, so there is no jsdom replacement test possible") was true when the plan was to rely on *native* containment — but after 1.6's fix, the trap is a hand-rolled JS `keydown` listener + `querySelectorAll` + `.focus()` (`Modal.tsx:102-130`), structurally identical to the *deleted* `PanelCreationModal.test.tsx` tests 2.7/2.8, which asserted this exact mechanism in jsdom via `fireEvent.keyDown(dialog, { key: "Tab" })` + `expect(document.activeElement).toBe(...)` — no native `<dialog>` behavior required, since it's plain JS event handling jsdom fully supports. That test-portability was not reconsidered after choosing to reimplement the trap as JS rather than deleting it, and `Modal.test.tsx` has no `Tab`/`trap`/`wrap`/`keyDown` test at all (confirmed via `grep`). The only coverage is the new `e2e/hel716-panel-creation-focus-trap.spec.ts`, which by its own header comment is "not part of the pre-commit gates" (`npm run e2e`, on-demand only). This means a future regression to this behavior — now shared across all 13 `Modal` consumers — would not be caught by the fast suite that gates every commit. **Change Request: add a `Modal.test.tsx` case (or two) asserting Tab-from-last-wraps-to-first and Shift+Tab-from-first-wraps-to-last using `fireEvent.keyDown` on the dialog + `document.activeElement`, mirroring the deleted `PanelCreationModal.test.tsx` 2.7/2.8 pattern.**

Everything else in Phase 2 is clean: `CONTRIBUTING.md`'s Imports & Qualifiers rule is followed throughout (no inline FQNs); `DESIGN.md`'s mechanical rules are followed in every CSS diff reviewed (`Modal.css`, `PanelCreationModal.css`, `PanelDetailModal.css`, `PanelDetailModal.mobile.css` — all values are `--app-*`/`--space-*`/`--text-*`/`--control-*` tokens, no hardcoded hex/px, breakpoints match the canonical 430/768 set); the CSS split (`PanelDetailModal.css`/`.binding.css`/`.sections.css`/`.appearance.css`/`.mobile.css`) stays well under the `panel-detail-modal-css-structure` ~400-line budget (max 307 lines); DRY is respected (the HEL-313 `[open]`-animation regression guard correctly moved to `Modal.css.test.ts` instead of being duplicated); error handling / security are not in scope for this change and nothing new was introduced there; no dead code, no leftover TODO/FIXME; `usePanelDetailModalLifecycle.ts` was correctly retired rather than left as a half-used shim.

Non-blocking: `PanelCreationModal.tsx` (557 lines, down from 627) and `PanelDetailModal.tsx` (417 lines, down from 428) both remain over `CONTRIBUTING.md`'s ~400-line soft-budget threshold — both were already over budget before this change and both shrank as a result of it, so this isn't a new violation, but `CONTRIBUTING.md` asks that a file crossing ~400 lines get a proposed split noted in the PR description, which wasn't done here.

### Overall: FAIL

### Change Requests

1. **Fix `PanelCreationModal`'s duplicate visible header.** `Modal`'s header now shows a static "Create panel" title with the wizard's own step eyebrow + step heading duplicated immediately below it in the body — new, previously-invisible content that contradicts `proposal.md`'s "footprints... stay pixel-equivalent" Non-Goal and is inconsistent with `AddSourceModal`'s existing per-step-dynamic-title pattern for `Modal`-based wizards (`AddSourceModal.tsx:286`). Recommend passing the per-step title dynamically as `Modal`'s `title` prop (mirroring `AddSourceModal`) and dropping the redundant body-level step `<h2>` (keeping only the "Step N of M" eyebrow, or folding the eyebrow into `Modal`'s `description` slot), rather than showing both a generic and a specific title stacked together. `PanelCreationModal.tsx:431` (Modal invocation) and the step-heading block now in `children` are the two touch points.
2. **Update planning artifacts to reflect `PanelDetailModal`'s new unified dismiss-vector behavior**, which is otherwise correctly implemented: (a) revise `proposal.md`'s Non-Goals — "No change to... save/discard semantics" is no longer accurate for the ✕-button case; scope it precisely (e.g. "no change to save persistence or discard-warning triggering conditions; the post-dismiss destination is unified per Decision 2"), and (b) add a spec delta for `openspec/specs/panel-detail-modal/spec.md`'s "Modal dismisses on Escape, backdrop click, and Cancel" requirement documenting that the ✕ button now also returns to view mode from edit mode (matching Escape/backdrop/Cancel) rather than closing outright, consistent with `PanelDetailModal.test.tsx`'s renamed tests.
3. **Add jsdom coverage for `Modal.tsx`'s new shared Tab/Shift+Tab focus-trap effect** in `Modal.test.tsx` — this is unit-testable in jsdom (it's hand-rolled JS, not native `<dialog>` behavior) using the same `fireEvent.keyDown` + `document.activeElement` technique the now-deleted `PanelCreationModal.test.tsx` tests 2.7/2.8 already proved works. Currently the only coverage is `e2e/hel716-panel-creation-focus-trap.spec.ts`, which is explicitly not part of the pre-commit/CI gates, leaving this now-shared-across-13-consumers a11y behavior unguarded by the fast suite.
