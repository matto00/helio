## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- Root-cause claim, checked against RGL 2.2.4 source (`node_modules/react-grid-layout/dist/chunk-QAWP6PEK.js`):
  - `ResponsiveGridLayout` (l.1359-1384): `derivedLayout` is non-null only when `!deepEqual(propsLayouts, prevLayoutsRef.current)`; `prevLayoutsRef` is only advanced in that branch. Internal drags never touch it. So the claim "Responsive resyncs only when the layouts PROP differs from the previous PROP" is TRUE, and an undo that writes a value deep-equal to the prop already held is a no-op for RGL. Root cause is credible.
  - `DesktopPanelGrid.tsx`/`useLayoutSave.ts`: during a drag only `latestLayoutRef` is written (via onLayoutChange); the store is untouched until persistLayout. Confirmed. Redo's wrong `currentLayout` (store = pre-drag) follows from `useLayoutUndoRedo.ts` reading the store layout. Confirmed.
- Decision 1's primary path is WRONG. RGL `GridLayout.onDragStop` (l.807-845) and `onResizeStop` (l.940-963) call `onDragStopProp`/`onResizeStopProp` FIRST and only afterwards `onLayoutChange(finalLayout)`. In addition the layout-effect `onLayoutChange` (l.746) is suppressed while `activeDrag` is set, so no `onLayoutChange` fires during a drag. Therefore when `handleDragStop`/`handleResizeStop` runs, `latestLayoutRef.current` is still the PRE-interaction layout (the same object as `preInteractionLayoutRef.current`). Dispatching `setDashboardLayoutLocally(latestLayoutRef.current)` at stop would commit the pre-drag layout: no fix, and a corrupt echo. The design's "executor must verify" hedge and fallback are insufficient because the fallback is underspecified (below).
- Fallback is underspecified/incorrect as written: the stop callback receives a single-breakpoint `Layout` array (`finalLayout`), not a responsive `layouts` object, and Responsive does not pass the active breakpoint to the stop callback. `fromResponsiveLayouts(panels, layouts)` takes a `{lg,md,sm,xs}` object, so "merged per breakpoint via fromResponsiveLayouts" has no defined inputs: which breakpoint is active, and where do the other three come from?
- Echo detection (Decision 2) ordering: the effect runs after render, by which time the post-stop `onLayoutChange(finalLayout)` has synchronously set `latestLayoutRef` to the final layout, so echo = equal holds IF the committed value is the true final layout. If the committed value differs from the final layout (wrong value above, or `resolveDashboardLayout` normalising/sanitising/overlap-bumping so `resolvedLayout` differs from the committed layout), the equality is false, the change is treated as non-echo, `persistedLayoutRef` is advanced to the dragged layout, and the drag is silently never persisted. The design does not address this.
- Persistence regression via redo (Decision 2 "advance persistedLayoutRef on any non-echo store change, including undo/redo"): drag (unsaved; persisted=pre), undo (non-echo: persisted:=pre, latest:=pre), redo (non-echo: persisted:=dragged, latest:=dragged). Server still holds pre-drag but the client now believes dragged is persisted; autosave/Save-now/unmount are no-ops. After this change the redo is VISIBLE and the user sees the drag restored, then reload loses it. The design acknowledges "undo/redo not persisted" as a follow-up, but its own persisted-ref rule is what turns an unsaved drag into a believed-saved one. Fix is cheap: only advance `persistedLayoutRef` on server-originated changes (initial mount, refetch, PATCH fulfilled), never on undo/redo; then persistLayout after undo/redo naturally PATCHes the right layout and the follow-up largely disappears.
- HEL-1023 (Linear): about per-breakpoint derivation/no-layout-for-breakpoint; the design stays in the store-to-grid sync. No conflict found, but note that committing `fromResponsiveLayouts` output writes all four breakpoints (including never-authored ones that RGL derived) into the store on first drag, which changes what HEL-1023 will see as "authored". Worth a sentence in the design.
- Spec delta present and consistent with proposal; AC coverage (keyboard, CommandBar, e2e rendered position) mapped to tasks 2.2/2.3. No placeholders.

### Verdict: REFUTE

### Change Requests
1. design.md Decision 1 / tasks 1.1+1.3: remove the claim that `latestLayoutRef` is (probably) final at stop. It is provably NOT (RGL calls onDragStop/onResizeStop before onLayoutChange; chunk-QAWP6PEK.js l.826-833, 957-961). Specify the actual mechanism. Suggested, concrete: set a `pendingCommitRef = true` in the stop handlers (kept alongside pushLayoutSnapshot) and, in `handleLayoutChange`, after `markLayoutChanged(next)`, if the flag is set, clear it and dispatch `setDashboardLayoutLocally({dashboardId, layout: next})` (onLayoutChange fires synchronously right after the stop callback in the same event). Define clearing the flag when no onLayoutChange follows (a drag that moved nothing never fires it) so a later unrelated onLayoutChange (width/breakpoint change, mount) does not commit. Alternatively, specify precisely how breakpoint and the other three breakpoints are obtained if the stop-callback layout is used.
2. design.md Decision 2: specify that `persistedLayoutRef` advances ONLY for server-originated store changes (initial, refetch, PATCH fulfilled with the PATCHed layout), not for undo/redo; add a task/test: drag, undo, redo, flush => exactly one PATCH carrying the dragged layout; drag, undo, flush => no stale PATCH of the dragged layout. Also state how echo equality copes with `resolveDashboardLayout` normalisation (compare against what was committed, not the resolved value, or prove idempotence).
3. design.md: state the HEL-1023 interaction (first drag now writes all four breakpoints into the store) and that it is accepted, or avoid it by merging only the active breakpoint.
4. tasks 2.1: add unit tests that exercise the stop-before-onLayoutChange ordering (stop handler fired before the layout-change callback), since a test that calls the handlers in the opposite order would pass against the wrong implementation.

### Non-blocking notes
- A click on the drag handle that moves nothing still pushes a no-op history snapshot (pre-existing); consider guarding while the stop path is being changed.
- CLAUDE.md's "debounced 250ms" statement is wrong per design; fixing the doc could ride along.
