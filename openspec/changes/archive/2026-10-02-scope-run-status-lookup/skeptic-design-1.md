## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- (a) Latent hole CONFIRMED. `grep cache.put|update|get` in backend/src/main: writers only in `SparkJobSubmitter.scala` (56/75/81/106); sole reader `PipelineRunService.scala:820` (`status`). `sparkJobSubmitter` is only constructed in Main.scala:183 and passed to ApiRoutes (ApiRoutes.scala:95); no `.submit(` call targets it (all `.submit(` hits are `PipelineRunService.submit`). So the cache is never populated on a running backend; the route 404s today.
- Route as described: `PipelineRunStatusRoutes.scala:34-37` does `val _ = pipelineId; runService.status(runId)`, 404 body `"Run not found: " + runId` (echoes the id).
- (b) Design is sound. `RunEntry`/`put`/`update` (PipelineRunCache.scala:21-50) carry no pipeline id; `SparkJobSubmitter.submit` has `pipeline: Pipeline` in scope, so binding at write time is feasible. `latestRun` (PipelineRunService.scala:795-799) already uses `findByIdShared(pipelineId, Some(user))` + `ServiceError.NotFound` -> `ServiceResponse.run`, a valid template. `status(runId)` has exactly one caller (the route; the other grep hits are comments or MfaService).
- (d) Other user-free run lookups: `run-events` (PipelineRunStreamRoutes.scala:29-37) gates on `pipelineExistsShared` before subscribing, so it is scoped. `history` (:838-841) and `latestRun` use `findByIdShared`. No other `cache.get` reader exists. Frontend `fetchRunStatus` (pipelineService.ts:232) exists but has no non-test caller; helio-mcp has no caller. Proposal's "no client calls" holds in substance.
- AC coverage: byte-identical 404 (2.2, 1.x), grantee/owner 200 (1.2), spec row (1.1), audit (3.1), patch-sets probe (3.2). No scope drift; spec delta present.

### Verdict: CONFIRM

### Non-blocking notes (implementer should address; they are gaps, not blockers)
1. Byte-identity coverage: the row-table mechanism (`ExistenceNotLeakedRoutesSpec` `run()`/`request()`) only compares foreign vs nonexistent PIPELINE id; both fail at the visibility lookup, never reaching the cache arms. The AC explicitly lists "wrong-pipeline" and "absent run" arms. Add one test asserting status + content-type + body equal across all four arms (foreign pipeline, absent pipeline, absent run under an owned pipeline, run of pipeline A requested via visible pipeline B), with run id substituted/normalised as `run()` does. Task 1.2 currently only says "same 404"/"wrong-pipeline red".
2. The row framework substitutes only `{id}`/`{dash}`. The probed segment is the pipeline id while the run id must be a real seeded cache key. Decide explicitly: e.g. seed a fixed run id into the `PipelineRunCache` that `buildApi` builds (owned by the seeded pipeline), and use it as a literal in the path. Note `seedOwned()` generates fresh pipeline ids per row, so seeding must occur after `seedOwned()` with the generated pipeline id (buildApi is called after seedOwned in the test body; ok, but the cache must be exposed/returned as design Decision 4 says).
3. Existing tests will break by design and need real rewrites, not just fixture signature updates: `PipelineRunRoutesSpec.scala:331-355` call `GET /pipelines/any/runs/$runId` (nonexistent pipeline) and expect 200 for a cache-only run (line 345 also uses `cache.update` without `put`). They must seed a real pipeline and run bound to it. `PipelineRunCacheSpec` calls `put(runId,status)` 2-arg. Task 2.1/2.2 should name these. Also decide `update`'s pipelineId handling (preserve via copy vs required param; an `update` on an absent key currently creates an entry).
4. Stale comments to refresh: `PipelineRunRoutesSpec.scala:485` and `PipelineRunLatestRoutes.scala:34` reference `runService.status("latest")` which is being removed.
5. Completeness guard 1 (access helper files) does not scan `findByIdShared`; the row's `sites` should still list `PipelineRunService.scala`. Guard 3 (Forbidden counts) is unaffected as the plan adds no Forbidden producer; keep that so.
6. Proposal "no frontend client" is slightly loose: `fetchRunStatus` exists unused; the 404 body message change is not observable by any live consumer.
