### Verdict: REFUTE

The measurement plan is mostly sound and the code claims check out. However, the input that decides whether V120 ships, and which index it adds, is underspecified, and the expected candidate is likely wrong for most of the age purges. Fixing this now is cheap. After execution it would mean a second measurement cycle.

### Change Requests

1. **D2/D4: name the tier mix that governs the index decision, and stop using all-owner as the headline for the age purges.** With every user owner-tier, the `free`, `beta` and unnamed purges join to zero users. Their plans become degenerate: a hash join on an empty inner may never scan the outer, and the planner estimates near-zero rows. So the all-owner S2 numbers say nothing about the cost of three of the four age purges. The decision then rests entirely on the owner purge, the one tier where a `captured_at` index is most selective. Revise D2/D4 as follows:
   - D4's rule is evaluated on an explicitly stated, realistic mixed-tier S2. State the mix and why it is realistic, for example mostly free.
   - Seed each Output's history depth from its tier's cap. A free Output has about 455 rows at steady state, not 790.
   - All-owner stays only as the worst case for the thin DELETE.

2. **D4: widen the candidate set beyond "a btree on the filter column."** Each age purge's selective predicate is `tier = X AND captured_at < cutoff`. The tier lives on `users` and reaches history only through `h.pipeline_id`, which has no index. `(captured_at)` alone is not selective for short-cap tiers in a mixed population. `captured_at < now-30d` (the free/unnamed cutoff) matches every beta/owner row older than 30 days, about 335 of an owner Output's 790 rows. Those rows are then discarded by the join. Require the after-measurement to compare at least `(captured_at)` against a join-driven `(pipeline_id, captured_at)`, which drives from the tier's pipelines into a range per pipeline. Pick by measured plans across all four age purges. The design's "Expected candidate: captured_at for the four age purges" must be removed or justified.

3. **D4: fix the firing rule's metric.** "Removes ≥99% of scanned rows by filter" does not fit these plans. The `captured_at` comparison is a Filter on the seq scan, but the tier restriction is applied by the join. For the free purge, the Filter may remove only about 60% even though the statement deletes almost nothing. Define the rule as rows scanned versus rows actually deleted (or joined) per statement, read from the EXPLAIN ANALYZE output, so it fires correctly on each of the four purges.

4. **D3/D7: measure lock hold time per transaction, not as one combined transaction.** The tick is two transactions, and each takes and releases the advisory lock on its own. D3's "the same transaction also measures the whole tick end-to-end … since the advisory lock is held for the transaction" merges them. That overstates the hold time on which D7's starvation verdict depends. Record (a) each repository's transaction time as its lock-hold time and (b) their sum as the tick's wall time, and apply D7 to (a).

5. **D2/tasks 1.3: say whether S1/S2/S3 coexist or are measured one at a time.** "All in the one scratch DB" can be read either way. If they coexist, the S1 and S3 plans run against a table that also holds S2's 8M rows, and the numbers are meaningless. State the sequence, for example: TRUNCATE (or rebuild), seed, VACUUM ANALYZE, measure, next scenario.

6. **tasks 1.1: state how Flyway is run against the scratch DB.** Nothing in the repo provides a standalone Flyway runner. Migration happens inside `Database.initApp` at backend boot, or in test harnesses via `Flyway.configure()`. Name the mechanism, for example booting the backend with `DATABASE_URL` pointed at `helio_hel1284_scratch`, or the Flyway CLI with `-locations=filesystem:backend/src/main/resources/db/migration`. Also state how it is proven that `helio` was untouched; "verify helio was not touched" needs a concrete check, such as `flyway_schema_history` max version and row count in `helio` before and after. Booting the backend also runs Main's startup jobs, which is harmless in scratch but should be noted.

### Non-blocking notes

- D6's scratch proof ("run the index statement as a non-superuser, non-BYPASSRLS owner role") requires re-owning the table to a temp role first. That only shows an owner can create an index, which is tautological. Keep it cheap and don't present it as evidence about prod ownership. The real prod question (does `helio` own `output_snapshot_history`?) can only be answered read-only against prod, or stated as an assumption.
- `helio_privileged` is cluster-global (V34: `CREATE ROLE ... IF NOT EXISTS` plus `GRANT helio_privileged TO current_user`). Migrating the scratch DB on the shared local cluster re-grants it to whichever role runs Flyway. Harmless, but D1's "drop any temporary role by exact name" should not include `helio_privileged`.
- The payload per-tier newest-N DELETE also ranks every payload row of the tier. Record it alongside the thin DELETE as a second unbounded-by-design statement.
- The ~340-byte `summary` mean "from the dev DB" should be reproduced by a read-only query recorded in measurements.md.
