### Verdict: REFUTE

Five of the six round-1 change requests are resolved, and the new arithmetic is correct. But the revised Flyway mechanism (CR6), followed as written, boots a backend against the shared `helio` DB and runs the retention DELETEs there. The planned "helio untouched" proof cannot detect that. This is a C2 violation, and fixing the plan now costs a few lines.

### Change Requests

1. **D1 / tasks 1.1: replace "boot with `DATABASE_URL` pointed at the scratch DB" with a mechanism that provably cannot read `backend/.env`.** `sbt run` (and `runMain`, which uses the same run envVars) loads `backend/.env` via `build.sbt:124`, and those values override the shell environment (sbt 2.0.9 `Fork`: `ProcessBuilder.environment().put`). Acceptable options, of which D1 must name one:
   - (a) `sbt assembly`, then `java -jar backend/target/scala-2.13/helio-backend.jar` under an explicit environment containing only `DATABASE_URL=<scratch URL>` (plus PATH/JAVA_HOME). With `GOOGLE_CLIENT_ID` etc. deliberately absent, `Main.requireEnv` terminates the process right after `Database.initApp` has migrated, and before the scheduler is spawned. The executor must verify that ordering in Main.scala before relying on it. Nothing seeded can be thinned, and no PID-kill is needed.
   - (b) A one-off Flyway call (for example a scratch-only Scala/JShell invocation of `Flyway.configure().dataSource(<scratch>).locations("filesystem:backend/src/main/resources/db/migration").load().migrate()`) that never starts Main.
   Do not edit `backend/.env` as the mechanism. It is shared operator config, and a forgotten revert re-points later boots.
2. **D1: replace the "helio untouched" proof with a positive one that would actually fail if the boot hit `helio`.** Record the effective JDBC URL the process used (a startup log line, or `pg_stat_activity.datname` for the migrating backend's connections). Show that the scratch DB's `flyway_schema_history` rows were installed by this run, with `installed_on` inside the boot window. `helio`'s Flyway counts are unchanged even when the boot does hit `helio`, so they prove nothing. If option (a) of CR1 is used, also record that the scheduler never started (the process exited at `requireEnv`). Keep the `helio` before/after counts as secondary evidence only.
