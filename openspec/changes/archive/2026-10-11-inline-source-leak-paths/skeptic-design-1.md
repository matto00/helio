## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed tree: `bcb0e891923094c1a1e85ecc053f30a73ee6d70f` (origin/main; change dir untracked). The artifacts and premise-validation.md were treated as claims and checked against the live code. Linear HEL-1475 was re-fetched: its description matches ticket.md's six paths.

### What I verified (with evidence)

- **Cycle guard cannot fire for a freshly created inline source: CONFIRMED.** `PipelineCycleGuard.checkAddReadAction` (infrastructure/persistence/pipelines/PipelineCycleGuard.scala, at the end of the file) calls `checkNoCycle(readEdges, writeEdges, Set(newReadSource), target, ...)` once for each of the pipeline's own `upsertsource` write targets. `PipelineCycleValidator.findReachablePath` (domain/pipelines/PipelineCycleValidator.scala) returns a hit only when `targets.contains(start)` or when some existing edge's `e.to` is in `targets`. Every `e.to` is an existing `WriteEdge.dataSourceId`, and `start` is an existing write target. A UUID minted moments earlier can be neither. The leak is still real for other failures after creation: `findByIdOwned` returning None, `pipelineNameQuery.head` (PipelineRootRepository.scala:87) on a pipeline deleted concurrently, and DB errors. `addRoot`'s `.recover` (PipelineRootWrites.scala) maps only `PipelineCycleRejected`, and nothing compensates. Decision 2 is sound.
- **Deciding `implicitConnector` from the request shape: sound for single-call create and addRoot.** In `SourceService.createRest`, only the `(None, Some(url))` branch calls `connectorRepo.create`. `(Some, Some)` and a defined `auth` return Left before anything is persisted, so a created source whose request was bare-url always points at the Auto Connector made in the same call. For patch-set rollback, the flag is only as sound as the positional pairing (see CR3).
- **The dependents guard is real, but only when it is wired.** `ConnectorRepository.delete` (ConnectorRepository.scala:283) defaults `dependentCount` to always-zero. The real count, `dataSourceRepo.countRestSourcesReferencing` (DataSourceRepository.scala:274, system context, counts across all owners), is wired only in `ApiRoutes.scala:648-650` for `ConnectorEntityService`. The design does say "with the real dependentCount", so this is acceptable (see notes). The credential row is deleted with the Connector (ConnectorRepository.scala:292-305).
- **Gap after the insert in `createSql`/`createRestWithConfig`: CONFIRMED.** `CreateSourceEnvelope.build` turns an `inferSchema` Left into `fetchError` (a success), but a failed Future from `inferSchema` or `upsertInferredSchema` escapes after `dataSourceRepo.insert` has committed.
- **`createStatic` has the same gap: REFUTED.** `DataSourceService.createStatic` (DataSourceService.scala:141-210) calls only `dataSourceRepo.insertDatasetSource`. That method (DataSourceRepository.scala:322-354) writes the `data_sources` row with `inferredSchema`, the `dataset_rows` and `dataset_schema` as one `DBIO` under `ctx.withUserContext`, which is `.transactionally` (DbContext.scala:50-51). The only step after commit is `audit(...)`, which is fire-and-forget Unit. createStatic never calls `upsertInferredSchema`. See CR1.
- **Proof plan feasibility.** `PipelineRootRepository`, `DataSourceRepository` and `ConnectorRepository` are non-final classes, so the planned fault-injection subclasses are possible. An existing test already subclasses one (`PipelineCreateInlineSourceCleanupSpec`). Sibling specs exist to extend: `PipelineCreateOrphanSourceRoutesSpec`, `PipelineRootRoutesSpec`, `PatchSetPipelineCreateOrphanSourceSpec`, `SourceServiceSpec`, `DataSourceServiceSpec`. The proof is feasible except the static post-insert case, which cannot be red (CR1).
- **Proposal path.** `validateRestConfig` (PipelineProposalService.scala:228-233) accepts `url`, so a proposal can express a bare url, and the design's hedge "if the proposal REST config cannot express a bare url" is moot. However, the public `rollback(response, user)` (line 443) receives only a `PipelineProposalApplyResponse` (`sources: Vector[DataSourceResponse]`), not `ResolvedSource`. Its callers are `CombinedProposalService.scala:117,132` and `FirstRunDashboardService.scala:145,148`. See CR2.
- **`deleteInlineRootSources`** (PatchSetApplyRollback.scala:201-224): silent `zip` truncation and the silent drop of a missing `dataSourceId` are confirmed. Pipeline-delete failure already returns `unrecoverable` (line 142), so the planned test for that path is valid.
- **Patch-set `dataSource/create`** is static-only (`DataSourceCreate(request: StaticDataSourceRequest)`, PatchSetApplyTypes.scala:48). It has no implicit-Connector sibling path, so excluding it is correct.
- **Path 4 deferral.** Undo (`PatchSetUndoService`) deletes only the pipeline. The ticket says the decision is a product call and to escalate. The plan makes no behaviour change and sends the question to the owner as a follow-up ticket, which is acceptable: nothing in this change depends on the answer. The follow-up must actually be filed, though (CR4).
- **Scope omission (createCsv, createCsvUrl, text/pdf/image).** Justified. None of them is an inline-root kind (`resolveInlineRootSourceId` explicitly rejects csv), and the ticket names only `createSql`/`createRest`. It needs a follow-up ticket (CR4).

### Verdict: REFUTE

### Change Requests

1. **Remove `DataSourceService.createStatic` from the post-insert-failure fix, or restate it as "verified not a leak".** design.md Decision 3 (third bullet), the Context bullet "has the same insert -> upsertInferredSchema shape", Decision 5 item 3 ("static create with a fault-injected upsertInferredSchema"), proposal.md What Changes and Impact, ticket.md AC3, and the spec requirement "Source creation leaves no row behind..." all assume a step after the insert that does not exist. `insertDatasetSource` writes the source row, rows, declared schema and inferred schema in one transaction (DataSourceRepository.scala:322-354; DbContext.scala:50-51). As written, C3 (measured red on the pre-fix tree) cannot be met for that case: the executor would either write a test that is green from the start or add dead cleanup code. Record it the way the cycle guard is recorded: not reachable, citing the transaction.
2. **Specify how the implicit-Connector flag reaches `PipelineProposalService.rollback(response, user)`.** Decision 1 lists `rollback` among the switched callers but carries the flag only on `ResolvedSource`, which `rollback` never sees. Choose one and write it down:
   - (a) widen `rollback`'s signature so its callers (CombinedProposalService.scala:117,132; FirstRunDashboardService.scala:145,148) pass the proposal's per-source bare-url flags, in the same order as `response.sources`;
   - (b) explicitly descope `rollback`, with a reason and a follow-up ticket.

   Do not add a field to `PipelineProposalApplyResponse`; Decision 1 already rejects that pattern for API protocol types. Also delete the moot hedge, since bare `url` is expressible (validateRestConfig, line 229).
3. **Decision 4 must not delete anything when the root counts differ.** "After still deleting every id it COULD pair" pairs by position after the positional pairing has just been shown to be untrustworthy. With the implicit-Connector flag taken from `request.roots(i)`, a mispaired summary entry could point at a source the user already had. If that source is unreferenced once the pipeline is gone, `DataSourceService.delete` removes it. Its explicit Connector then has zero dependents and passes the guard. That is user data loss, which is worse than an orphan. Required:
   - When `summaryRoots.size != request.roots.size`, warn, delete nothing, and report `unrecoverable`.
   - Only when the counts match may a per-entry missing `dataSourceId` skip that one entry (warn and report `unrecoverable`) while the other correctly paired entries are deleted.
   - Update the spec requirement "Patch-set rollback reports roots it cannot line up" so it states that no delete is attempted on a count mismatch.
4. **Add tasks for the acceptance criteria that are not code.** No task in tasks.md covers:
   - (a) filing the path-4 follow-up that asks the owner the undo product question (ticket.md AC4: "a follow-up ticket asks the owner");
   - (b) commenting on HEL-1441 that item 3 is already satisfied (the last AC);
   - (c) the follow-up tickets design.md Non-Goals promises: the other `DataSourceService` create paths, and prod orphan cleanup.

   An AC with no task is easy to drop at delivery.

### Non-blocking notes

- In the Decision 1 helper, name the exact guarded delete: `connectorRepo.delete(id, user, dataSourceRepo.countRestSourcesReferencing)` or an injected `ConnectorEntityService` built with that function. A bare `connectorRepo.delete(id, user)` silently uses the always-zero default (ConnectorRepository.scala:286), and the guard would not exist. A unit test with the explicit-`connectorId` guard case (already in Decision 5) catches this only if the Connector is still referenced elsewhere. Consider a second guard case where another source references the Auto Connector.
- Optional defense in depth: before deleting, have the helper also check that the Connector it is about to delete is named `s"Auto: ${source.name}"` (the name `createRest` gives it). That way a wrong flag cannot delete a Connector the user named.
- Decision 3's bare-url bullet: delete the source before the Connector, and log the Connector delete's refusal if the source cleanup failed. The design implies this order; stating it saves a cycle.
- Prod-count query (b), "unreferenced inline-root-shaped sources", is an upper bound, and the design already says so. Keep that label in the PR body.
