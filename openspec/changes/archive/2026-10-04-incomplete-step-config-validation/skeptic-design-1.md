## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- Read ticket.md, proposal.md, design.md, tasks.md, both spec deltas, repro-findings.md; spot-checked against code at HEAD 63a0b3ea.
- Repro claims hold: InProcessPipelineEngine.scala:264-275 (requiredConfigProblems -> IAE -> StepExecutionException.from), :48-52 IAE allowlist, PipelineRunService previewAtNode/executeRunFailure log.error(..., ex) at ~:524, ~:623, ~:1095, backfill ~:733/:756.
- (a) IAE reachability from step evaluation (grep of `IllegalArgumentException` in domain/steps and domain/engine):
  - Data-dependent: DateBucketStep.scala:80 ("none of N row(s) ... could be parsed as a timestamp/date") is a failure on the DATA, not config.
  - Reference/data errors: JoinStep:96/104, UnionStep:88/99, LookupStep:116/127 ("Lane reference not found", "DataSource not found for join/union/lookup") raised inside step evaluate.
  - AI steps: GenerateTextStep.scala:46-75 (and Analyze/ConvertFormat) `fail()` throws IAE for field-missing (data), ai-unavailable, ai-error (API status / transport), ai-quota-exceeded, ai-guardrail: external-provider and runtime failures.
  - repro-findings explicitly lists the AI `fail()` helpers and others as "Not reproduced", so D2's audit scope ("internal invariants") never addresses them.
  - Under D1 all of these would be flagged isStepConfigError, demoted to WARN-no-stack, and returned as code "STEP_CONFIG_INVALID", with the tray saying "Upstream X step is not fully configured". That is wrong, and it is the inverse of the ticket's goal for provider outages (real incidents hidden at WARN).
- (b) ServiceError consumers: ServiceResponse.statusCodeFor (:88) and completeError (:75) are the only exhaustive matches; completeError currently always emits ErrorResponse(message), so the new body needs an explicit arm (design says "new response case class" - OK). Scheduler/proposal/combined/assistant code only builds or forwards Left(err)/.message; none match UnprocessableEntity in a way a sibling variant breaks. BUT existing tests do: PipelineRunServiceSpec.scala:505 (failing stringops step via submit) asserts `a[ServiceError.UnprocessableEntity]` and would go red for a config-IAE; tasks.md only says PipelineRunRoutesSpec pins stay green.
- (c) Absent-field: design.md/spec/tasks 3.2 claim "a stored config with absent name (inserted bypassing write validation) previews -> named 422". Not verified, and the code says otherwise: UpsertTarget.format.read (UpsertSourceConfig.scala:99-105) throws StepConfigTypeMismatch for newSource without a string name; UpsertSourceStep.requiredConfigProblems swallows that via Try(...).toOption -> Vector.empty; PipelineStepRepository.rowToDomain (:1320-1350) turns a decode Failure into IllegalStateException while reading steps, before the engine runs, i.e. outside the StepExecutionException/.recover path. Likely a 500/unattributed failure, not a named 422. Create already returns 422 for absent name (repro table), so the AC's absent case is currently only honestly covered at create.
- (d) Tests: 3.1 would be red on main (body lacks `code`); 3.4 is red on main (ERROR logged today); mutations named are real. 3.5 is red only by non-compilation. 3.2b as written cannot be made green by the planned fix (see c).

### Verdict: REFUTE

### Change Requests
1. D1 over-classifies. Do not key `isStepConfigError` on "any IAE through StepExecutionException.from". Introduce an explicit marker (e.g. `StepConfigError extends IllegalArgumentException`, StepConfigTypeMismatch already is one) thrown at the requiredConfigProblems branch (engine :266) and at audited config-only sites (FillNull:85/92, Window:100-143, Pivot:81, StringOps config sites, Aggregate/GroupBy unsupported fn, ChunkByTokenCount, DateBucket floorFn), and key the flag on it. Keep IAE -> message passthrough (HEL-859) unchanged. Data/reference/external IAEs (DateBucket:80, Join/Union/Lookup not-found, AI-step fail() incl. ai-error/unavailable/quota/field-missing, source loaders) must stay ERROR+stack (or at minimum a deliberately chosen separate class) and must NOT get code STEP_CONFIG_INVALID. Rewrite D2 as a per-site table classifying config / data / external / invariant, not just "invariant -> IllegalStateException". Add a test per non-config class (AI ai-error, datebucket unparsable) asserting ERROR remains and body is the old unnamed 422.
2. Fix the absent-field story honestly. Probe what a stored newSource config with no `name` actually does at preview (rowToDomain IllegalStateException?). Then either (a) make that path a named result (tolerate in rowToDomain/requiredConfigProblems) or (b) state in the spec/tasks that absent is rejected at create (422, assert no ERROR log) and unreachable at preview, and rewrite 3.2 and the "absent name" scenario accordingly. As written the scenario's second half asserts an unverified behaviour.
3. tasks.md must list the existing tests the new variant changes (PipelineRunServiceSpec.scala:505 and any other `a[ServiceError.UnprocessableEntity]` on a config-IAE run/preview) with the deliberate update, or choose a design (e.g. StepConfigInvalid as a UnprocessableEntity-compatible shape) that keeps them green. Do not leave "edit assertion until green" to the executor.
4. Spell out ServiceResponse.completeError needing a new arm for the structured body, and that DashboardAuthoringRoutes' reuse of statusCodeFor needs the new variant mapped (compile will force it, but the body-shape change is not compile-checked). Add a route-level assertion that MCP-relevant `message` is byte-identical.

### Non-blocking notes
- D5 (refuse, not empty preview) is sound.
- Root-source IAEs (CSV missing path, fetch failure; engine :534-789) are plain IAE, not SEE, so stay ERROR; consider stating that as an explicit non-goal.
- 3.5 is red only via compile error; add the behavioural nested-passthrough assertion first.
