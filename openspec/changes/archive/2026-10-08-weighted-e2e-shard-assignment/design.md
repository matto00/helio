## Context

See proposal.md (Why). Facts this design rests on:

- `.github/workflows/ci.yml` `e2e` job: 4-leg matrix, step `npx playwright test --shard=N/4`, CI `workers: 2`,
  JSON report at `test-results/results.json` uploaded as `playwright-json-shard-N` (`playwright.config.ts`).
- Playwright 1.55.1 `filterForShard` (`node_modules/playwright/lib/runner/testGroups.js`) cuts the ordered test groups
  by TEST COUNT; parallel-mode describes become one group per test; there is no weighting option in 1.55.
- CLI file args are unanchored, case-insensitive regexes (`util.js` `forceRegExp`) unless written `/.../`, and an empty
  arg list runs everything.
- Precedent: `backend/project/TestShards.scala` (LPT, unknown = median weight, `verifyExactlyOnce`) +
  `gen-test-suite-weights.py` + `test-suite-weights.tsv` (HEL-1287); `scripts/e2e-profile.mjs` (HEL-1288) already
  parses the CI JSON report.
- Baseline (5 runs 37661644840, 37663167352, 37666908476, 37671667190, 37672748835; per file, durations summed
  across ALL shard reports of a run, then median across runs): total ~1455 s, i.e. ~364 s per leg if balanced.
  `state-surface-contrast-guard.spec.ts` alone ~273 s. A parallel-mode file can straddle two legs (e.g.
  `hel773-top-anchored-mobile-nav-sheet.spec.ts` appears in both the s3 and s4 reports of every baseline run, ~70 s
  per run in total), so per-report medians understate it.
- Discovered set: 39 spec files (49 `e2e/*.spec.ts` minus 8 `testIgnore` matches + the regression spec glob); one,
  `hel1351-aggregated-chart-overlay.spec.ts` (HEL-1351, `de1ae5b00`), postdates the baseline runs.

## Goals / Non-Goals

Goals: balanced per-leg test time; exact-once partition verified per leg; HEL-951 glob/`testIgnore` contract kept.
Non-goals: see proposal.md; also no per-TEST weighting (file granularity suffices — largest file 273 s < 364 s).

## Decisions

**D1 — A Node script selects and runs the leg's files: `scripts/e2e-shard.mjs`.** Modes: `run <index> <count>`
(CI) and `weights <runDir>...` (regenerate the table; each `runDir` holds ONE CI run's per-shard
`results.json` files, e.g. `<runDir>/<shard>/results.json`). Node, not Scala/Python, because the e2e toolchain is
Node and the CI step already has it. Alternative rejected: renaming/moving spec files to steer the count-based split —
fragile, silently undone by the next added spec, and churns spec history.

**D2 — Discovery stays Playwright's.** `run` first calls `npx playwright test --list --reporter=json` (stdout only, so a
list pass never writes the CI JSON artifact `test-results/results.json`; honours
`testDir` + `testIgnore`; needs no servers), collects the distinct spec files, then partitions them. Nothing is a
hand-picked list; a weight-table entry for a file Playwright did not discover is ignored (and reported as stale).

**D3 — LPT over files, mirroring TestShards.** Sort by (-weight, path), assign each to the least-loaded leg (ties:
lowest index). Unknown files weigh the median of the table rows for currently discovered files (stale rows ignored). Recompute ALL legs and verify exact partition (missing /
duplicate / not-discovered) before selecting this leg — fail naming files.

**D4 — Selection is anchored and re-verified.** Pass each file as an anchored regex arg (`/(^|\/)e2e\/<escaped>$/`
form, no `g` flag) and, before running, re-list with exactly those args and require the listed file set to equal the
assignment; otherwise fail naming the difference. An empty assignment exits non-zero with a message (never invokes
Playwright with zero args). The re-list also uses `--reporter=json` (stdout). The script `spawn`s `npx playwright test
<args>` (config reporters, as today) and exits with its exit code — a child killed by a signal (`code === null`) maps
to a non-zero exit — so a script failure can never degrade into an unfiltered or falsely-green run.

**D5 — Weight table `e2e/shard-weights.tsv`** (`<file>\t<seconds>`, `#` comments). For each run directory, a file's
test-result durations are summed across ALL of that run's shard reports (a file split across two legs gets its whole
weight, not half); the weight is the median of those per-run sums across runs. Generated by `node
scripts/e2e-shard.mjs weights ...` from the 5 baseline runs named in Context (run ids recorded in the header). Never
hand-tuned. `playwright.config.ts` sets `retries: 0`, so a report holds one result per test and flaky retries cannot
inflate a weight; `weights` nonetheless refuses a report with `flaky > 0` as well as `unexpected > 0`. A discovered spec with no row (today: `hel1351-aggregated-chart-overlay.spec.ts`) gets the median weight
and `run` prints it as `defaulted` — the acceptance signal is "every discovered spec has a row OR is reported as
defaulted", never a hand-added row.

**D6 — CI step** becomes `node scripts/e2e-shard.mjs run ${{ matrix.shard }} ${{ strategy.job-total }}` (1-based
index, as today). The step name and HEL-951 comments — the step's own and `ci.yml:81-85` (the
`check:state-contrast:selftest` comment that cites "the `e2e` job's `npx playwright test` glob") — are updated to say
discovery is still the config glob.

**D7 — Selftest `scripts/e2e-shard.selftest.mjs`** tests the pure functions (LPT determinism/balance, unknown-weight
default, exact-partition failure naming, regex escaping/anchoring, empty-shard refusal, a file split across two shard
reports of one run weighted by its sum, signal-killed child mapped to non-zero) and includes a
demonstrated-red mutation (e.g. a partition that drops a file must fail). Wired as `check:e2e-shard:selftest` in
`package.json`, `.husky/pre-commit`, and the CI job other selftests use — whatever `check-precommit-ci-parity` demands.

**D8 — Measurement.** Before = the 25-run baseline (premise evidence; leg + `Run e2e` step, jobs API) AND the same
metrics over the 5 named baseline runs (like-for-like with the >= 5 after runs), plus the per-file weight table. After = the first 5 counting CI runs of the PR head (one at a time: wait for each to finish, then
`gh run rerun`), same metrics via the GitHub API, recorded in `profile.md` in this change with run ids/attempts. Full
logs kept for any failing run. Target (AC2 restated by owner ruling, 2026-10-07): imbalance = slowest leg's median
`Run e2e` step minus the mean of the four legs' medians; after <= 15 s and below the before-25 value (25.5 s), with a
same-window control (below) — three explicit pass/fail lines. Estimator: median-first (per-leg median over the
set, then max minus mean); the per-run estimator (max minus mean within each run, then median) is reported beside it for
honesty but is not the bar.
- **Counting rule:** a run counts only if all 4 `e2e (N)` legs concluded `success` and all 4 `playwright-json-shard-N`
  reports were downloaded; others are recorded with logs (C2) and excluded from every set. Reruns are always full
  `gh run rerun <id>` (never `--failed`, which leaves earlier-attempt artifacts on untouched legs).
- **Fixed after set:** the FIRST 5 counting runs of the regenerated-table head, in order. No extra runs added or
  substituted. If any pass/fail line fails, profile.md reports it as not met and the orchestrator escalates.
- **Control:** ALL qualifying control runs — `ci.yml` runs on OTHER heads that contain the origin/main commit merged in task 3.1 (the
  merge's second parent; SHA recorded in profile.md; inclusion decided per head by `git merge-base --is-ancestor`,
  recorded) and still use count-based `--shard`. Each qualifying run contributes its FIRST attempt that meets the counting
  rule, timed by that attempt's `run_started_at` (GitHub API `actions/runs/<id>/attempts/<n>`). The control is every such
  attempt whose `run_started_at` lies between the first and last after attempt's `run_started_at`; if fewer than 5,
  extend backwards in `run_started_at` order to 5; escalate only if fewer than 5 exist at all. Every included and
  excluded run id/attempt is recorded in profile.md; no subset selection. Same estimator. If (a)/(b) pass but (c) fails, profile.md says the improvement is not distinguishable
  from old sharding in this window.
- **Before:** the 25-run before-25 baseline (profile.md states that all 25 runs have all 4 JSON artifacts, so they are
  counting runs) (pre-merge code) is the named "before" in the spec; the before-5 (42.5 s) is
  history only. Absolute leg time is dominated by ~170 s
of non-test overhead and apt install spikes — out of scope, HEL-1368.

**D9 — Post-merge weight regeneration (C1).** After merging origin/main (HEL-1330/1363/1366/1331 touched nearly every
spec and added `hel1331-history-payloads-toggle.spec.ts`), the table is regenerated only from CI runs of code that
contains those changes: the first 5 COUNTING attempts of this PR's merged head (download each attempt's
`playwright-json-shard-N` artifacts immediately after it completes — a rerun overwrites them). Each report is
authenticated to its attempt by content: its `stats.startTime` is recorded in profile.md beside that attempt's jobs-API
`Run e2e` step `started_at` and must agree within the ~5 s `--list` lead. `weights` mode is hardened to refuse a runDir
that does not hold exactly the expected number of shard reports, or any report whose `stats` is missing or has
`unexpected > 0` (naming runDir and shard), so an incomplete run cannot feed the table
silently. Then `weights <runDir>...` over those 5 runs, commit, and measure >= 5 fresh after runs of the new head. The first measurement (run 37676655366,
pre-merge) stays in profile.md as history.

## Risks / Trade-offs

- [Two `--list` passes per leg add seconds] → measured at ~5 s per leg in run 37676655366; reported in profile.md.
- [Weights go stale as specs change] → unknown = median weight keeps new specs running; the regenerate command is
  documented in the script header and e2e/README.md.
- [Leg-max tail stays high from apt install spikes] → explicitly out of scope; reported in the after maxima.
- [Re-list mismatch from regex collisions] → anchored args + equality check fail loudly instead of mis-running.

## Gate-Chain Implications Checklist

This change adds `npm run check:e2e-shard:selftest` (`node scripts/e2e-shard.selftest.mjs`) as a line in
`.husky/pre-commit`. Isolation transcript: `test-gate-in-isolation.sh HEL-1361 scripts/e2e-shard.selftest.mjs
check:e2e-shard:selftest` -> `PASS` (evidence under `.concertino/runs/HEL-1361/evidence/.concertino/gate-chain-isolation-evidence/`).

- **What does it execute?** `node scripts/e2e-shard.selftest.mjs`: pure-function unit cases of
  `scripts/e2e-shard.mjs` (LPT, exact-partition checks, regex anchoring, weights-report guards on in-memory report
  objects) plus one child `node` spawn of the CLI (`run 5 4`) that exits at argument validation. It never starts Playwright, a server or a browser, and
  never runs `git`.
- **What environment does it inherit, and from where?** Git's hook environment (`GIT_DIR`, `GIT_INDEX_FILE`, and
  `GIT_WORK_TREE` where set) plus the user's `PATH`/`HOME`. The selftest reads none of the `GIT_*` variables and
  runs no git command, so an inherited `GIT_DIR` from a linked worktree cannot redirect it. The isolation run
  exercised exactly that shape (`GIT_DIR`/`GIT_INDEX_FILE` pointing at a linked-worktree gitdir).
- **Does it write anything outside its own sandbox?** No. It imports `scripts/e2e-shard.mjs` and builds its
  report fixtures in memory; it creates no files at all, so nothing is written to the repo, the index,
  `e2e/shard-weights.tsv` or `test-results/`.
- **Does it behave differently from a linked worktree than from a main checkout?** No. It resolves paths from
  `import.meta.url` relative to the script, not from `git rev-parse` or the cwd's `.git`; the isolation test ran it
  from a `git worktree add` fixture and it passed, as it does from this linked worktree and from the main checkout.
- **What happens on its first run?** Nothing is created or cached: no state file, no baseline. It runs the 15 cases
  and exits 0 (15 passed in the isolation transcript), or non-zero naming the failing case. The commit is blocked only
  on a genuine failure.
