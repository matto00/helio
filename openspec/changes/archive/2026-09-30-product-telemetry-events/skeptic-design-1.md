### Change Requests
1. Decision 3 is incoherent; rewrite it. Specify ONE final table set, each with columns, PK and exact derivation: (a) `product_event_daily(day,event,event_count,active_users)`; (b) DAU/WAU either as two columns on ONE `product_active_users_daily(day, daily_active_users, weekly_active_users)` (trailing 7 days ending that day, distinct users across all events, computed from raw rows at rollup time) - delete the "DAU ... NOT possible ... so store" stream-of-consciousness; (c) `product_ttfd_daily`; (d) `product_event_property_daily`; (e) `product_rollup_state`. Define: median/p90 method (percentile_cont vs disc; state which, since the AC requires hand-computed values), histogram bucket bounds and JSON shape, units. Also state that recomputing WAU for a day >= 7 days old after purge is impossible and therefore rollupDay for old days never overwrites existing weekly values from partial data (see 4).
2. `product_event_property_daily`: the spec's "Daily rollups" requirement never mentions it or WAU; add requirement text + scenario (template counts survive purge). Bound cardinality: `firstrun_template_chosen.template` is only a regex slug (`^[a-z0-9-]{1,40}$`), so any user can mint unlimited distinct values into a permanent, unpurged table. Either allow-list template slugs in the registry (and CHECK/test equality) or cap/bucket to "other". Name exactly which event/keys are rolled up (provenance_opened.variant, firstrun_template_chosen.template; not panelCount/source) and the PK.
3. Privileged-pool grants: do not rely only on V38 default privileges. Add explicit idempotent `GRANT SELECT, INSERT, UPDATE, DELETE ON <each new table> TO helio_privileged` (V105/V102 precedent; V38 defaults apply only to the migrating role's objects and the repo already had one silent gap, V102). Also make the scratch-DB task (1.1) explicitly run as a non-BYPASSRLS LOGIN role that SET ROLEs helio_privileged, exercising rollup + purge on the privileged pool, not just the insert/cross-user select. Design.md wrongly says the rollup tables have "no grant path for the app pool": the app pool role OWNS them (V91 header), so it can read/write them; correct the claim and state the consequence (aggregate data, no user id; acceptable; HEL-1211 must use privileged/owner-tier read).
4. Purge-safety/idempotency holes:
   a. Multi-instance (Cloud Run max-instances 2): two ticks can run delete-then-reinsert for the same day concurrently, yielding PK violations or lost rows. Require `pg_advisory_xact_lock` (existing precedent in PipelineRunRepository) or INSERT ... ON CONFLICT DO UPDATE in rollupDay and for the hourly purge throttle, and a test or reasoning for it.
   b. Purge gate is "day <= high-water-mark", but the tick recomputes today and yesterday only. State the invariant: a day is added to HWM only once it is older than the clamp window (occurredAt >= now-24h plus flush delay), so no late row can land in an already-HWM'd day; purge 90 days out makes this safe but the spec must say it. Also: rollupDay on a day whose raw rows were partly purged (e.g. after a HWM reset/recompute) must not clobber rolled data; define this.
   c. TTFD: a signup_completed row is purged at 90 days, so a user whose first dashboard comes after day 90 is silently excluded, and a cleared-localStorage re-emit after the first_dashboard_rendered row is purged passes the unique index (dedupe is bounded by the window). Decide and state: exempt these two event names from purge, or accept and document the bias and the re-emit double count (and exclude it from TTFD/event_count).
5. Public provenance variant: `ProvenanceVariant` includes "public" (unauthenticated share view), but POST /api/events requires auth, so public opens can never be recorded and would 401 on each open. Decide: skip client tracking when unauthenticated and drop "public" from the server enum (and state provenance_opened counts authenticated opens only), or justify otherwise. The spec scenario "Provenance open tracked" must match.
6. Task coverage gaps against ACs:
   - AC "Reproduce RLS as non-superuser": task 1.2 has cross-user isolation but no task to run the ROLLUP/PURGE path as the privileged role under a non-superuser login; add (see 3).
   - Task 2.3 must say the signup insert runs AFTER userRepo.insert commits, in `withUserContext(newUser.id)` (FK needs the committed users row), best-effort via recover.
   - First-dashboard server-side dedupe (spec scenario) has no explicit test task; add it to 2.2 (two posts -> one row, both 2xx) using bare/targeted `ON CONFLICT` matching the partial index predicate.
   - Add to 3.1 fixture: pre-ship user exclusion and negative-diff exclusion (spec scenarios), and to 4.3 the public/unauth no-emit case if 5 is resolved that way.
   - Task 1.1 must include adding the new tables to any test-harness TRUNCATE/grant lists that enumerate tables (harnesses grant on ALL TABLES so likely fine; state verified).
7. Minor: Decision 2 "executor must create ... NOLOGIN/LOGIN role" - say LOGIN (NOLOGIN cannot connect); Decision 4 "throttled by a stored timestamp" names no column - put it in `product_rollup_state`.
