### Change Requests
1. **D8 pre-merge measurement contradicts revised D7.** Under D7 a PR run never saves a compile entry, and no main-scoped entry exists before this PR merges, so every pre-merge PR run of the final head is a COLD compile (D11 itself says cold leg ~6.5 min), yet D8/6.2 require the slowest-leg median <= 5.0 min from >= 3 green PR runs, and D7 cites "the exact-hit rerun already measured" as the pre-merge warm timing. The 3.4-3.7 min result in run 37387080368 only exists because an earlier head saved a PR-scoped entry (refs/pull/773/merge) that this save-on-main-only design deletes the ability to reproduce. Revise D8/D7/tasks 6.2 to state the measurement protocol explicitly: which cache state each recorded PR run is in (cold / restored from a leftover PR-scoped entry), what pre-merge bound is required (cold-leg figure vs warm figure), and that the warm number is only provable post-merge on main. Do not let a leftover PR-scoped entry silently produce the "<= 5.0 min" evidence.
2. **Dependency-cache key widening is undecided and contradicted.** D7 says the sbt-<hash> key "keeps the key already on the branch", but the branch key differs from main's (`hashFiles('**/build.sbt', 'backend/project/build.properties', 'backend/project/*.sbt')` vs main's `hashFiles('**/build.sbt')`, which `security` and `e2e` still use). After merge that splits one shared ~911 MB entry into two (backend wide key, security/e2e narrow key), against owner scope 3 ("one shared entry per key", "do not change the key again unless required, say why"), and task 3.4 (unchecked) still says "cache key widened per D7". Either revert the backend key to match main's, or record in D7 why widening is required (restore-keys `sbt-` already falls back for plugin changes, so it does not obviously look required), and fix task 3.4's wording to match.
3. **C4 contradicts the owner scope additions.** Standing constraint C4 ("ci.yml edits confined to the backend job (and ci-complete needs)") is violated by D10 (workflow-level concurrency) and D11 (frontend/security/ci-complete timeouts). Amend C4 to name the owner-approved exceptions, and state the ownership/merge-order against HEL-1288 for the single workflow-level `concurrency:` stanza (HEL-1299's description says concurrency and timeouts are "being handled" in 1287/1288, so the risk is two PRs each adding the stanza).
