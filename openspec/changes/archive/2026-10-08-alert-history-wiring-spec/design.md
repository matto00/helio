## Context

`ApiRoutes` builds `alertEvaluationServiceOpt` (ApiRoutes.scala ~409-413) only when both `alertRuleRepo` and `alertEventRepo` are passed, and hands it `resolvedOutputHistoryRepo` (Main's instance, else one derived from `dbContext`). `PipelineRunService` then receives `alertEvaluationServiceOpt.orNull` and `outputHistoryRepo = resolvedOutputHistoryRepo`. `AlertEvaluationService.evaluateBaselineRule` skips with a warn when its history repo is null (AlertEvaluationService.scala ~130). Main passes `alertRuleRepo`, `alertEventRepo`, `outputHistoryRepo`, `nodePayloadHistoryRepo` explicitly (Main.scala ~243-278).

Existing coverage: `AlertEvaluationServiceSpec` (unit, deterministic exclusion proof), `PipelineRunServiceAlertBaselineSpec` (HEL-1278 seam: hand-built PipelineRunService, identical data across runs, so baseline == current), `NodePayloadWiringSpec` (HEL-1276/1334: composed ApiRoutes, payload/history routes only, no alert repos). None constructs `ApiRoutes` with alert repos.

## Goals / Non-Goals

**Goals:** a composed-ApiRoutes spec that is red when any of the three alert/history wiring edges in `ApiRoutes` is cut, and green on main; deterministic; distinguishes current-run exclusion from self-inclusion.

**Non-Goals:** re-testing baseline arithmetic, thinning (HEL-1285), retention (HEL-1272), payload wiring (HEL-1334), or `rolling_avg` semantics beyond what's needed. No production changes.

## Decisions

**D1 — Construction mirrors Main for the edges under test.** Construct `ApiRoutes` with the same positional args as `ApiRoutesPipelineRunGuardSpec`/`NodePayloadWiringSpec` plus `dbContext = ctx`, `alertRuleRepo`, `alertEventRepo`, and `outputHistoryRepo` (the test-only `ReadAfterWriteHistoryRepo(ctx)` subclass of D3b — a real `OutputHistoryRepository` with one read override), passed through the same param Main uses. The spec holds its own reference to that history repo only for read-back assertions; it must never construct `AlertEvaluationService` or `PipelineRunService` itself (that would bypass the wiring under test). Rationale: the test's value is exercising ApiRoutes' own composition.

**D2 — Drive runs through the real route; the response is sequenced after evaluation.** Runs are triggered with `POST /api/pipelines/:id/run` through the full `ApiRoutes.routes` tree (session cookie + CSRF header, as the sibling specs do). Verified at the design gate: the route returns `runService.submit`'s future; the success branch is `followUp = onRunSuccess(...)` then `followUp.map(...)`, and `writesChain` (PipelineRunService.scala ~1628-1636) awaits both `materializedWrites` and `alertEvaluation`, returned through `publishTerminalAfter` (~997-1003). So DB state read after `check { status shouldBe OK }` is final for that run. No `eventually`, no sleeps.

**D3 — Fixture.** Seed via SQL like the sibling specs: a user, a `dataset` data source, a pipeline + root, one enabled step, one Output bound to it (reuse `OutputHistoryFixtures` / `DatasetRowsTestSupport` / the seam spec's seeding pattern, WITH ONE DIFFERENCE: `amount` cells MUST be JSON numbers, e.g. `{"columns":[{"name":"amount","type":"integer"}],"rows":[[10],[20]]}`. The seam spec's string cells (`["10"]`) work for the baseline summary reducer but `extractMetric`/`numericValue` (AlertEvaluationService.scala ~45-52) treat every String as None, so a threshold rule would never fire.) Two alert rules on that Output:
  - Baseline rule: metric `amount`, `{"baseline":"previous","mode":"abs","comparator":"gte","threshold":<T>}` with a strictly positive threshold chosen so it breaches ONLY if the baseline is run 1's value. Example: run 1 rows sum to 30, run 2 rows sum to 100, threshold 50: exclusion → delta 70 ≥ 50 → fires; self-inclusion (baseline = 100) → delta 0 → does not fire. Verified at the design gate: `HistoryBaseline.summaryValue` uses the column `sum` for both current and baseline, so 30 → 100 with `gte 50` gives 70 (fires) under exclusion and 0 (does not fire) under self-inclusion.
  - Threshold rule: metric `amount`, a non-baseline condition that breaches on run 1 (e.g. `gte 1`).

**D3b — Force read-after-write ordering so exclusion is actually observable (test-only).** `materializedWrites` (PipelineRunService.scala ~1446) and `alertEvaluation` (~1565) are eager, concurrent futures (AlertEvaluationService.scala ~126-127 says the triggering run's point "may or may not be committed yet"). Without intervention, a broken exclusion would only show when run 2's history point happens to commit before `listRecent` reads — a race, so the `baseline == run1` assertion would be a probabilistic guard, not a proof. To make it deterministic WITHOUT a production change, the spec passes a test-only subclass `ReadAfterWriteHistoryRepo extends OutputHistoryRepository(ctx)` as ApiRoutes' `outputHistoryRepo` constructor param (the SAME param Main passes, so `resolvedOutputHistoryRepo` — and hence both AlertEvaluationService and PipelineRunService — get this instance; M1/M3 still cut exactly the production edges). Its only override is `listRecent(outputId, limit)`: when the test has armed it with an expected point count N for that output, it first waits until a count of `output_snapshot_history` rows for that output reaches N, re-checking the DB on a bounded schedule (Pekko `after`/scheduler, e.g. 20ms interval, hard cap ~5s; on timeout it fails its own future) — a wait on an observable DB condition, never a fixed sleep standing in for it. Then it delegates to `super.listRecent`. Armed with N=2 before run 2, this forces the "run 2's own point is visible to evaluation" side of the race every time, so self-inclusion deterministically yields baseline 100 / delta 0 / no event, and exclusion yields baseline 30 / delta 70 / one event. Unarmed (N unset), it is a pure pass-through. **A timeout is NOT loud on its own**: the per-rule `.recover` in `AlertEvaluationService.evaluateForOutput` (~:110-118) and `PipelineRunService`'s `recoverWith` (~:1590) swallow it, the run still returns 200, and the symptom (no baseline event) is identical to M4's self-inclusion red. So the subclass MUST record every armed wait's outcome (thread-safe counters or a concurrent list: `satisfied` / `timedOut`), and the spec MUST assert, before any alert-event assertion for run 2, that at least one armed wait was satisfied and zero timed out (fresh counters per armed run). Only evaluation-path waits count: the spec disarms the repo (N unset) before any `GET /api/outputs/:id/history` read, or otherwise ensures the GET-history read never enters the armed wait. Deadlock check: `materializedWrites` does not depend on `alertEvaluation` (both start eagerly), so waiting inside `listRecent` cannot block the write it waits for — executor must confirm this from the code before relying on it. If the executor finds `listRecent` is final/not overridable, or the write genuinely depends on evaluation, stop and report rather than improvising.

**D4 — Data changes between runs.** After run 1, replace/append the dataset rows (direct SQL via `DatasetRowsTestSupport`, or the real dataset rows write route if simpler) so run 2's value differs. Note: if the executor uses a route that triggers HEL-1093 dataset-write auto-run, either it is not wired in this construction (no `autoRunDebounceRepo`) or it must be accounted for; prefer direct SQL to keep exactly two runs.

**D5 — Assertions.**
  - After run 1: a history row exists for the Output (read via `GET /api/outputs/:id/history` through the same route tree); threshold rule has an active firing event; baseline rule has NO event (no prior point).
  - After run 2: baseline rule has exactly one `alert_events` row (counted per rule id — the threshold rule's event is upserted, not duplicated, and must not be counted with it), with `pipeline_run_id` = run 2's id and value `{"value":100,"baseline":30,"delta":70,"mode":"abs"}` (compare via JsNumber/BigDecimal as the seam spec does). History has 2 points.
  - What this proves: the wiring edges (M1-M3, deterministic). The `baseline == 30` assertion is a current-run-exclusion check ONLY because D3b forces read-after-write; its strength is reported as the measured M4 red rate (D6), not asserted by narrative. The unit-level deterministic exclusion proof remains `AlertEvaluationServiceSpec` (~:420/:433/:446). If M4 is not 5/5 red, the evidence file and PR must say exactly what the measured rate is and must not describe the assertion as an exclusion proof (C1).

**D6 — Mutation proof (required evidence).** Executor applies each mutation to `backend/src/main/scala/com/helio/api/ApiRoutes.scala` in the worktree, runs ONLY this spec via `sbt "testOnly com.helio.api.ApiRoutesAlertHistoryWiringSpec"`, records the failing assertion, and reverts (confirm `git diff --stat` on ApiRoutes.scala is empty afterward):
  - M1: `new AlertEvaluationService(ruleRepo, eventRepo, resolvedOutputHistoryRepo)` → `new AlertEvaluationService(ruleRepo, eventRepo)` (history repo unwired; the ticket's required red). Expected: baseline assertion red, threshold still green.
  - M2: `alertEvaluationServiceOpt.orNull` → `null` in the PipelineRunService construction. Expected: threshold + baseline red.
  - M3: `outputHistoryRepo = resolvedOutputHistoryRepo` → `outputHistoryRepo = null` in the PipelineRunService construction. Expected: history-row assertion red.
  - M4 (measurement, not a required red): drop the `filterNot` that excludes the triggering run at `HistoryBaseline.scala` ~97; run the spec 5x; record how many runs go red (expected 5/5 with D3b); revert. If 0/5, state plainly in evidence + PR that AC3's distinction is not observable at this layer without a production change and escalate to the orchestrator (production changes need driver approval).
  Every M4 red run's transcript must show the D3b precondition held (satisfied ≥ 1, timedOut = 0) — a red caused by a timed-out wait is not evidence of anything. Under M3 the armed wait is expected to time out (no history written); note that in the M3 transcript (the precondition assertion itself will be the red there, which is fine — it is still red).
  For M2, confirm the red is an assertion failure (not a compile error) and paste the failing assertion line.
  Transcripts (command + failing assertion lines) go into a committed evidence file in the change dir (e.g. `mutation-evidence.md`) and are summarized in the commit message/PR.

**D7 — Determinism.** No `Thread.sleep`, no `eventually`. D3b's bounded condition wait is the only wait; its timeout is swallowed by production recover layers, so its outcome is recorded and asserted as a precondition (satisfied ≥ 1, timedOut = 0) rather than relied on to fail the test. History ordering: with correct code, exclusion is by run id so the prior point is unambiguous; with broken exclusion, D3b guarantees the triggering run's point is present. If `captured_at` ordering of the two points could tie and change which point `listRecent` returns first, the executor must confirm it does not affect the outcome (e.g. limit k+1 = 2 returns both) and document it. Run the spec at least 3 times consecutively green (nice -n 19) and record it.

**D8 — Test residue.** Embedded Postgres per spec (as siblings) — no shared dev DB writes, so no residue ids to record. Never use matt@helio.dev; the seeded user email is a `@test.local` address.

## Risks / Trade-offs

- Concurrency of history write vs. evaluation → handled by D3b; residual risk reported via M4's measured rate.
- D3b adds a test-only subclass of a production repository. It overrides one read method and is pass-through when unarmed; it does not alter which instance ApiRoutes wires where.
- The spec duplicates some seeding from sibling specs; acceptable for a test-only ticket — prefer reusing existing fixtures over adding a new shared helper.
