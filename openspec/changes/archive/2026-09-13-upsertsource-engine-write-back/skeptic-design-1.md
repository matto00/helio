## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed HEAD 0cc7aef797be23b6358266daf9a96f3b96f9b7ff. Artifacts: ticket.md, proposal.md, design.md, tasks.md, specs/pipeline-upsertsource-{config,execution}/spec.md.

### What I verified (with evidence)

1. **D3 apply point / ordering: sound.** `PipelineRunService.executeRun` (PipelineRunService.scala:872-1011): `Success` goes to `onDryRunSuccess` (isDry) or `onRunSuccess` (:1055). `onRunSuccess` computes `blockingFailures` and branches to `onBlockedRun` (:1081) or `onUnblockedRunSuccess` (:1109). `onUnblockedRunSuccess` publishes `"succeeded"` as its FIRST statement (:1123), before any node-snapshot write. So applying writes in between (after the block check, before `onUnblockedRunSuccess`) is the only point that keeps "succeeded" from going out before the commit, and it also skips dry runs and blocked runs. The Failure branch (:927-962) is a real template for the bookkeeping. A sibling-lane failure makes `runFuture` fail, so it never reaches Success. Previews (`previewStep` :322, `previewAtNode` :432) do not go through `onRunSuccess`, so a default, never-read sink never writes. Confirmed.
2. **D4 MVCC: sound, and the test can fail.** `replaceRows` (DataSourceRepository.scala:423-465) does lock, then `delete`, then `++=`, all inside one `ctx.withUserContext(...)`, which is `db.run(... .transactionally)` (DbContext.scala:50-51). Under READ COMMITTED, a single-statement reader on another connection sees only committed snapshots. Task 3.10's mutation (split the transaction) would actually turn 3.3 red, so the test is not vacuous. There is one caveat on the reader, see note N1.
3. **D5 cross-tenant: sound.** `withUserContext(owner)` sets the GUC on the app pool, never `withSystemContext`/privileged (DbContext.scala:53-64). `data_sources` and `dataset_rows` are FORCE RLS (V106:155-156). `lockSource`/`schemaColOpt` return nothing for a foreign id, which gives `None` (not found), at DataSourceRepository.scala:357, 437-440. The scheduler already submits as `AuthenticatedUser(pipeline.ownerId, System)` (PipelineSchedulerService.scala:110). Re-resolving through `findByIdOwned(target, owner)` before writing closes the "persisted by another path" case.
4. **HEL-1101 cycle guard on D1 paths: covered.** `cycleCheckForUpsertAction` (PipelineStepRepository.scala:53) is wired into `insertInternalAction` (create, PipelineService.scala:573), `spliceInsertAtInternal`/`attachTailInternal` (addStep, :1850-1952), `updateInternal` when `config.isDefined` (:454, called at PipelineService.scala:2057) and duplicate (:2205). Each passes the caller's `actingUserId`. It short-circuits on `kind != "upsertsource"` and on `NewSource`.
5. **D6 validator semantics match the claim.** `DatasetRowValidator.validateRow` treats `JsNull` as missing, then applies default, then `required` (DatasetRowValidator.scala:117-135), so "absent column becomes JsNull" works as designed. The 500 cap is `DataSourceService.staticMaxRows` (private val, DataSourceService.scala:64). Append's cap counts existing plus new rows (DataSourceRepository.scala:388).
6. **D9 frontend fallback: premise real, names wrong.** `?? OP_TYPES[0]` exists at `frontend/src/features/pipelines/state/stepNarrowing.ts:251`, but the function is `pipelineStepToStep` (:247). There is no `fromPersisted` anywhere in `frontend/src` (grep: 0 hits). The config PATCH is sent from `hooks/useStepCardState.ts:211` (`updatePipelineStep`), not from `StepOpEditor.tsx`. `StepOpEditor` dispatches on `step.opType.id` (StepOpEditor.tsx:98+). `pipelineStepToStep` has a second consumer, `utils/proposalLaneGraph.ts:50`.
7. **D10 enumeration sites (sample found by grep):** `PipelineAnalyzeService.scala:454` pass-through arm, `helio-mcp/src/tools/write.ts:375-377` (op list in the tool description), `frontend/src/features/pipelines/types/pipelineStep.ts`, `stepNarrowing.ts`, `StepOpEditor.tsx`. The registry is the single backend allow-list (PipelineStep.scala:205, `PipelineStepKind.All` :274).
8. **D7 transaction and pool claim: NOT sound as written** (see CR1). `updateInternal`, the only cycle-guarded step-config update, runs as `ctx.withSystemContext(action.transactionally)` (PipelineStepRepository.scala:463), a separate privileged-pool connection returning a `Future`. `cycleCheckForUpsertAction` is `private`, and its doc assumes "this whole DBIO runs on the BYPASSRLS privileged connection" (:49-51). `applyWriteBacks` runs on the app pool through `withUserContext`. One transaction cannot span both pools.

### Verdict: REFUTE

### Change Requests

1. **D7: specify a step-config rewrite that really is in the same transaction and cycle-guarded.** As written, "update the step row's config ... under the same owner context ... through PipelineStepRepository's cycle-guarded update action" is not implementable. `updateInternal` is a privileged-pool `Future`, so using it makes the rewrite a second commit, which breaks "rewrite ... in the same commit" (spec, New-source requirement). design.md must name one of the following, with the reason:
   - (a) a new `private[persistence]` DBIO builder that runs the config update plus `cycleCheckForUpsertAction` (actingUserId = owner) inside the `withUserContext(owner)` transaction. It must also state that `pipeline_steps`' FORCE RLS policy (V35/V98) permits the owner's UPDATE under the GUC, verified in the RLS test (3.7).
   - (b) an explicit, justified exception.
   
   Whichever you pick, the rewrite must be a compare-and-set: lock the step row `FOR UPDATE` and check that its persisted config is still the same `NewSource` config the run evaluated. A user PATCH to the step between run start and commit must not be silently overwritten. Also define what happens when a second concurrent run (for example a manual run racing a scheduled one) finds the step already rewritten: write to that id rather than creating a second "Signups" dataset. Add a task and test for the race.
2. **D7 zero-row case is self-contradictory.** "Zero rows with a new-source target still creates an empty dataset with an empty declaration only if rows exist; with zero rows the step is a no-op" says two opposite things in one sentence. Pick one. Record it in the execution spec (the New-source requirement currently has no zero-row scenario) and add it to task 3.8.
3. **D9 / tasks 2.1-2.2 name code that does not exist.** Replace `fromPersisted` with `pipelineStepToStep` (stepNarrowing.ts:247). Move the "skip config PATCH" to where the PATCH is actually sent, `useStepCardState.ts:211`, and add a test there. State how `UNSUPPORTED_OP_TYPE` fits `OpType` (types/step.ts:15) without being added to `OP_TYPES`. Account for the `proposalLaneGraph.ts:50` consumer, which gets the same fallback.
4. **D1 pre-flight identity is unspecified for editor grantees.** `validateTargetOwnership(target, user, ...)` checks the *caller*, but D5 writes as the *owner*. So a grantee can add a step targeting the grantee's own dataset: it passes pre-flight, then always fails at run time ("data source not found"). HEL-1101's cycle check likewise uses the grantee's visibility, not the owner's. State whether the pre-flight (and the cycle check's actingUserId) resolves against `pipeline.ownerId` or deliberately against the caller, and add a spec scenario and test for the grantee-authored step.
5. **D3 Spark rejection site is unnamed.** `SparkJobSubmitter` is constructed in `Main.scala:145` and does its own terminal writes (see PipelineRunService.scala:1364 doc). Name the exact check point (service-level before `backend.execute`, or inside the submitter), and say whether it runs at submit time or at step-create time, so the "clear error" is testable. Task 1.6 has no location.

### Non-blocking notes

- N1: Test 3.3's reader should use the real row-read path (or a single `SELECT`). A reader that issues separate schema and rows statements outside a transaction can mix snapshots. That would be a test-harness artifact, not an implementation bug, so pin the reader shape in the task.
- N2: D10 can seed its audit with the concrete sites listed in item 7 above, especially the `helio-mcp/src/tools/write.ts:375` op list that HEL-1102 owns.
- N3: `staticMaxRows` is `private` in `DataSourceService`. D6's "passed through" needs it exposed or duplicated. Say which.
- N4: two `upsertsource` steps targeting the same dataset in one run: ordering by walk order is stated. A same-transaction relock is harmless. Worth one test.
