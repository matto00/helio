## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed HEAD 7e1df62a67ada4de6dd2499cbb5d84cec69e7dbb (planning artifacts untracked in the change dir).

### What I verified (with evidence)

- **CI arithmetic (driver claim): verified.** `results.json` in the failed-run artifacts: `C_lg_coords_everywhere ... failed 9795 ms`, message `light @1500 (md) P8 Divider right`, `Expected: <= 1478, Received: 1876`. Spec line 450 asserts `r.x + r.w <= container.x + container.w + 2`, so 1478 = 264 + 1212 + 2 (container x = 264 at 1500), and 1876 = 264 + 1612, the lg container's right edge. The lg fixture puts P8 at x=6,w=6, so its right edge is the container's right edge. The arithmetic holds.
- **The claim that the divider is special is not supported.** In `error-context.md` the page snapshot lists the grid articles in DOM order **P8, P7, P6, P5, P4, ...** (reversed). `readRects` returns rects in DOM order and the assertion loop (spec ~448) stops at the first failure. So P8 is simply the first item checked, and like P2/P4/P6 it sits at the 12-col right edge at lg. The failure tells us nothing about whether other items were stale too. The proposal ("fix the grid/divider render path") and design D2 ("e.g. a memoised divider") still frame this as divider-specific.
- **The container-width gate does not measure what the design says it does.** `.panel-grid` is RGL's `<Responsive className="panel-grid">` root (`frontend/src/features/panels/ui/grid/DesktopPanelGrid.tsx:349`). CSS sets its width, and it follows the viewport on the next reflow. RGL's own `width` prop is a different thing. It comes from `useContainerWidth` on `.panel-list__zoom-container` (`PanelList.tsx:76`). Per `frontend/node_modules/react-grid-layout/dist/chunk-BMN6M2VL.js:44-54` (v2.2.4), the path is ResizeObserver → **`requestAnimationFrame`** → `setWidth`, and only then does the item re-layout. So `settledRects`' `expect.poll(container.w).toBe(1212)` can pass before RGL has seen the new width. Two reads 150 ms apart (`page.evaluate`, which needs no frame) can then agree on stale geometry whenever frame production or rAF is delayed on a loaded headless CI runner. design.md's Context says "the container itself had already re-measured" and concludes that this "makes a pure animation frame race less likely and a stale-render (product) ... more likely". That inference comes from a misread of what the poll observes. It biases the investigation's prior toward a product bug.
- **The decision rule (design D2) has a misclassification trap.** It says that if the rect stays at old geometry "indefinitely (or until an unrelated event)", that means a product bug, and one listed example is "a width-provider that updates the container before the layout". But that ordering is exactly how RGL is designed to work (CSS width first, RO→rAF→state second). A stall that ends at "an unrelated event" is also the signature of rAF/frame starvation: a screenshot, an input, or the next frame would unstick it. Under D2 as written, an environmental or harness timing effect can be filed as a product bug, and C3 then forces a product change.
- **One proposed test-fix route is not available as written.** D2 suggests waiting on "RGL's current breakpoint/cols reflected in the DOM". `grep -rn "data-breakpoint\|data-cols\|onBreakpointChange" frontend/src` returns nothing, so no such DOM signal exists today. Adding one is a product-code change made for observability, and the plan does not scope or acknowledge it. The other route, "rects stable over a window derived from the measured lag", is a tuned settle window, which is the same kind of fix C1/AC4 forbid.
- **The ticket's ACs are otherwise covered.** AC1 → 2.1. AC2 → 2.2 (the candidate list matches the ticket). AC3 → 3.1. AC4 → C1. AC5 → D3/4.1, where (1−p)^N ≤ 0.05 is the right zero-failure bound. AC6 → 3.1. HEL-1300/HEL-1392 interaction is mentioned (design non-goal, task 2.2). C4 respected. No placeholders or TODOs.
- **Existing precedent the plan doesn't cite:** `e2e/support/settleTransitions.ts` (HEL-1288) already awaits a real rAF plus `getAnimations()` CSS transitions. Any test-side fix should reuse it or explain why it doesn't fit.

### Verdict: REFUTE

These are cheap revisions to make now. The current text points the executor toward the wrong prior and leaves a decision rule that can misfile an rAF/RO timing race as a product bug.

### Change Requests

1. **design.md Context: correct the premise.** State that `settledRects`' container poll reads the CSS box of `.panel-grid`, not RGL's `width` state. State that RGL's width arrives via ResizeObserver → rAF → setState (`react-grid-layout/dist/chunk-BMN6M2VL.js:44-54`; `PanelList.tsx:76`, observing `.panel-list__zoom-container`). Remove or recast the sentence claiming a frame race is "less likely". Add "rAF / frame-production starvation between the RO callback and RGL's re-layout" as an explicit, first-class candidate next to the ticket's "ResizeObserver timing".
2. **design.md D2: tighten the product-vs-test rule** so it turns on whether RGL actually received the new width, not on elapsed time. Classify as a **product bug** only if the probe shows RGL rendered with `width`≈1212 (md breakpoint/cols active) and an item still sits at lg geometry. If RGL's width/breakpoint had not yet updated, it is a measurement race (test-side), even when the stall persists "until an unrelated event". Delete "a width-provider that updates the container before the layout" from the product-bug examples, because that is RGL's normal ordering.
3. **tasks.md 2.2: make the probe able to separate those cases.** Record timestamps for the RO callback, the rAF callback and setWidth (or the `width`/breakpoint RGL renders with) alongside the divider rect series, plus `document.visibilityState` and whether rAF fires at all during the stale window. Without those, the "never updates vs. updates late" split can't tell a product stale-render from rAF starvation.
4. **tasks.md 1.1 / 2.2: record staleness for every item**, not just the divider. P8 failed first because of DOM iteration order (error-context.md shows P8 first). Name a divider-specific cause only if the probe shows the other items at md geometry while P8 stays at lg.
5. **design.md D2 test-fix options:**
   - Drop "rects stable over a window derived from the measured lag". It is a tuned settle window, which C1 forbids.
   - Choose between a causal frame/rAF-based wait (reuse or extend `e2e/support/settleTransitions.ts`, e.g. await rAF ticks before the stability check) and a product-side observability hook (e.g. a breakpoint data attribute on the grid). The latter is a product-code change; if chosen, scope it explicitly in proposal Impact and add a unit test.
