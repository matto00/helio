A standing cycle among other nodes that `writeTarget` cannot reach can never produce a result. The tests tell the two cases apart:

### Non-blocking notes
- The CR3 timing test proves that the advisory-lock key serializes transactions. It does not go through the guard itself. That the guard depends on the lock rests on the documented one-time mutation run, which is not a test in the suite. That is acceptable under the round-1 wording, but a future refactor could remove `lockAction` from one guard action without any test failing.
- The update-exclusion filter removes every write edge for the pipeline that matches the old target. If the same pipeline had two upsertsource steps with the same target, both would be dropped during one step's update. That can only make the check less strict, only in that narrow case, and that path is not reachable until HEL-1100 lands.
