## Goals / Non-Goals

**Goals:** the desktop three-region layout; every step kind editable through one focused editor; per-step row counts on load (persisted) and after an in-session run; branches and extra sources visible and selectable; at 1280×800 spine + editor + ≥8 preview rows with no page scroll for a 3-step pipeline; accent only on Run, the selected step and focus; every existing affordance kept somewhere (nothing dropped); existing tests pass or are migrated with no lost assertions.

**Non-Goals:** draft mode, "Save & run", Discard-draft, the "live" marker, changed-row flash and the live Output render (HEL-1581; `docs/live-draft-preview.md`); the phone layout (HEL-1582: ≤768px keeps today's river view, untouched); the shell-wide "document never scrolls" guard on every route (HEL-1585 — we add the guard for this page only and report on the rest); changing step semantics or the run engine.

### D6 Selection model
Selected step id lives in the URL search param `step` (`replace`, so it does not spam history), coexisting with `?outputId=`: every write uses the functional `setSearchParams(prev => …)` form so one param never clobbers the other. Default: first step of root 0's trunk; none when there are no steps. A created step (add/insert/branch/duplicate/shape) becomes selected once its real id exists; removing the selected step selects its predecessor in the same lane, else the parent step, else the first step. An unknown `?step=` falls back to the default. Selecting a step updates the editor and the preview table (AC 2).

### D7 Focused editor (AC 1)
`StepCard` gains `variant: "card" | "focused"` (default "card": phone and existing tests unchanged). "focused": always expanded, no expand toggle, no chevron, no OutputsRail, no Preview button/tray, no drag handle/move buttons; header "Step <n> <label>" + markers; quiet text actions **Disable/Enable** (aria-label kept "Disable step"/"Enable step", `aria-pressed` kept), **Duplicate** ("Duplicate step"), **Remove** ("Remove step"); body = warnings region, validation/draft errors, `StepOpEditor` (every kind via the existing if-ladder, including unsupported read-only). The editor is keyed by `stepRenderKey(step)`. **No edit is lost on selection change:** `useStepCardPersist` gains an opt-in `flushOnUnmount` flag set only by `variant="focused"` (the phone card keeps today's clear-on-unmount: C4). With the flag, a pending debounced persist (400ms) is sent on unmount instead of cleared, **except** when the step is being removed: the focused editor's Remove cancels the pending persist before calling `onRemove`, and the flush is skipped when the step id is no longer in the page's steps. A flushed PATCH that fails (including a 422 for the `captureErrors` editors: cast, enum, fillnull/window/pivot, upsertsource) reports into a page-level `stepSaveErrors: Record<stepId, string>` (cleared on that step's next successful save): the spine row shows a save-error marker (icon + accessible name "Couldn't save the last change to this step") and, when the step is selected again, its editor shows the message in the existing `InlineError` position. Tests: edit then immediately select another step → PATCH sent with the edited config; edit then Remove → no PATCH; flushed 422 → row marker + message on re-select. The `creatingStepIds` guard (a step being created cannot be edited) is preserved as a disabled/"Saving step…" state in the focused editor.

### D8 Preview table
`StepPreviewTable` (new) for the selected step: fetches `fetchStepPreview(pipelineId, stepId)` on selection immediately and on the step's config fingerprint change with the existing 500ms debounce (logic extracted from `useStepCardPreview` into a shared hook, so the phone tray and the desktop table run the same code; the localStorage `previewOpen` gate does not apply to the table). Header: "Rows after step <n>" + "<rowCount> rows" (mono) + `StepSchemaDiffChips` + output-schema chips (`getAnalyzeOutputSchema(stepId)`, `OutputSchemaDisclosure` above the existing threshold — moved from the footer). Columns: `DataGrid variant="preview"` with header cells "name" + mono type from the analyze output schema (type omitted when analyze has no entry). States: loading (skeleton rows), error (`role=alert`, existing copy; a `STEP_CONFIG_INVALID` rejection renders its named reason exactly as today's tray does via `previewErrorMessage`, per `pipeline-step-preview`), empty ("No rows to preview."), disabled step ("This step is off, so rows pass through unchanged." and no fetch), creating step (no fetch). No "live" marker (DESIGN §11 reserves it for draft-recomputed surfaces). Sticky header, internal scroll. **Boot bound:** the table issues exactly one step-preview GET for the initially selected step per page open, also under StrictMode: requests go through a page-scoped **in-flight-only** dedupe keyed by `stepId + configFingerprint`: a second request for a key whose request is still in flight joins it (enough for StrictMode's double effect); a settled response is never reused, so every selection (including re-selecting a step after editing an upstream step, whose own fingerprint does not include upstream config) fetches fresh. **Save ordering:** the preview GET for a newly selected step waits until every pending step save has settled (the D7 unmount flush of the previously selected step, and any other in-flight step write tracked by a page-level pending-saves promise set: config saves from `useStepCardPersist` and the enable/disable save `updatePipelineStepEnabled`, both of which change what the preview returns; the unmount flush registers with the tracker synchronously in its cleanup), so the rows always reflect the saved upstream config; while it waits the table shows its loading state. Tests: (a) select step 3, edit step 1, re-select step 3 → a new GET is issued and its rows render; (b) edit step 1 then immediately select step 2 → the step-2 GET is sent only after step 1's PATCH resolves; (c) StrictMode open → one GET.

### D9 Per-step row counts persistence (owner ruling `persist-last-run-counts`)
Follow the V104 precedent. **V135** (next free: origin/main ends at V134, no lane claims V135; re-checked before merge): `ALTER TABLE pipeline_runs ADD COLUMN step_row_counts JSONB NULL; ALTER TABLE pipelines ADD COLUMN last_run_step_row_counts JSONB NULL;` — NULL means "not recorded" (no backfill). The run row and the pipeline row are two separate writes today; each new column is written **in the same statement as its sibling**: `pipeline_runs.step_row_counts` with the run row's `row_count` (`updateRunTerminal`/`updateRunTerminalInternal`), and `pipelines.last_run_step_row_counts` with `last_run_row_count` (`updateLastRun`/`updateLastRunInternal`), exactly as `last_run_truncated` already is.

Every writer, and what it writes (mirrors `row_count`/`last_run_row_count` exactly):

| Path | `pipeline_runs.step_row_counts` | `pipelines.last_run_step_row_counts` |
|---|---|---|
| Succeeded run (`PipelineRunTerminalWrites` succeeded path, owner `updateLastRun` and editor `updateLastRunInternal`) | the engine's `stepCounts` | the engine's `stepCounts` |
| Execution failed / write-back failed / blocked (`PipelineRunTerminalWrites` ~:117, ~:202, ~:235) | NULL | NULL |
| `PipelineRunService.scala:254` (failed before execution) | NULL | NULL |
| Spark paths (`SparkJobSubmitter` ~:88, ~:112) | NULL (no per-step counts from Spark) | NULL |
| Reaper raw SQL (`PipelineRunRepository.scala:404`) | NULL | NULL (added to its `SET`) |
| Dry run (`onDryRunSuccess` → `insertDryRun`/`insertGranteeDryRun`) | NULL (not plumbed; the in-session dry run's counts are shown from redux instead) | untouched (dry runs never call `updateLastRun`, so `last_run_row_count` is untouched too) |

The executor verifies each line number against the tree and adds any further `last_run_row_count`/`row_count` writer it finds with the same rule. Plumbing: `stepCounts` is threaded from `PipelineRunExecutor` (`:290-296`) through `onRunSuccess` → `onUnblockedRunSuccess` → `writeTerminal`/`updateRunTerminal(Internal)` and `writeLastRun`/`updateLastRun(Internal)`.

**User-visible consequence (accepted under the AC's "latest run"):** after a failed latest run, a reload shows "—" for every step until the next successful run, just as "Rows written" is blank today; an in-session dry run's counts still show.

`PipelineSummary`/pipeline response gains `lastRunStepRowCounts: { [stepId]: number } | null`; the JSON schema under `schemas/pipelines/` is updated in the same change. Frontend: `stepRowCount(stepId) = runStepRowCounts?.[stepId] ?? currentPipeline.lastRunStepRowCounts?.[stepId] ?? null`; ids of removed steps are ignored; steps added after the run show "—"; disabled steps show "off".

RLS: no new policy; `pipeline_runs` (V35 indirect-owner policy) and `pipelines` policies cover the columns. Proven with the existing non-BYPASSRLS fixture (`TwoUserRlsApiFixture.scala`): the owner run path (`updateLastRun`, RLS-enforced) and the editor-grantee run path (`updateLastRunInternal`) both write the counts; the owner reads them; a non-owner/non-grantee reads no row. Fail-first: the spec is shown red before the write is wired.

- **Header width at 820–1100px:** truncation rules in D3; verified at 820 in screenshots.
