### Change Requests

1. **D3 / Migration Plan / task 3.1 misdescribe `boundPipelineStepSchema`'s actual location — the "add one `export` keyword" plan does not work as stated.** Read `helio-mcp/src/tools/write.ts` in full: `export function registerWriteTools(server: McpServer, api: HelioApi): void {` opens at line 39 and the matching closing `}` is at line 928. `const boundPipelineStepSchema = z.object({ type: z.string().min(1), config: z.record(z.unknown()).default({}) });` sits at lines 535-538 — *inside* that function body, not at module scope. `export` is only a legal modifier on a top-level module declaration; it cannot be applied to a function-local `const` (attempting `export const boundPipelineStepSchema = ...` in place, as design.md D3 ("now exported") and tasks.md 3.1 ("add `export` to `boundPipelineStepSchema`") literally instruct, will not compile). The design's Migration Plan claim — "no existing tool touched beyond the one `export` keyword" — is factually wrong about the current file structure.
   **Required revision:** correct design.md D3 and tasks.md 3.1 to specify the actual mechanical step: hoist the `const boundPipelineStepSchema = z.object({...})` declaration out of `registerWriteTools` to module top-level scope as `export const boundPipelineStepSchema = ...` (it closes over nothing — no reference to `server`/`api`/other locals — so this is still safe and behavior-preserving for `create_bound_panel`, which continues to reference the same binding), then import it from the new `pipelineProposal.ts`. This is a small fix, but as currently written the task instructs an operation that doesn't type-check, and a competent implementer following it literally will stall on a compile error the design should have caught.

2. **Task 6.3 cites a call-routing test precedent in `write.test.ts` that does not exist, and the design never addresses how these tests avoid the TS2589 failure mode D4 goes out of its way to avoid for the warnings module.** Task 6.3: "Add a thin call-routing test per tool (mirrors `write.test.ts`'s pattern for verifying a tool calls the right `api.*` method) confirming `analyze_pipeline_proposal` calls `api.analyzePipelineProposal` and `apply_pipeline_proposal` calls `api.applyPipelineProposal` ... and that a rejected `api.*` call surfaces as `isError: true`." I read `write.test.ts` in full (17 lines + the `describe` block): it tests only `buildUpdateMetricBody`, a pure function imported from `metricSchemas.ts` — it never imports `write.ts`, registers a mock `McpServer`, or invokes any tool handler. No file anywhere in `helio-mcp/src/**/*.test.ts` (`context.test.ts`, `proposal.test.ts`, `write.test.ts` — the complete set) does this either. There is no existing "call a registered tool's handler and assert on its `api.*` call / `isError` shape" pattern in this codebase to mirror.
   To actually exercise `analyze_pipeline_proposal`/`apply_pipeline_proposal`'s handler logic (call the right `api.*` method, surface `isError: true` on rejection), a test needs the handler function reachable — which means importing `pipelineProposal.ts` (or `index.ts`, which imports it transitively). `pipelineProposal.ts` will both call `server.registerTool(...)` three times *and* import `boundPipelineStepSchema` from `write.ts`'s zod-schema surface (which `metricSchemas.ts`'s own docstring calls "pathologically expensive to type-check under this repo's root `tsconfig.json`/ts-jest combination ... reproduced against `write.ts` unmodified on `main`"). That is precisely the combination (`registerTool` calls + a big Zod object type in the import graph) design.md D4 identifies as TS2589-triggering for the *warnings* function — and D4's whole reason for splitting out `pipelineProposalValidation.ts` was to keep that one function testable without pulling in that combination. Task 6.3 asks for a second kind of test (call-routing, not pure-function) against the *same* file, with no equivalent extraction plan and a false claim that a working precedent already exists.
   **Required revision:** design.md must specify how `propose_pipeline`/`analyze_pipeline_proposal`/`apply_pipeline_proposal`'s call-routing behavior gets covered by a unit test that does not import `pipelineProposal.ts` (e.g., extract each handler's body — the `guarded(() => api.analyzePipelineProposal(proposal))` / `guarded(() => api.applyPipelineProposal(proposal))` calls — into small exported functions in a non-`registerTool`, non-full-Zod module that a test can import directly, mirroring D4's `pipelineProposalValidation.ts` split), or provide verified evidence that importing `pipelineProposal.ts` from a jest test in fact does *not* hit TS2589 (e.g., because its own Zod surface is smaller than `write.ts`'s — not demonstrated anywhere in the current design). The ticket's own Scope section requires this test ("Tests: MCP unit tests ... that each tool calls the right endpoint and surfaces errors"), so dropping it is not an acceptable resolution — the design needs a workable mechanism, not silence.

### Non-blocking notes

- `tasks.md` 4.1 lists five warning cases (a-e), but `specs/mcp-pipeline-proposal-tools/spec.md` only has explicit scenarios for four of them — there is no scenario for "neither `sourceId` nor `type` set" (design.md D4 item 3's "or neither" half, tasks.md 4.1(b)). Task 6.1 says tests will cover "all five warning cases," so this is just a spec.md completeness gap, not an implementation-blocking ambiguity — worth a one-line scenario addition for spec/tasks parity, but not required before execution starts.
- D3's phrase "it is the same DTO `add_pipeline_step`/`create_bound_panel` use" is slightly loose: `add_pipeline_step`'s `inputSchema` (write.ts:257-261) is a separately-inlined flat `{pipelineId, type, config}` shape, not a literal reference to `boundPipelineStepSchema` — only `create_bound_panel` actually uses that binding today. The underlying claim (both produce the same `CreatePipelineStepRequest` wire shape) is true; the wording just slightly overstates which tools share the literal zod object. Not blocking, but worth tightening now that finding 1 already requires touching this sentence.
