- **`backend.execute` cannot run over supplied rows (claim holds).** `InProcessExecutionBackend.scala:28-60` always calls `engine.loadRowsWithStats` for every root before `executeTree`. - **`trunkOfRoot` is pure (claim holds),** but it is an instance method on `PipelineStepRepository` (`:1308`), so `executeTree` still needs a repository instance. `rowToDomain` is private, but `domainOf(rows)` (`:343`) is a public, pure (kind, config) -> `PipelineStep` path. `companionFor` alone only yields an `Any` config, not a step.
- **Context reads (claim holds).** `ctx.dataSourceRepo` / `ctx.loadSource` / `ctx.aiClient` are used only in Join/Union/Lookup (`findByIdInternal` then `loadSource`), UpsertSource (`UpsertTargetCheck.checkExisting(..., ctx.dataSourceRepo)`, `UpsertSourceStep.scala:52`) and the two AI steps. The plan's three context replacements plus `resolveSecondarySource` therefore close every source-read and AI path, provided `upsertsource` is handled (see CR4).
- **A step failure aborts the whole walk.** In `executeTree` `loop` (`:458-475`), `evalNode(...).flatMap{...}` has no recovery, so the first failed step fails the returned Future and no later node evaluates. `evalOneStep` (`:276-282`) only wraps the error in `StepExecutionException`.
- **Limiter wiring (claim holds).** `ApiRoutes.scala:806-850` nests the routes as `pathPrefix("api")` > `requireCsrfHeader` > `rateLimitDirective.rateLimit()` > `confineScopedToken` > concat(auth / optionalAuthenticate / authenticate). Mounting the new route inside `authenticate` keeps CSRF and confinement. `RateLimitDirective.rateLimit` (`RateLimitDirective.scala`) has no exemption today. `rateLimitConfig` is a `private val ... = RateLimitConfig.fromEnv()` (`ApiRoutes.scala:297`), so specs cannot inject it. The comment at `:196-199` says so, and contrasts it with the injectable `pipelineRunGuardConfig` / `productTelemetryConfig`.
- **Route overlap.** `PipelineRoutes` uses `path(PipelineIdSegment / "<literal>")` and has no generic two-segment POST, so the new route has no fall-through collision. `PipelineIdSegment = Segment.map(PipelineId(_))` (`IdParsing.scala:18`).
- **Access under RLS (claim holds).** `findByIdShared` (`PipelineRepository.scala:75`) reads the row under system context and the grantee's grant under `withUserContext`. `findGrantRole` (`:186`) and `checkPreviewAccessInternal` (`:205`) both use `withSystemContext` and are read-only. No lock is taken, so the HEL-1629 lesson about locks matching zero rows does not apply. `checkPreviewAccessInternal` returns `NotAuthorized` for both viewer and stranger, so the earlier `findByIdShared` is what makes a stranger a 404. That ordering is sound.
- **Precedent for the HEL-1516 revoke test.** `Hel1516GranteeDriftPreviewSpec` revokes inside an overridden repository read placed between the first ACL read and the re-check. The draft path does no DB read between those two checks, so the plan has to name its own seam (CR5).
- **Caps.** `SourceSampleService.SampleMax = 1000` (`:96`). `application.conf` sets no `pekko.http`, so Pekko's default `max-content-length` is 8m. A 413-mapping precedent exists in `CsvUploadGate` (`CsvUploadDirectives.scala`). That gate also caps concurrent uploads, because "an upload buffers the whole body, so concurrency is what multiplies heap use". Prod runs 1Gi memory (`infra/deploy-backend.sh:112`) with `--concurrency=80` and `-XX:MaxRAMPercentage=75.0` (`backend/Dockerfile:46`), which is about 768 MB of heap.
- **Streaming and abort.** `HttpEntity.Chunked.fromData` plus `watchTermination` on disconnect already exist (`PipelineRunStreamRoutes.scala:45`, `PipelineRunRegistry.scala:117-119`), so the server can observe the cancel. But the design's `onNodeFrame: (NodeKey, Seq[Row]) => Unit` is synchronous and fire-and-forget. The walk never waits on the consumer, and pure steps over 1,000 rows take milliseconds (doc §6.1: about 6-9 ms per 500 rows). Without a gate the whole walk finishes before any client abort arrives.
- **Client pacing.** Doc §6.3 means sends to happen *during* a drag ("a continuous drag sends <= ~100 requests/min; unbounded 3/s would be 180"). D8 specifies a pure trailing debounce (350 ms) followed by the floor. With an edit every 16 ms, a trailing debounce never fires until the drag stops.
- **Cell codec.** `SampleRowJson.encodeValue` handles only null/Boolean/Int/Long/String/Double and throws `UnsupportedValue` on anything else. `PipelineRowJson` shows engine rows can also carry Float, BigDecimal and nested Map/Seq.
- **Cited files exist:** `frontend/src/services/csrfHeader.ts`, `features/panels/services/pipelineRunFanout.ts`, `testsupport/JsonSchemaValidation.scala`, `TwoUserRlsApiFixture.scala`, `SourceSampleSeamSpec.scala`, `sourceSampleWire.contract.test.ts`.

### Verdict: REFUTE

The architecture is sound. The `executeTree` seam, the context replacements, the shared-`PathMatcher` exemption mounted inside `authenticate`, and the access sequence all hold against the live tree. But D1 promises error behaviour the engine cannot produce. And several group-5 proofs, as written, cannot fail under the mutations they name, or cannot be built with the seams the plan provides.

### Change Requests

1. **D1/D2 contradict the engine on step failure (`InProcessPipelineEngine.scala:458-475`).** D1 and the "A failing step" scenario promise an `error` line, `downstreamOfUnavailable` for that step's subtree only, and the walk continuing to a `rows` line. `executeTree` fails the whole walk on the first step error, so sibling branches would never evaluate. The design must either:
   - add a further defaulted engine change (for example a per-node `onNodeError` that records the failure and prunes only that subtree's descendants and lane-dependents from `remaining`), or
   - redefine the contract: an error ends evaluation, and every not-yet-evaluated step gets a distinct reason such as `notEvaluated`, never `downstreamOfUnavailable` for steps that are not downstream.

   Either way, also fix D1's ordering sentence ("every `unavailable` line is emitted first"), which contradicts `downstreamOfUnavailable` lines that are only known after an error. Add a spec case with a failing step in one branch and an independent sibling branch.

2. **`rows` line target under planning (D1, D2).** `executeTree` computes `trunkTerminalId` with `trunkOfRoot` over the steps it receives (`:487-494`). Once the planner removes unavailable steps, `TreeWalkResult.rows` silently becomes the last *available* trunk step's frame, a different node from the one the client asked for. State that:
   - `rowsStepId` (default: the trunk terminal) is resolved over the full request step set;
   - the service takes rows from `nodeOutcomes(StepKey(rowsStepId))`, never from `TreeWalkResult.rows`;
   - if `rowsStepId` is unavailable or errored, the line is `{"type":"rows","step":null,"rows":[],"count":0,"truncated":false}` (or whatever is chosen, written down in the schema).

   Add a spec where the trunk terminal sits below an AI step.

3. **D7 caps: heap and expanding upstream frames.** I was asked to judge these.
   - **(a) Heap.** An 8 MiB JSON body is buffered and parsed to a spray AST, decoded to rows, and every node frame is kept in `nodeOutcomes`, on a roughly 768 MB heap with `--concurrency=80` and no in-flight bound. The per-principal rate limit does not bound concurrency. A few concurrent maximum-size requests, or aborted requests still holding parsed bodies, can exhaust heap. `CsvUploadGate` exists for exactly this reason. Either add an in-flight concurrency gate for draft-preview (taken after the limiter and before the body is read, `429` + `Retry-After`, with a default and an env var), or lower the byte cap and record a measured peak heap for a maximum-size request in evidence. Saying it matches `max-content-length` is not enough on its own.
   - **(b) 1,000-row frames.** That is the right cap for a *source sample*. But the `input` frame is the output of client-evaluated upstream steps (unpivot, splittext, join fan-out), which can legitimately exceed 1,000 rows from a 1,000-row sample. The design must say what happens then: either raise the per-frame row cap (the byte cap stays the memory bound), or have the client truncate to the head 1,000 and send `inputTruncated: true` so the counts are labelled. Do not leave it as a silent 413 that permanently blocks server preview for such pipelines.
   - **(c) Client pre-checks.** D8 pre-checks only the 8 MiB body size. Add client-side checks for every request cap: rows per frame, 8 secondary frames, 50 steps, 64-character ids. Report them as `tooLarge` with the cap named, so a cap violation never spends a request from the 120-request budget.

4. **`upsertsource` pass-through mechanism is unspecified (D3).** `UpsertSourceStep.evaluate` always runs `checkTarget(ctx)`, which reads `ctx.dataSourceRepo` (`:47-52`). It also fails when `ownerUserId` is `None`, which is what a draft context would pass. "Evaluated as a pass-through in draft mode" can be read two ways: a context flag, or replacing the step. Specify the exact mechanism. Recommended: `DraftPreviewService` replaces each `upsertsource` step with an identity step before calling `executeTree`, so step code needs no draft-mode branch. State whether it gets a `step` line. Make 5.6 failable: mutating the endpoint to apply the `writeBackSink` must turn it red.

5. **Proofs that cannot fail as written (tasks.md group 5; the header requires each to be "shown red by a named mutation").**
   - **5.5:** the named mutation (`requireEditor=false` -> viewer red) cannot reach. D6 already refuses a viewer at the owner-or-editor role check, before `checkPreviewAccessInternal`. Name the revoke seam: for example, a `PipelineRepository` subclass whose `findGrantRole` revokes the editor grant right after answering (the `Hel1516GranteeDriftPreviewSpec` seam-R pattern). Name a mutation that reaches: removing the re-check must turn the revoked-editor case red.
   - **5.1:** a "loader counter" that lives in the draft context is circular, because code that never uses the draft context also reads 0. Ground the never-read proof in observation that does not depend on the code under test:
     - a spying `DataSourceRepository` / loader passed to the engine, or content markers (the persisted primary and secondary sources hold rows different from the supplied frames);
     - a join with a persisted source secondary supplied with `complete: true` (the result must come from the supplied rows), plus one with `complete: false` (must be `unavailable` / `sourceNotSupplied`);
     - a mutation that actually reaches a read, for example the draft context's `resolveSecondarySource` delegating to the default, or the planner not marking `complete: false`.

     Swapping in the real `loadSource` does not reach: nothing in the draft path calls `loadSource`, because primaries arrive as `rootFrames`.
   - **5.8:** the abort spec is non-deterministic. The walk is not paced by the consumer and finishes in milliseconds, so "read first line, abort, steps evaluated < total" passes only by luck, or never does. Specify a deterministic seam, such as an injectable per-node hook in `DraftPreviewService` (test-only, defaulted to a no-op) that blocks after node 1 until the cancel flag is set (with a timeout). Name a mutation: removing the cancel check in `onNodeFrame` must turn it red.
   - **5.3:** "general limit set low" needs a constructor seam that does not exist (`ApiRoutes.scala:297` is `private val rateLimitConfig = RateLimitConfig.fromEnv()`). Add an injectable `rateLimitConfig` (default `fromEnv()`), and likewise for `DraftPreviewRateLimitConfig`, to task 3.4, or rewrite 5.3 to work at the default 120/120. Both limits default to 120, so the spec must also show *which* limiter produced the 429, for example by its distinct message.
   - **5.10:** under a pure trailing debounce, an edit every 16 ms produces one send, after the drag ends. "<= 100 sends, every gap >= 600 ms" is then vacuous, and a floor of 0 stays green. Doc §6.3 intends mid-drag sends paced at the floor. Specify `maxWait` (or leading-plus-trailing throttle) semantics so a continuous drag sends at the floor cadence, and assert a lower bound as well (for example >= 90 sends in 60 s). Name the mutations `floorMs: 0` -> red and `maxWait` removed -> red.
   - **5.4, 5.6, 5.7 (log sentinel), 5.9:** name the mutation for each. Examples:
     - 5.4: mount `DraftPreviewRoutes` outside `confineScopedToken` / `requireCsrfHeader` -> red.
     - 5.7: log the request body at DEBUG/INFO -> sentinel red.
     - 5.9: rename one line field in the Scala encoder -> seam red.

### Non-blocking notes

- **D2:** name `PipelineStepRepository.domainOf` (public, pure, `:343`) as the (kind, config) -> `PipelineStep` path. `companionFor` gives only the decoded `Any` config. Keep the 400 for each undecodable step: `rowToDomain`'s `Failure` arm maps to a sentinel that must be detected, not run.
- **D2 `contextOverride`:** make it a transform `PipelineExecutionContext => PipelineExecutionContext` applied to the engine-built context, not a replacement value. Otherwise the engine's `resolveLane` closure over the live `nodeOutcomes` (`:427`) is lost. A case-class field default cannot reference sibling fields, so model `resolveSecondarySource` as an `Option` field with a method fallback.
- **D2 `externalLanes`:** seed both `nodeOutcomes` and `evaluatedIds`, or `isReady` (`:453-455`) never fires for a step whose lane is external. Reject a `lanes` key that collides with a request step id (400).
- **D1:** say whether the response `rows` cells also use the lossless encoding (they should, because `wire.ts` decodes it). Check that every value type a server-evaluated kind can emit is covered by `SampleRowJson` (BigDecimal, Float and nested Map/Seq are not). An unencodable cell should be that step's `error`, not a whole-request `failed`.
- **D1:** several parentless steps all hang off the single `input` frame. Write down that the client must send one request per distinct input frame (sibling branches whose server steps have different upstream frames), so (e) does not merge branches.
- **D5:** an `exempt: HttpRequest => Boolean` predicate sees the absolute `/api/...` path, while the route's matcher runs after `pathPrefix("api")`. Evaluate the shared matcher against the unmatched path (a `RequestContext` predicate or a `Directive0`), or the "same `PathMatcher` value" guarantee is only nominal. Use `PipelineIdSegment` in both places for consistency.
- **D5:** an exempt request refused before the draft limiter (scoped PAT 403, missing CSRF header 403, 401) is now counted by no limiter. Its cost per request matches the general directive's own key-resolution lookup, so this is acceptable, but state it in the spec as a known property.
- **D4 / doc §6.3:** the doc's HTTP/1.1 mitigation was to let a stale request finish and ignore it, rather than abort. D8 always aborts. That is fine on h2, but note the h1 reconnect cost in the client's comment.
