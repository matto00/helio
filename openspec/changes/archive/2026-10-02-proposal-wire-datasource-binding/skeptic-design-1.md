## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence, against live code at 8c07ca97)
- Direct form create path (PanelService.buildForCreate, PanelService.scala ~L318-345): `rejectMissingDataSource(None)` is a no-op (L659-670), so an UNBOUND form is creatable directly (FormPanelConfig.read defaults missing dataSourceId to ""). Design claim confirmed. Existence+ownership: `findByIdOwned` -> NotFound "Data source not found" (no oracle). Dataset-kind check: ALREADY present in `rejectInconsistentForm` (L725-745, `case Some(_: DatasetSource)` else 400), plus FormSchemaConsistency field check. So D3's "if the direct path lacks the dataset-kind check, add it" is moot: it exists, and the shared piece to reuse is `rejectInconsistentForm` (private in PanelService, reads dataSourceRepo) — design should say it must be extracted/made shared, since ProposalPanelSupport has no dataSourceRepo today.
- Wire inventory vs code: ProposalPanel is used by DashboardProposalService (apply -> preValidateBindings L67), DashboardContentsService (L63), CombinedProposalService, AssistantProposalToolSchemas (type enum already includes "form", L54), dashboard-proposal.schema.json (description L35 currently documents the passthrough-succeeds behavior that D2 will intentionally change; must be rewritten). `DataPanelKinds = Set("output")` (DashboardProposalService L183) is regex-parsed by check-schema-drift.mjs. Inventory is accurate and complete.
- Combined: `validate` (non-mutating, L46-48) deliberately skips preValidateBindings; `apply` creates the pipeline FIRST, then dashboardProposalService.apply, rolling the pipeline back on failure. So a bad form dataSourceId would only be caught after the pipeline write on apply.
- Patch-set create: resolver (PatchSetApplyResolvers L270-290) only runs validateCreatePanelRequest/resolveCreateConfig, then executes via panelService.create — an unbound form passes today.
- `agentFacingPanelTypes` (check-schema-drift.mjs L238) is `filter(t => t !== "divider")`. Stated reason in code/schemas (proposal.ts L37, schema L35, script L233) is only "parity with create_panel" (historical). Divider IS expressible on the wire (`orientation` exists on ProposalPanel; write.ts L771 create_panel enum includes divider).

### Verdict: REFUTE

### Change Requests
1. **D6 / AC4 is undecided and its stated mechanism cannot work.** The predicate "kind's required binding is not expressible on the wire" does NOT hold for `divider` (no binding required, orientation is on the wire). The design defers ("if no defensible mechanical reason exists... surface in report"), which leaves AC4 uncovered and guarantees a mid-execution stall. Decide now, in design.md/tasks.md: either (a) include `divider` on the agent surfaces (and list every enum/schema/zod/assistant surface that changes, plus tests), or (b) keep it excluded with an explicit non-binding reason (e.g. "decorative; no data value to an agent") and a test that pins the exclusion table and fails if an excluded kind later becomes bound/expressible, or (c) explicitly ESCALATE. Also state how the new binding-requirement table is made parseable by the script (it currently regex-parses `DataPanelKinds` by name; a new source-bound table "next to" it needs the same parse contract and a fail-loud guard).
2. **D3 shared-helper is under-specified.** The dataset-kind and schema-consistency logic lives in private `PanelService.rejectInconsistentForm` and uses `dataSourceRepo`; `ProposalPanelSupport.preValidateBindings` has only `outputRepo`. Task 2.2 must name the extraction (e.g. move to a shared helper taking DataSourceRepository), the signature change to preValidateBindings and ALL its callers (DashboardProposalService, DashboardContentsService, wiring in the service constructors/ApiRoutes), and state whether FormSchemaConsistency (fields vs declared schema) also runs at propose time (it should, "never weaker" than create). Remove the stale "if direct path lacks dataset-kind check" branch.
3. **Combined proposal atomicity.** `CombinedProposalService.validate` skips DB-backed binding checks and `apply` writes the pipeline before dashboard validation. A form's dataSourceId does not depend on the `$pipelineOutput` sentinel, so D4/task 2.2 must require a form source check in BOTH `validate` (so propose_combined warns/rejects without writing) and before `pipelineProposalService.apply` in `apply` (or explicitly rely on and test the rollback). Specify which, with a test that no pipeline remains after a rejected combined form.
4. **Patch-set create (task 2.4) must not be left as "or documents why not".** Unbound form creation via the direct path is evidently intentional (builder), so the check cannot live in shared PanelService.create without violating the non-goal. Decide: add the check in the patch-set `resolveCreatePanel` resolver (L270-290) for `type == form` (missing/empty config.dataSourceId -> 400 "edit N: ..."; plus owned/dataset via the shared helper), and note this is patch-set-specific. Specify a failing-first test.
5. **Document the intentional behavior change** in the spec delta: the existing schema description (dashboard-proposal.schema.json L35) and HEL-1083 tests that assert passthrough `config.dataSourceId` succeeds must be updated; list them in tasks 3.1 so the executor does not treat those test failures as regressions or weaken the new rule. D2's rejection of config-only binding is acceptable but the error text must name the flat `dataSourceId`.

### Non-blocking notes

- Seam test D7 "where feasible" is vague; require at minimum the shared fixture consumed by both sides (already specified) and name the real-route harness (existing backend RouteTest spec) so feasibility is not an escape hatch.
- Task 1.1 red evidence is well framed; keep it.
