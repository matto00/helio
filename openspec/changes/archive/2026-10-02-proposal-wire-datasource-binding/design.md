## Context

`ProposalPanel` (backend) and its schema/MCP/assistant mirrors carry `outputId` as the only binding. `form` binds to a dataset source via `config.dataSourceId`. Today a `form` proposal can only bind through the untyped `config` passthrough, which no schema, tool description or validator tells an agent about, and `ProposalPanelSupport.validatePanel` does not require it; `PanelService.rejectMissingDataSource(None)` is a no-op, so an unbound form can be created. The executor MUST first prove, per wire, what actually happens today (created unbound / dropped / 400), and record that as the red evidence. Wires to enumerate: dashboard proposal apply (`POST /api/dashboards/apply-proposal`), dashboard contents replace (`PUT /api/dashboards/:id/contents`, reuses `ProposalPanel`), combined proposal, patch-set `panel create` (generic `CreatePanelRequest`, already carries `config`), MCP `propose_dashboard`/`propose_combined`/`create_panel`, assistant proposal tool schemas, and the authoring (NL) path.

## Goals / Non-Goals

**Goals:** one first-class `dataSourceId` on every proposal wire that carries a panel; loud rejection of an unbound/invalid form at validation; apply yields a bound, submittable form; agent-facing types derived from wire expressibility; a seam test.

**Non-Goals:** letting a proposal create the dataset itself (a product question; if the executor/skeptic thinks it is required, ESCALATE, do not decide); migrations; changing the direct form-create path's strictness except where mirroring requires a shared helper (never weaker).

## Decisions

**D1. Flat optional `dataSourceId` on `ProposalPanel`** (wire string, absent = unset, spray-json omits None), mirroring `outputId`'s convention. It is authoritative over `config.dataSourceId` after the config merge (same re-apply rule as `outputId` in `mergeConfig`). It is not allowed on non-source-bound kinds? Decision: ignored-is-silent is forbidden here, so a `dataSourceId` on a kind that does not bind to a source is rejected with a clear message (analogous to the existing controls-only-on-output rule).

**D2. Required-binding table, one place.** Backend declares which kinds are source-bound (`form`) next to `DataPanelKinds` (output-bound). `validatePanel` rejects a source-bound kind without `dataSourceId` A `config.dataSourceId` passthrough does NOT count as a binding (flat only, one source of truth); the error text names the flat `dataSourceId`.

**D3. Pre-write binding validation (verified against live code).** The direct create path (`PanelService`) already enforces, for a form with a non-empty `dataSourceId`: existence + caller ownership via `findByIdOwned` (NotFound "Data source not found", identical for foreign and nonexistent ids, so no existence oracle), dataset kind and field-vs-declared-schema consistency (`rejectInconsistentForm`, private, uses `dataSourceRepo`). Its config decode rejects an empty `dataSourceId` ("dataSourceId is required"), but only at create time, after dashboard/pipeline writes on a proposal path (hence the proposal-level structural check below). `rejectMissingDataSource(None)` itself is a no-op. Proposal validation must therefore: (a) require the flat `dataSourceId` (D2), and (b) run the SAME ownership + dataset-kind + schema-consistency logic. Extract `rejectInconsistentForm`/`rejectMissingDataSource` into a shared helper taking a `DataSourceRepository` (e.g. `FormBindingValidator`), used by both `PanelService` (behavior unchanged) and the proposal path. `ProposalPanelSupport.preValidateBindings` gains a `dataSourceRepo` parameter (nullable-optional like `outputRepo`, unwired fixtures skip); update ALL callers (`DashboardProposalService`, `DashboardContentsService`, `CombinedProposalService`) and their constructor wiring in `ApiRoutes`/service factories. Field consistency (the form's fields vs the dataset's declared schema) also runs at propose time, never weaker than create. Validation is read-only and runs before any write.

**D4. Wire plumbing.** Update: `DashboardProposalProtocol` (read/write), `ProposalPanelSupport.buildCreateRequest` (inject `dataSourceId` into config as authoritative), `schemas/dashboards/dashboard-proposal.schema.json` (including rewriting its line-35 description which today documents config-passthrough binding as working), `schemas/authoring/combined-proposal.schema.json`, `AssistantProposalToolSchemas` (decode-pinned), MCP `proposal.ts`/`combinedProposal.ts`/`types.ts`/`proposalValidation.ts` (warning when form lacks/has unknown dataSourceId, mirroring outputs warnings) and tool descriptions telling the agent how to obtain a dataset source id.

*Combined proposal atomicity.* `CombinedProposalService.validate` is non-mutating and today skips DB-backed binding checks; `apply` creates the pipeline FIRST, then applies the dashboard, rolling the pipeline back on failure. A form's `dataSourceId` does not depend on the `$pipelineOutput` sentinel, so the form source check (D3) MUST run in `validate` AND in `apply` BEFORE `pipelineProposalService.apply`, so a rejected combined form never writes a pipeline. Test: after a rejected combined proposal with a bad form, no pipeline row remains (exact-id assertion on the test's own ids).

*Patch-set create.* `resolvePanelCreate` (PatchSetApplyResolvers) currently passes an unbound form (it only runs `validateCreatePanelRequest`/`resolveCreateConfig`). The direct create path already rejects an empty `dataSourceId`; the patch-set resolver check exists to fail up front with an `edit N:` message rather than a forward-write failure, so it is NOT added to shared `PanelService.create`; instead the patch-set resolver, for `type == form`, rejects a missing/empty `config.dataSourceId` with a 400 `edit N: ...` message and runs the shared D3 validator (owned, dataset, consistency). This is patch-set-specific and says so in the code. Failing-first test required.

*Intentional behavior change.* A config-only (`config.dataSourceId`, no flat field) form proposal is now rejected; the error text names the flat `dataSourceId`. Existing tests (HEL-1083-era) and the schema description that assert the passthrough succeeds are updated deliberately, listed in task 3.1 so they are not mistaken for regressions or "fixed" by weakening the new rule. A form with both `dataSourceId` and `outputId` is rejected.

**D5. Layout.** Proposal layout validation (HEL-1071) is kind-agnostic; the test must apply a proposal containing a form panel and assert a valid layout.

**D6. `agentFacingPanelTypes` derivation (decided).** The wire-expressibility rule is: a canonical kind is agent-facing unless it appears in an explicit exclusion table `{ kind: reason }`; and EVERY agent-facing kind's required binding must be expressible on the proposal wire. Backend declares the binding tables side by side in `DashboardProposalService`: `DataPanelKinds = Set("output")` (needs `outputId`) and a new `SourceBoundKinds: Set[String] = Set("form")` (needs `dataSourceId`); `check-schema-drift.mjs` parses `SourceBoundKinds` with the same regex contract as `DataPanelKinds` and fails loudly if it cannot find or parse it. The script then asserts: for each binding table, the proposal schema's `ProposalPanel.properties` and MCP zod schema contain the required field (`outputId` / `dataSourceId`); so adding a future source-bound kind without a wire field fails the check. Exclusion table: `divider` stays excluded with the stated reason "purely presentational layout chrome: no content, binding or data an agent can author; `create_panel`'s enum excludes it, and the proposal surfaces mirror that parity" (it IS expressible on the wire via `orientation`, so the reason is stated as a product-scope reason, NOT a binding predicate). A test (node test for the script helper, plus an assertion in the script itself) pins: each exclusion has a non-empty reason, every excluded kind is a canonical kind (no stale entry), no excluded kind is source/output-bound (an excluded kind that later gains a binding must be re-decided, so it fails), and no hardcoded kind-name comparison remains outside the table. No `form`-specific exception anywhere.

**D7. Seam test.** One shared fixture file (a wire JSON for a form proposal) under `shared-test-fixtures/`, consumed by (a) a helio-mcp test that the MCP zod schema/handler accepts and serializes it, and (b) a backend spec that decodes it and applies it via the real route. The real-route harness is the existing backend RouteTest/spec infrastructure used by the proposal route specs and the helio-mcp tests that already run handlers against stubs; at minimum the shared fixture is consumed by both sides, AND a backend spec asserts the MCP-serialized wire (the fixture) is accepted by the real apply route. A test drives the real MCP handler (`propose_dashboard`/apply) against a real backend route instance. AC1's end-to-end: apply, then `POST /api/panels/:id/submit`, then assert the row in the dataset.

## Risks / Trade-offs

- Strict-key decoding elsewhere may reject the new field (check every schema's `additionalProperties:false` and every Scala strict reader).
- Dev DB is shared across worktrees: record exact ids of any rows created; clean exact ids only.
- Rejecting `config.dataSourceId`-only form proposals changes behavior for anyone relying on passthrough; acceptable (it was undocumented), noted in the PR.
