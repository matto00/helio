## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- 500 origin CONFIRMED: PanelService.scala:597 `effectiveOutputConfig` (def at :679-683) calls `OutputPanelConfig.Patch.decode` -> `convertTo[OutputControlSpec]` synchronously inside a flatMap lambda; DeserializationException becomes a failed Future -> 500. `resolvePatch` (PanelServiceHelpers.scala:21) never decodes config. Note the later `PanelPatchApplier` path goes through `PanelConfigCodec.safe` (-> 400) but is never reached.
- `validateConfig` is NOT called on the PATCH path (only PanelService.scala:332 create, DashboardService.scala:386 import). So D2's "put uniqueness in validateConfig" does not cover PATCH by itself; design does say to apply a helper to the PATCH effective config, which is correct.
- Duplicate id: OutputControlsValidator.reject builds `existingById` map and filters by id; confirmed dup ids are not detected.
- Non-output PATCH: effectiveOutputConfig returns None for non-OutputPanel, controls silently dropped (the text patch decoder ignores the key). Confirmed. ProposalPanelSupport.validateControlsShape:~85 has the cited "controls are only supported on an output panel" message.
- Frontend callers: grep of frontend/src shows controls are only read from output panels (PanelDetailModal gates on isOutputPanel; OutputControlsEditor is output-only). No evidence of a non-output PATCH echoing controls, but design correctly leaves this to executor.
- Wiring: ApiRoutes.scala:363-367 passes the validator to DashboardProposalService and DashboardContentsService; both default `controlsValidator = null`; preValidateControls skips on null. CombinedProposalService/assistant reuse `proposalService`, so no third wiring site.

### Verdict: REFUTE

### Change Requests
1. D5 wiring test is under-specified in a way that can make it vacuous. In ApiRoutes, `outputRepoOpt = Option(dbContext).map(...)` (ApiRoutes.scala:240) so without a real `dbContext` the validator gets a null outputRepo and `reject` returns Right (OutputControlsValidator: `case Some(_) if outputRepo == null`) — identical to the null-validator case. A test through ApiRoutes with no dbContext passes with and without the wiring and cannot be mutation-red. Revise D5/task 3.1 to state: the test MUST construct ApiRoutes with a real DbContext (as ApiRoutesSpec.scala:144 / ApiRoutesPipelineRunGuardSpec do), seed a real Output+schema, and drive both the propose route and PUT contents with an ineligible control, asserting 400 with the validator's message. Also state that the pre-mutation green run and per-argument red run (propose-only removal, contents-only removal) are both pasted, since each service needs its own red.
2. D3 contradicts itself: body says "Rejects presence of a non-empty `controls`" yet the spec delta says "carries `config.controls`" and Risks mention echoing `controls: []` on text panels. Pick one rule (recommend: reject presence of the key with a non-empty array; `[]`/absent on a non-output panel tolerated, or reject any presence — but say which) and make the spec scenario and the red test match it.
3. Non-array `controls` is NOT a decode failure on create paths: `OutputPanelConfig.decode` (OutputPanel.scala:~140) maps a non-array `controls` to `Vector.empty` (silent drop), and a non-object config to Empty. Design Context claims create "catches it in resolveCreateConfig" — true only for element decode errors. Since the spec requires non-array -> 400 on EVERY write path, add to D1/D4 an explicit decision to make the create/import/contents/duplicate decode strict for non-array `controls` (and non-object element, already strict), with a red test per path; do not leave this to discovery.
4. D4 enumeration omits write paths that exist in code: batch PATCH (`PanelMutationRepository.scala:~105`, applies config patches via applyConfigPatch with no controls validator, no non-output check, no dup check, no eligibility check) and dashboard snapshot restore (`DashboardSnapshotRepository.scala:174`). Add both explicitly to the table, and state that batch update must also reject duplicates/non-output controls. Also note blank id/label/unknown kind are validated by validateConfig only on create/import, not PATCH/batch PATCH; decide whether the shared helper includes structural checks so "same error shape everywhere" holds.
5. D2's rationale "the server never rewrites ids" is false for proposals (`ProposalPanelSupport.controlSpecsOf` mints a UUID for a missing id). Reword: duplicate check applies to explicitly supplied/ final ids after minting (collision only possible for explicit ids).
