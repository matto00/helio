### A reproduced, live-verified defect: theme toggle does not re-resolve the tooltip while the panel stays mounted

This is the **exact scenario** the ticket's AC #3 ("Tooltip/hover styling updates correctly after a light/dark toggle... without remount glitches"), design.md's Decision 5, and the spec delta's **ADDED** Requirement 5 ("Tooltip colors update after a light/dark toggle... WHEN the user toggles between light and dark theme while a chart panel is mounted THEN the next tooltip shown uses the newly active theme's colors, without the chart remounting") all describe — and which `evaluation-1.md`'s Phase 3 explicitly claims to have live-verified ("switched theme and accent via Settings... No remount glitches observed").

**Reproduction (without ever navigating away — the panel `<article>` DOM node stayed mounted throughout):**

1. Fresh page load, dark theme (confirmed `document.documentElement.getAttribute('data-theme') === 'dark'`). Hovered the chart → tooltip correctly dark-themed (see above).
2. Toggled theme to **light** via the command palette (`Ctrl+K` → "Switch to light theme" — the same `toggleTheme()` from `useTheme()` every other toggle entry point uses). Waited, moved the mouse away from the canvas and back (to force a fresh tooltip instance, not a repositioned stale one), then hovered again. **The tooltip still rendered with dark-theme values** (`background-color: rgb(38,35,32)`, dark box-shadow) while the rest of the page (panel card `<article>`, sidebar, header) had correctly switched to light theme's colors.
3. Reloaded the page fresh while still in light theme (full remount) → tooltip now **correctly** showed light values (`background-color: rgb(255,255,255)`, light shadow) — confirming the base tokens/CSS variables themselves are correct; only the **live in-place re-resolution** is broken.
4. Toggled back to **dark** via the command palette (same mechanism), waited 1.5s, moved away and back, hovered again. **The tooltip still rendered with LIGHT-theme values** (`background-color: rgb(255,255,255)`, light box-shadow) while the page (`<article>` background `rgb(26,24,22)`) had switched to dark. Screenshot taken at this exact moment, persisted at:
   `/home/matt/Development/helio/.concertino/runs/HEL-566/evidence/.concertino-skeptic-evidence/hel566-theme-toggle-stale-tooltip-dark-page-light-tooltip.png`
   — visually shows a dark-themed dashboard/panel with a plainly white, light-shadowed tooltip box.

This reproduced in **both directions** (light→dark and dark→light), each with a forced fresh-tooltip-instance (mouse moved off-canvas and back) and a wait, ruling out a one-off timing fluke. `ChartPanel.tsx`'s option `useMemo` does list `theme`/`accentColor` in its deps array and `notMerge={true}` is set on `ReactECharts`, so the wiring looks correct on paper — but the live, ground-truth behavior contradicts that. I did not chase the root cause further (that's the executor's job per `systematic-debugging.md` — a probe-confirmed root cause is required before a fix, and I don't want to guess at a fix here), but candidates worth the executor's first probes: whether `echarts-for-react`'s `ReactECharts` is actually calling `setOption` on every `option` reference change in this exact case, or whether ECharts' own tooltip component caches `extraCssText`/`backgroundColor`/`textStyle` computed from a previous `setOption` call and only reapplies them under narrower conditions than a full option replacement.

**Why this is not just a re-statement of the evaluator's own already-covered ground**: `evaluation-1.md` describes navigating via "re-opened the dashboard (same SPA session, no reload)" for its theme-toggle check — that phrasing is consistent with navigating away and back to the dashboard (a full `PanelGrid`/`ChartPanel` remount at the route level), which would mask exactly this bug by re-reading fresh theme tokens at mount time rather than testing the specific "no remount" claim the AC and spec Requirement make. My test never navigated away at all.

**Why this is not just a weak-test gap that happens not to matter**: the one live-in-place test that exists, `ChartPanel.test.tsx`'s "recomputes the option... when accentColor changes alone" (task 3.2), only asserts `resolveChartTheme` was **called** more times via a `jest.spyOn` count — it does not assert the rendered DOM/tooltip actually reflects a new value, and `resolveChartTheme()` in jsdom always returns the same `FALLBACK_CHART_THEME` constant regardless of accent, so a passing test here is consistent with the exact live failure I reproduced (the function can be called again without the visible result changing). This is the "evidence-shaped non-evidence" pattern — a green check that doesn't actually exercise the failure mode the AC cares about.

### Verdict: REFUTE

### Change Requests

1. **Fix live re-resolution of tooltip/hover styling on theme toggle without remount** (`frontend/src/features/panels/ui/ChartPanel.tsx`, `frontend/src/utils/chartAppearance.ts`). Root-cause first (per `systematic-debugging.md`) — probe whether `ReactECharts`/`echarts-for-react` is actually invoking `setOption` on every `option` prop-identity change in this exact configuration, or whether ECharts' tooltip component is caching computed DOM styles from a prior `setOption` and not reapplying them on a subsequent one. Reproduction steps are in this report's "Reproduced defect" section above — no fixture rebuild needed, they're generic (any two-series bar/line chart panel with `appearance.chart` set).
2. **Add a regression test that would actually catch this** — the existing `ChartPanel.test.tsx` "recomputes the option... when accentColor changes alone" test (and an equivalent for a full theme toggle, which currently has no live-remount-free component test at all) needs to assert the **rendered tooltip DOM's actual computed values** (or at minimum, the `option` object passed to the mocked `ReactECharts`/`echarts-for-react`) reflect the new theme/accent after the change — not merely that `resolveChartTheme` was called more times. A call-count spy proves the function ran again; it does not prove the chart's displayed output changed.
3. Once (1) is fixed, re-verify AC #3 and the spec's Requirement 5 live, in both toggle directions, without navigating away — the exact procedure in this report's reproduction section.

### Non-blocking notes

- The five genuinely-missing gaps identified by the premise-check (tooltip shadow/radius, mono-font values, axis-trigger multi-series tooltip, reduced-motion-aware hover emphasis, `accentColor` dependency fix) are all correctly implemented in the code and correctly covered by meaningful unit/component tests — confirmed by direct code reading and by my own live fixture on a fresh page load. The defect above is specifically about **live, in-place re-resolution after a toggle**, not about whether the underlying styling/tokens/gating logic is correct.
- `frontend/src/features/panels/ui/PanelContent.tsx`'s `OutputPanelContent` requires a panel's own `appearance.chart` to be explicitly set for any base tooltip styling (including the pre-existing F-025 background/border, unchanged by this diff) to apply at all — a panel bound to a chart Output via the "Add panel" dialog does not get this populated automatically in the current build. This is a pre-existing, HEL-566-unrelated gap (the same conditional guard existed before this diff) surfaced only because I built a fixture from scratch; not a defect in this ticket's scope, but worth a follow-up ticket if genuinely new chart panels commonly ship unstyled tooltips as a result.
