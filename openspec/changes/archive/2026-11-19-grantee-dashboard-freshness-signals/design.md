## Decisions

### D1. One dashboard-scoped status route, not a per-panel route and not a dashboard SSE stream

`GET /api/dashboards/:id/panel-status` in a NEW route file `api/routes/dashboards/DashboardPanelStatusRoutes.scala`, mounted in the authenticated `/api` tree (session or PAT; no `token` parameter). Inside: `aclDirective.authorizeResourceWithSharing("dashboard", id, Some(user), shareToken = None)` (the same directive every per-panel route uses), so owner/editor/viewer pass and a stranger or unknown id gets the directive's own `404`. Response (`DashboardPanelStatusResponse`, schema `schemas/dashboards/dashboard-panel-status-response.schema.json`):

```json
{ "items": [ { "panelId": "...", "lastRunAt": "ISO|null", "runStatus": "succeeded|failed|null", "dataUpdatedAt": "ISO|null", "invalid": false } ],
  "sources": ["Sales CSV"] }
```

- `items`: one per `OutputPanel` of the dashboard (via `panelRepo.findAllByDashboardId(..., accessAlreadyGranted = true)` with a single page at `Page`'s maximum limit, 500 — the panel list's own ceiling; panels beyond the 500th in panel order are omitted from `items` and contribute nothing, stated in a code comment and covered by no test beyond the bound constant) whose `outputId` and its Output and pipeline resolve; other panel kinds and unresolvable bindings are omitted. Order: panel order.
- `lastRunAt`/`runStatus`: the pipeline row's `lastRunAt`/`lastRunStatus` (the same values the owner's `deriveDashboardMeta` reads from the pipeline summary); `runStatus` is mapped to exactly `succeeded`, `failed` or `null` (any other stored value -> `null`).
- `dataUpdatedAt` (skeptic-design-1 CR1): the latest `output_snapshot_history.captured_at` of the panel's Output, read through `withSystemContext` after the ACL — NOT `withUserContext` as `DashboardChangesRepository` runs it (under `helio_app` a dashboard-only grantee's user context sees 0 history rows) — one query for all the dashboard's Outputs, the same LATERAL `LIMIT 1` shape `DashboardChangesRepository.dataQuery` uses on the `(output_id, captured_at DESC)` index), or `null` when the Output has no history point. This, not `lastRunAt`, is the run-finish trigger (D3): on a successful run `pipelines.last_run_at` is written by `updateMeta` CONCURRENTLY with the node-snapshot writes (`PipelineRunSucceededWrites.scala` ~258-264, eager vals awaited together), so a poll can see `last_run_at` advanced while the rows are still the old ones; the history summary point is inserted in the SAME transaction as the node snapshot replace (`NodeSnapshotRepository.overwriteRowsWith` / `overwriteRowsAction(...).andThen(...)` in one `withSystemContext`, ~line 128), so when `dataUpdatedAt` advances the new rows are already committed. Retention thinning never deletes an Output's newest 101 history points (CLAUDE.md, `GET /api/outputs/:id/history`), so `dataUpdatedAt` never moves backwards. The executor re-verifies both commit-order facts (cite file:line in files-modified.md) and verifies a history point is written for every Output kind a grantee panel can show on a real successful run; any Output kind that gets no history point on a run is listed, and for it the panel-scope run-finish refresh is documented as not available (the freshness fact still updates) — the executor stops and reports if that set includes `table`/`chart`/`metric`.
- `invalid`: the `OutputService.assertionStatus` rule, factored into one shared internal function both the Output route and this route call (no second copy of the rule), evaluated with internal (system-context) reads after the dashboard ACL. Latest non-dry run per pipeline is read once per pipeline per request, not once per panel.
- `sources` (skeptic-design-1 CR2): the distinct source names the public per-panel provenance route would show for some Output panel of this dashboard, in first-seen panel order (within a panel, provenance's own order) — computed by ONE source-resolution method factored out of `ProvenanceService` (skeptic-design-2 CR2): `closureFor` / `feedingRootIds` / `secondarySourceIds` / the name lookup become `ProvenanceService.sourcesFor(...)` (a batched form over the dashboard's Outputs, grouped by pipeline), and `forOutput` itself calls it, so there is exactly one derivation (m9 bites both). The new route calls only that method — never `forOutput`, whose other reads (`latestNonDryRunInternal`, `assertionsFor`, `nodeSnapshotRepo.countRows`, an unbounded `count(*)` over `node_snapshots`) would be discarded and repeated every poll. Steps and roots are read once per distinct pipeline per request; data-source names in one batched lookup. This deliberately differs from the owner's meta row for a multi-root pipeline whose bound Outputs read only some roots: the owner's row lists every root of every feeding pipeline (`deriveDashboardMeta` over `PipelineSummary.roots`), the grantee's lists only the sources that feed the Outputs actually on the dashboard. When `ProvenanceService` is not wired (the `Option` is `None`), `sources` is `[]`.
- Never present: pipeline/step/run/Output/owner ids, step or pipeline names, `errorLog`, assertion details. Enforced by a key allow-list assertion in the route spec, plus a JSON Schema with `additionalProperties: false`.

Why one dashboard-level route: all three consumers (meta row, card refresh, card badge) need the same per-panel facts at the same moment; one request per tick for the whole dashboard instead of one per panel. Why polling (D3) over a dashboard SSE stream: the registry stream is keyed by pipeline and its events carry run ids; a dashboard stream would need panel->pipeline resolution at connect time, reconnection on panel-set change and its own reconcile route anyway (the owner fan-out needs `/runs/latest` for exactly this reason, HEL-1174). The status route is that reconcile route; polling it alone is the smaller surface with the same disclosure. Trade-off: run-finish latency is up to one poll interval rather than near-immediate. Alternative rejected: extending the panel list with `runStatus`/`invalid` — the panel list is re-read only on navigation and is shared with the public viewer path, so it would need polling of the whole panel payload.

### D2. Client store: module-scoped, ref-counted, keyed by dashboard id

`features/panels/state/panelStatusStore.ts` (name may differ; one module): `subscribePanelStatus(dashboardId, listener) -> unsubscribe` and `getPanelStatusSnapshot(dashboardId)`, a `useSyncExternalStore`-friendly pair. The first subscriber for a dashboard starts polling; the last unsubscribe stops it. One in-flight request per dashboard at a time. Service function `fetchDashboardPanelStatus(dashboardId)` in `features/dashboards/services/` (or panels services; executor picks the existing convention) calling `/api/dashboards/:id/panel-status`. The store is reset with the other freshness state on logout (`onFreshnessReset`) and has a test reset helper.

Hooks:
- `useSharedDashboardMeta(dashboardId | null, panels)` -> `DashboardMeta` (same type as `useDashboardMeta`), via a pure `deriveDashboardMetaFromStatus(panels, status)` beside `deriveDashboardMeta`: `refreshState` `unknown` when `items` is empty or status not yet loaded, `never` when items exist and none has `lastRunAt`, else `ran` with the latest `lastRunAt`, intent from that item's `runStatus` (same mapping as `deriveDashboardMeta`); `sources`/`moreSources` capped by `MAX_SHOWN_SOURCES`. `null` dashboard id -> no subscription.
- `usePanelStatus(dashboardId | null, panelId)` -> the item or `undefined`.
- `usePanelStatusRefresh(dashboardId | null, panelId, refresh)` -> calls `refresh` when D3 says so.

### D3. Poll cadence and the refresh trigger

- Interval `PANEL_STATUS_POLL_MS = 15000` while `document.visibilityState === "visible"`; no polling while hidden; an immediate read on becoming visible again. Exported so jest drives it with fake timers; e2e waits for it (worst case one interval plus the rows read).
- A failed read keeps the last good snapshot and retries on the next tick (no backoff state beyond that; no error UI).
- Refresh trigger per panel: the store keeps the previous snapshot. A panel's refresh fires when its item's `dataUpdatedAt` is strictly later than in the previous snapshot, or goes from `null` to a value (first ever run while watching). `lastRunAt`/`runStatus` never trigger a refresh (a failed run writes no history point, so it never fires either). The first snapshot after subscribe (per dashboard) is the baseline and never fires. A panel newly appearing in `items` is baseline for that panel.
- The pull-to-refresh / "Refresh dashboard" control in panel scope triggers an immediate status read in addition to what it already does (the executor verifies what `usePullRefreshControl` does on a non-owned dashboard and that it makes no Output/pipeline request; if it does, stop and report).

### D4. Wiring per surface (panel scope only; owner scope unchanged)

Same render path for the facts. Owner-only actions (share, owner Ask) unchanged.

## Risks / Trade-offs

- [Run-finish latency up to 15 s for grantees, near-immediate for owners] -> accepted; interval is one exported constant.
- [Polling load: one request per open grantee tab per 15 s] -> per-request query bound: 1 panel page read; 1 batched Output read; 1 batched pipeline read; per distinct pipeline P: 1 latest-non-dry-run read (the same `listByPipelineInternal` + first `status != "dry_run"` path the Output route uses, so one shared function keeps the Output route's behaviour exact), at most 1 assertions read for that run, 1 steps read and 1 roots read; 1 batched history-latest read over all Outputs (LATERAL `LIMIT 1` on the `(output_id, captured_at DESC)` index); 1 batched data-source name read. So O(P) small indexed reads plus a constant, independent of row counts; no `count(*)` over `node_snapshots` and no row read of any snapshot runs on the poll path. Visible-only polling; the general `/api` rate limit (120/min) is far above 4/min. If `listByPipelineInternal` is unbounded per pipeline (reads every run row), the executor bounds it (`LIMIT` on the newest rows, same ordering) inside the shared function and proves the Output route's assertion-status specs unchanged.
- [`lastRunAt` advances on a failed run too] -> it updates the fact (danger intent) only; the row refresh is keyed solely on `dataUpdatedAt` (D3), which a failed run never writes, so a failed run never refreshes rows (the owner path likewise refreshes on `succeeded` only).
- [The Output's inferred schema (`updateSchemaInternal`) is written AFTER the snapshot+history transaction (`PipelineRunSucceededWrites.scala` ~151-160)] -> a grantee refresh landing in that window gets the new rows with the previous schema, so a newly added column shows in code-point order (HEL-1705) until the next refresh. Cosmetic and rare (same as any owner read in that window); the e2e must not add a column in its run-finish step.
- [Information disclosure] -> `lastRunAt` = the panel list's `dataAsOf`; `runStatus` and `invalid` follow from per-panel provenance's `lastRun.status` and assertion counts; `sources` is restricted to names per-panel provenance shows for a panel on this dashboard (CR2); `dataUpdatedAt` is the capture time of the data the grantee's panel already renders (the per-panel history route already exposes point `capturedAt`). Enforced by the allow-list test and `additionalProperties: false` schema.
- [`invalid` reads `false` while a real run is in flight and briefly after its terminal write (that run is the latest non-dry run and its assertions are inserted after `updateRun`)] -> identical to the owner badge; the e2e asserts the badge only after `dataUpdatedAt`-driven refresh has settled (or polls for it), so a flicker is not misdiagnosed.
- [Self-decision S1] Run status `failed` is shown to grantees as the danger intent on the fact, as for owners: it is a status already in the grantee's provenance popover, not error text. If the skeptic or owner reads the ticket's "no errors" as excluding the status itself, the fallback is mapping `failed` to `null` intent — a one-line change.
