### Change Requests

1. **The run-finish trigger can fire before the run's rows are committed, and then never fires again (design D1/D3, spec "Grantee panels refresh when a run finishes").** The trigger is "`lastRunAt` strictly advanced AND `runStatus === succeeded`", read from `pipelines.last_run_at/last_run_status`. On a successful run that row is written by `updateMeta`, which runs concurrently with, not after, `materializedWrites` (node snapshots) in `PipelineRunSucceededWrites.scala` (eager vals at ~258-264, only awaited together at the end). A poll landing in that window fires the refresh once, re-reads the per-panel rows route, gets the pre-run snapshot, and the baseline has now advanced, so the panel stays stale until the next run. The owner path does not have this hole only because HEL-1366 publishes the SSE event after the whole chain. Revise the design to key the trigger on a value committed atomically with (or after) the rows. The concrete candidate already in the tree: per panel, the latest `output_snapshot_history.captured_at` of its Output (inserted in the same transaction as the node snapshot replace; already read this way by `DashboardChangesRepository.dataQuery`). Keep `lastRunAt`/`runStatus` for the freshness fact. Add: (a) a backend spec case where `pipelines.last_run_at` is advanced to `succeeded` with no new history point, asserting the panel's trigger field does not advance; (b) a mutation that switches the trigger back to `last_run_at`, red at that case; (c) a statement of what the trigger does for a panel whose Output has no history yet (first run) and whether thinning can ever lower the latest point (it cannot per CLAUDE.md "never deletes an Output's newest 101 history points" — cite it). If the executor chooses a different signal, the design must name it and show its commit order relative to the snapshot write. Update the D5 allow-list and the JSON Schema for whatever field is added (still no Output/run id).

2. **`sources` can reveal source names no grantee panel shows (AC 3: "reveals nothing beyond what the grantee's panels show"; design Risks claims "Everything the new route returns is a subset").** D1 says `sources` = "the same names `deriveDashboardMeta` collects from `PipelineSummary.roots[].dataSourceName`", i.e. every root of every feeding pipeline. For a multi-root pipeline where the dashboard's Outputs consume only some roots, that lists data sources the grantee's provenance popovers never show (provenance lists only the Output closure's feeding roots and secondary sources, `ProvenanceService.forOutput`). Revise D1 so `sources` is derived per panel through the same feeding-source resolution provenance uses (reuse it; do not write a second derivation), restricted to names provenance would show for some panel on this dashboard, in first-seen panel order. State explicitly that this can differ from the owner's meta row for multi-root pipelines, and add a backend case: a two-root pipeline whose bound Output reads only root 1 -> root 2's source name absent from the body (with a mutation that uses all pipeline roots -> red). Correct the "subset" sentence in Risks accordingly.
