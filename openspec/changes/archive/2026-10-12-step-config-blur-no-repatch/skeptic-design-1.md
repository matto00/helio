### Non-blocking notes

- **UpsertSource loses an incidental blur-retry.** Today a failed upsertsource save (captureErrors) is retried, byte-identical, when the field blurs: `persist` clears `saveError` and re-PATCHes. After the fix, a transient failure (5xx or network) stays visible until the user edits the name. A 422 would fail the same way again, so the loss only matters for transient errors. This is acceptable. It also slightly undercuts the proposal's Non-goals argument that dedupe "could suppress a deliberate retry", because the chosen fix removes that blur-triggered retry too. The executor should state this behaviour change in the commit or PR body, and may add a one-line Risk entry to design.md. No owner ruling is needed.
- Correct the D2 citation: `handleStepConfigChange` is in `hooks/usePipelineStepMutations.ts`.
- The spec scenario "Blur without an edit sends no save" is covered at component level by the inverted blur-only tests. A StepCard-level focus-then-blur-with-no-change case (expect 0 `updatePipelineStep` calls, red before the fix) would cheaply pin the second scenario end-to-end.
- `PipelineDetailPage.test.tsx` blur calls (2720/2737/2745/2774/3089) are on the pipeline-name input, which is out of scope. They should stay unchanged.
