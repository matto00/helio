### Change Requests

1. **write-path-audit: the plan restates panel title/appearance writes as `PATCH /api/panels/:id`, which is no longer true.** The delta's scenario (`specs/write-path-audit/spec.md`, "Audit covers all panel-level write paths") says "PATCH /api/panels/:id for title updates, appearance updates, and Output swaps". In the current UI, title and appearance edits accumulate and flush as `POST /api/panels/updateBatch` (evidence above). Only the Output swap is a `PATCH /api/panels/:id`. Task 2.1 also frames payload detail 8 as "state when `appearance.chart` is sent, per `PanelDetailModal`", but the modal never sends `chart`. As planned, AC3 ("match the current code") would ship a newly authored stale claim. Revise design.md (write-path-audit bullet + Decision 2) and tasks.md 2.1 so that:
   (a) the delta scenario names the real transport: title/appearance via `POST /api/panels/updateBatch` on flush (auto-save / Save now / unmount), Output swaps via `PATCH /api/panels/:id` `{config:{outputId}}`;
   (b) payload detail 8 describes the batch item `{ id, appearance: { background, color, transparency }, title? }` and the flush trigger, citing `PanelDetailModal.tsx:129-141`, `panelPayloads.ts:125-137` and `usePanelUpdatesFlush.ts:93`;
   (c) the Source Locations `PanelDetailModal.tsx` role becomes "panel title/appearance accumulation (flushed via updateBatch)", and `OutputPicker.tsx` is added (or named) for the swap;
   (d) the call-volume "Panel data binding saves" replacement and both totals are recomputed on the batched model.
   Rows 7/8 in the Write Path Table and the "Panel renames"/"Panel appearance saves" call-volume rows share the same root cause. Either correct them in this change, which I recommend (same evidence, same section, and needed for AC3's "Panel appearance" row 8 to be true), or record them explicitly as an observed-not-edited non-goal and justify it. Do not leave them silently contradicting the corrected rows.
2. **echarts delta: the restated requirement overclaims the field-mapping fallback for heatmap and histogram, and contradicts itself on chartType's source.** In `specs/echarts-chart-panel/spec.md`, the requirement says "When the Output's `fieldMapping.xAxis` is unset the first column SHALL be used as the x axis, and when `fieldMapping.yAxis` is unset every numeric column other than the x column SHALL be rendered as a series". That is false for `heatmap` (renders nothing unless x/series/yAxis are all mapped, `heatmapHistogramOptions.ts:93-96`) and `histogram` (needs a mapped `xAxis`, ignores yAxis, `:228-229`). Scope both that sentence and the scenario now planned as "A chart Output with no yAxis mapping auto-detects numeric series" to `bar`/`line`/`scatter` (with the pie exception already noted), or state the heatmap/histogram behaviour. Separately, "the chart's data, `fieldMapping`, `chartType` and `aggregation` come from the bound Output's config" contradicts the next sentence, which makes the panel's stored `appearance.chart.chartType` win. Drop `chartType` from that list or qualify it. Task 1.1's re-verification should cite `chartDataOptions.ts:82-85` for this.
3. **tasks.md 3.1: the verification command contradicts the "tests unchanged" constraint.** `grep -rn typeId frontend/src/features/panels/hooks/` cannot come back empty while `usePanelPolling.test.ts` keeps its `typeId` variable and test titles (L42,100,102,104,111,117). State one of: (a) also rename the test's local variable and titles to `outputId`, with assertions unchanged (my preference, since otherwise the stale name survives in the hook's own test); or (b) narrow the grep to `usePanelPolling.ts`. Either way, the executor should not have to choose.
