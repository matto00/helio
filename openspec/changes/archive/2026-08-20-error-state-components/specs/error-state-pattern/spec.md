## ADDED Requirements

### Requirement: EmptyState renders an intent-error variant with an alert role
The `EmptyState` component SHALL accept an `intent` prop (`"neutral" | "error"`, default `"neutral"`).
When `intent="error"`, on both the `main` and `sidebar` variants: the icon-wrap SHALL use a solid
error-tinted background (mixed against the opaque surface token, not a translucent wash alone) and an
error-tinted border, instead of the default accent tint and neutral border; the icon glyph itself SHALL
also render in the error intent color, not the default accent color; the root element SHALL carry
`role="alert"` and SHALL NOT carry `aria-label` (the live region's own content already announces the
title, so a separate `aria-label` would double-announce it). The `main` variant's title SHALL remain
rendered in the Fraunces display font exactly as the `neutral` intent does.

#### Scenario: Error intent applies intent-error tokens, glyph color, and an alert role
- **WHEN** `EmptyState` is rendered with `intent="error"`
- **THEN** the icon-wrap element and its glyph carry error-tinted styling instead of the accent tint
- **AND** the root element carries `role="alert"` and no `aria-label`

#### Scenario: Neutral intent is the default and unchanged
- **WHEN** `EmptyState` is rendered with no `intent` prop
- **THEN** it renders identically to its pre-existing (accent-tinted, role-less, `aria-label`-carrying)
  behavior

### Requirement: EmptyState icon and cta icons accept a ReactNode
The `EmptyState` component's `icon` prop, and its `cta.icon`/`secondaryCta.icon` props, SHALL each accept
either a FontAwesome `IconDefinition` (existing behavior, rendered via `FontAwesomeIcon`) or a `ReactNode`
(rendered directly), selected by `React.isValidElement`.

#### Scenario: A FontAwesome IconDefinition still renders via FontAwesomeIcon
- **WHEN** `EmptyState` is rendered with `icon={faTableColumns}`
- **THEN** the icon renders identically to its pre-existing behavior

#### Scenario: A ReactNode icon renders directly
- **WHEN** `EmptyState` is rendered with `icon={<AlertTriangle />}`
- **THEN** the provided element is rendered directly, not wrapped in `FontAwesomeIcon`

### Requirement: EmptyState supports a secondary action alongside a primary cta
The `EmptyState` component SHALL accept an optional `secondaryCta` prop, of the same shape as `cta`,
rendered using the Secondary button recipe (distinct from `cta`'s Primary recipe) when provided, alongside
`cta` rather than replacing it.

#### Scenario: Both cta and secondaryCta render together
- **WHEN** `EmptyState` is rendered with both `cta` and `secondaryCta`
- **THEN** both actions are rendered, `cta` using the Primary recipe and `secondaryCta` using the
  Secondary recipe

### Requirement: EmptyState and InlineError cta/retry actions support a disabled, in-flight state
`EmptyState`'s `cta`/`secondaryCta` SHALL accept a `disabled` boolean that disables the action; the
in-flight label text (e.g. "Retrying…") for `EmptyState` SHALL be supplied by the caller via the action's
own `label`, not generated by the `EmptyState` component itself — `EmptyState` is a generic primitive
shared by non-retry empty states and SHALL NOT hard-code retry-specific copy. `InlineError`'s Retry action
SHALL accept a `retrying` boolean, and — unlike `EmptyState`'s `disabled` — the component itself SHALL
disable the action AND swap its own visible label (or `aria-label`/`title` for `retryVariant="icon-only"`)
to a distinct in-flight label, since `retrying` is retry-specific by construction.

#### Scenario: EmptyState cta renders the caller-supplied label while disabled
- **WHEN** `EmptyState`'s `cta` is rendered with `disabled: true` and `label: "Retrying…"`
- **THEN** the action is disabled and renders exactly the supplied label — `EmptyState` does not
  generate or alter that label itself

#### Scenario: InlineError retry is disabled and swaps its own label while retrying
- **WHEN** `InlineError`'s banner variant is rendered with `kind="error"`, an `onRetry` callback, and
  `retrying={true}`
- **THEN** the Retry action is disabled and its label (or accessible name, for `retryVariant="icon-only"`)
  is swapped by the component itself to a distinct in-flight label

### Requirement: Permission-denied and not-found states never render a retry action, with copy that does not assert deletion
The system SHALL NOT pass a `cta` (no Retry action) to an `EmptyState intent="error"`, and SHALL NOT
render a Retry action from `InlineError`, for a `forbidden` or `not-found` classified failure. The
`not-found` copy SHALL be true under both of its possible causes (the resource was deleted, or the
current user does not have access to it) and SHALL NOT assert that the resource was deleted — e.g. "We
couldn't find this resource. It may have been deleted, or you may not have access to it." The `forbidden`
copy SHALL read as a distinct, non-generic denial — e.g. "You don't have access to this resource."

#### Scenario: Forbidden state shows no retry action
- **WHEN** a fetch fails with a classified `forbidden` kind
- **THEN** the resulting error state renders with no `cta`/Retry action

#### Scenario: Not-found state shows no retry action and does not assert deletion
- **WHEN** a fetch fails with a classified `not-found` kind
- **THEN** the resulting error state renders with no `cta`/Retry action
- **AND** its copy does not assert that the resource was deleted

#### Scenario: Generic error state shows a retry action
- **WHEN** a fetch fails with a classified `error` kind
- **THEN** the resulting error state renders a Retry action that re-dispatches the failed fetch

### Requirement: A deterministic capability limitation is never presented as a retryable error
The system SHALL NOT attach a Retry action to a deterministic, non-network capability limitation (e.g.
`SourceDetailPanel`'s "Preview is not supported for this source kind" message, which is not the result of
a failed request and can never succeed on retry), even where the same view's error-state surface can also
be reached by a real, retryable fetch failure and both otherwise use the same visual treatment — the two
SHALL be rendered distinctly.

#### Scenario: A capability-limitation message never renders a retry action
- **WHEN** `SourceDetailPanel` renders its "Preview is not supported for this source kind" message
- **THEN** no Retry action is rendered

#### Scenario: A real fetch failure on the same surface still renders a retry action
- **WHEN** `SourceDetailPanel`'s preview fetch fails for a source kind that does support preview
- **THEN** the resulting error state renders a Retry action that re-runs the preview fetch

### Requirement: classifyRequestError derives a message and kind, called inside the failing thunk
The system SHALL provide a shared `classifyRequestError(err, fallback)` helper at
`frontend/src/services/classifyRequestError.ts` that derives `{ message, kind }` from a failed request,
where `kind` is `"forbidden"` when the response
status is 403, `"not-found"` when 404, and `"error"` otherwise, and `message` SHALL be derived by calling
the existing `frontend/src/services/extractErrorMessage.ts`'s `extractErrorMessage` — not a
reimplementation of it, and not any of the per-slice local helpers of the same name, which remain
untouched and continue to serve their own existing call sites. Each thunk that surfaces a classified error
SHALL call this helper inside its own `catch` block (including every rejection site within that thunk,
not only its outermost `catch`), binding the caught error, and SHALL widen its `rejectValue` to carry both
`message` and `kind` — classification SHALL NOT be attempted at a call site that only receives the thunk's
rejected string payload, since the original response status is no longer available there.

#### Scenario: 403 response classifies as forbidden
- **WHEN** `classifyRequestError` is called with an Axios error whose response status is 403
- **THEN** it returns `kind: "forbidden"`

#### Scenario: 404 response classifies as not-found
- **WHEN** `classifyRequestError` is called with an Axios error whose response status is 404
- **THEN** it returns `kind: "not-found"`

#### Scenario: Any other failure classifies as error
- **WHEN** `classifyRequestError` is called with a failure whose response status is neither 403 nor 404
  (or has no response, e.g. a network error)
- **THEN** it returns `kind: "error"`

### Requirement: A panel data fetch clears its prior stored error whenever it next succeeds
The panel data fetch path (`usePanelData`) SHALL clear its stored error both when a retry is explicitly
triggered, and whenever a fetch for the same key subsequently fulfills by any means — including a
background refetch triggered by a cache invalidation (e.g. after a pipeline run completes), not only a
fetch triggered by the Retry action itself — so that a panel never continues to render a prior error once
its data has successfully loaded.

#### Scenario: A successful retry clears the prior error
- **WHEN** a panel's data fetch has failed and its stored error is set
- **AND** the fetch is retried and subsequently succeeds
- **THEN** the panel renders its data, not the prior error state

#### Scenario: A successful background refetch clears the prior error without an explicit retry
- **WHEN** a panel's data fetch has failed and its stored error is set
- **AND** a cache invalidation triggers a background refetch for the same panel (not via the Retry action)
  that subsequently succeeds
- **THEN** the panel renders its data, not the prior error state

### Requirement: Both PanelContent rendering contexts offer retry
`PanelContent`'s error state SHALL offer a Retry action wherever it is rendered, including both the panel
grid (`PanelCard`) and the panel detail modal (`PanelDetailModal`) — a fetch failure rendered inside the
modal SHALL NOT be missing the Retry action that the same panel's grid rendering has.

#### Scenario: The panel detail modal's error state offers retry
- **WHEN** a panel's data fetch fails while its detail modal is open
- **THEN** the modal's rendering of `PanelContent`'s error state includes a Retry action

### Requirement: Named views render a visible error state with retry on fetch failure
The system SHALL render a visible, intent-error styled state (via `EmptyState intent="error"`,
`InlineError variant="banner"`, or `StatusMessage`, matching each view's existing full-surface vs. inline
treatment) in each of `PanelContent`, `PanelList`, `SourcesPage`, `SourceDetailPanel`, `PipelinesPage`,
`PipelineDetailPage`, `TypeRegistryPage`, `TypeDetailPanel`, and `ProposalReviewPage` on a fetch failure
classified as `"error"`, offering a Retry action that re-runs the failed fetch and clears the error on
success. No listed view SHALL silently render nothing on a fetch failure.

#### Scenario: A generic fetch failure shows a retry action that recovers
- **WHEN** any of the named views' data fetch fails with a classified `"error"` kind
- **THEN** the view renders a visible error state with a Retry action
- **AND** activating Retry re-runs the fetch, clearing the error state and rendering the data on success

#### Scenario: No silent failure
- **WHEN** any of the named views' data fetch fails
- **THEN** the view never renders as if nothing happened (no blank/unchanged view)
