## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed: ticket.md, proposal.md, design.md, tasks.md, specs/patch-set-undo/spec.md (untracked in worktree) against live code at HEAD 83e5655e4913d716e51e4f51919a567f058bac52 (branch bug/undo-guard-later-alert-rules/HEL-1811, assert-cwd READY).

### What I verified (with evidence)

- **Defect is real (premise).** `PatchSetUndoConflictCheck.guarded` runs only `PatchSetUndoBoundPanels.blocker`, `PatchSetUndoLaterChildren.blockers` (pipeline/pipelineStep) and `PatchSetUndoDatasetLaterWork.inlineBlockers`; `checkPipeline` compares only `name`; `checkOutputCreate` only existence. No undo file reads `alert_rules`, `pipeline_schedules` or `pipeline_roots` (grep of `PatchSetUndo*.scala`: "fingerprint" appears only in the draft-save outcome). `PipelineService.delete` (PipelineService.scala:132) has no dependents guard. Cascades confirmed in migrations: V94:391 `alert_rules.target_output_id ... ON DELETE CASCADE`, V62:25 `pipeline_schedules.pipeline_id ... UNIQUE ... CASCADE`, V98:80 `pipeline_roots.pipeline_id ... CASCADE` (with `created_at TIMESTAMPTZ DEFAULT now()`, so the timestamp fallback has a column to read).
- **Cascade enumeration is complete for this ticket.** Every `REFERENCES pipelines(id)` / `outputs(id)` cascade: steps (V23, guarded HEL-1795), runs (V24), payload history (V116), auto-run debounce (V110), binary_refs (V94:425), snapshot history (V115), insights (V145), outputs (V94:208, guarded), panels (V94:344, guarded), alert_rules/alert_events (V94:391/394), schedules (V62), roots (V98). After this change the only unguarded ones are the by-products the ticket puts out of scope. `resource_permissions` (V16) is polymorphic with no FK, so grants do not cascade.
- **Premise staleness claim (editor cannot alert on a created Output) holds.** `AlertRuleService.create` validates via `OutputRepository.findByIdOwned` (`r.ownerId === user`, OutputRepository.scala:224-228); `update` cannot change the target. Only `AlertRuleService.create` inserts alert rules (grep). So a rule on a created Output belongs to that Output's owner. The design's generic "any owner" check plus a direct-insert test labelled API-unreachable is the right treatment.
- **(a) Schedules and later roots as blockers: within the rulings, no escalation needed.** The ticket says "Also check: schedules and extra roots ... These cascade too" and the binding ruling is "Only what the patch set itself created is excused; same-user later additions block too." A patch set cannot create a schedule (no schedule/alertRule target kind in the apply resolvers; `PatchSetPipelineDefinition` only *reads* schedule/alert rules for fingerprints). Treating both as blocking applies the ruling directly, it does not invent policy. The design's Risks section discloses it for the PR. Multi-root pipeline create exists (`PatchSetPipelineResolvers` `request.roots`, non-empty array), so the excusal is needed. The draft save diffs roots and preserves existing root ids (`DraftSaveTransaction` insertRoots/deleteRoots on the plan), so a later draft save does not make create-made roots look later. There is no root-update API (grep), so a root id cannot silently change source.
- **(b) Extending the `output` create arm is in scope.** The ticket's Expected text is "when someone adds an alert rule after the apply to an Output the patch set created", and the `output` arm (`deleteCreatedOutput` -> `deleteIfUnboundInternal`) cascades exactly that rule while counting only panels (OutputRepository.scala:355-365). Leaving it out would leave the defect half-fixed. The diff is small.
- **(c) D5 in-transaction count is sound.** `deleteIfUnboundInternal` already takes `SELECT 1 FROM outputs WHERE id = ? FOR UPDATE` after the panel and pipeline locks. An `alert_rules` INSERT referencing the Output takes FOR KEY SHARE on that row, which conflicts with FOR UPDATE, so a concurrent rule insert either committed before the count (READ COMMITTED, the next statement sees it) or waits until this transaction ends, by which time the Output is gone and the FK insert fails. A plain `SELECT count(*) FROM alert_rules` takes no row lock, so the HEL-1629 lock-order note (draft save locks rules before the Output; the pipeline lock serialises them) is unaffected. It runs on `withSystemContext` (privileged pool, DbContext.scala:63), the same context `findAlertRuleDefinitionsAction` uses, so other users' rules are counted. The only caller besides undo is `PatchSetUndoLaneSpec:132` (`.isRight`), and the design names it.
- **(d) Root excusal is right.** The journaled `rootIds` come from the same post-create read as the HEL-1795 `stepIds`/`outputIds` (`captureCreatedChildren`, PatchSetApplyService.scala:209-221). `listRootDataSourceIdsInternal` (PipelineRepository.scala:127) already returns root ids. `JournaledCreatedChildren` is `jsonFormat2` today (PatchSetApplicationRepository.scala:154-157). Adding an `Option` field with a default as `jsonFormat3` reads old rows as `None`, and spray ignores the extra field on old code. The legacy fallback `created_at <= appliedAt` mirrors the shipped HEL-1795 step rule over the same `applied_at` column (V79), and it blocks when in doubt.
- **(e) The test plan proves the defect red-first on the real role.** D6 and task 1.2 build on `PatchSetUndoLaterOutputsSpec`'s fixture (lines 37-135: `SET ROLE helio_app_test`, asserts `rolbypassrls = false`). The red cases go through the real service paths (`AlertRuleService.create`, `PipelineScheduleService.put`, editor `addRoot`) and assert the fixed behaviour. Today they fail with the undo succeeding and the rule, schedule or root gone. The red `.txt` is committed before implementation (C6). The plan has row-level "nothing changed" assertions, no-id assertions over every relevant id, and a route-level 409 to rule out `PATCH_SET_STALE`. Each of the six mutations named in D6 maps to a blocker or excusal it must turn red.
- **No contradictions found** between proposal, design, tasks and the spec delta. Every spec scenario has a matching D6 test. Every AC (the red test on `helio_app_test`, then 409 with nothing changed and HEL-1720 naming) is covered by tasks 1.2 and 3.1.

### Verdict: CONFIRM

### Non-blocking notes

- D5's `output` arm: `deleteIfUnboundInternal` currently returns `Either[Int, Unit]` and the caller maps `Left(n)` to `boundDuringUndo(n)` ("N panel(s) were bound"). When the count includes alert rules, don't let rules be reported under the panel phrase. Either widen the `Left` to carry both counts, or use a combined counts-only phrase. This text is logged at ERROR, not shown to the user, so it matters for honesty, not for correctness.
- D4's shared alert-rule clause is lifted from `DraftRestore`, which names every owned rule with no cap, while `nameList` caps at `NameCap = 10`. Keeping DraftRestore byte-identical is correct. Say in the code doc that the alert-rule clause is deliberately uncapped, or cap it only on the new path, so the next reader does not "fix" one to match the other.
- D4 roots: say which sharing-aware data-source read gives the name (for example `DataSourceRepository.findById(id, Some(user))` or its equivalent). Counting is the safe default whichever read is chosen. Note that the pipeline GET already shows root source names to pipeline readers (`PipelineRootSummaryResponse` carries `dataSourceName`), so hiding is conservative, not load-bearing.
- A root added later via `addRoot` with an inline spec creates a data source that survives the pipeline delete as an orphan. That is outside this ticket (the root still blocks, so the undo never orphans it). Worth a follow-up only if a later ticket lets these roots be excused.
- Grants (`resource_permissions`, no FK) survive a pipeline delete as orphan rows. They are not work, and the ticket does not list them. Recorded only so nobody re-derives this.
