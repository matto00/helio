## Context

`JoinStep.evaluate` merges `leftRow ++ rightRow` (inner and left join). `PipelineAnalyzeService.inferJoin` mirrors "right wins" for lane-kind secondary inputs and is a documented passthrough (left schema only) for source-kind inputs because `analyzeNodes` has no repo access to resolve a DataSource schema. `LookupStep` has its own `leftRow ++ brought` merge (out of scope; follow-up). Rows are `Map[String, Any]`, so column order is not guaranteed at runtime; only the column-name set is comparable.

Owner ruling (binding): auto-prefix the right side; never error, never drop a value.

## Goals / Non-Goals

**Goals:** one shared collision rule used by runtime and analyze; deterministic collision-proof names; parity test; red/green/mutation evidence; surface renames where schemas are computed; dev-DB inventory (read-only) of existing colliding joins; PR-body analysis of bound Outputs/panels.

**Non-Goals:** changing `LookupStep`/`UnionStep`; rejecting collisions; a migration rewriting existing pipelines/bindings; production checks.

## Decisions

1. **Pure helper** `JoinColumnNaming` (in `domain/steps`): `resolve(leftCols: Seq[String], rightCols: Seq[String], joinKey: String): Map[String,String]` returning right-column-name -> output-name for every right column. Rule: key column maps to itself and is DROPPED from the right side's contribution (left copy kept; on a left join with no match the key is the left value; on a matched row the values are equal by construction). Non-key right column not in left -> keeps its name (but its name is reserved). Colliding right column -> `right_<c>`, then `right_<c>_2`, `_3`... until the name is not in (left names U names already taken by non-colliding right columns U already-assigned outputs). Reserved-set must include non-colliding right column names so a rename never lands on a real right column; process COLLIDING right columns in ascending (code-point) name order for determinism (runtime rows are Maps, so no original order exists; sorting makes names independent of map order). Left columns are never renamed.
   - Ragged rows: at runtime the left/right name sets are the unions of the left/right rows' keys (computed once per join evaluation, not per row), so every row is renamed with the same mapping. **Documented divergence:** a column declared in the analyze-time schema but absent from EVERY left row (e.g. empty left input) is not a left column at runtime, so a same-named right column is NOT renamed at runtime while analyze would rename it; with no left row carrying the column nothing is overwritten, so no value is dropped. This is accepted, spec'd, and covered by a parity test case that asserts the divergence explicitly. Empty right rows: no right columns, nothing to rename.
2. **Runtime**: `apply` computes the mapping once from the union of left row keys and right row keys, then builds each merged row as `leftRow ++ renamedRightRow` (key dropped from the right row, other right values re-keyed by the mapping). No value is ever overwritten.
3. **Analyze**: `inferJoin` calls the same helper on schema field names; output = left fields ++ right fields (renamed, key excluded, types preserved). **Source-kind secondary inputs (committed outcome, option a):** the existing root-schema loading does NOT cover a join's secondary source (it only loads ROOT data sources' `inferredSchema`), so add an async pre-resolution step at EVERY `analyzeNodes` call site (PipelineService has five, L354/995/1099/1309/1409 -- grep and centralize the resolution in one helper so none keeps the passthrough): for every enabled join/union/lookup step with a `source`-kind secondary input, load that source's `inferredSchema` via `findByIdInternal` (the same privileged, cross-owner resolution `JoinStep.evaluate` uses; the pipeline ACL is the gate) and pass it into `analyzeNodes` as a new optional map `secondarySourceSchemas: Map[dataSourceId, Vector[SchemaField]]` (default empty so existing callers compile). `analyzeNodes` consults it when the secondary is `source`-kind, exactly as it consults `results` for lane-kind. Unresolvable/missing source or missing inferredSchema -> the existing left-schema passthrough (documented, no error; the runtime still fails with "DataSource not found for join"). Scope note: only `join` consumes it in this ticket; union/lookup keep their current behavior (follow-up if desired) but the map is keyed generically.
4. **Parity test** runs `JoinStep.evaluate` and `PipelineAnalyzeService.analyzeNodes` over the same left/right inputs, for BOTH lane-kind and source-kind secondary inputs, comparing `rows.flatMap(_.keys).toSet` with the inferred schema names, for cases: no collision, single collision, several, `right_x` pre-existing on left, `right_x` pre-existing on right, key on both sides, left join with no match (right-only columns absent from unmatched rows; the inferred schema still lists them), and ragged rows (see Decision 1 divergence note).
5. **Spark path (committed outcome):** `SparkJobSubmitter` DOES implement JoinStep (source-kind only, `df.join(rightDf, Seq(joinKey), ...)`), where same-named non-key columns would stay duplicated/ambiguous. Apply `JoinColumnNaming.resolve` to `df.columns`/`rightDf.columns` and `withColumnRenamed` the colliding right columns BEFORE the join, so Spark output columns equal the in-process engine's. Unit-test the helper on column-name lists (no Spark session needed); if a Spark-session test exists in the repo for the submitter, extend it, otherwise cover via the helper test plus a code-path assertion that the rename call is made.
6. **Frontend / MCP**: these read analyze output; executor verifies no client-side join column computation exists (grep) and that renamed columns flow through (including the source-kind case now resolved by Decision 3); any client-side mirror must use the same rule.
7. **Existing-pipeline impact**: before the change, a bound `cnt` read the right value for matched rows (right overwrote left) and ... after, `cnt` reads the LEFT value and `right_cnt` the right. NOTE this is a value change under the same name, not a no-op: the ticket's own framing ("today they silently read the left value") must be verified against the code (`leftRow ++ rightRow`: right wins, so today they read the RIGHT value on matched rows) and the corrected statement written in the PR body.
8. **Dev-DB inventory** (read-only, exact SELECTs only) of join steps whose two input schemas collide; report.

## Risks / Trade-offs

- Renaming breaks bindings in existing pipelines with collisions (owner-accepted); documented in the PR.
- Ragged rows: mapping derived from key unions; a column present only in some rows still gets a stable mapping.
- Key-column rule: dropping the right key copy changes nothing when the key is the same name on both sides (values equal on matches).
