## Standing Constraints

- [C1] RETIRED (superseded by C6 at the round-1 design gate — its premise that an agent-proposed form cannot bind a source was refuted). Retained, never deleted, per the constraint-id rule.
- [C2] Every new guard must be mutation-proven to go red. `PanelRowMapper.rowToDomain`'s `case _ => OutputPanel` fallthrough means a form test can pass whether or not `form` is registered. Record the mutation.
- [C3] One Flyway migration (V108) carries BOTH the `form_config` column and the `panels_kind_check` widening — never two migrations.
- [C4] `form_config` MUST be folded into `configColumnsOf` and `configColumnValuesOf`. HEL-296/HEL-909: a column in `PanelRow` but absent from those tuples makes writes silently keep the OLD value while returning the new one.
- [C5] Installed `lucide-react` is 1.40.0 while the lockfile pins 1.43.0 (HEL-830 trap). A frontend gate failure naming a lucide export is environmental — confirm by measurement, never fix code to satisfy it.
- [C6] `ProposalPanel` has no typed data-source field, but its generic `config` passthrough reaches `decodeCreateConfig`, so a proposal supplying `config.dataSourceId` creates a form panel SUCCESSFULLY. The loud-400 applies only to the no-config shape. Never claim an agent-proposed form cannot bind a source; never silently drop or auto-repair either shape; a cross-owner `dataSourceId` supplied that way must still be rejected.
- [C7] A mutation must exercise a path the test actually TRAVERSES. `PanelRepository.insert` returns the in-memory panel and `PanelRoutes` has no authenticated GET, so a POST-response assertion never reaches `rowToDomain`. Name the read path and confirm it reaches the mutated code before claiming a mutation proves a guard.
- [C8] Unrecognized form-config field attributes are REJECTED with 400, never silently dropped. A `step` that vanishes on PATCH is the same silent-degradation family as the `PanelContent.tsx` and `PanelRowMapper` fallthroughs. Decode strictness is stated in the spec, not left to the implementation.
- [C9] A deferral must be RECORDED IN AN ARTIFACT, never merely asserted. Round 2 found `PanelPacker.Bounds` claimed as "deferred and reported" while appearing in no artifact — i.e. dropped. Every out-of-scope site is named in design.md with an include/exclude decision and a reason.
- [C10] An if-chain dispatch is NOT typecheck-protected. `PanelContent.tsx` dispatches panel kind via an if-chain, so adding a member to the `PanelKind` union does not fail `tsc` and the file's own "union is closed so this is unreachable" comment silently becomes false — a `form` panel would fall through to `MetricRenderer`. Exhaustive-switch sites fail the build; if-chain sites must be enumerated BY HAND. Never infer frontend coverage from a green typecheck.
- [C11] A tolerant read path must be DESIGNED, not asserted. Strict-on-write and tolerant-on-read are two distinct functions: if the 400-throwing decode is reused on the read path, a row written by a future or rolled-back version becomes a 500-on-read. The tolerant wrapper is named in task 1.9 and proven by task 4.9.
- [C12] When a gate adds a task that WIDENS scope, re-check every scope label and Impact list in the SAME edit. Round 3's `PanelContent` fix (task 3.4) made proposal.md's "types only — no new components" and the section-3 heading false, and left `PanelContent.tsx` absent from every Impact list. A scope label is a claim that decays the moment a task is added.
