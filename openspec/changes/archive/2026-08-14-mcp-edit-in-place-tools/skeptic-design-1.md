## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

**The six ground-truth claims the design docs make about the backend, all independently re-checked against the actual Scala source (not the docs' own assertions):**

1. `UpdateDataSourceRequest(name: Option[String])` — confirmed, `backend/src/main/scala/com/helio/api/protocols/DataSourceProtocol.scala:106`. No other mutable field exists on the case class. Rename-only is correct; ticket.md's own scope-table phrasing ("rename / edit source config in place") is looser than the actual backend surface, so design.md D1's clarification is warranted.

2. `UpdatePipelineRequest(name: String)` — confirmed, `backend/src/main/scala/com/helio/api/protocols/PipelineProtocol.scala:14`. Single field, non-`Option` (required). Matches design.md D1's claim exactly.

3. `UpdatePipelineStepRequest(type: Option[String], config: Option[JsObject], position: Option[Int])` — confirmed, `backend/src/main/scala/com/helio/api/protocols/PipelineStepProtocol.scala:142`. Verified `PipelineService.updateStep` (`backend/src/main/scala/com/helio/services/PipelineService.scala:521-566`): a `type` differing from `existing.kind` → `ServiceError.BadRequest("Cannot change step type ... Delete the step and create a new one instead.")` (line 543-547); a matching/absent `type` proceeds; `config`, when provided, is decoded via `PipelineStepConfigCodec.decode(existing.kind, ...)` — i.e. against the EXISTING kind (line 559), exactly as design.md's Context section states. D2's "omit `type` entirely" call is well-grounded — there is genuinely no successful use of that field from the MCP layer.

4. `UpdateDataTypeRequest(name, fields, computedFields: Option[...])` — confirmed, `backend/src/main/scala/com/helio/api/protocols/DataTypeProtocol.scala:25-29`. Verified `DataTypeService.applyUpdate` (`backend/src/main/scala/com/helio/services/DataTypeService.scala:79-119`): both `updatedRegularFields` (line 90-92) and `updatedComputedFields` (line 110-112) are built via `request.X.map(...).getOrElse(existing.X)` — a wholesale replace when provided, never a per-item merge. Matches the claim exactly; the tool-description requirement (design.md/spec.md) to state this explicitly is warranted given `update_panel_appearance`'s true partial-merge precedent in the same file would otherwise mislead an agent.

5. No existing `helio-mcp` zod schema models `DataFieldPayload`/`ComputedFieldPayload` — confirmed. `grep` across `helio-mcp/src/` finds only TypeScript **response**-type interfaces with this shape (`types.ts:87-99`, `DataFieldResponse`/`ComputedFieldResponse` — read-side), no zod input schema. `write.ts`'s only `nullable()` zod usage is unrelated (metric `description`/`format`). Claim 5 holds — these would be genuinely new input schemas, not a missed reuse opportunity.

6. No existing capability spec covers `write.ts`'s core CRUD tools — confirmed. Searched all `openspec/specs/*/spec.md` for `create_pipeline`/`add_pipeline_step`/`update_panel_appearance`; every hit is an incidental mention inside a *different* capability's spec (e.g. `pipeline-lookup-op`, `mcp-pipeline-shape-tools` documenting that `add_pipeline_step` gained a new `op` value), never a `### Requirement:` that defines these three tools themselves. Read `openspec/specs/mcp-data-source-tools/spec.md` in full: its three Requirements are all about *creating* CSV/REST/SQL sources; nothing about editing an existing source. D4's rationale (new capability, not folded into `mcp-data-source-tools`) holds.

**Cross-checked internal consistency** across ticket.md/proposal.md/design.md/tasks.md/spec.md: the four tools, their field sets, the rename-only/wholesale-replace/type-omission semantics, and the AC list are consistent with each other everywhere I could trace them — except for the contradiction below.

**No placeholders** (`TODO`/`TBD`/deferred decisions) found anywhere in the change dir (`grep -rn "TODO\|TBD"` — no hits).

### Verdict: REFUTE

### Change Requests

1. **design.md D3 ("no body-builder") directly contradicts tasks.md 4.1/4.2's own testing instructions, and neither doc reconciles it — an implementer cannot satisfy both as written.**

   - Tasks.md 1.2/1.4 both describe the `HelioApi.updateDataType`/`updatePipelineStep` methods as taking "an already-built partial body." This phrasing is lifted from the pre-existing precedent in `helio-mcp/src/helioApi.ts:755-759` (the `updateMetric` docstring): *"`patch` is the ALREADY-BUILT wire body ... the tool layer (`write.ts`'s body-builder) does the omit-vs-null encoding before calling this method."* That precedent's "body-builder" is a **named, exported, separately-unit-tested function**: `buildUpdateMetricBody` in `helio-mcp/src/tools/metricSchemas.ts:45-63`, imported into `write.ts` (`write.ts:17`) and called at the `update_metric` registration call site (`write.ts:762`).
   - design.md D3 explicitly **rejects** creating an analogous builder for `update_data_type`: *"an inline `if (x !== undefined) body.x = x` per field at the call site is proportionate; a body-builder would be one more indirection for three lines."* No equivalent decision is recorded for `update_pipeline_step` (2 fields), but D3's own reasoning applies at least as strongly there.
   - Tasks.md 4.1 then requires: *"Unit test the `update_data_type` partial-body construction (only provided keys present; an all-omitted call sends `{}`) — **mirrors `write.test.ts`'s existing `buildUpdateMetricBody` coverage style**."* Task 4.2 makes the identical demand for `update_pipeline_step`.
   - I read `helio-mcp/src/tools/write.test.ts` in full (95 lines, pre-existing from HEL-541, unmodified by this change — confirmed via `git log -- write.test.ts` showing only `cec72098` and `git diff main...HEAD --stat` showing zero changes so far). Its own header comment (lines 1-16) states explicitly *why* `buildUpdateMetricBody` is tested by importing it from its own small module rather than from `write.ts`: `write.ts`'s "full ~20-tool Zod-schema surface is pathologically expensive to type-check under this repo's root `tsconfig.json`/ts-jest combination." Every test in the file is a direct call to the imported, standalone function — there is no example anywhere in this file (or, per the `git log`, anywhere else in `helio-mcp`) of unit-testing logic embedded inline inside a `registerTool` handler closure.
   - Consequence: if the implementer follows D3 literally (inline `if` statements inside the `update_data_type`/`update_pipeline_step` handler closures in `write.ts`, no standalone function), there is **no way to satisfy task 4.1/4.2's literal instruction** to test it "mirroring `buildUpdateMetricBody`'s coverage style" — there is no importable function to call in isolation, and importing anything from `write.ts` directly reproduces the exact type-check cost `write.test.ts`'s own header comment says was the reason `metricSchemas.ts` was split out in the first place. The only way to honor 4.1/4.2 as written is to extract a small builder module (mirroring `metricSchemas.ts`) for `update_data_type`/`update_pipeline_step` too — which directly contradicts D3's explicit "no body-builder, disproportionate for 3 fields" ruling.
   - This is not a stylistic nit: it is a genuine, unresolved conflict between a binding design decision (D3) and a binding task-list instruction (4.1/4.2) that traces to two different, real precedents already in the codebase. An implementer would have to invent the resolution — exactly the class of finding this gate exists to catch. Fix by doing one of:
     - (a) Retract D3 and extract small, named, exported builder functions for `update_data_type` and `update_pipeline_step` (mirroring `metricSchemas.ts`, testable the same way `buildUpdateMetricBody` is) — the option that keeps tasks.md 4.1/4.2 achievable as written and consistent with the only testing pattern this file already has; or
     - (b) Keep D3's inline-construction call but rewrite tasks 4.1/4.2 to specify a different, concretely-achievable test strategy (e.g. explicitly scope them as evaluator/manual verification like task 4.3, not a `write.test.ts`-style unit test) and drop the "mirrors `buildUpdateMetricBody`'s coverage style" language, since it cannot be honored under D3.

2. **(Minor) Ticket.md AC "Follows the pipeline-op wiring / apply-infer parity conventions where a step type touches transform config" is never addressed, referenced, or dismissed anywhere in design.md/tasks.md/spec.md.** This AC's vocabulary (apply/infer parity, per this project's existing new-pipeline-op-wiring convention) applies to adding a *new* step-type/op, not to this ticket's scope (editing an existing step's `config` via PATCH, no new op, no backend change). It is plausibly satisfied trivially — design.md's Context section already establishes that `config` is decoded via the same `PipelineStepConfigCodec` path `add_pipeline_step` already uses (`PipelineService.scala:559`, confirmed above) — but no doc draws that connection or states the AC is satisfied for that reason. An evaluator checking this AC off at the final gate would have to guess. Add one sentence to design.md (or a Planner Note) stating explicitly that this AC is satisfied because `update_pipeline_step` reuses the existing, unmodified `PipelineStepConfigCodec`/kind-check validation path with no new op wiring involved, so the convention has nothing new to apply to.

### Non-blocking notes
