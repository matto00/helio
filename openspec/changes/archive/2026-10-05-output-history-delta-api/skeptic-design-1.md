### Change Requests
1. **False premise on the non-BYPASSRLS proof (design D7, task 4.6).** design says the route spec "asserts `rolbypassrls = false`, as `OutputRoutesSpec` does today". It does not: `OutputRoutesSpec.scala` (1950 lines) creates a NOSUPERUSER role (lines ~101-120) but contains no `rolsuper`/`rolbypassrls` assertion (grep over `api/routes/pipelines` finds none). The only such helper is `appPoolRlsPosture()` in `ApplyProposalSpecBase.scala:~300`. Revise D7/4.6: name where the new spec's fixture comes from (a new spec file, since OutputRoutesSpec is far past the size guidance), and state the explicit assertion (query `rolsuper OR rolbypassrls` through the app pool, assert false, before any 200/404 assertion). Also state the fixture grants cover `output_snapshot_history` (GRANT ... ON ALL TABLES runs after Flyway, so fine) and that grantee/non-grantee seeding goes through a real `resource_permissions` row.
2. **Spec contradiction on sparkline (spec "Comparison resolution").** It says the fields incl. `sparkline` are "independent of `limit`/`since`" and also that `sparkline` "SHALL list the returned points' capture times and headline values". These conflict when `limit`/`since` is passed (and 4.5 asserts "comparison ignores since/limit"). Pick one: either sparkline = the returned `points` (then remove it from the independence list and say so in 4.5), or sparkline is a fixed independent series (then D3 needs a query/size rule, and note design's "no new query" claim would change). Add a scenario that distinguishes them.
3. **Fixture must make the D6 mutations killable (task 4.2/4.3, MISTAKES.md: assertion the fixture guarantees).** The mutation "target from wall-clock now" is indistinguishable from the correct code if the newest point T is at or near the test's "now". Require in 4.2 that T is placed far enough in the past (e.g. now-3d) that `now-7d` and `T-7d` select different points (e.g. points T-9d, T-8d, T-6d with now-7d landing between others), and in 4.3 that earliest+w, current+w and earliest all differ; record the mutation result for each. Also add the empty-history case to the spec: zero points -> current/baseline/availableFrom all null for window and previous_run (design D3 step 2 needs `current`; its behaviour when absent is unstated).
4. **Task 4.10 has no mechanism and the bound is under-specified.** grep finds no statement-counting infrastructure in `backend/src/test`. State how JDBC statements are counted (e.g. wrapping the `DataSource` of both pools with a counting proxy / Hikari `setMetricRegistry` / pg_stat_statements reset+read) and that BOTH pools (app + privileged) are counted. Note `withUserContext` adds a `set_config` statement and BEGIN/COMMIT per call, so "documented bound" must be an actual number written into the spec/design, not "5 round trips". The mutation (per-point query) must be shown to flip the equal-count assertion.
5. **Compare validation placement misses proposal-time grounding (design D2).** The PipelineService hunk is "in `buildOutputsAction`", but proposal-time validation (`resolveOneProposalOutputAnalysis`, PipelineService ~1500+) calls the same private `validateOutputFieldMapping` and not `buildOutputsAction`. Either put the compare check inside `validateOutputFieldMapping` (one site, covers both create and propose) or state explicitly that propose-time accepts a bad compare and only apply 400s, and add a task/test either way. D2's claim that "proposal applies" are covered is true only for apply.

### Non-blocking notes
- Name collision: the new protocol `OutputHistoryPoint` has the same simple name as L1's `infrastructure.persistence.pipelines.OutputHistoryPoint`; the service must import both. Rename (e.g. `OutputHistoryPointResponse`) to avoid an ambiguous-import/aliasing hazard. Note `check-schema-drift.mjs`'s case-class regex is not paren-balanced (documented in-file): keep new protocol case classes free of nested parens/defaults.
- D1: the regex admits `P` and `PT` alone and huge digit runs; `Duration.parse` throws on overflow (`P99999999999999999999D`). Say that the parse is wrapped (-> 400, never 500) and add those to `OutputCompareSpec`.
- 4.8 hedges "real-run (or reducer-produced)"; prefer a real run for at least one seam response (the ticket brief asks for a seam test of the response shape), and mutate by dropping a null as planned.
- The since/limit-prefix claim assumes `limit` >= 1 and `since` parsed as an Instant; keep the 400 tests for both.
- Public summary exposes per-column stats/series for all columns regardless of the panel's control columns; consistent with D8 ("public gets the summary") and with `rows` already being public, so acceptable, but state it in the PR body.
