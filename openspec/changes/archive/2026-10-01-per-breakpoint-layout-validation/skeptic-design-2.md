### Verdict: CONFIRM

D11 closes the two named lockout sources and the general "client-authored invalid breakpoint that differs from the client's baseline" class. Remaining holes are bounded (self-heal via D11.3 re-sync), so non-blocking, but the executor should adopt the notes below.

### Non-blocking notes (executor should fold in)
1. Baseline-vs-server gap (stale tab / MCP agent edits while UI open). D11.2's rule compares against the client's last-acknowledged layout, not the server's stored layout. An UNCHANGED-vs-baseline but invalid breakpoint is sent as-is; if the server's stored copy has since changed (agent repaired xs via the new MCP tool, auto-layout, another tab), it "differs from stored", gets validated and 400s. D11.3 turns this into a visible error plus resync (one lost edit, not a permanent lockout). Cleaner fix: have `persistLayout` send ONLY breakpoints that differ from the baseline (D3 already supports partial PATCH); this also stops a stale valid breakpoint clobbering a server-side change. Recommend adopting; at minimum test the stale case.
2. `persistLayout` `.then` sets `persistedLayoutRef = nextLayout` (the authored layout). With substitution, the server stored the RESOLVED breakpoint, so the baseline must be set from the server response (or the sent body), not `nextLayout`; otherwise a second undo to the same bad snapshot compares equal to baseline, is sent as-is and 400s. Add a test: undo-to-bad, save, undo-to-bad again.
3. Guard substitution when the panel list is not loaded: `resolveDashboardLayout` restricts to live panel ids, so an empty/stale `panels` would yield an empty (valid) breakpoint and wipe stored items. Only substitute when panels are loaded for that dashboard.
4. D11.3 premise is partly stale: a toast already exists (toastListeners.ts:160, generic "Failed to save dashboard layout.") but the thunk (`dashboardsSlice.ts:157-161`) discards the server message via `rejectWithValue` constant. The work is to forward the server's 400 message, not to add a first notification; reword task 3b.3 accordingly. Re-sync must also respect the existing concurrent-fetch upsert guard noted at dashboardsSlice.ts:50-53.
5. Spec requirement "A changed breakpoint must be valid..." still names only `PATCH /api/dashboards/:id`; add `PATCH /api/dashboards/:id/update` (the route the web client uses) for consistency with D3.
6. Naming: create response already has `layout` (lg item); the new `layouts` field next to it is easy to confuse. Consider documenting that `layout` is retained for compatibility and `layouts` is authoritative.
