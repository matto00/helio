## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- Frontend wire shape: `frontend/src/features/dashboards/services/dashboardService.ts:50-58` sends `PATCH /api/dashboards/:id/update` with `{fields:["layout"], dashboard:{layout}}` (the batch route, `DashboardRoutes.scala:80`), NOT `PATCH /api/dashboards/:id` as the design/tasks name it. Both routes funnel to `DashboardService.update`, so the D3 choke-point claim holds, but `UpdateDashboardBatchRequest(fields, dashboard: UpdateDashboardRequest)` wraps the same payload and the design never mentions it. `useLayoutSave.persistLayout` (lines 108-121) sends the whole authored four-breakpoint layout; `DesktopPanelGrid` line ~319 builds `{...layout,[bp]:items}`. The design's claim that the wire carries all four breakpoints is TRUE.
- Write-path list: grep confirms `dashboardRepo.update` in AutoLayoutService:117, PanelService:286, DashboardService:252/264, `replaceContents` in DashboardContentsService:96, plus import/duplicate in DashboardSnapshotRepository. D8 covers these. Panel delete does not write layout (PanelMutationRepository:130).
- Overlap producers: `scaleItemsToBreakpoint` used at AutoLayoutService:105-107, DashboardContentsService:142-144; `scaleWidthAndX` at DashboardProposalService:160; `placeDefaultLayout` (PanelService:268-286) uses lg bottom y for every breakpoint. Matches the design.
- Patch-set rollback/undo send full prior layouts via the update payload (PatchSetApplyRollback:305, PatchSetUndoInverse:99); D7's RestorePriorStored exemption is needed and correct.

### Verdict: REFUTE

### Change Requests
1. LOCKOUT (blocking): the frontend's optimistic panel-create layout diverges from what the server will now store. `frontend/src/features/panels/state/panelThunks.ts:118-143` merges the new panel into the LOCAL dashboard layout (`setDashboardLayoutLocally`), appending to md/sm/xs a `scaleLayoutItem(lgItem, ...)` at lg's y (the same collapse-to-2-columns overlap producer). Nothing refetches the dashboard (only panels are refetched). Today this equals the server's `placeDefaultLayout` output, so the next layout PATCH sends xs "identical to stored". D4 changes the server to per-breakpoint bottom y, so the client's local md/sm/xs for the new panel will differ from stored AND is likely overlapping/out of bounds. The next drag in lg then PATCHes all four breakpoints, the xs differs from stored, gets validated, and returns 400. `useLayoutSave` swallows the error (`.catch` no-op), so the user's edit silently never persists, and every retry fails until a reload. This breaks AC6 / owner ruling C2 ("existing dashboards stay editable"). The design's "Frontend: tests only, no behavior change" is wrong. Required: change the design so the client adopts the server's placement (preferred: after create, replace the dashboard's layout from the server, e.g. refetch the dashboard or return the full layout; or mirror D4 exactly in `panelThunks`), delete/replace the client-side collapse projection, add a test that createPanel followed by a layout PATCH is accepted, and add a task enumerating every `setDashboardLayoutLocally` caller (panelThunks, DesktopPanelGrid, useLayoutUndoRedo, CommandBar:122/130, dashboardsSlice) for the same divergence.
2. LOCKOUT (blocking, same family): layout undo/redo (HEL-1028; `useLayoutUndoRedo.ts:36,47`, `CommandBar.tsx:122,130`) restores a pre-interaction authored snapshot locally, which `useLayoutSave` then persists. Sequence: dashboard has stored-bad xs; the user drags in xs (repairing it, now stored valid); user presses undo, so the client holds the old bad xs, which now DIFFERS from stored, is validated, 400, swallowed. Local view reverts while the server keeps the repaired one, silent divergence. D7's exemption covers only server-side patch-set undo. Required: state the intended behaviour and test it (e.g. frontend surfaces the 400 / re-syncs from server, or undo snapshots are taken from the resolved layout so they are valid). Also require that the layout PATCH failure no longer be fully silent, or explicitly justify it.
3. (Required clarification) Name `PATCH /api/dashboards/:id/update` and `UpdateDashboardBatchRequest` in D3/tasks 2.1/2.4 and the spec; the route-level tests in 2.3 must run through BOTH routes. Task 2.4's "re-confirm the PATCH wire shape" is answered by the above; update the text to the verified shape so the identity-vs-presence justification cites the real endpoint.
4. (Required clarification) D2 must say the identity comparison is made on the normalized payload (`validateDashboardLayoutItems` trims panelId) against stored, so a whitespace difference is not a spurious "changed".
