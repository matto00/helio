### Change Requests

1. **D5 and the proposal (and task 2.3): stop claiming the composed spec proves current-run exclusion. Say what it really guards.** Evidence: PipelineRunService.scala:1446 and :1565 start the history write and alert evaluation concurrently; AlertEvaluationService.scala:126-127. Revise D5 to say the following:
   - `baseline == run 1's value` catches self-inclusion only when run 2's history point is already committed at `listRecent` time, which is a race. It is a probabilistic guard for exclusion, not a proof.
   - The deterministic exclusion proof remains `AlertEvaluationServiceSpec` (:420/:433/:446). The composed spec's job is wiring (M1-M3).
   - Add a characterization task, **M4**: temporarily change `HistoryBaseline.scala:97` to keep the triggering run's point (drop the `filterNot`). Run the new spec 5x under `nice -n 19 sbt "testOnly com.helio.api.ApiRoutesAlertHistoryWiringSpec"`, record how many runs went red, and revert. A red is not required for M4. The measured rate goes into `mutation-evidence.md` and the PR, so the AC3 claim is backed by a number rather than a narrative.
   - If M4 reds 0/5, state in the evidence file and PR that AC3's distinction is not observable at the composed layer without a production change (which needs driver escalation per ticket.md). Do not present the assertion as an exclusion check.
   - D7's sentence "exclusion is by run id, so with exactly two points the prior is unambiguous" is only true for correct code. Reword it the same way.
2. **D3: say explicitly that `amount` cells must be JSON numbers** (for example `{"columns":[{"name":"amount","type":"integer"}],"rows":[[10],[20]]}`, then run 2 sums to 100), not the seam spec's string cells. Threshold rules use `extractMetric`, which treats every `String` as `None` (AlertEvaluationService.scala:45-52). With string cells the threshold rule never fires, so the "threshold fires" assertion would fail, or tempt a re-worded assertion. Also update "reuse the seam spec's seeding pattern" to note this difference.
