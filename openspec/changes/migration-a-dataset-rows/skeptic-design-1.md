## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

- **Column/constraint names: correct.** `V4__data_sources_and_types.sql` defines `source_type TEXT NOT NULL CHECK (source_type IN ('rest_api','csv','static'))`; `V49__add_image_source_type.sql:4-8` drops/re-adds `data_sources_source_type_check`. No `kind` column on `data_sources`. The design's correction holds.
- **V-number: correctly left unresolved.** The worktree's max is V105 and `origin/main` (freshly fetched) is also V105. Task 1.1 says to re-verify at commit time. Fine.
- **`config` type.** `V33__jsonb_columns.sql:33-34` converted `data_sources.config` to JSONB. design.md Context calls it "text/JSON". That is harmless, but `'{}'` must be written as JSONB.
- **RLS precedent: the design cites the wrong one.** `V35` never ran a DML backfill. The repo's established pattern for DML against a FORCE-RLS table in a migration is the **`NO FORCE` / `FORCE` bracket** in `V96__canonicalize_inferred_schema_type.sql:26-58` and `V94__outputs_model.sql` sections 0/22 (lines 122-131, 1309-1330). `V96`'s header says exactly why: the `data_sources_owner` policy calls `current_setting('app.current_user_id')` without `missing_ok`, which throws SQLSTATE 42704 when unset. That is the failure that broke three prod deploys (HEL-943). `V94` also creates new tables *without* FORCE and applies FORCE at the very end so the owner's own inserts pass. The harness that proves this non-superuser path is `FlywayNonSuperuserMigrationSpec` (role `helio_migration_test`), not `RlsOwnerTablesSpec`.
- **Persistence-layer kind mapping (not addressed anywhere in the design).** `DataSourceRepository.scala:40-76` `rowToDomain` dispatches on `row.sourceType` against `DataSourceKind.Static = "static"` (`DataSource.scala:189`). `case other => throw new IllegalStateException("Unknown data source type in DB: ...")`. `domainToRow` (`:88`) writes `DataSourceKind.Static` (`"static"`) for every `StaticSource` insert.
- **Readers use the blob's `columns` array, not just rows.** `PipelineRowJson.parseStaticRows` (`:138-150`) takes column names and their order from `columns`. `SparkJobSubmitter.loadDataFrame` (`:166-190`) builds its Spark `StructType` from each column's **declared** `type` (`sparkDataType(col.fields("type"))`). `DataSourceService.previewStatic` (`:929-946`) takes its headers from `columns`. `inferred_schema` holds *runtime-derived* types (`staticColumnRuntimeType`, HEL-893). In the real fixture, a column declared `integer` holds values that `inferred_schema` records as `float`.
- **Real fixture exists.** `backend/src/test/resources/db/fixtures/hel904-real-dump.sql` has genuine `static` rows (lines 1187-1190), including one with `owner_id NULL` (line 1187).
- **Call-site enumeration matches the tree.** `grep parseStaticPayload|readRawConfig|updateStaticPayload` gives the same sites as design.md Context.
- **HEL-1075 design** (`openspec/changes/archive/2026-09-10-decide-dataset-row-storage/design.md:82-88,117-125`) says to backfill, stop writing `config` for dataset sources, and move both readers. Decision 4 (b) matches its intent. It does not say whether to clear `config` or keep it at rest. Decision 3 resolves that explicitly, and I accept its reasoning (see CR 3 for a precondition).

### Verdict: REFUTE

### Change Requests

1. **Decision 2 is wrong and hands the most dangerous part of this migration to the executor.** Its claim that the backfill and `UPDATE data_sources` "execute under real RLS … the intended proof surface" is false for this schema. Under FORCE with no `app.current_user_id`, the `data_sources_owner` policy throws 42704, so the `UPDATE data_sources`, the `dataset_schema` backfill, the `config` clear, and even the `INSERT … SELECT FROM data_sources` feeding the backfill all fail as `helio`. Option (b), setting `app.current_user_id` per source row inside a migration, is not a viable mechanism. Required revisions:
   - Replace Decision 2 with the established `V94`/`V96` pattern: `ALTER TABLE data_sources NO FORCE ROW LEVEL SECURITY` before the first statement that touches `data_sources`, and restore `FORCE` at the end. Create `dataset_rows` with ENABLE plus its policy, but apply `FORCE` only after the backfill, as `V94` does for `outputs`/`node_snapshots`.
   - Cite `V94`/`V96` instead of `V35`.
   - Retarget task 3.2 at `FlywayNonSuperuserMigrationSpec` (the non-BYPASSRLS migration-role harness). `RlsOwnerTablesSpec` covers runtime access only.
   - Add a task to register `dataset_rows` in `RlsPolicyGuardSpec`'s expected-table list.
2. **Migrated rows would crash the app, and new static sources would be rejected.** The design says the ADT and `DataSourceKind` stay untouched (Non-Goals, Decision 5). But once `source_type = 'dataset'` is in the DB:
   - `rowToDomain` hits `case other => throw IllegalStateException` for every migrated source. That breaks `findAll`, so the whole data-source list call fails for any owner who has one.
   - `domainToRow` still writes `'static'`, which the new CHECK rejects. `createStatic` (and the inline-static creation paths in `PipelineService:763`, `PipelineProposalService:374`, and `PatchSetApplyResolvers`) would all fail on insert.

   The design must specify the persistence-boundary mapping in this ticket: `rowToDomain` maps `'dataset'` to `StaticSource`, and `domainToRow` writes `'dataset'` for `StaticSource`. It must also add tasks and tests for both directions. This stays compatible with HEL-1073 owning the ADT rename and the wire alias. `DataSourceKind.Static` stays `"static"` on the wire (`StaticSourceResponse.type`); only the stored string changes. The spec delta should state this.
3. **Specify where the column list (names, order, declared types) lives after `config` is cleared.** All three readers need the blob's `columns` array, and Spark needs the *declared* type. `dataset_rows` holds only per-row values, and the proposed `dataset_schema` backfill source (`inferred_schema`) holds runtime-derived types that differ from declared ones (fixture line 1187: declared `integer`, stored as a float-typed number). A source with zero rows has *only* `columns`. As written, clearing `config` (Decision 3) destroys the declared schema, and the "behavior-preserving" AC cannot hold for Spark. Required revisions:
   - Decide explicitly that `dataset_schema` is backfilled from the blob's `config->'columns'` (declared `{name,type}` in order). That also makes it genuinely the "declared schema", consistent with the static-data-connector delta's "persist the declared columns as `dataset_schema`". Alternatively, justify another source and show that Spark's output types are unchanged.
   - State that `readDatasetRows` reconstructs `{columns, rows}` from `dataset_schema` plus the `dataset_rows` ordered by `seq`.
   - Reconcile this with the ticket's "backfilled from their existing inferred schema" wording (if you diverge, record why in the design; the ticket text was written before the `kind` correction too).
4. **Pin the shape of `dataset_rows.data`.** Is it the positional array (`["a", 1, 1.2, true]`) or an object keyed by column name? This is an irreversible storage choice. Either reading of the task is plausible, and it affects duplicate or renamed column names and HEL-1077's write API. Choose one and record it (checking the v0.8 spec's schema-declaration decision).
5. **Fix the migration statement order in tasks 1.6/1.7.** The current CHECK allows `'static'` and not `'dataset'`, so `UPDATE … SET source_type = 'dataset'` (task 1.6) violates it unless the constraint is dropped *first*. Required order: drop the constraint, run the UPDATE, re-add it. Also specify that the 1.4 parity gate is an in-migration `DO` block that `RAISE EXCEPTION`s on mismatch (it must abort the transaction). A test-only check does not protect prod.
6. **Resolve the contradiction between the spec delta and the design on key types.** `specs/dataset-row-storage/spec.md` says `id` and `data_source_id` are UUID; design Decision 1 says TEXT. `data_sources.id` is TEXT (`V4`), so the spec delta must say TEXT. (The `data-source-persistence` delta's "`id` (UUID PK)" is also stale; correct it while you are there.)
7. **Define what happens to sources with `owner_id IS NULL`, which exist in the real fixture.** Their backfilled rows are invisible on the app pool by policy. The spec scenario "visible to that row's owning user" is undefined for them. State the expected result and cover it in 4.2.
8. **Make Decision 4's writes atomic.** `refresh` as delete-then-reinsert, and `create` as source insert, rows insert, then schema upsert, must run in one DB transaction (a single `DBIO` under `withUserContext`). Otherwise a mid-way failure leaves a dataset with zero or partial rows and no blob to fall back on. Also state that refresh updates `dataset_schema` (the spec delta says so; tasks 2.5 does not).
9. **Name the concrete fixture and before/after mechanism in tasks 4.1/2.6.** Use `hel904-real-dump.sql` (it already has genuine `static` sources). Specify that the "before" outputs come from the legacy readers on the pre-migration fixture state and are captured as golden values in the test. Otherwise "diff before/after" is unexecutable once the legacy readers are removed in the same diff.

### Non-blocking notes

- The static-data-connector delta still says "`kind = 'dataset'`" and "stored `kind`". Say `source_type`, to match the correction.
- The `seq` "stable JSONB array order" risk note is correct (JSONB arrays preserve order). Use `WITH ORDINALITY`, as `V96` does.
- Decision 1's index `idx_dataset_rows_data_source_id ON (data_source_id, seq)` is fine. Consider `UNIQUE (data_source_id, seq)` now, since HEL-1077's append concurrency will want it.
