### Two real gaps found

**Gap 1 — missing JSON Schema contract update (a genuine "missing contract update," not a nit).**
`AssistantConversationResponse` gains 2 new fields per D1/task 4.1, but `schemas/assistant-conversation
.schema.json` (title `"AssistantConversationResponse"`, currently `required: [id, title, pinned,
updatedAt, transcript]`, `additionalProperties: false`) is not mentioned anywhere in proposal.md,
design.md, or tasks.md — I grepped all four artifacts for `schemas/`/`schema.json`/`check-schema-drift`
and got zero hits. I ran `node scripts/check-schema-drift.mjs` against the current tree and confirmed
it's clean today (`schemas in sync with JsonProtocols (55 checked...)`). `.husky/pre-commit` runs
`npm run check:schemas` (→ this exact script) as a **mandatory** pre-commit gate (verified by reading
`.husky/pre-commit`). Once the case class gains `hopBudgetExhausted`/`searchedWithNoResults` with no
matching schema properties, this script will fail with "in case class, missing from schema" and block
every commit unless the executor bypasses hooks (against CLAUDE.md policy) or discovers this
reactively mid-implementation. Proposal.md's own "No schema/migration changes" line (Impact section)
is factually wrong for this specific meaning of "schema" — it's true for DB migrations but false for
the JSON Schema contract.

**Gap 2 — D4's system-prompt nuance, as literally scoped, risks being an actual textual contradiction,
not "two branches of one decision."** The existing system-prompt sentence
(`AssistantSystemPrompt.scala:57-58`) is unconditioned: *"If find turns up nothing relevant to the
goal, don't give up: propose_pipeline or propose_combined can create the data the goal needs from
scratch."* Design.md D4 and tasks.md 3.1 both commit to this sentence staying exactly as-is
("the existing... sentence stays," "without removing the existing 'propose anyway' guidance") while a
**new, separately-worded** clause is added for the underspecified-goal case. Read literally, on the
identical trigger ("find returns nothing"), the prompt would then contain two co-equal, unlinked
imperatives — one absolute ("don't give up, propose anyway"), one conditional ("ask a clarifying
question first") — with no explicit textual link between them establishing which one governs when.
Whether Claude actually gets confused isn't testable (correctly flagged as a Risk in design.md), but
the coherence problem is squarely a text-authoring one, and the plan's instruction to leave the old
sentence untouched is what creates it. This needs the OLD sentence itself edited to become one explicit
branch of the SAME conditional (e.g., "...for goals concrete enough to act on. If the goal is too
underspecified to confidently build a propose_pipeline/propose_combined call, ask a clarifying
question instead."), not left as an independent, unconditioned absolute next to a new conditional one.

### Verdict: REFUTE

### Change Requests

1. Add a task to tasks.md section 4 (design.md D1) to update `schemas/assistant-conversation
   .schema.json`: add `hopBudgetExhausted`/`searchedWithNoResults` as optional (`type: ["boolean",
   "null"]` or simply absent-from-`required`, per this repo's existing optional-field schema
   convention) properties, and correct proposal.md's Impact/"No schema/migration changes" line to
   scope it explicitly to DB migrations (it is currently misleading about the JSON Schema contract).
   Without this, `npm run check:schemas` (a mandatory `.husky/pre-commit` gate) will fail the moment
   task 4.1 lands.
2. Revise design.md D4 and tasks.md 3.1 to require editing the EXISTING "don't give up, propose
   anyway" sentence in `AssistantSystemPrompt.text` — not just appending a new sentence next to it —
   so the two branches are explicitly and textually linked as one conditional (e.g., qualify the old
   sentence with "for goals concrete enough to act on" and have the new clause read as its explicit
   else-branch). As currently scoped ("existing sentence stays," unedited), the plan risks shipping
   two literally-contradictory absolute instructions on the same trigger condition, which is exactly
   the failure mode D4 claims to avoid.

### Non-blocking notes

- `AssistantTurnResult.toolCallCount` (already-shipped field, `AssistantService.scala:126-130`) counts
  `ToolUse` blocks across the ENTIRE cumulative `fullHistory` (all turns of a multi-message
  conversation, not just the newest turn) — a pre-existing scoping quirk unrelated to this ticket.
  D6/task 5.2 correctly avoids reusing it for telemetry and instead re-derives `toolCallCount` from
  `result.fullHistory`'s new turns only (mirroring `converseFlow`'s own `.drop(history.length)`
  slicing) — this is the right call, but tasks.md doesn't say *why* `result.toolCallCount` is
  unsuitable, which could tempt an implementer to "simplify" back to the wrong field. Worth a one-line
  comment pointer when implemented.
