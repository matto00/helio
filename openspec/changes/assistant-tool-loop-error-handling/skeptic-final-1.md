### Blocking issue found during live verification

**A conversation that hits the hop cap becomes permanently unusable for any further message — directly contradicting this ticket's own "graceful give-up" acceptance criterion.**

Reproduced twice, deterministically, against the real dev backend + real Claude API:

1. In an existing chat, sent a prompt that forces 4 sequential `find` calls (exceeding the 3-hop cap). The UI correctly rendered the new "cut short" `ToolCallIndicator` treatment and the synthesized "I couldn't find enough in 3 lookups — can you narrow this down?" fallback bubble — this part of design.md D5 works exactly as specified.
2. Independently confirmed via `fetch()` from the browser that the persisted transcript's LAST turn is `{role: "assistant", content: ["text", "tool_use"]}` — i.e. it ends in an unresolved `tool_use` with no paired `tool_result`, which is exactly what `ClaudeToolOutcome.HopBudgetExhausted(history :+ assistantTurn, ...)` produces (`ClaudeClient.scala:105`) and what `AssistantConversationRoutes.converseFlow` persists verbatim (`result.fullHistory.drop(history.length)` → `service.appendTurn`, `AssistantConversationRoutes.scala:127,137`).
3. Sent **any** follow-up message in that same conversation (literally taking the assistant's own "can you narrow this down?" advice) — it fails, twice in a row, with the identical error surfaced to the user:
   `Claude API error (400): {"type":"error","error":{"type":"invalid_request_error","message":"messages.22: \`tool_use\` ids were found without \`tool_result\` blocks immediately after: toolu_01GaaeQtgJLEnKFrXYYFscP9. Each \`tool_use\` block must have a corresponding \`tool_result\` block in the next message."}}`

**Root cause**: `AssistantService.seedHistory` (`AssistantService.scala:87-90`) unconditionally appends the new user turn as plain text onto whatever `history` it's given: `history :+ ClaudeToolMessage.text(ClaudeRole.User, turnText)`. When `history`'s last turn is a hop-cap-exhausted assistant turn ending in an unresolved `tool_use` (exactly the state `converseFlow` persists for this ticket's own new feature), this violates the Anthropic Messages API's structural invariant that a `tool_use` block must be immediately followed by a `tool_result` in the very next message. Every subsequent `POST /:id/converse` call against that conversation fails identically — it's not a transient/flaky error, it's a deterministic function of the persisted transcript shape.

This is squarely in-scope for HEL-667: it is triggered by, and only by, the exact "hop cap hit" failure mode this ticket claims to handle "gracefully" (ticket.md: *"graceful give-up, not a silent failure or a forced low-quality guess"*). The `searchedWithNoResults`/`FinalResponse` path is unaffected (that outcome's trailing turn is always text-only, never a dangling `tool_use` — confirmed by reading `ClaudeClient.sendWithTools`'s `FinalResponse` branch, `ClaudeClient.scala:100-103`). No test in the diff exercises two sequential `converse` calls on one conversation (`AssistantConversationRoutesSpec` only ever posts once per conversation in the turn-outcome-signal tests, `AssistantConversationRoutesSpec.scala:297-347`) — this is exactly the missing coverage that would have caught it. The evaluator's live check (evaluation-1.md Phase 3) confirmed the hop-cap turn renders correctly but never sent a follow-up message afterward, so this never surfaced.

### Verdict: REFUTE

### Change Requests

1. **Fix conversation continuation after a hop-cap-exhausted turn** (`backend/src/main/scala/com/helio/services/AssistantService.scala:87-90` `seedHistory`, and/or `backend/src/main/scala/com/helio/api/routes/AssistantConversationRoutes.scala:114-146` `converseFlow`'s persistence of `newTurns`). Before continuing (or when persisting) a `HopBudgetExhausted` outcome's trailing turn, any unresolved `tool_use` block(s) must be paired with a synthetic `tool_result` (mirroring the exact `isError` idiom this ticket already establishes elsewhere — e.g. a canned "not executed — the tool-call budget was reached before this could run" result) so the persisted transcript is always structurally valid for the next `converse` call. Add a regression test doing two sequential `POST /:id/converse` calls on the same conversation where the first hits the hop cap — the second call must succeed (not error), which is the scenario currently absent from `AssistantConversationRoutesSpec`.
