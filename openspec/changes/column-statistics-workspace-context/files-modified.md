- **Cycle-4 fix (`skeptic-final-3.md`, REFUTE round 3) — a DIFFERENT function/location than rounds 1-2, not another `asNumeric` gap**: round-3's cold skeptic confirmed `asNumeric`/`rawNumericCandidate` are now structurally airtight (adversarially attacked, held), then found the SAME symptom (fabricated `mean`/masked-`null`) survives one level up: `computeColumnStatsForField`'s running `numericSum` can overflow even though every value it sums individually passed `asNumeric`. **The human coordinator personally reviewed this and mandated the fix location** (quoted verbatim in `workflow-state.md`): guard at the `WorkspaceContextColumnStats` construction site (Scala `:377` at the time), not the intermediate `(min, max, mean)` tuple the skeptic proposed — "the terminal boundary... nothing performs further arithmetic on it... one invariant covers min, max, and mean together." Implemented exactly as directed on both sides. **While implementing, empirically discovered (via a temporary probe, removed after verification) that the human's own assumed fix — a bare `.filter(_.isFinite)` on the constructed `mean` — does NOT actually work**: Java's `math.round(Double): Long` silently CLAMPS a non-finite (or merely `Long`-range-exceeding) input to `Long.MaxValue` rather than propagating non-finiteness, so the OLD `math.round(mean * 10000) / 10000.0` rounding technique produces a deceptively-FINITE fabricated value (confirmed: `math.round(Double.PositiveInfinity)` → `Long.MaxValue` → `9.223372036854776E14`, and `Double.isFinite` on THAT is `true`) — a naive post-round finiteness check would never catch it. Root-caused and fixed the ACTUAL defect: replaced the rounding technique with `BigDecimal.setScale`-based rounding (no intermediate multiply-by-10^scale step, so no overflow surface), then applied the finiteness filter to that. This also means a genuinely huge-but-mathematically-correct mean (e.g. one enormous legitimate outlier averaged with 499 ordinary rows) is now correctly REPORTED rather than either fabricated OR needlessly dropped to `None` — verified via a dedicated regression test on both sides.
- **Pre-existing, unrelated limitation discovered while writing the DB-backed serialization-boundary test (not fixed, flagged as a spinoff)**: writing a `JsNumber` of magnitude ~1e308 through the REAL `dataTypeRowRepo.overwriteRows`/`listRows` round-trip fails — PostgreSQL's `jsonb`-to-`text` cast canonicalizes large numeric literals to their full plain-decimal-digit expansion (e.g. ~309 characters for `1e308`), and spray-json's `JsonParser` has a hardcoded `maxNumberCharacters = 100` limit, so re-parsing the stored value throws `ParsingException: Number too long`. This is a genuine pre-existing gap (the app currently cannot durably store/retrieve ANY sufficiently large `float`/`integer` Structured value at all, for any reason, not specific to column stats) — out of scope for this ticket (CONTRIBUTING's refactor discipline: real but non-trivial bugs go to a spinoff ticket, not an inline fix mid-cycle). **Consequence for change request 3** ("one test that asserts the invariant at the serialization boundary"): implemented in the PURE-UNIT spec file instead of a DB-backed one, using the explicitly-permitted "(or the relevant WorkspaceContextResponse/columnStats slice)" alternative — constructs a full `columnStats` map via `computeColumnStats` (in-memory, no DB round-trip needed) and round-trips it through the REAL spray-json wire format to confirm the actual serialized JSON never contains a literal `"NaN"`/`"Infinity"` token, in addition to the domain-level finiteness check.
