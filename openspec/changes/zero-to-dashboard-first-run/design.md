## Context

Premise facts (verified on main 7417e638): CSV columns always materialize as `string`; `cast` is a real step (`{casts:{field:string|integer|long|double|boolean|date}}`, failure -> null); no shape emits cast so it is prepended as an explicit step; inline csv roots are rejected by apply (create the source first, reference `sourceId`); `CombinedProposalService` resolves the `$pipelineOutput` sentinel only when exactly ONE output exists; panels without `layout` stack at x=0 (full width) via `PanelService.placeDefaultLayout`, while a partial explicit layout drops the other panels and xs scaling of mixed x/w overlaps; `/api/proposals/apply`, `PipelineProposalService`, `DashboardProposalService` have no Claude dependency; the authoring/refinement/assistant routes are tier-gated by `ChatAccessService`; no authenticated `/dashboards/:id` route exists; selected dashboard is Redux-only; `ChatPage` has no context/prefill plumbing; tier is `state.auth.currentUser.tier`.

## Goals / Non-Goals

Goals: deterministic zero-Claude path; <= 60 s / <= 5 interactions; atomic with rollback; mobile-safe; a11y. Non-goals: persona templates (HEL-1210), `RolledUpTemplateSlugs` (HEL-1218), editing the sentinel contract.

## Decisions

1. **Server-side rule builder, not a client chain.** `FirstRunDashboardService.build(userId, sourceId)` in `services/firstrun/`, route `POST /api/first-run/dashboard` (authenticated, NOT tier-gated, no ClaudeClient constructor parameter, so the zero-Claude property is structural and also asserted with a counting `ClaudeTransport` double on the full `ApiRoutes`: `ApiRoutes` gained two default-preserving test seams, `claudeConfigProvider` and `claudeTransportFactory`, so the double is wired through every Claude-bearing service, with a positive control proving a beta user's authoring call does reach it). Rationale: type detection needs row data, atomicity needs rollback, and it is testable without a browser.
2. **Atomicity without extending the sentinel.** Rather than extend `$pipelineOutput` to name outputs (a contract + schema + drift change), the service calls `PipelineProposalService.apply` (create + run; its own failure rollback) then builds a `DashboardProposal` with real output ids and calls `DashboardProposalService.apply`; on dashboard-phase failure it calls `PipelineProposalService.rollback` exactly as `CombinedProposalService` does. A rollback test is required: the dashboard phase is injected as a function (`applyDashboard`, wired to `DashboardProposalService.apply`, which is final) so the spec injects one that fails, asserting the pipeline no longer exists (red first against a service that skips rollback). `CombinedProposalService` is not modified.
3. **Type-detection heuristic (stated, deterministic).** Sample up to the first 200 data rows of the source via `DataSourceService.preview(id, 200, user)` (the existing CSV read, which uses `SchemaInferenceEngine.parseCsvRows`); the source is looked up with `DataSourceRepository.findByIdOwned(id, user)` (another user's or unknown id -> 404; non-csv source type -> 400). A column is `numeric` if >= 90% of non-blank cells match a plain decimal/scientific literal (`^[+-]?(\d+\.?\d*|\.\d+)([eE][+-]?\d+)?$`, finite) and is then cast `double`; thousands separators, currency symbols and a trailing `%` are NOT accepted, because the `cast` step uses `String.toDouble` and would turn them into null (such a column falls through to categorical/text); `integer`-only columns still cast `double` (keeps aggregates uniform). The measure column for every aggregating shape is the leftmost numeric column that is not identifier-shaped (`id`, `*_id`, `fooId`), else the leftmost numeric column. Numeric is tested FIRST: a column that is numeric is never date-like (so an epoch-numeric column is numeric; datebucket would also accept epoch longs but we deliberately do not bucket them). A non-numeric column is `date-like` if >= 90% of non-blank cells parse via exactly the formats `DateBucketStep.parseToUtcDate` accepts for non-epoch input (Instant, offset datetime, ISO local datetime, space-separated datetime, ISO `yyyy-MM-dd`); the predicate is a shared helper extracted from/next to DateBucketStep so the two cannot drift; `MM/dd/yyyy` and other non-ISO formats are NOT date-like. Date-like columns are NOT cast (cast `date` is a no-op) and are consumed by `time-series`'s datebucket. A column is `categorical` if it is neither and its distinct count in the sample is >= 2 and <= max(20, 50% of sampled rows), otherwise `text`. Header names are used as the field names; blank headers are skipped. Cast step is emitted only for numeric columns, as the first step.
4. **Shape rule and outputs (max 3 outputs, deterministic order).** Always output 1: `passthrough` over all columns (a table; table-only when no numeric column). If a date-like and a numeric column exist: `time-series` (granularity day when the sample has <= 90 distinct dates, else month, counted over the 200-row sample; `sum` of the first numeric column, alias `<col>_sum`) -> chart output. If a categorical and a numeric column exist: `top-n` (`n=10`, direction desc, measure = first numeric) -> chart output; since top-n takes no group-by, it is preceded by an `aggregate` group by the categorical column summing the numeric measure (alias `<col>_sum`). Step wiring: the `cast` step (hand-built) and the `aggregate` pre-step for top-n (hand-built) have clientIds `cast` and `agg_topn`; the shape-expanded steps come from `PipelineShapeService.expand` (passthrough select, datebucket/aggregate/sort for time-series, sort/limit for top-n) with clientIds `<shape>_<i>`; each output chain's first step has `parentStepId` = `cast` (or no parent plus the single root's `rootClientId` when there is no cast), later steps chain via `parentStepId`, and each output's `nodeStepClientId` is its chain's last step. Each output gets one panel; the table panel is first, full width. Names derive from the source name + shape.
5. **Layout (amended round 1).** Default placement is NOT full width (table 6x6, chart 6x4 at x=0 -> half width at every breakpoint, leaving a blank half-column on phones), so every panel gets an explicit `layout` (all-or-none, since a partial layout drops the others): lg `x=0, w=12`, `h` = 6 for the table and 4 for charts, `y` cumulative (table first). md/sm/xs derive via `LayoutBreakpointScaling` (w=10/6/2 = full width, y/h unchanged), so items stack full width without overlap (all x=0, w=full). A test asserts the PERSISTED layout (applyLayout swallows update failures, so the test reads the layout back from the repository, not the apply response): no overlapping items and full width at lg/md/sm/xs for 1, 2 and 3 panels.
6. **Run before render.** Pipeline apply submits a run synchronously enough that outputs hold rows when the dashboard exists (verified by the existing apply path; run failure/block -> 422 and rollback). The service returns dashboard id, panel count, pipeline id, source id.
7. **Landing URL.** (Amended in implementation: `/dashboards/:id` is added to the `sections` registry as a non-nav dashboards-picker route and `isDashboardViewPath` replaces the `pathname === "/"` checks in `App.tsx`/`CommandBar.tsx`, otherwise the landed dashboard would lose its rename/zoom/appearance/share controls.) Add protected route `/dashboards/:id` inside `AppShell`: wrapper `DashboardRoute` waits for `fetchDashboards` to settle, dispatches `setSelectedDashboardId(id)` (unknown id -> not-found state with link to `/`), renders `PanelList`. After build the client navigates to `/dashboards/<id>` (the public viewer is the different, longer `/dashboards/:id/panels`).
8. **Drop zone supersedes the checklist; checklist is the secondary path.** `useOnboardingHost` activation unchanged; `PanelList` renders `FirstRunDropZone` (not the checklist) when zero dashboards and the user has not chosen "Set up step by step" (local state); the checklist remains for that path and for the re-open affordance. Spec corrected to 3 steps.
9. **Client upload reuse, not a fork.** Extract AddSourceModal's `inferFromCsv` -> force-string fields -> `createCsvSource` into shared plain functions in `features/sources/utils/csvSourceCreate.ts` (`forceStringFields`, `createCsvFromFields`, `inferAndCreateCsv`, `createCsvFromUrl`; no hook is needed because the functions hold no React state, and each caller owns its own refetch/selection follow-up) consumed by both AddSourceModal (behavior unchanged, its tests stay green) and the drop zone; URL path uses the existing `{type:"csv", config:{url}}` create. Client-side guards: file size over a configured cap shows an error before upload only if a cap constant is available client-side, otherwise rely on the 413 message; surface status-specific messages (413 size, 400 not-csv/not-https, 502 fetch failed, zero-column CSV).
10. **Beta refine.** Visible iff `currentUser.tier` is `beta` or `owner` (same check pattern as ChatPage/SidebarBody; no new tier logic, no backend call to decide). Click navigates to `/chat` with `location.state.draft` = prompt naming the source and pipeline (names + ids); `ChatPage`/`MessageComposer` read it once as the initial draft. Free users: the control is not rendered. The existing HEL-1205 gate remains the enforcement.
11. **Telemetry.** `track("firstrun_file_dropped", {source})` when a file/URL is accepted by the drop zone (drop or file picker -> `drop`, paste URL -> `paste`); `track("firstrun_dashboard_created", {panelCount})` after a successful build. No `first_dashboard_rendered` emission added.
12. **a11y.** Drop zone is a focusable region with a visible "Choose a file" button and labelled URL input + submit; progress via an `aria-live="polite"` status region (Uploading, Reading columns, Building dashboard, Running pipeline), errors via `role="alert"`; no drag-only affordance.

## Risks / Trade-offs

Heuristic can misclassify (documented thresholds; cast failure -> null, table still shows raw); datebucket parsing of non-ISO dates (not date-like, so time-series skipped); one more route to maintain; sync-vs-async pipeline run time against the 60 s budget (measured live).
