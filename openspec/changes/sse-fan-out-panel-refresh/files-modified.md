## Systematic-debugging evidence (Iron Law)

**Root cause (design flaw caught before commit, not a runtime bug):** the sr-only status region's initial implementation gated the "refresh completed" announcement on `usePanelData`'s own `isLoading` flag. `isLoading` is deliberately `false` throughout a background refresh of a panel that already has rows (it only reflects the panel's first-ever load), so that implementation would never announce a fan-out-triggered refresh for the exact "chart panel already showing data" scenario the ticket's AC describes.
**Probe:** read `usePanelData.ts`'s `isLoading` derivation (`paginationEntry == null || (paginationEntry.isLoadingMore === true && rows.length === 0)`) directly, then traced the write path of the effect it would gate.
**Fix:** removed the dependency on `isLoading` entirely — the status announcement now bumps directly inside the fan-out callback (`handleFanoutRefresh`), matching react.dev's "subscribe to an external system, call setState in a callback" pattern rather than deriving state from a watched-value transition inside a `useEffect` (which `react-hooks/set-state-in-effect` and this codebase's `react-hooks/refs` — no ref access during render — both independently reject; see PanelCard.tsx's inline comment for the full chain of three eslint iterations this went through).
**Verification:** `frontend/src/features/panels/ui/PanelCardBody.fanoutStatus.test.tsx` asserts the region's text changes distinctly across two fan-out-triggered refreshes; `e2e/hel1094-sse-fan-out-panel-refresh.spec.ts` confirms the same live, against the real backend (see run transcript in the executor's report).

## C2 "show the red" evidence (Standing Constraint)

`pipelineRunFanout.test.ts`'s "delivers succeeded to two panels bound to the SAME pipeline from one connection" test (task 3.1) was run against a temporarily-reverted, naive per-subscriber-connect implementation (each `subscribeToPipelineSucceeded` call unconditionally opened its own connection, mimicking the pre-fan-out bug this ticket exists to fix) and failed exactly as expected: `expect(fetchMock).toHaveBeenCalledTimes(1)` received `2`. The implementation was then restored (verified byte-identical to the pre-revert version via `diff`) and the full suite re-run green (10/10). This is the actual defect surface C5 protects against; the e2e spec (`hel1094-sse-fan-out-panel-refresh.spec.ts`) exercises only a single output-bound panel per pipeline, so it would not have distinguished the naive implementation from the correct one — the red/green demonstration was done at the unit level where the property is actually observable, not redundantly re-run against the live backend (each live run costs ~30-40s of real wall-clock debounce+tick time).
