## Context

HEL-1773 (merged 62df9ff48; archive `openspec/changes/archive/2026-11-18-viewer-grantee-dashboard-access/`, spec `openspec/specs/dashboard-grantee-access/spec.md`) gates every Output-route feature with `useCanUseOutputRoutes()` (`features/dashboards/state/dashboardAccessContext.tsx`), which is `role === "owner"` for the role `PanelList` provides from `selectDashboardAccessRole(state, selectedDashboardId)`. Gated sites (grep `useCanUseOutputRoutes`): `PanelCardBody`, `PanelCard`, `PanelFullscreenOverlay`, `MobilePanelStack`, `PanelDetailModal`, `usePanelDetailData`, `useCrossFilterServerOps`, `useOutputHistory`, `InsightPanelBody`. Rows for a non-owned dashboard already go through `fetchPublicPanelRows` with no token (`panelThunks.ts` non-owner branch, keyed by the panel's own `dashboardId`) and Output meta through `/output-meta` (`outputMetaCache` scoping).

Facts verified in planning (the executor re-verifies before relying on them):

- `PublicDashboardRoutes.scala` serves, behind `authorizeResourceWithSharing("dashboard", ...)` with optional token: `rows` (with `sort`/`filter`), `filter-capabilities`, `distinct-values`, `output-meta`, `history`, `insight`, `provenance`. `ApiRoutes.scala:952` wires all optional services (history, insight, provenance) in prod.
- `PublicOutputControlScope` (C11) restricts the per-panel `rows` sort and filter columns, `distinct-values` and `filter-capabilities` to the panel's own `output_controls` columns, and rejects `quick` outright. Owner ruling R4: this boundary does NOT move.
- The public share viewer (`PublicDashboardViewerPage.tsx`) already renders controls (`fetchPublicDistinctValues`), history (`HistorySource` `{variant:"public", dashboardId, token}`), insight (`useInsight` public source, `CitationChip` public variant), and provenance (`ProvenanceTrigger variant="public"`, `fetchPublicProvenance`) through these routes. Those variants take a required `token: string` today.
- The per-panel history resolver returns the summary-only allow-listed shape (no point `id`/`hasPayload`), so payload rows cannot be linked from it.

## Decisions

### D1. Role read per panel, not per selected dashboard

Replace the single `PanelList`-level provider value as the source of the Output-vs-panel-route decision. Add `usePanelReadScope(panel)` (in `features/panels`, or `dashboardAccessContext.tsx`) that reads `selectDashboardAccessRole(state, panel.dashboardId)` and returns a discriminated value:

```ts
type PanelReadScope =
  | { kind: "output" }                                   // caller owns the panel's dashboard
  | { kind: "panel"; dashboardId: string; panelId: string; token?: string }; // per-panel routes
```

Every former `useCanUseOutputRoutes()` call site that has a panel switches to it. `useCanEditPanels`/`useDashboardRole` (edit gating from HEL-1773) are unchanged. `useCanUseOutputRoutes` is deleted if no call site remains (no dead helper).

**One routing rule for hooks and the thunk (skeptic-design-1 CR3).** The scope decision lives in one pure function `panelReadScopeFor(state, dashboardId, panelId)` (fail-closed: `kind: "output"` only when `selectDashboardAccessRole(state, dashboardId) === "owner"`; an unknown dashboard or unknown role is `panel` scope). `usePanelReadScope` is a selector over it. `fetchPanelPage` takes the panel's `dashboardId` as a REQUIRED thunk arg (every dispatch site has the panel) and routes by the same function, replacing `isKnownNonOwnedDashboard(state, scopedPanel.dashboardId)` and the `state.panels.items.find` lookup there. So a panel missing from `state.panels.items`, or a dashboard missing from the store, can never fall through to `GET /api/outputs/:id/rows`. `isKnownNonOwnedDashboard`'s other call sites (`fetchPanels` meta scoping, `showDashboardPanels`) are listed below. Jest (task 2.1): `fetchPanelPage` for a panel whose dashboard is absent from the store calls `fetchPublicPanelRows`, never `getOutputRows`.

**Fail-closed everywhere, and what that does to tests (skeptic-design-3 CR1).** `panelReadScopeFor` has NO "absent dashboard means owner" exception in production code: a dashboard the store does not hold is panel scope. The `DashboardAccessContext` default `"owner"` stops influencing read routing (`useCanUseOutputRoutes` is removed; the context remains only for HEL-1773's edit gating via `useCanEditPanels`/`useDashboardRole`, unchanged). `isKnownNonOwnedDashboard`'s fail-open is removed from `fetchPanelPage` (it stays only where HEL-1773 uses it for `outputMetaCache` scoping in `fetchPanels`/`showDashboardPanels`, knowingly left, see below).
- Production mounts: the executor greps every mount of the migrated components (`PanelCard`, `PanelCardBody`, `MobilePanelStack`, `PanelFullscreenOverlay`, `PanelDetailModal`, `OutputPanelContent` consumers) outside `PanelList` and lists in files-modified.md how each one's dashboard is in the store. If any OWNER-facing production surface renders a panel whose dashboard is not in the store (so it would flip to panel scope), the executor stops and reports rather than adding an exception.
- Existing owner-path tests (about 28 jest files that mock/assert `getOutputRows` or other Output-route calls and seed no dashboard — found by `grep -rlE "getOutputRows|getDistinctValues|getFilterCapabilities|fetchOutputHistory|fetchOutputProvenance|fetchOutputInsight" frontend/src --include=*.test.ts --include=*.test.tsx`, then filtered to those that seed no dashboard) are migrated by seeding the panel's dashboard as owned (`accessRole: "owner"`) explicitly in each file, via one small exported test helper (e.g. `seedOwnedDashboard`). `renderWithStore` does NOT auto-seed ownership, so the fail-closed rule stays observable. These are PLANNED fixture changes (task 2.1): files-modified.md lists every migrated test file under a "D1 planned fixture migration" heading, and each diff in them is limited to the seeding (no assertion changes). Any other test-fixture change is reported separately with its reason.

**Output-keyed seams (each changed or knowingly left):**
- `outputMetaCache.panelScopes` (outputId -> per-panel scope, set by `fetchPanels`/`showDashboardPanels`): LEFT as HEL-1773 shipped it. The only caller who can see one Output both as owner and as grantee is one who can already read it through the Output route, so a scope flip for them serves correct meta either way; a dashboard-only grantee never has an owner-scope entry.
- `filterCapabilitiesStore` (keyed by outputId): CHANGED, see D5.
- `insightChromeStore`: LEFT owner-only. It is fed by `InsightPanelBody` only in output scope (`!isPublic`) and carries owner chrome (Update insight, pipeline ownership); panel scope does not feed it. The panel-scope signal for "this is an insight panel" is the per-panel Output kind, D7.
- Provenance and history caches are already keyed `publicProvenanceKey`/`publicHistoryKey` by `(dashboardId, panelId)`: unchanged. The fail-closed rule of HEL-1773 D3 still applies (unknown role -> not owner -> `panel` scope). A jest test mounts a card whose panel belongs to shared dashboard A while `selectedDashboardId` is owned dashboard B (and the reverse) and asserts the request target follows the panel's dashboard; an e2e step switches shared -> owned -> shared and asserts no `/api/outputs/` or `/api/pipelines/` request is attributed to a shared panel (the e2e records the shared dashboard's Output ids AND pipeline ids, and the owned dashboard in that step uses different Outputs and pipelines, so attribution is unambiguous; no shared Output id may appear under `/api/outputs/` and no shared pipeline id under `/api/pipelines/`).

### D2. One per-panel read source, token optional

Generalise the existing public variants rather than adding a third path: `HistorySource`, `useInsight`'s public source, `CitationChip`'s public variant, `ProvenanceTrigger`/`fetchPublicProvenance`, `fetchPublicDistinctValues`, `fetchPublicFilterCapabilities` take `token?: string` and omit the `token` query param when absent (same rule `fetchPublicPanelRows`/`fetchPublicOutputMeta` already follow since HEL-1773). Caches keyed by `(dashboardId, panelId)` stay correct (same data for token and grant callers of one panel). The public viewer page keeps passing its token, unchanged. The authenticated render paths build these from `PanelReadScope` `kind: "panel"`.

### D3. Viewer controls and distinct values

`PanelCardBody`, `PanelFullscreenOverlay`, `MobilePanelStack` (via `PanelCardBody`) and `usePanelDetailData` stop zeroing `controls` for non-owners. `fetchDistinctValues` uses `fetchPublicDistinctValues(dashboardId, panelId, undefined, column)` in `panel` scope, `getDistinctValues(outputId, column)` in `output` scope.

### D4. Sort and filter split (R4)

`usePanelSortFilter` (and `handleLoadMore`) keep producing the same `{sort, filter}` intent. In `panel` scope a pure helper `splitForPanelScope(intent, controlColumns)` returns:

- `server`: `sort` if its column is a control column; `filter.columns` entries whose key is a control column; every viewer-control `ops` entry (always control columns); the cross-filter `eq` only when D5 chose server mode. `quick` is never in `server`.
- `client`: `sort` on a non-control column; `filter.columns` entries on non-control columns; `quick`.

**The split is enforced inside `fetchPanelPage`'s panel-scope branch (skeptic-design-1 CR2),** using the scoped panel's own `config.controls` (looked up by `panelId` in state; when the panel is not in state the branch sends no sort and no filter at all, still per-panel). That is the one point all four dispatch sites pass through — `usePanelData` initial/refresh/replay (`replay?.sort`/`replay?.filter`), `usePanelData`'s `CROSS_FILTER_EQ_REJECTED` retry, `usePanelSortFilter`'s sort/filter change, and `PanelCardBody`'s Load more — so no caller can bypass it. Callers keep dispatching the FULL intent (`sort`, `filter`, `crossFilterEq`); `paginationState` keeps recording the full intent exactly as today, and the split is applied only on dispatch, so replay and the TableRenderer client part read one consistent intent. `crossFilterEq` in panel scope: folded into `ops` only when its column is one of the panel's control columns (D5 server mode); otherwise dropped from the request (the client-fallback narrowing still applies in `OutputPanelContent`). `fetchPublicPanelRows` already accepts `sort`/`filter`; the branch passes `server.sort`/`server.filter` to it. Jest (task 3.2): one case per dispatch site (initial/replay, sort change, load more, cross-filter retry) asserting the per-panel request carries no non-control column and no `quick`. **Client part — new behaviour, not existing (skeptic-design-2 CR2).** Today, with `onSortChange` wired, `useTableRows.ts` (~195) never sorts client-side; `LoadedScopeDisclosure` renders nothing for a sort alone; and a zero-match filter on a truncated table shows a bare "No rows match your filter.". So:
- (a) `useTableRows` gains an optional `clientOps?: { sort?: {key, direction}; columns?: Record<string,string>; quick?: string }` input. When present it sorts/filters the loaded rows by exactly those terms, independent of whether `onSortChange` is wired (the `onSortChange != null` test no longer suppresses a client sort that `clientOps` names). `TableRenderer` passes `clientOps` = the panel-scope `client` part (computed by the same `splitForPanelScope` against `panel.config.controls`); in output scope `clientOps` is `undefined` and the hook behaves exactly as today. The server part still flows through `onSortChange`/`onFilterChange` -> `usePanelSortFilter` -> `fetchPanelPage` (whose split drops the client terms). Filters AND-compose, so server narrowing then client narrowing is exact over the loaded rows.
- (b) `LoadedScopeDisclosure` gains an optional `clientScope?: { sorted: boolean; filtered: boolean; loaded: number; total: number }` prop, shown only when `clientScope` is set, a client term is active AND `loaded < total` (when every row is loaded a client sort/filter is exact and needs no disclosure). Copy (DESIGN.md tone, sentence case): sort only "Sorted within the {loaded} loaded rows of {total}."; filter/quick only "Filtered within the {loaded} loaded rows of {total}."; both "Sorted and filtered within the {loaded} loaded rows of {total}." Owner rendering never sets the prop.
- (b2) Precedence with the existing disclosure (skeptic-design-3 CR2): in panel scope, whenever any client term is active, the existing `filtering` branch of `LoadedScopeDisclosure` never shows `totalRowCount` as a match count (in panel scope that is the server total without the client terms). Exactly one line renders: if `loaded < total`, only the `clientScope` note; if every row is loaded and a client FILTER/quick is active, "{n} results." with `n` = the client-filtered loaded row count (existing copy, derived count); if every row is loaded and only a client sort is active, nothing. With no client term active (server-only filter on control columns), the existing behaviour stands (`totalRowCount` is then correct). Owner scope unchanged.
- (c) Empty state: in panel scope, when a client filter or quick search matches zero loaded rows and `loaded < total`, the table shows "No loaded rows match your filter. Only {loaded} of {total} rows were searched." with the existing Clear filters action and, when more rows exist, the existing Load more action; never the bare "No rows match your filter.". With every row loaded the existing copy stays.
- (e) No server dispatch for a client-only change (skeptic-design-4 CR1). In panel scope, when a sort, filter (incl. each quick-search keystroke) or cross-filter change leaves the split's `server` part equal to the `server` part of the panel's current window, NO `fetchPanelPage` is dispatched: the loaded rows (including Load-more pages) are kept and only `clientOps` re-derives. "Equal" = the normalized split server query compared the way `normalizeQuery` in `panelRowsReuse.ts` compares. Enforced in `usePanelSortFilter`'s `dispatchFetch` (the hook knows the current window). When it skips, it dispatches a synchronous reducer action that records the new FULL intent in `paginationState` (no fetch), so replay and Load more carry the current client terms; Load more after a client-only change carries the same server part (the thunk's split is unchanged). A change that alters the server part (control-column sort/filter, viewer control, server-mode cross-filter) still dispatches page 0 as today. Owner scope unchanged (no split, always dispatches as today). Jest (task 3.2): panel scope, two pages loaded, then (i) non-control sort, (ii) quick search, (iii) non-control cross-filter each dispatch no `fetchPanelPage` and keep all loaded rows; a control-column sort/filter change still dispatches. Mutation m10 (always dispatch) must turn that jest red.
- (d) Owner-scope rendering is byte-for-byte unchanged: every existing `useTableRows`/`TableRenderer`/`LoadedScopeDisclosure` test passes unmodified.
Jest (task 3.2) for (a)-(c) and (b2) — including: panel scope, every row loaded (total 40), quick search matching 3 shows "3 results." and never "40 results."; the truncated variant renders exactly one note; the e2e asserts the sort-only disclosure text; C10 grep for "No rows match your filter." and the disclosure strings across `e2e/`. Invariant (jest + e2e): no per-panel rows request ever names a non-control column or carries `quick` (which the server answers `400`); zero 4xx in the e2e.

### D5. Cross-filter (R2)

`useCrossFilterServerOps(panel, output)` takes the read scope. In `panel` scope, capabilities come from per-panel `filter-capabilities` (already narrowed server-side to control columns), and the decision is: `server` iff the dimension is one of this panel's control columns, its capability includes `eq`, column type is not `timestamp`, and no control `eq` already names the dimension (existing clash rule); otherwise, if `isPanelFilterableByDimension` holds, `client-fallback`; else `none`. `useOutputFilterCapabilities` gains a per-panel source (fetch `fetchPublicFilterCapabilities` without token). **Per-panel capabilities are keyed by `(dashboardId, panelId)` (skeptic-design-1 CR1)**, like `publicProvenanceKey`/`publicHistoryKey`, and never share a key with an `outputId` Output-route entry: two panels bound to one Output with different controls get different capabilities. The thunk's cross-filter `400` path (`CROSS_FILTER_EQ_REJECTED`, `panelThunks.ts` ~441) invalidates the key of the scope that made the request: the per-panel key in panel scope, the `outputId` in output scope. Jest (task 3.3): two panels on one shared dashboard, same Output, different controls — each panel's cross-filter mode follows its own capabilities, and the 400 invalidates the right key. In `output` scope nothing changes.

### D6. History and compare sparklines

""` fallback is removed (an empty `token=` reaches `authorizeResourceWithSharing` as `Some("")`); with no token the param is omitted, and the D2 jest case covers history. The per-panel response carries no point `id`/`hasPayload`, so no payload-rows affordance can render (HEL-921). Backend proof (D9) that the payload route 404s for a dashboard-only viewer as `helio_app`.

### D7. Insight bodies and the insight Refresh (S1)

`InsightPanelBody` drops the "Not available on shared dashboards yet" branch; in `panel` scope it receives `historySource` (read scope) and reads `/api/dashboards/:id/panels/:panelId/insight` (public source, no token); citations render with the public `CitationChip` variant (no Output link). `usePipelineOwnership` stays unmounted in `panel` scope (it calls `/api/pipelines/:id`). **Signal for S1 (skeptic-design-2 CR1):** `PanelCard` and `MobilePanelStack` read the panel's Output `kind` from the per-panel Output meta (`useOutputMeta(outputId)`, which in panel scope resolves through `/api/dashboards/:id/panels/:panelId/output-meta` via `outputMetaCache` — the same cached read `PanelCardBody` already makes, so no extra request). In panel scope, the header Refresh is not rendered when that kind is `insight`, and also not rendered while the kind is still unknown (meta loading or failed): fail closed, no do-nothing button. For any other kind the header Refresh re-reads rows through the per-panel route as today. Owner scope is unchanged (it keeps using `insightChromeStore`). The card footer's insight "Updated <date>" line (fed by `insightChromeStore`) is not shown in panel scope; the body renders the per-panel `render.renderedAt` only if the public insight body already shows it (the executor states which in files-modified.md; no new copy is added). ## Risks / Trade-offs

- Mixed server/client sort/filter (R4) means a grantee's non-control sort covers only loaded rows; the disclosure states it. Accepted by the owner.
- Per-panel history is summary-only (no run ids/trigger sources): a grantee's compare/sparkline shows values without run attribution. Intended.
- Dual-grant users lose nothing they had in HEL-1773 and gain the features through per-panel routes, but not full Output-route parity (e.g. server sort on non-control columns). Intended (S2).
- Bumping the provider design to per-panel reads touches many components; HEL-1776 (popover focus code) is in flight — avoid `shared/ui` popover files; `ProvenanceTrigger` changes are limited to its props/fetcher.
