### Root cause (round 2, systematic-debugging.md required evidence)

- **Root cause:** the round-1 fix's `${LOG_FORMAT:-plain}` property substitution only matches the literal string `json` exactly. Any other non-empty value (`JSON`, `Json`, a typo) resolves `LOG_APPENDER` to that literal string, which then fails to match either declared appender name (`json`/`plain`) in `<appender-ref ref="${LOG_APPENDER}">` — an unresolvable appender reference, which Logback treats identically to no appender at all: the root logger ends up with nothing attached, silently dropping all application/Flyway output, the same defect class HEL-1128 exists to fix.
- **Probe:** Rebuilt the real `Dockerfile` image (after adding `LogFormatPropertyDefiner` and switching `logback.xml` to `<define>`) and ran it against a real throwaway `postgres:16` container with `LOG_FORMAT=JSON` (uppercase) and separately with `LOG_FORMAT=garbage`.

## Root cause (round 1, systematic-debugging.md required evidence)

- **Root cause:** In this repo's exact toolchain (logback-classic 1.5.38 + Janino, packaged via `sbt-assembly`'s fat jar), any `<if>` block in `logback.xml` — regardless of where it is nested (top-level wrapping `<root>`, or inside `<root>` wrapping only `<appender-ref>`) — causes Joran's model-based configuration processor to report a clean "End of configuration" with no ERROR status, yet leaves the runtime root logger with **no appender actually attached**, so every subsequent application/Flyway log call is silently dropped at the `Logger.callAppenders()` layer.
- **Probe:** Built the real `Dockerfile` image and ran it against a real throwaway `postgres:16` container with the full prod-shaped env set, both with `LOG_FORMAT=json` and unset, and separately with `-Dslf4j.internal.verbosity=DEBUG -Dlogback.debug=true`; then rebuilt the same image with `<if>` removed entirely (appenders declared unconditionally, selection via `<appender-ref ref="${LOG_APPENDER}">` property substitution) and re-ran identically.
- **Probe output (unfixed, `<if>`-based config):** `-Dlogback.debug=true` run showed `01:32:49,686 |-WARN in Logger[org.apache.pekko.event.slf4j.Slf4jLogger] - No appenders present in context [default] for logger [org.apache.pekko.event.slf4j.Slf4jLogger].` — the exact defect signature — and zero application/Flyway lines reached stdout on either `LOG_FORMAT` branch afterward, reproducing prod revision `helio-backend-00077-55c`'s 13-lines-then-silence signature exactly. A control run with `<if>` removed entirely (no conditional at all) produced full Flyway ("Schema \"public\" is up to date. No migration necessary.") and startup ("Helio backend listening on ...") output immediately, proving `<if>` itself — not which branch executes, not fat-jar packaging conflicts (jar content inspection found a single clean `META-INF/services/org.slf4j.spi.SLF4JServiceProvider` entry and byte-identical `logback.xml`), not a missing Janino dependency (present in the jar) — is the failure surface.
- **Probe output (fixed, property-substitution config):** Rebuilt image with `LOG_FORMAT=json` produced `{"...,"message":"Successfully validated 106 migrations...` / `{"...,"message":"Schema \"public\" is up to date. No migration necessary.","severity":"INFO",...}` / `{"...,"message":"Helio backend listening on /[0:0:0:0:0:0:0:0]:8080","severity":"INFO",...}` as single-line JSON with `severity` present; the `LOG_FORMAT`-unset branch produced the equivalent plain-text lines. `docs/verify-backend-logging.sh` (task 3.1) codifies this as a repeatable red-before-green check: exit 1 against the unfixed config, exit 0 against the fix.
