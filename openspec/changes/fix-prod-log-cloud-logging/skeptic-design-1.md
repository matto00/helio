### Change Requests
1. **The core premise is unverified and plausibly false.** design.md Context item 1 and ticket.md's premise findings say prod "almost certainly runs with LOG_FORMAT unset". Cloud Run env vars persist across revisions, `--update-env-vars` merges, and `deploy-backend.sh` (which sets `LOG_FORMAT=json` via `--set-env-vars`) is the most plausible source of the non-workflow vars the workflow says already exist on the service. So the live value is unknown. It may well be `json`, which is what the ticket reports. Revise design.md and ticket.md to call this an open hypothesis, and add a read-only probe task before any fix. Two options: `gcloud run services describe helio-backend --region us-west1 --format='value(spec.template.spec.containers[0].env)'`, or `gcloud logging read` on revision `helio-backend-00077-55c` to see whether its 13 logback-init lines are JSON or plain text. Reading does not break C2. If gcloud access is unavailable, say so in the design and treat both branches as possible live states.
2. **Task 2.1 is an unconditional fix, written before root cause is known.** It adds `LOG_FORMAT=json` to cd-backend.yml no matter what the probes find. Gate it on task 1 evidence. Keep it as defensive hardening only if the live value turns out to be unset, or so the workflow stops depending on leftover script state. Label it that way, and do not present it as the root-cause fix unless a probe confirms it.
3. **Task 1.1 assumes its result.** It says to "confirm it shows only logback-init + request lines" with `LOG_FORMAT` unset. The plain branch logs to stdout too, so that outcome is not expected. Rewrite 1.1/1.2 as neutral: run both `LOG_FORMAT` values and record which, if either, reproduces the symptom (logback init, then no app or Flyway lines). If neither does locally, record that as a finding. It points at a prod-only factor such as the env, stderr vs stdout, or a classpath/binding difference in the assembled jar.
4. **The Docker repro cannot reach Flyway as written.** Task 1.1 says "required env stubs". Flyway runs `migrate()` against `DATABASE_URL`, and a stubbed or unreachable DB fails before any Flyway success line (fatal path: `System.err.println` plus `halt(1)`). Name the DB setup: a reachable Postgres, such as a throwaway container or local Postgres on a non-shared database. Do not use the shared dev DB; see MEMORY's shared-dev-DB Flyway collision hazard. Then say which exact Flyway line counts as the reproduction signal.
5. **Name the logging-binding suspects in design.md Decisions.** The fat jar contains logback, janino, the logstash encoder, and log4j-core/log4j-1.2-api 2.25.5 from Spark. The assembly merge strategy (duplicate `logback.xml`, SLF4J service-provider files, or `log4j2` configs from dependencies) can decide which config or binding wins inside the jar but not under `sbt run`. The design already says it won't pre-guess, which is fine. But 1.3 needs a concrete probe step covering all of these: inspect the jar with `unzip -l helio-backend.jar | grep -i -E 'logback|slf4j.*Provider|log4j2'`, and read logback's own init lines to see which config URL it loaded.
6. **Task 3.1's regression guard must be failable.** It must fail against the pre-fix config or wiring. If the confirmed cause is in the CD YAML or the assembly merge, a unit test that only checks logback.xml's JSON branch proves nothing. Require the test or script to target the confirmed cause and to show red before the fix, or to be labelled as a mutation-verified guard.
