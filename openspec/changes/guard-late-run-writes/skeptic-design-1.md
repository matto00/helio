### Verdict: REFUTE

### Change Requests

1. **D7 misses a deadlock against workspace teardown and is silent on the repo's binding lock order, Order O* (`docs/live-draft-preview.md` §"Order O*").**
   - **The cycle.** `WorkspaceTeardownRepository.planAndExecute` takes (0) tagged `data_sources FOR UPDATE`, then (1) panels, then (3) `lockPipelinesRootedOn` (pipeline `FOR NO KEY UPDATE`, granted), and only then `DELETE FROM pipelines` (needs `FOR UPDATE`, lines 141-168). The new W10 transaction takes pipeline `FOR KEY SHARE` and run `FOR SHARE`, then `UPDATE pipelines`, which needs `FOR NO KEY UPDATE`. The interleaving: teardown holds (3), W10 holds KEY SHARE, W10's UPDATE waits on teardown's (3), and teardown's DELETE waits on W10's KEY SHARE. That is a cycle. PostgreSQL aborts one transaction with `40P01`, which can be the user's teardown.
   - **The same inversion for W1.** For an ExistingSource target, the write-back would now take the pipeline and run locks before the target's `data_sources FOR UPDATE` (lock (0)). A teardown of a tag containing both the pipeline and its write-back dataset holds (0) and waits on the guard's locks at its DELETE (pipeline `FOR UPDATE`, cascading to the run row).
   - Order O* says dataset writers "touch no pipeline ... row, so they cannot form a cycle". This change breaks that premise, and the design does not mention it.
   - **Revise D7:**
     - (a) Place every guarded transaction (W1-W5, W10) in Order O*, and say where the guard's two locks sit.
     - (b) Pick an ordering that removes the cycles. For example, W10's pipeline lock is taken in the mode it will need (`FOR NO KEY UPDATE`, as its first lock) rather than KEY SHARE followed by an upgrade. The W1 guard runs after the target source's lock (0) but before any write. Whatever is chosen, it must be argued against O* and not only against the reaper.
     - (c) Add 3.4 cases for W10 and for W1 against a workspace teardown, in the `DraftSaveDeadlockSpec` style, each with a control that reproduces the cycle.
     - (d) Update the Order O* doc (or its dataset-writer sentence) in the same change, since it states a property this change alters.

2. **D8 will break three existing retention tests, but the plan says "existing retention scenarios still pass" (tasks 3.6).** In `PipelineRunRepositorySpec`, "deleteOldRuns retains only the N most recent runs" (line 158), "15 runs all older than 24h are pruned to the newest 10" (line 193) and "the cap bounds a very busy pipeline" (line 205) all seed with `insertRun`. That inserts `status = 'queued'` with `completed_at = NULL` (`PipelineRunRepository.scala:95-101`). Under `completed_at IS NOT NULL` nothing they seed is deletable, so each of them goes red. List these tests in tasks. Plan to re-seed them as terminal runs, with the reason stated: the semantics changed on purpose, so the evaluator should not have to read this as a fixture edited to make tests pass. Reuse one of them, unchanged, as the "old prune predicate" mutation witness.

3. **The per-write tests must say how they beat the eager W6 race (C2 / 3.1).** W4, W5 and W10 run concurrently with the run's own `succeeded` write (`updateRun`, line 258). If the reap is placed "before the write" with a hook in that write's repository, W6 has often already committed. The reap then no-ops, the guard admits `status = 'succeeded'`, and the test fails nondeterministically. With an unlucky schedule the guard-removal mutation can also look green. Task 3.1 must say that the run's terminal write is held (the harness's gated terminal write, `LateFinisherSpecBase` around lines 84-90) until the reap has committed, or that the reap happens at a single hook reached before W6 can start. It must also say which of the two is used per write.

4. **D2 states something false about the code, and task 3.7 is ambiguous for W3.** D2 says "both the history and no-history branches use `overwriteRowsWith`". The no-history branch calls `nodeSnapshotRepo.overwriteRows(...)` (`PipelineRunSucceededWrites.scala:128`). Fix the statement and say that branch is switched to `overwriteRowsWith`. Because W3 moves into the node transaction, it has no guard of its own. Restate the W3 mutation in 3.7 as "move the schema update back out of the node transaction" (or equivalent), and say what it must turn red.
