## Context

`SqlConnectorDriver.connect` is the single chokepoint that opens a JDBC connection to a user-supplied host (all of `execute`, `testConnection`, `inferSchema`, `fetch`, previews and pipeline runs reach it; the executor must re-enumerate and prove this by grep). It runs `checkConfigEgress` (DNS lookup 1, shared policy) then `DriverManager.getConnection(url)`, where the driver does lookup 2. The only other `DriverManager` use is `PipelineRunNotifyBus`, which opens the app's own Cloud SQL connection (private IP) and must stay exempt.

## Goals / Non-Goals

**Goals:** close the rebinding window for postgresql and mysql; refuse unknown dialects; keep TLS behaviour unchanged; prove it with a failable test red on main.
**Non-Goals:** URL rewriting to IP literals (breaks TLS hostname verification and vhost routing); changing the egress policy itself; touching the app DB pool.

## Decisions

### D1 Re-validate at TCP connect via a validating Socket subclass (owner ruling; mechanism corrected per design-gate round 1, verified against the real jars)
Neither driver hands the factory a resolved address, so the hook is a `java.net.Socket` subclass (`EgressValidatingSocket`) whose `connect(SocketAddress, int)` checks the `InetSocketAddress`'s `getAddress` (the InetAddress actually being connected to, never `getHostName`, never re-resolution) with `ContentSourceSupport.isBlockedAddress` and throws before `super.connect`. A null/unresolved address is refused (fail closed).
- pgjdbc 42.7.13: `PGStream.createSocket` calls the factory's no-arg `createSocket()` then `socket.connect(new InetSocketAddress(host, port), timeout)` (JDK-resolved). The factory is a `javax.net.SocketFactory` subclass whose `createSocket()` returns the validating Socket. pgjdbc then wraps that Socket for SSL itself.
- mysql-connector-j 8.3.0: `com.mysql.cj.protocol.SocketFactory.connect(String host, int port, PropertySet, int)` receives a HOSTNAME and resolves via `InetAddress.getAllByName` itself, looping per address and swallowing only `SocketException`. The factory therefore subclasses `StandardSocketFactory` and overrides the protected `createSocket(PropertySet)` to return the validating Socket, keeping the driver's resolution, TLS handshake (`performTlsHandshake` wraps rawSocket) and retry loop. The refusal is a distinct non-`SocketException` (`SqlEgressRefusedException` is a RuntimeException; wrapped in a `java.io.IOException` subclass only if the driver's loop requires it, to be verified), so a blocked record aborts rather than silently falling through to the next record; either way the blocked address is never connected to. The executor verifies exact propagation and records it here.
Alternatives rejected: IP-literal URL rewrite (TLS/vhost); strict pin registry.

### D2 Policy reachability and test-predicate separation
Drivers construct the factory reflectively (pgjdbc tries `(Properties)`, then `(String)` if `socketFactoryArg` set, then no-arg), so no per-request state is passed through the URL (which would also be a user-injectable surface). Instead the factory reads the connect-time predicate from a `ThreadLocal[Option[(InetAddress)=>Boolean]]` set by `SqlConnectorDriver.connect` around the synchronous `DriverManager.getConnection` call (both drivers connect on the calling thread; the executor must verify no driver thread hop, else fall back to a `socketFactoryArg`/property-keyed registry) and cleared in `finally`; absent -> production `isBlockedAddress`. The predicate is a NEW parameter (`connectIsBlocked`), separate from the existing guard seam (`resolveHost`/`isBlocked`, which only feeds the pre-connect guard lookup): a test can make the guard permissive and see that only the factory blocks loopback, which is what makes the rebinding test discriminate factory from guard. Positive-path tests (embedded Postgres on loopback, TLS) pass `connectIsBlocked = _ => false` explicitly.

### D3a URL-parameter injection closed (design-gate round 1 finding)
`SqlSourceConfig.database` (and `host`/`port`) are interpolated into the JDBC URL, and URL query parameters outrank Properties in both drivers, so `database = "x?socketFactory=javax.net.DefaultSocketFactory"` would override the guard. Fix: `database` must match `^[A-Za-z0-9_.$-]+$` (no `?&;/#%`, whitespace, `=`); host is already constrained by `checkEgressHost`/Invalid (executor verifies it rejects `?`,`/`,`#`,`@`, whitespace and `:` forms) and port is an Int. Refused with 400 at create and a typed refusal at connect (shared validator, same single place as the dialect check). The final URL is asserted to carry no user-controlled query component beyond the fixed driver options. Test: `database="x?socketFactory=..."` cannot disable the guard (mutation: drop validator -> red).

### D3 Unknown dialects refused
A single shared validator `SqlConnectorDriver.validateConfigShape` (dialect in {postgresql, mysql}, database pattern) is called from EVERY path that accepts a SQL config: `SourceService` create/validate, `PipelineService` (~1621), `PipelineProposalService` (~214), `AssistantToolExecutor`/assistant proposal apply and `DataSourceConfigCodec` decode paths (executor re-enumerates by grep), each mapped to 400, with a test per path; plus connect time. `buildJdbcUrl` no longer has a `case other`; a dialect outside {postgresql, mysql} yields a typed refusal. Create time (`SourceService` sql create/validate path) returns 400/BadRequest with a clear message; connect time throws a typed exception mapped to the same message (analogous to `SqlEgressRefusedException`). Existing persisted sources with other dialects will fail at connect with that message; the executor inventories them read-only in the dev DB.

### D4 TLS
pgjdbc connects the plain socket via the factory, then wraps it in SSL itself after the SSLRequest exchange; MySQL (`useSSL=false` in the current URL) similarly upgrades over the supplied socket. The factory only controls TCP connect and returns an ordinary `Socket`, so SSL wrapping is unchanged. Proof required: a pgjdbc connection with `sslmode=require` (or verify-full against a test cert) through the factory succeeds against a TLS-enabled embedded/test server, or the exact change is stated.

### D5 Two-lookup residual
Lookup 1 (guard) remains for the clear refusal message and the create-time check; lookup 2 (driver) is now authoritative because the factory validates what it connects to. Multi-record answers: the driver tries one address; the factory refuses any blocked one, and the guard still refuses if any record is blocked.

## Execution findings (verified against the jars / by test)
- pgjdbc 42.7.13: `SocketFactoryFactory` instantiates via `ObjectFactory` (`(Properties)`, then `(String)` if arg, then no-arg); `PGStream.createSocket` calls `factory.createSocket()` then `socket.connect(address, timeout)` on the calling thread when `loginTimeout=0`; `connectionProperties` pins `loginTimeout=0` and a test asserts it.
- mysql-connector-j 8.3.0: `StandardSocketFactory.connect` calls `InetAddress.getAllByName`, loops, `createSocket(PropertySet)` then `connect(InetSocketAddress, timeout)`, and swallows only `SocketException`. The refusal (`EgressConnectRefusedException`) is an `IOException` that is NOT a `SocketException`, so it aborts the loop; the driver wraps it in `CommunicationsException` and `SqlConnectorDriver.connect` unwraps the typed `SqlEgressRefusedException` from the cause chain (N1). The validating socket closes itself on refusal (N4).
- Deviation from D2's wording: `connectIsBlocked` is an optional parameter (`Option[InetAddress => Boolean] = None`) that defaults to the existing `isBlocked(config.host, addr)` seam rather than a required separate predicate. This keeps every existing loopback-based test working without threading a new parameter through every service, while a test can still pass `connectIsBlocked` explicitly to make only the hook strict (`SqlConnectorRebindingSpec`, "hook on its own"). Production never overrides either seam.
- TLS: proven for pgjdbc (`SqlConnectorTlsSpec`, throwaway openssl cert, `pg_stat_ssl.ssl = true` for `sslmode=require` and for the default `prefer`). MySQL: `useSSL=false` stays in the URL and the TLS upgrade path (`StandardSocketFactory.performTlsHandshake` over `rawSocket`) is the inherited driver code operating on our `Socket` subclass; there is no MySQL server in the test environment, so MySQL TLS is stated, not proven.
- JDBC open sites: `SqlConnectorDriver.connect` (the only `DriverManager.getConnection` carrying user-supplied hosts; reached by `execute`, `testConnection`, `inferSchema`, `fetch`) and `PipelineRunNotifyBus` (own DB, no factory). No other `DriverManager`/`jdbc:` use in `src/main`.

## Risks / Trade-offs
- Driver-internal API drift (reflection contract) is mitigated by tests that open real driver connections via `DriverManager`.
- Refusing unknown dialects breaks pre-existing odd-dialect sources: owner-accepted; inventoried.

## Gate-Chain Implications Checklist
Not applicable: no `.husky/**` or pre-commit-invoked script is touched.

## Test strategy
Rebinding test per dialect through the real driver connect path: injected guard resolver answers public for the test host, the driver's own resolution of the name lands on a loopback listener that counts accepts (embedded Postgres for pg; a counting `ServerSocket` for mysql if no embedded MySQL), asserting zero accepts and an egress refusal. Red first on main (accept count 1 / connection reaches the listener), mutation (remove the factory's blocked-address check) turns the new tests red. Factory unit tests for blocked/allowed/unresolved addresses; app pool untouched proof (grep plus a test that the factory property is absent from the app's JDBC config).
