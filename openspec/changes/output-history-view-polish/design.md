## Context

See proposal.md for motivation. All four items live in the HEL-1277 History view (`frontend/src/features/pipelines/ui/outputHistory/`) and the Output card's History button (`OutputGalleryCard.css`). Capture-time labels are produced by `frontend/src/features/panels/history/formatCaptureTime.ts` (`formatCaptureTime(iso, withSeconds)` + `sameMinute(a, b)`), called independently from `HistorySummary` (header, "vs" caption, metric baseline), `HistoryChart` (overlay label) and `HistoryRows` (comparison notes). The backend serialises `capturedAt` as a `java.time.Instant` string (sub-second precision from Postgres `timestamptz`, i.e. microseconds), so two points in the same second normally differ at the millisecond.

## Goals / Non-Goals

**Goals:** the four ticket items, per DESIGN.md, verified in the running app in light and dark themes; RTL tests for the "No row changes" note and the label disambiguation.

**Non-Goals:** the scrubber's per-point accessible names (minute precision; not a "vs" label and not named by the ticket); the dashboard panel-level history/sparkline labels in `chartOverlay.ts`'s custom-compare path; any change to `diffRows` semantics; any backend change.

## Decisions

### D1 — Ghost button: radius-sm + weight-medium; keep the existing hover surface
`.output-gallery-card__history` gets `border-radius: var(--app-radius-sm)` and `font-weight: var(--weight-medium)` (DESIGN.md §5: "All at … `--app-radius-sm`, `--weight-medium`"). Its hover background stays `--app-surface-raised`, deliberately NOT §5 Ghost's `--app-surface-soft`: the button is a descendant of `.output-gallery-card`, whose own `:hover` paints `--app-surface-soft`, so hovering the button always hovers the card too and a `--app-surface-soft` button hover would be the exact same colour as its background — an invisible hover state, the HEL-866 defect class. Acceptance is measured, not inspected (DESIGN.md's HEL-866 note: "non-identical but not measurably different" is rejected). Computed WCAG contrast of `--app-surface-raised` against the hovered-card backdrop `--app-surface-soft`: dark 1.122 (`#232019` vs `#161514`), light 1.179 (`#ffffff` vs `#efece6`), against the HEL-866 guard threshold `CONTRAST_THRESHOLD = 1.10` (`e2e/state-surface-contrast-guard.spec.ts`). The dark margin is thin, so task 4.2 samples the RENDERED hovered-button pixel against the hovered-card pixel in both themes (after transitions settle) and records the ratio; a rendered ratio below 1.10 in either theme is a defect to fix, not to document. A CSS comment states the backdrop explicitly (`--app-surface-soft`, the hovered card — a backdrop HEL-866's table does not list), the measured ratios and the threshold. Alternative considered: switch to `--app-surface-soft` literally — rejected as it produces an invisible hover. Alternative: use the shared `IconButton` — rejected, it is icon-only and this is a labelled button.

### D2 — One label helper guaranteeing a distinct pair
Add `formatCapturePair(selectedIso: string, comparisonIso: string | null): { selected: string; comparison: string | null }` (with a `null` comparison — the oldest point — the selected label is minute precision exactly as today and `comparison` is `null`) to `formatCaptureTime.ts`. Precision escalates: different minute → minute precision (today's default); same minute, different second → seconds; same second → seconds plus milliseconds (`fractionalSecondDigits: 3`); if the two strings are still equal (identical instant, or a timestamp `Date` cannot parse) the comparison label gets the suffix " (older capture)". `formatCaptureTime` gains a precision parameter (keeping its current `withSeconds` boolean callers working, or migrating them — executor's choice provided `chartOverlay.ts` and `HistoryScrubber.tsx` output is unchanged). `HistorySummary`, `HistoryChart` and `HistoryRows` all derive their selected/comparison labels from this one helper so the header and every "vs" label agree. `sameMinute` has no remaining caller once the three components move to the helper, so it is removed. Unit and RTL tests assert relationships (header text differs from the "vs" label; a same-second label contains the millisecond digits; the identical-instant label ends "(older capture)"), never exact localized strings, since `toLocaleString(undefined, …)` and `fractionalSecondDigits` output vary by locale/ICU build. Alternative: append an ordinal ("run 2 of 3") — rejected as noisier and meaningless across a 100-point window. Alternative: always show seconds — rejected, it lengthens every label to fix a rare case and still fails for same-second pairs.

### D3 — "No row changes vs <time>" note
In `HistoryRows`, when the diff is ready and `diff.changed.size === 0 && diff.noLongerPresent === 0`, `comparisonNote` becomes `No row changes vs <comparison label>`. It uses the existing `.output-history__note` styling (muted xs text), same slot as the "no longer present" note. Not shown when the diff is unavailable (missing/loading/failed payload) — those branches are untouched. When the diff has changed rows but nothing removed, behaviour is unchanged (no note; the highlighted rows speak).

### D4 — Table area sizes to content, capped at 360px
`.output-history__table` changes from `height: 360px` to `max-height: 360px` so the DataGrid's own content height determines the area for short tables. The executor must confirm in the running app at THREE sizes, recording the measured `getBoundingClientRect().height` of `.output-history__table` and `.ui-data-grid` for each: (a) a 2-row payload — the table collapses to its rows and the note sits directly beneath; (b) a non-virtualised overflowing payload (roughly 20–150 rows) — it scrolls inside the 360px cap; (c) a payload above `VIRTUALIZATION_ROW_THRESHOLD = 150` (`DataGrid.tsx`; windowing engages only when `variant === "full" && rows.length > 150`, and payloads can reach `PAYLOAD_HISTORY_MAX_ROWS` = 1000) — the table is virtualised, the scroll container's rendered height is at most 360px, and scrolling to the bottom renders the final rows with no blank spacer gap and no unbounded growth. A fixture at or below 150 rows passes whether or not the virtualised scroll container is bounded (the HEL-1060 trap), so (c) is mandatory. If `max-height` alone does not bound the scroll container (e.g. `.panel-content`'s `flex: 1; align-items: center` prevents the grid from shrinking/growing), adjust only the `.output-history__table …` descendant rules in `OutputHistoryModal.css` — never shared `PanelContent.css`/`TableRenderer.css`/`DataGrid.css`, which the dashboard grid depends on. A jsdom test cannot measure layout, so the CSS guard test asserts the rule shape (no fixed `height: 360px`, `max-height: 360px` present) and the real proof is the running-app check.

## Risks / Trade-offs

- [Short-table sizing interacts with shared renderer flex rules] → scoped descendant overrides only, verified in the running app with both row counts and both themes.
- [Millisecond labels are long] → only used when two points share a second, which is rare.
- [The existing CSS guard test only checks `height: var(--control-sm)`] → extend it to assert radius-sm/weight-medium on the History button and the table's max-height, so a regression is caught mechanically.
