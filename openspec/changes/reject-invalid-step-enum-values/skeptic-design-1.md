- **The precedent the design copies.** `AggregateStep.scala:182-186` is `super.validateRawConfig(raw).orElse { Try(decode).toOption ... }`, exactly as the design describes. `aggregationProblem` is public and is shared by `apply` and the analyze `validateAggregate`. Confirmed.
- **Line citations.** The `apply` enum checks are at FillNull :84-87, Window :99-118 and Pivot :80-83. The analyze validators are at :399-449, and the `shapeRejection` short-circuit is at :370-373. The decoders default missing values to `""` (`str(obj, key, "")`), and the editor's new-step defaults are at `stepNarrowing.ts:310-328`. All accurate.
- **(a) Empty means draft.** This matches the ticket's owner-approved scope ("keep accepting incomplete drafts ... etc.") and the existing rejection spec ("An omitted key is not rejected", "A draft with an empty required value is still accepted on write"). An explicit `"strategy": ""` decodes the same as an omitted key, so the two cannot be told apart. The editor never sends `""`: `handleStrategyChange` and `handleFunctionChange` coerce unknown values to defaults. The boundary is sound.
- **(b) Offset checked only for lag/lead.** `WindowStep.apply` reads `offset` only for lag/lead (`offset.getOrElse(1)`, else `0`), and the existing analyze `validateWindow` uses the same condition. Rejecting offset on row_number would be a new contract that the run path does not enforce. The design's scoping is correct.
- **(c) Analyze reports each problem exactly once.** `validateStepConfig` returns `shapeRejection` alone when it is non-empty. The per-kind validator and `requiredConfigProblems` run only on the else branch. `inferWindow` and `inferPivot` do not emit an enum error (`inferWindow` falls back to `string` for an unknown function), so there is no second channel. `stepConfigProblem` (:52), which `AutoRunTriggerService` uses, is the same function, so auto-run still skips these steps. Exactly-once holds structurally, and task 3.2 tests it.

### Non-blocking notes

1. **Fallback error text is upsertsource-specific. Fix it during implementation.** `useStepCardState.ts:303-306` falls back to "Failed to save this step's target or mode — the server didn't say why." D7 as written ("pass `captureErrors = true`") would show this text on a fillnull, window or pivot card whenever a rejection carries no server message. Make the fallback kind-neutral, or pass it per call site. Also update the `persist` doc comment at :259-264, which says only `onUpsertSourceChange` passes `true`.
2. **Analyze hides sibling problems behind the enum error.** Because of the short-circuit, a config like `{"function":"ntile"}` with an empty `outputColumn` now reports only the function error in analyze. Before, it reported both, joined. This is the same trade-off HEL-1310 accepted, and it satisfies "exactly once". It is a small loss of information worth one line in the design's Risks section.
3. **Op specs could mirror the aggregate precedent.** HEL-1310 added a write-time scenario to `pipeline-aggregate-op` (:156). Matching scenarios in the fillnull, window and pivot op specs would keep those capability docs from implying that execute time is the only enforcement point. This is optional, since the new requirement in `pipeline-step-config-rejection` is authoritative.
4. **Task 3.7 guard tests must mutate the right thing.** The pinned frontend lists are hand-maintained copies of the backend sets. The mutation that proves each guard can fail should alter the option constant, not the test's expected array.
