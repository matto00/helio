### Verdict: REFUTE

### Change Requests

1. **D3 has an unaddressed false-positive class: projections known to be INCOMPLETE, not just stale.** The only completeness skip in D3 is "empty projected input schema", which is local to the step. But `analyzeNodes` silently produces a structurally incomplete (left-only) schema in several cases that are not stale-schema cases at all:
   - a `union` with a `source`-kind secondary input — `sourceDependencyOf` covers `join` only, so union source-kind secondaries are NEVER resolved and `inferUnion` returns the left schema (PipelineAnalyzeService.scala, `inferUnion` `case None`);
   - a `join` whose source-kind secondary is missing, inaccessible (proposal path uses `findByIdOwned`), or has an empty inferred schema (`resolveSecondarySourceSchemas` drops it; `inferJoin` `case None` = passthrough);
   - descendants of an empty root schema: the root-level step is skipped, but a column-adding step there (e.g. `lookup` appending requested columns, `aggregate`) produces a NON-empty output, so its children are checked against a schema missing every real source column.
   In each case a downstream `select`/`filter`/`aggregate`/etc. that correctly references a right-side or source column would get a confident `field-not-in-input-schema` warning for a field that exists at run time. Required revision: D3 (and the spec's "Missing referenced field warns" requirement) must define projection completeness and propagate it — a node is "incomplete" if its root schema was empty, or it is a join/union/lookup whose secondary schema was unresolved, or any ancestor (parent chain AND lane dependency) is incomplete — and suppress `field-not-in-input-schema` on incomplete nodes. Specify the exact rule (including whether an op that fully redefines its output, e.g. aggregate/groupby, resets completeness) and add negative test cases to task 2.1: (a) union with source-kind secondary followed by a step referencing a secondary-only column → no warning; (b) join with an unresolvable source secondary followed by the same → no warning; (c) a column-adding step under an empty root followed by a reference to a source column → no warning. Same consideration applies to the join-key "missing left key" warning (spec: "a missing left key is a field-not-in-input-schema warning instead") when the join's own LEFT input is incomplete.

### Non-blocking notes

- helio-mcp `propose_pipeline` already returns `warnings: string[]` that drive `applyReady` (pipelineProposalHandlers.ts:44-57), and `runWarnings.ts` is another `warnings` channel. The new analyze `warnings` are objects and non-blocking; the tool descriptions (task 5.2) should explicitly distinguish them so an agent does not conflate the two.
- The spec says `warnings` is always present on both responses, but D9 types it optional in the frontend. Either type it required (backend always sends it) or note why optional.
- `WorkspaceContextService.buildPipeline` consumes `pipelineService.analyze` and drops everything but `steps`; warnings will not surface in `get_workspace_context`. Fine as out of scope, but worth one line in the proposal's Impact/Non-goals so it is a decision, not an omission.
- Adding the new response case class field: give it a default (`= Vector.empty`) or every existing test constructing `PipelineAnalyzeResponse(...)`/`PipelineAnalyzeProposalResponse(...)` (PipelineAnalyzeRoutesSpec, PipelineAnalyzeProposalRoutesSpec) must change; check whether `check-schema-drift.mjs` requires a schema for the new `AnalyzeWarningResponse` case class.
- D5 says "`JoinColumnNaming.resolveWithKey` exactly as `inferJoin`/`inferLookup` do" — `inferJoin` calls `resolve` (a wrapper). Equivalent; wording nit.
- Join-key type mismatch is scoped to `join` only; `lookup` (`sourceKey` vs `lookupKey`) has the same failure mode. Acceptable as scoped to the ticket text, but consider a one-line non-goal or follow-up.
