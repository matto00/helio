## Context

`PipelineAnalyzeService.analyzeNodes` already projects every node's `inputSchema`/`outputSchema` across trunk, tails, lanes and rejoins, and resolves a `join`/`lookup`/`union` secondary schema (lane via the walk, `join` source-kind via `secondarySourceSchemas`, HEL-1236). The only per-step finding it reports is a blocking `validationError`, which feeds `costVerdict.canRun` (`step-config-invalid`). Three schema-visible mistakes produce no finding at all (HEL-1069): a missing referenced field on ops that do not validate references, a join-key type mismatch, and a join column collision (now a silent `right_<name>` rename since HEL-1236/HEL-1250).

Constraints from adjacent work (verified on main at 9fbdd426):
- HEL-1279 (c26c3056): `PipelineAnalyzeService.stepConfigProblem` gates the dataset-write auto-run on step-CONFIG problems only, deliberately not on schema-derived problems, because stored inferred schemas can be stale (HEL-1280, open). Its guard test must stay green.
- Write paths validate with `validateRawConfig`; analyze-time findings must not leak into write-time rejection.
- HEL-893: CSV sources infer every column as `string` (the loader never casts), so a CSV key is honestly `string` in the schema.
- HEL-1267 (queued next) and HEL-1385 (filed) touch `PipelineAnalyzeService.scala`; keep edits there minimal.

## Goals / Non-Goals

**Goals:** three schema-only, non-blocking warning classes on the persisted, proposal and concise analyze responses; contract (JSON Schemas, helio-mcp types + tool docs, frontend types) in the same change; red-first test per class.

**Non-Goals:** frontend rendering of warnings (follow-up); surfacing warnings in `get_workspace_context` (`WorkspaceContextService.buildPipeline` keeps only `steps`); a `lookup` key type-mismatch warning (`sourceKey` vs `lookupKey`, same failure mode — follow-up); turning any existing `validationError` into a warning or vice versa; write-time rejection; row-level checks; numeric-function-on-string warnings (HEL-1403, which can reuse this channel); fixing HEL-1280 staleness.

## Decisions

### D1. Top-level `warnings` array keyed by `stepId`, not a per-step field
`AnalyzeStepResponse` has ~25 sealed subtypes, each a hand-listed case class with its own `jsonFormat`. A per-step field would touch every one of them (and every JSON Schema step variant). A top-level `warnings: [{stepId, code, message}]` on `PipelineAnalyzeResponse` and `PipelineAnalyzeProposalResponse` is additive, keeps per-step shapes byte-identical, and is easy for an agent to scan. Always present (empty array when none), so consumers never need to distinguish absent from empty. Codes: `field-not-in-input-schema`, `join-key-type-mismatch`, `join-column-renamed`. Alternative (per-step `warnings`) rejected for blast radius.

### D2. A pure post-pass in its own file, run on the final projections
New `domain/engine/AnalyzeSchemaWarnings.scala` (object) exposing a pure function over `(steps: Vector[NodeStepInput], projections: Map[String, AnalyzedStep], secondarySourceSchemas: Map[String, Vector[SchemaField]]) => Vector[AnalyzeWarning]`. It re-derives each join/lookup's secondary schema with the same rule `analyzeNodes.processNode` uses (lane → that node's projected output; join source-kind → `secondarySourceSchemas`); the small lane/source-dependency helpers in `PipelineAnalyzeService` may be made package-visible rather than duplicated. `analyzeNodes`, `AnalyzedStep`, `validateStepConfig`, `stepConfigProblem` and every `infer*` are NOT changed. It runs on the projections AFTER `UpsertTargetAnalysis.overlay` (so a step whose overlay added a `validationError` is skipped, D5). `PipelineService.analyze`, `analyzeConcise` and `analyzeProposal` each call it with the exact `nodeInputs`/`secondarySchemas` they already pass to `analyzeNodes` — no second schema resolution.

### D3. Missing-field: per-op reference table, only where analyze does not already error
The pass extracts referenced INPUT field names from each op's decoded config. Ops whose analyze path already reports unknown fields as a `validationError` (compute, convertformat, analyzewithai, generatetext, splittext, extractheadings, chunkbytokencount, pivot, unpivot, assert — verify) are excluded entirely, so a reference is never both an error and a warning. The executor builds the table for the remaining field-referencing ops (at least: aggregate groupBy names + aggregation `field`, groupby `groupBy` + `aggColumn`, filter, sort, dedupe, select, rename source names, cast, datebucket, window, fillnull, stringops, lookup `sourceKey`, join `joinKey` on the left side) by reading each op's config class AND its runtime step, and records for each: which config paths are input-field references, and which values mean "no field" (empty string, a documented wildcard such as a `count` with no field) — those never warn. Output-only names (aliases, `outputColumn`, new names) are never checked. An op whose config cannot be decoded is skipped (the existing config-error path owns it). The table lives as a single match in `AnalyzeSchemaWarnings`, with a test case per row.
Skips: disabled step; step with `validationError`; a step whose input projection is not name-complete (D3a).

### D3a. Projection completeness, propagated through the graph (skeptic design-1 CR1)
`analyzeNodes` silently produces structurally incomplete schemas that are not staleness at all, so a correct downstream reference to a column that exists at run time would otherwise warn. The pass therefore computes two flags per node, in the same topological order as `analyzeNodes` (parent chain AND lane dependency), from the same `steps`/projections/`secondarySourceSchemas`:

- **name-complete(output of N)** is false when ANY of:
  1. N is root-level and its root's source schema is empty;
  2. N is a `join` or `union` with a secondary input whose schema did not resolve (source-kind `union` is never resolved today; source-kind `join` is dropped when missing/inaccessible/empty), or whose lane node's output is not name-complete;
  3. N carries a `validationError` (its projected output is the identity fallback, not what runs) or its op is unknown;
  3b. N is an op whose run-time output column NAMES depend on the data and are not projected by analyze — `pivot` (analyze projects only `index`; `PivotStep` emits `<values>_<v>` columns from data values), and any other op task 1.2 finds with data-derived names;
  4. N's parent output (or the root, for a root-level N) is not name-complete —
  EXCEPT that `aggregate` and `groupby` reset name-completeness to true when they have no `validationError`: their output column NAMES are wholly determined by config (`lookup` with an unresolved secondary is name-complete too, since its appended names come from `config.columns`). A disabled node is transparent: its output flags equal its input flags.
- **type-complete(output of N)** is defined POSITIVELY (skeptic design-2 CR2): it is true only when name-complete is true AND N's input(s) are type-complete AND N's op is in the TYPE-TRUSTED allow-list — ops whose projected output types equal the run-time value classes they produce, either because they pass input types through unchanged or because they set the type authoritatively at run time. Initial allow-list (task 1.3 must confirm each entry against the op's runtime step, and remove any it cannot confirm): `filter`, `sort`, `limit`, `dedupe`, `select`, `rename`, `cast`, `compute`, `fillnull`, `stringops`, `assert`, `upsertsource`, and `join`/`lookup` only when their secondary resolved and is itself type-complete. Explicitly NOT trusted (type-incomplete for themselves and all descendants, no reset): `aggregate` (group-by `type` is informational — `AggregateStep` groups by the raw value), `groupby`, `window` (lag/lead `string` fallback), `pivot`, `unpivot`, `union` (lane union keeps the parent's type when the sides disagree), `lookup`/`join` with an unresolved secondary, every AI/text op, and any op not on the list. A root-level node's input is type-complete iff its root schema is non-empty.

Rules: `field-not-in-input-schema` is emitted only when N's INPUT (parent output / root) is name-complete — this also covers the join "missing left key" case. A join's right-side key reference is checked only when the secondary is resolved and its lane output (if lane-kind) is name-complete. `join-key-type-mismatch` is emitted only when BOTH the left input and the secondary are type-complete. `join-column-renamed` is emitted only when the secondary resolved and both sides are name-complete.

### D4. Join-key mismatch compares runtime-equality families, conservatively
`JoinStep` indexes the right side by raw key value (`groupBy(_.getOrElse(joinKey, null))`) and looks up left values by `==`/hash, so a `String "1"` never matches a numeric `1`, while Scala's cooperative equality makes boxed `Long 1` and `Double 1.0` match. The check maps each declared canonical type (`DataFieldType.CanonicalWireValues`) to the family of its RUNTIME representation and warns only when both families are known and differ. The executor MUST establish each type's runtime representation by probe (what value class does a row carry for a `date`/`datetime`/`string-body`/`boolean` column from each producer) and record it in a task note; any type whose runtime representation is not pinned (or can be a `String`) maps to the string family or to "unknown" (no warning) — never a confident false positive. Integer vs float: no warning unless the probe shows they fail to match at runtime. Requires the key present on both sides, the secondary schema resolved, and both sides type-complete (D3a); otherwise no type warning.

### D5. Collision: report the HEL-1236 rename, never change it
For `join` (key = `joinKey`) and `lookup` (dropped key only when `sourceKey == lookupKey`, requested columns = `config.columns`), compute `JoinColumnNaming.resolveWithKey` exactly as `inferJoin`/`inferLookup` do and emit one `join-column-renamed` warning per right column whose output name differs from its original name (`inferJoin` reaches `resolveWithKey` via its `resolve` wrapper; same function). The projected schema is untouched (it already shows `right_<name>`); the warning makes the rename visible next to the step, consistent with the owner ruling that a collision never errors.

### D6. Non-blocking by construction, guarded by tests
Warnings are a separate output of a separate function; nothing reads them except response assembly. Guard tests (each labelled as a guard, and each shown failable by a mutation that routes a warning into the blocking path): (a) a pipeline with all three warning shapes analyzes with `costVerdict.canRun == true` and no warning-derived `reasons`, and every step's `validationError` absent; (b) `stepConfigProblem` returns `None` for those steps' configs; (c) the existing HEL-1279 guard test is unmodified and green; (d) a write (create/update step) with such a config is accepted.

### D7. Wording handles schema staleness (HEL-1280)
Messages state the evidence base, never existence: e.g. `aggregate: field 'amount' not found in this step's inferred input schema (available: category, total)`; `join: key 'id' is string on the input but integer on the secondary input; values of different types never match, so the join may return no rows`; `join: right-side column 'total' collides with an input column and will appear as 'right_total'`. Available-field lists are capped (e.g. first 20 names + `…`). A stale stored schema can still produce a wrong warning; because warnings never block (D6), that cost is a misleading hint, not a refused run — the reason these are warnings and not errors.

### D8. Concise mode: per-node messages, omitted when empty
`ConciseAnalyzeNode` gains `warnings: Option[Vector[String]] = None` (messages only, omitted when none), so a concise-mode agent still sees them. `PipelineAnalyzeConciseByteBudgetSpec` must stay green unchanged.

### D9. Contract surfaces in the same change
`schemas/pipelines/pipeline-analyze-response.schema.json` and `pipeline-analyze-proposal-response.schema.json` add a required `warnings` array (`additionalProperties: false` on both, so the property must be declared); the concise schema adds the optional node `warnings`. helio-mcp `types.ts` adds `AnalyzeWarning` and the fields; `analyze_pipeline` and `analyze_pipeline_proposal` descriptions state warnings are non-blocking and do not affect `canRun`. The executor must check every helio-mcp code path that reshapes an analyze response (`pipelineProposalHandlers.ts`, `combinedProposal.ts`, `write.ts`) and either pass `warnings` through or document why that path does not surface analyze output. Frontend: analyze response types gain `warnings` as a REQUIRED field on the full/proposal response types (backend always sends it) and optional on concise nodes; no rendering. The backend case-class fields default to `Vector.empty` so existing constructions in tests compile unchanged; the executor checks whether `scripts/check-schema-drift.mjs` needs a schema entry for the new `AnalyzeWarningResponse` case class. Tool descriptions must distinguish these analyze `warnings` (objects, non-blocking) from `propose_pipeline`'s existing `warnings: string[]` (which drive `applyReady`) and from `run_pipeline`'s run warnings.

## Risks / Trade-offs

- [False positives from stale stored schemas (HEL-1280)] → warnings only, evidence-based wording (D7).
- [False positives from structurally incomplete projections] → completeness propagation (D3a).
- [False type-mismatch warnings] → runtime-representation families from a probe, unknown → no warning (D4).
- [Reference table drifts as ops are added] → one match with a test per row; a new op with no row simply does not warn (fail-quiet, same as today).
- [Merge friction with HEL-1267/1385 on `PipelineAnalyzeService.scala`] → logic in a new file; only visibility tweaks in the existing file.
