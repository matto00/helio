## Context

See proposal.md. Existing patterns: `audit_events` (V91) is append-only with a privileged-pool insert; `pipeline_run_rate_window` (V109) is the direct-owner RLS pattern (`ENABLE` + `FORCE` + one owner policy on `current_setting('app.current_user_id')`); `DbContext.withUserContext` vs `withSystemContext` (privileged pool, BYPASSRLS, V38 default DML grants); `PipelineRunGuardConfig` reads env once and holds the `SOURCE_FETCH_RATE_LIMIT_PER_WINDOW` precedent with a separate limiter instance; `PipelineSchedulerService.tick()` is the existing periodic tick. No account-deletion path exists in the backend (verified by grep), so FK cascade is the mechanism.

## Goals / Non-Goals

**Goals:** ingest allow-listed events safely; serve the later admin view (HEL-1211) from rollups; stay correct under the production non-BYPASSRLS role.
**Non-Goals:** any read endpoint, admin view, funnels UI, emission of the first-run events (declared only), backfill.

## Decisions

1. **Table `product_events` (V113).** `id UUID PK`, `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`, `event TEXT NOT NULL CHECK (event IN (...))`, `properties JSONB NOT NULL DEFAULT '{}'`, `occurred_at TIMESTAMPTZ NOT NULL`, `received_at TIMESTAMPTZ DEFAULT now()`. Index `(occurred_at)` for rollup/purge and `(user_id, event)`. Partial UNIQUE index on `(user_id, event)` WHERE event IN ('signup_completed','first_dashboard_rendered') gives server-side once-per-user dedupe via `ON CONFLICT DO NOTHING`. The CHECK list duplicates the Scala allow-list as defence in depth; a test asserts the two sets are equal.
2. **RLS and grants.** `ENABLE` + `FORCE`; policy owner-scoped `USING/WITH CHECK (user_id = current_setting('app.current_user_id')::uuid)` (V109 pattern), inserts via `withUserContext`. Rollup and purge touch all users, so they run on the privileged pool (`withSystemContext`). V113 adds explicit idempotent `GRANT SELECT, INSERT, UPDATE, DELETE ON <each new table> TO helio_privileged` (V105/V102 precedent; V38 default privileges are not relied on). The app-pool role OWNS every new table (V91 header), so it can read/write the rollup tables: they hold aggregates only (no user id), which is accepted; HEL-1211 must read them on the privileged/owner-tier path. The FK cascade on user delete is an FK action, not RLS-gated. Verification: the executor creates a non-BYPASSRLS LOGIN role in an isolated scratch database (never the shared dev DB), applies V113 as it, and exercises (a) user-context insert, (b) cross-user select isolation, (c) rollup and purge via `SET ROLE helio_privileged`.
3. **Rollups: materialized on the scheduler tick**, not compute-on-read, because per-user rows are purged and history survives only as stored rollups. Final table set (all in V113, no user id in any, no RLS):
   - `product_event_daily(day DATE, event TEXT, event_count BIGINT, active_users BIGINT, PRIMARY KEY(day,event))`: per UTC day, rows and distinct users for that event.
   - `product_active_users_daily(day DATE PRIMARY KEY, daily_active_users BIGINT, weekly_active_users BIGINT)`: distinct users across ALL events on `day`; WAU is distinct users across all events in the 7 UTC days ending on `day`, computed from raw rows at rollup time. WAU cannot be recomputed once earlier raw rows are purged, so `rollupDay` upserts WAU only while `day - 6` is still inside the retention window; otherwise it leaves any existing row untouched.
   - `product_ttfd_daily(day DATE PRIMARY KEY, sample_count INT, median_seconds DOUBLE PRECISION, p90_seconds DOUBLE PRECISION, histogram JSONB)`: samples are users whose `first_dashboard_rendered` fell on `day`; seconds as defined in decision 9; median = `percentile_cont(0.5)`, p90 = `percentile_cont(0.9)` (continuous interpolation, hand-computable); histogram = JSON object of bucket upper bound (seconds) to count with fixed bounds `{"60","300","900","3600","86400","+Inf"}` (non-cumulative, `<= bound`).
   - `product_event_property_daily(day DATE, event TEXT, property_key TEXT, property_value TEXT, event_count BIGINT, PRIMARY KEY(day,event,property_key,property_value))`: ONLY for `firstrun_template_chosen.template`. Cardinality is bounded: the value is rolled up as-is only when in the registry's `RolledUpTemplateSlugs` allow-list (empty now, extended by the first-run leaf), else bucketed to `other`.
   - `product_rollup_state(id SMALLINT PRIMARY KEY CHECK (id=1), rolled_through DATE, last_purge_at TIMESTAMPTZ)`: high-water mark and purge throttle timestamp.
   `rollupDay(day)` runs in one transaction under `pg_advisory_xact_lock` (Cloud Run may have two instances; precedent in PipelineRunRepository) and upserts with `INSERT ... ON CONFLICT DO UPDATE`, so concurrent or repeated runs are idempotent. The tick recomputes today and yesterday each pass and advances `rolled_through` to a day only once it is at least 2 UTC days old, running `rollupDay(D)` one final time immediately before advancing past D. Invariant: a day enters the high-water mark only after the `occurredAt` clamp (now-24h) plus flush delay has passed, so no late row can land in a rolled day; purge is 90 days out, making this doubly safe. `rollupDay` for a day whose raw rows were partly purged never overwrites (skipped when day is before the purge cutoff).
4. **Purge.** `purge(now: Instant, windowDays)` with an injected clock deletes rows with `occurred_at < now - window` only where `day <= rolled_through`, running rollup first for any uncovered day. **`signup_completed` and `first_dashboard_rendered` rows are exempt from purge** (at most one row per user each, a timestamp and no properties): purging them would silently exclude long-tail users from TTFD and let a cleared-localStorage re-emit pass the unique index. They are removed by account deletion (FK cascade). This is a documented deviation from "all per-user rows purged" and is called out to the driver. Window default **90 days: a DRIVER DEFAULT, not an owner ruling**, env `PRODUCT_EVENTS_RETENTION_DAYS`. Throttled to once per hour via `product_rollup_state.last_purge_at`, under the same advisory lock. Tests inject time; no wall-clock wait.
5. **Validation.** A single Scala registry maps event -> allowed property keys -> typed validators: `signup_completed` (server-only, `{}`), `first_dashboard_rendered {panelCount: int 1..500}`, `provenance_opened {}` (authenticated opens only; the client skips tracking in the unauthenticated public share view because the endpoint requires auth, and the spec counts authenticated opens only), `firstrun_file_dropped {source: "drop"|"paste"}`, `firstrun_dashboard_created {panelCount: int 1..500}`, `firstrun_template_chosen {template: slug ^[a-z0-9-]{1,40}$}`. Batch 1..25, whole-batch 400 on any violation. `occurredAt` from the client is clamped to `[now-24h, now+5min]` (offline tolerance) else server now.
6. **Rate limit.** `PRODUCT_EVENTS_RATE_LIMIT_PER_WINDOW` (default 60), its own limiter instance via the existing `RateLimitDirective`, window reuses `RATE_LIMIT_WINDOW_SECONDS`; documented in the CLAUDE.md env table in this change, plus `PRODUCT_EVENTS_RETENTION_DAYS`.
7. **`signup_completed`.** Recorded inside `AuthService.register` and, for a newly created user, `AuthService.completeOAuth` (Google signup), so OAuth-created users are not silently absent from signups/day and TTFD. Recorded AFTER `userRepo.insert` commits (the FK needs the committed users row), via `withUserContext(newUser.id)`, best-effort through `recover` (a failure logs and never fails registration).
8. **`first_dashboard_rendered`.** Emitted when a dashboard view has at least one output panel whose rows fetch resolved with row count > 0. Client guards with a per-user localStorage flag set only after the server has CONFIRMED delivery (by the queue, on a 2xx), plus an in-memory per-page-load claim to stop duplicate queuing; an unconfirmed or dropped event is re-emitted on a later visit, which is safe because of the server dedupe; the server unique index is the real dedupe (multi-tab, cleared storage).
9. **TTFD.** Seconds difference per Spec; users lacking `signup_completed` are EXCLUDED, no backfill from `users.created_at`: a synthetic signup time is not an observed event, and it would mix a measured population with an assumed one. Negative differences excluded. The day key is the day of the first dashboard.
10. **Client.** `frontend/src/features/telemetry/track.ts`: queue in memory and `localStorage`, flush via `fetch(..., {keepalive:true})` on a timer / `visibilitychange`, never awaited by callers, errors swallowed with a single `console.warn`, bounded queue (200). Each queued event carries the user id it was queued under (identity supplied via `setTelemetryIdentity`, wired in `main.tsx`); the server attributes a batch to the session user, so on flush events queued by a different user are discarded and nothing is queued or sent with no signed-in user. The one typed `TelemetryEvent` union mirrors the server registry.

## Risks / Trade-offs

- [RLS masked locally] -> non-superuser scratch-database reproduction and skeptic review of the migration.
- [Shared dev DB poisoned by a half-applied V113] -> apply first in an isolated scratch database; only then the shared DB via the standard path.
- [90-day window is a guess] -> flagged as driver default, env-configurable.
- [WAU from daily rows] -> computed at rollup time from raw rows while they exist; not recomputable after purge, accepted.
- [Client clock skew] -> clamp.

## Migration Plan

V113 only (one migration, created tables have no FK from other tables; rollback = drop the product_events table and all five rollup/state tables). Purge/rollup wired into the existing tick, no new timer.
