### Verdict: REFUTE

Round 2's six items are genuinely addressed and the newly-cited line numbers and return types are all accurate — I re-derived every one. But my independent pass found (a) a class of caller that structurally breaks Decision 7's central "one row per actor-initiated API call" invariant and is unmentioned anywhere in the artifacts, and (b) one new Decision 9 bullet whose factual premise about the code is wrong, making its instruction unimplementable as written.

### Change Requests

1. **Composite *apply* callers fan out through the very service methods being instrumented, silently violating Decision 7 — and one of them will write a false `dashboard.delete` row.** This is the biggest gap and it is invisible to task 7.5, because it is not a route-to-action mapping question (7.5's shape) but a cardinality question about instrumented services being called N times by one API call.
   - `services/patchsets/PatchSetApplyForward.scala:26 applyOne` applies each resolved edit **via the existing per-resource service methods** — its own header comment says so: "applies one resolved edit via the matching EXISTING per-resource service method only — no direct repository writes." It dispatches to `panelService.create/update/delete`, `dashboardService.create/update/delete`, `dataSourceService.createStatic/update/delete`, `dataTypeService.update/delete`, `pipelineService.*` (`:33-90`). So one `POST /api/patch-sets/apply` (`PatchSetRoutes.scala:40`) will emit **one audit row per edit in the patch set**, not one per API call. Same for `POST /api/patch-sets/:id/undo` (`PatchSetUndoRoutes.scala:30` → `PatchSetUndoService.undo:64`), which replays inverse edits — an undo will be recorded in the trail as a fresh series of user-initiated creates/updates/deletes with no indication it was an undo.
   - `services/proposals/DashboardProposalService.scala:64 apply` calls `dashboardService.create(...)` (`:88`) then `panelService.create(...)` per panel (`:113`) and `panelService.update(...)` (`:192`) — one `POST /api/proposals/apply` (`CombinedProposalRoutes.scala:37` → `CombinedProposalService.apply:71`) becomes 1 + N rows. Worse: `:93` calls `dashboardService.delete(dashboard.id, user)` as a **rollback on failure**, so a *failed* apply would write a `dashboard.create` **and** a `dashboard.delete` row for a dashboard the user never successfully created — an audit trail asserting an action that never happened, which is exactly what Decision 2 exists to prevent.
   Required: add a decision (extending Decision 7) that rules explicitly on fan-out callers — either (a) these composite endpoints emit their own single event and the underlying per-resource calls are suppressed for them (which needs a stated mechanism, e.g. an audit-context/flag parameter threaded through the service call, since the service can't otherwise tell who called it), or (b) N rows are accepted as correct for these paths and Decision 7's "one row per actor-initiated API call" is explicitly narrowed to exclude them. Either way the internal-rollback-delete case (`DashboardProposalService.scala:93`) must be ruled on by name. Add tasks and at least one spec scenario. Note this cuts at the core service-layer premise: instrumenting at the service layer does **not** yield one row per API call whenever another service composes those calls.

2. **Decision 9's `ImageUploadService` bullet is factually wrong about the code, and its instruction cannot be carried out.** It states `ImageUpload` "is a `DataSource`-producing ingestion path exactly like `DataSourceService`'s own `createImageUpload`/`createImageUrl`" and directs the executor to emit `data_source.create` with "`resource_id` = the resulting upload's data source id". Verified otherwise: `ImageUpload` (`domain/model/model.scala:648-656`) is `(ImageUploadId, UserId, storageKey, mimeType, filename, sizeBytes, createdAt)` — **no data source id exists on it** — and its own doc comment at `:645-647` says it "has no parent DataType/row — it is a direct-owner upload backing an Image panel's `imageUrl`, served back unauthenticated via `GET /api/uploads/image/:id`." `ImageUploadService.upload:48` writes bytes via `fileSystem.write` and inserts into `repo` (the image-upload repo); it never touches `DataSourceService`, which reaches its own image path via the separate `ingestImage` helper (`DataSourceService.scala:388-406`). Task 5.4 inherits the same wrong instruction. Required: re-decide this call site against what the code actually is — either a distinct action (e.g. `upload.create` / `image_upload.create`) with `resource_id` = the `ImageUploadId`, or explicitly out of scope — and correct both design.md Decision 9 and task 5.4. Do not leave `data_source.create` with a nonexistent id.

3. **MFA lifecycle mutations are half-in, half-undecided.** Decision 6 already pulls `MfaService` into scope for `verifyLogin`, and task 6.2 instruments it. But `MfaRoutes.scala` exposes four further `POST` mutations that change a user's authentication posture — `enroll` (`:59` → `startEnrollment`), `enroll/confirm` (`:62` → `confirmEnrollment`), `backup-codes/regenerate` (`:69`), `disable` (`:76` → `disable`) — and no artifact mentions them, not even to exclude them. Given the ticket's stated auth scope and that `MfaService` is already receiving an `AuditService`, leaving these unruled means the executor decides an auth-namespace question at implementation time. Required: one line each in design.md ruling them in (with action names, e.g. `auth.mfa.enroll`/`auth.mfa.disable`) or out, plus tasks if in.
