## Skeptic Report — design gate (round 1, skeptic-design-1.md)

Reviewed tree: HEAD 625e1deff20f2ba73e98b2cfa0a1d0d1e298e25a (planning artifacts untracked under the change dir).

### What I verified (with evidence)

- **The leak is real, and the root cause matches the design.** In `PipelineService.create` (PipelineService.scala:147-187), `resolveRootSourceIds`/`resolveRootDataSources` run `resolveOneRootSourceId` → `resolveInlineRootSourceId` (774-818), which commits the source through `createStatic`/`createSql`/`createRest` before `createTransactional` (314-384) or `pipelineRepo.create` runs. Every step and Output check sits inside `buildStepsAction` (525-609) or `buildOutputsAction` (614-668), and those run inside `runTransactionally`, so the rollback cannot reach the source.
- **Point 3 (statuses):** `ServiceResponse.scala:102` maps UnprocessableEntity to 422. `rawConfigProblem` returns 422 (564-566). An unknown type returns 400 "Invalid step type" (548-551). Decode failure returns 400 (570). A disallowed Output key goes through `OutputConfigValidation.validate`'s "Unknown config key" into BadRequest, so 400 (691-694). An absent fieldMapping column returns 400 (`OutputBindingSpec.scala:193-201`, which is strict, so an empty schema also fails). An unknown root `sourceId` returns 404 on both paths: transactional via `findByIdOwned` None (226), simple via `pipelineRepo.create` "Data source not found" mapped to NotFound (173). All spec scenario statuses match the live code.
- **Point 1 (compensation vs one transaction):** the AC reads "validate … BEFORE any write, **and/or** run source creation inside the same transaction". Validate-first is explicitly allowed. Decision 2's compensation only goes beyond the AC to cover the residual post-creation classes. `createSql`/`createRest` insert and then do an outbound `inferSchema` (SourceService.scala:81-86, 222-227; CreateSourceEnvelope.scala:47-60), so a single transaction would need a new cross-service DBIO API and would hold a transaction open across network I/O. Compensation is an acceptable fix, and **no escalation is needed**. `DataSourceService.delete` (DataSourceService.scala:649-662) refuses (409) while any reference exists. So if compensation ever fired after a commit, it would refuse instead of deleting a live root's source. That backstop is good.
- **Patch-set:** `resolvePipelineCreate` (PatchSetApplyResolvers.scala:537-584) pre-checks only roots and `rawConfigProblem`. `rawConfigProblem` returns None for an unknown kind (PipelineStep.scala:283-284), so unknown type and bad Output config reach `PatchSetApplyForward.scala:86-89`, which creates the inline source. Production wires `sourceService`/`dataSourceService` into the same `pipelineService` that the patch-set uses (ApiRoutes.scala:396-403, 525). The leak is live on that path.
- **Point 4 (red-first):** each 1.1 case with an inline `dataset` root commits through `createStatic` before the failing check, so a count by `owner_id` is red on the pre-fix tree. The superuser `DbContext(db, db)` does not affect this, because the count is by exact owner id and nothing in the leak depends on RLS. The patch-set unknown-type and bad-Output-config cases pass resolve on the pre-fix tree (see above), so they are red-first-capable *provided the test wires `dataSourceService` into `PipelineService`*. Without it, the inline branch returns InternalError (775-776) and nothing is created.
- **Point 2 (enumeration):** this is incomplete; see CRs 1, 2 and 4.

### Verdict: REFUTE

### Change Requests

1. **The pre-flight ordering silently changes an existing failure class (C4 violation).** Today, `validateStepCrossOwnerRefs.validateLane` (429-441) runs for every step before `buildStepsAction`:
   - A lane `secondaryInput` naming a clientId absent from the request returns **422** "Lane reference '<id>' does not exist in this request."
   - A self-reference returns 400 "cannot reference the step itself."

   Decision 1 puts the "lane forward reference (400)" check (the `rewriteLaneClientId` logic, 595-601) into the pre-flight and orders the pre-flight *before* `validateStepCrossOwnerRefs`. A nonexistent or self lane id is also "not an earlier clientId", so these requests would now get the forward-reference **400** with a different message. No existing test pins the 422 (grep over `src/test` for "does not exist in this request" returns zero hits), so the gates would not catch it.
   - **Required:** state in design.md that the pre-flight runs the pure request-scoped lane checks (self, exists-in-request, ancestor; same messages and statuses) before that step's forward-reference check, or leaves the forward-reference check out of the pre-flight.
   - Add tasks asserting, with an inline root, that a nonexistent lane reference still returns 422 with today's message, that a self-reference still returns today's 400 message, and that zero new `data_sources` rows exist.

2. **The failed-Future branch of Decision 2 has no proof.** Decision 2 claims cleanup on "any unexpected exception". But every planned test exercises a `Left`, never a failed `Future` outside the transaction's `recover`. The uncovered calls are the `findByIdOwned` re-lookup (225), `resolveSecondarySourceSchemas` (364) and the simple path's `pipelineRepo.create`, none of which is recovered today.
   - **Required:** add a task for a service-level case where a call after creation returns a failed Future, using a stub repo whose `findByIdInternal` or second `findByIdOwned` throws. Assert that the inline source is deleted, and specify whether the original exception is re-thrown after cleanup (it should be; it must not be swallowed into a different error). This is red-first-capable: on the pre-fix tree the source survives.

3. **The simple-path multi-root case is mandatory, not conditional.** Decision 4 says "plus the simple path if a reachable post-creation failure exists". On the pre-fix tree it is reachable: with no steps and no Outputs, `roots: [inline dataset, {sourceId: <unknown>}]` commits root 0 and then returns 404 from `pipelineRepo.create` (PipelineService.scala:166-175; PipelineRepository `create` "Data source not found"). Task 1.1's multi-root case does not say whether it carries steps.
   - **Required:** split it into two cases, one on the simple path (no steps/outputs) and one on the transactional path, both red-first.

4. **Same-family leaks are not enumerated.** The AC says "Check the patch-set … path for the same leak", and Non-Goals already does this for `addRoot`. Give each of these an explicit disposition: fix it, or list it as a Non-Goal plus a follow-up candidate.
   - **(a) Patch-set mid-set rollback.** A `pipeline create` edit with an inline root succeeds, then a later edit fails. `PatchSetApplyRollback.scala:137-145` deletes only the pipeline, so the inline source is orphaned while the response (HTTP 200, `PatchSetApplyService.scala:126-129`) reports the edit `rolledBack`.
   - **(b) Bare-`url` inline `rest_api` root.** It creates an implicit "Auto: <name>" Connector with a credential write (SourceService.scala:119-170). `DataSourceService.delete` does not remove it, so Decision 2's compensation leaves an orphan Connector. HEL-826 already treated an orphaned implicit Connector as a defect.
   - **(c) Failed Future inside `createSql`/`createRest` after insert.** If `dataSourceRepo.insert` has committed and `inferSchema`/`upsertInferredSchema` then returns a failed Future, the id never reaches the tracking list, so this is an orphan that Decision 2 cannot see.

5. **The design must acknowledge the recorded ruling it partly reverses, and plan the docstrings it will falsify.** `PipelineService.create`'s doc (138-141) records that a create-then-compensate delete "was cycle 4's implementation; the coordinator ruled it out explicitly". `resolveOneRootSourceId`'s doc (750-752) says root creation "has no … 'delete the inline source if the rest of the request later fails' undo step to track".
   - **Required:** in Decision 2, cite the HEL-906 ruling and distinguish it. It covered pipeline, step and Output rows, where one DBIO transaction was proven to work. It did not cover inline sources, which cannot join that transaction without a new API and network I/O under an open transaction.
   - Add a task to update both docstrings, so the code does not contradict itself after the change.

### Non-blocking notes

- Running the pre-flight before `validateStepCrossOwnerRefs` also changes precedence when one request has several errors. For example, an unowned join source (404) in one step and a refused config (422) in a later step: today's 404 becomes 422. Precedence is not a contract, but say so in Risks next to the inline-root precedence note.
- Task 1.2: say explicitly that the patch-set test wires `PipelineService` with `sourceService`/`dataSourceService`, as `PipelineRootRoutesSpec` does at lines 119-131. Otherwise the inline branch returns InternalError and the "red" never appears. C2 would catch this, but it is cheaper to state it.
- Task 2.3's cleanup-fails case is a guard, not a red-first test. Label it as one, and show it can fail: for example, remove the original-error preservation and confirm the test fails.
- The fieldMapping *slot-name* check (`OutputBindingSpec.validateFieldMapping`) depends only on the request and could join the pre-flight. Keeping it post-creation is fine because Decision 2 covers it.
- A Pekko request-timeout returns 503 while the Future continues. If the create then succeeds, the source is not orphaned (the pipeline references it); if it fails, compensation runs. Nothing to do.
