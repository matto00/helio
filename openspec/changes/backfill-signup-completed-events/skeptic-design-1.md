## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)
- Read ticket/proposal/design/tasks/spec delta. Latest migration is V113 (so V114 is free).
- V113__product_events.sql: ENABLE+FORCE RLS, policy product_events_owner uses bare current_setting('app.current_user_id')::uuid for USING and WITH CHECK; partial unique index uq_product_events_once_per_user matches the ON CONFLICT predicate in the design. Confirmed.
- No migration enables RLS on `users` (grep of db/migration): that claim holds.
- ProductEventRollupService.tickAt: with rolled_through Some(rt), start = min(rt+1, today-1); only None starts at earliestEventDay. ProductEventRepository.rollupDayAction returns false (no write) for days <= rolled_through that are <= retention cutoff; setRolledThrough only moves forward.
- product_rollup_state is seeded with one row (rolled_through NULL) by V113, has no RLS.

### Verdict: REFUTE

### Change Requests
1. **The core AC is unmet by the planned design when prod rolled_through is already non-NULL, and this is the likely case; the design defers it to the executor as "escalate".** tickAt only rolls from rolled_through+1 (bounded to today-1) once any event has been rolled. Any prod event after telemetry shipped (a signup_completed, firstrun event, etc.) makes the first tick set rolled_through; from then on the backfilled historical days are never rolled and /admin/usage (rollup-tables only) shows nothing for them. The ticket AC "/admin/usage shows signups per day back to earliest real user" then fails despite a perfect V114 insert. This cannot be left to an executor-time escalation (the unit test with rolled_through NULL would pass green while prod stays broken). Revise the design to choose a mechanism now, for example: V114 also sets product_rollup_state.rolled_through = NULL when it inserted rows (rollup of recomputable days is idempotent; rollupDayAction recomputes from raw rows, so confirm and document that already-purged days (> retentionDays, other-event rows gone) are not corrupted by the recompute -- the `covered` guard is what protects them, and resetting to NULL removes it), or a bounded reset to (min backfilled day - 1) via a state update, or a one-off rollupRange. If the owner must pick between these, raise a formal ESCALATION now with options instead of deferring it. The mechanism must be proven in a test that starts from rolled_through NON-NULL with rolled days present (not only NULL), and the spec delta scenario "History becomes visible on the first rollup tick" must be rewritten to cover that case (currently it only specifies rolled_through null).
2. Task 3.2 ("determine and report whether rolled_through can be non-NULL") is a research task whose answer is already derivable from the code (yes, trivially). Replace it with the implemented fix plus its test; add a task for the corrupted-day check in request 1 (days older than retention cutoff with partially purged non-signup rows).
3. Add to tasks 2.x an explicit assertion that the migration runs inside Flyway's transaction under the non-superuser role (set_config is_local=true leak check, Decision 2 states this but the task only says "not left set"; make it asserted on a fresh connection/statement after the migration, and cover the zero-users case: the DO loop must not fail on an empty users table).
4. Decision 1 says "Alternative bracket if empirical failure" but also the design must state the table-owner/privilege assumption: migration role needs SELECT on users and INSERT on product_events (owner under FORCE RLS still subject to policy -- fine). State that the red-first test uses the same non-superuser role setup as FlywayNonSuperuserMigrationSpec (migrate to V113, seed users, attempt plain INSERT -> expect 42704/RLS violation, then run V114), so the red step is on the real schema, not a hand-built table.

### Non-blocking notes
- DAU for historical days being signup-only is correctly documented as a limitation; also consider noting that WAU is NULL for days older than the retention window by existing design (wauComputable).
