## Context

`product_events` has ENABLE + FORCE RLS with policy `product_events_owner` (`user_id = current_setting('app.current_user_id')::uuid`, bare form: raises 42704 if unset). Prod Flyway runs as the non-BYPASSRLS table owner `helio`; FORCE means even the owner is subject to it. A plain `INSERT ... SELECT FROM users` passes locally (superuser) and fails in prod. `users` itself has no RLS policy (verified by grep of migrations), so the migration role can read all users.

## Goals / Non-Goals

**Goals:** backfill signups under the prod role, idempotent, proven under a NOSUPERUSER NOBYPASSRLS role with actual rows; verify the rollup consequence.
**Non-Goals:** `first_dashboard_rendered` backfill; any rollup semantics change.

## Decisions

1. **Mechanism: per-user transaction-local `set_config` inside a `DO` block loop** (`FOR u IN SELECT id, created_at FROM users LOOP PERFORM set_config('app.current_user_id', u.id::text, true); INSERT ... ON CONFLICT (user_id, event) WHERE event IN ('signup_completed','first_dashboard_rendered') DO NOTHING; END LOOP`). Alternative: the repo's NO FORCE/FORCE bracket (V94/V98). Chosen over it because it takes no ACCESS EXCLUSIVE DDL lock on a live table, does not depend on table ownership, and exercises the real WITH CHECK policy. Preconditions: the migration role is the table owner with SELECT on `users` and INSERT on `product_events` (FORCE RLS still applies to the owner, so the policy is evaluated). The red-first test uses the same non-superuser setup as `FlywayNonSuperuserMigrationSpec`: migrate to V113, seed users, show the plain INSERT failing with an RLS/42704 error, then apply V114. The executor MUST verify empirically under the non-superuser role; if it fails, fall back to the bracket and record why. The loop is O(users), acceptable (small user count); `is_local=true` scopes to the migration transaction.
2. **No leak:** `set_config(..., true)` is transaction-local; the test asserts `current_setting('app.current_user_id', true)` is empty/NULL on a fresh statement after migration. If Flyway runs the migration in a transaction (default) this holds; test must prove it.
3. **Idempotency** via the existing partial unique index and `ON CONFLICT ... DO NOTHING`; a user with an existing event is skipped; new signups that land concurrently during deploy are unaffected (their row wins, conflict no-ops).
4. **Rollup consequence and the non-NULL `rolled_through` case (skeptic round 1, decided now).** With `rolled_through` NULL, `tickAt` starts at `earliestEventDay()` and `rollupRange(from, today, advanceThrough = today-2)` rolls everything in ONE transaction under one advisory lock. But once any day <= today-2 has been rolled, `rolled_through` is non-NULL and `tickAt` resumes from `rolled_through+1` (bounded to today-1), so backfilled history would never reach `/admin/usage`. Prod telemetry started ~2026-10-02 20:28Z; `rolled_through` advances only once today-2 >= the earliest event day, so whether it is already set at deploy time depends on release timing -- it must not be assumed NULL. **Decision:** V114 ends with `UPDATE product_rollup_state SET rolled_through = (min backfilled `occurred_at` UTC day) - 1 WHERE id = 1 AND rolled_through IS NOT NULL AND rolled_through >= (that day)`, executed only if the backfill inserted at least one row. A NULL stays NULL (the tick already starts at `earliestEventDay()`, now the earliest signup). This lowers the high-water mark so the next tick recomputes forward from the earliest backfilled day; `rollupDayAction` is an idempotent recompute from raw rows. `product_rollup_state` has no RLS (verified), so no bracket is needed. **Corruption bound:** lowering the mark removes the "covered AND partly purged" guard for the re-rolled days, so a day older than the retention cutoff whose non-signup rows were already purged could be recomputed from partial rows. This cannot occur at the intended deploy (telemetry is ~1 day old versus `retentionDays` 90, so nothing has been purged), and V114 runs once; the executor must nonetheless TEST the guard behaviour and the design states the accepted limitation: V114 must not be re-applied to a database with purged history (Flyway guarantees run-once). The simple form above is the decision; no retention-dependent clamp. Verify in tests: (a) rolled_through NULL, ~400-day history: one tick rolls all days through today-2, sets `rolled_through`, time measured; (b) rolled_through NON-NULL (e.g. today-2) with rolled days present, V114 lowers it, next tick rolls the historical days and restores the mark; (c) WAU: non-NULL for days inside the retention window, NULL for older days is by existing `wauComputable` design; (d) purge keeps `signup_completed` rows. DAU for historical days is signup-only (documented limitation).
5. Migration file is additive, never edited after applied.

## Risks / Trade-offs

- Prod-only failure class (RLS) is invisible to superuser checks -> mitigated by red-first non-superuser test with rows.
- Active-user metrics for historical days are signup-only; this is inherent to the owner's ruling and is documented, not fixed.
