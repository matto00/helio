### Verdict: REFUTE

The security core (Decisions 1–3, 6) is sound and matches ground truth. What is missing is (a) the one thing that would make the headline tenant-isolation AC *provable* rather than merely asserted, and (b) three concrete under-specifications a competent implementer could read two ways.

### Change Requests

1. **Tasks 2.4 will pass vacuously as written — bind the isolation proof to the non-BYPASSRLS harness.** Design Decision 2 asserts RLS is the fail-closed backstop *and* Decision 2/Task 1.1 require a redundant app-level `actorUserId === callerUuid` filter. A route-level integration test running on the ordinary (superuser/BYPASSRLS) test connection cannot distinguish "RLS held" from "the app filter held" — it will go green even if `withUserContext` were replaced with `withSystemContext`. Add an explicit task: a `findPaged` test in `AuditEventRepositorySpec` (or a sibling spec) using that file's existing `helio_app_test` non-BYPASSRLS role, asserting user A's `findPaged` returns none of user B's rows **with the app-level actor filter's contribution neutralized** (e.g. also assert the RLS-scoped path returns empty when the context user is B and the filter targets A's rows) — i.e. a test that would fail red if RLS were bypassed. Keep 2.4's route-level two-user test as well; just do not let it be the only evidence for the ticket's primary AC.

2. **No deterministic sort order is specified anywhere — pagination is unstable without one.** `findByActor`/`findByResource` sort by `createdAt.desc` only, and a single request routinely emits multiple audit rows with identical/near-identical `created_at`. With `offset`/`limit` paging over a non-unique sort key, rows can be duplicated across pages or skipped entirely. `design.md` Decision 1 and `tasks.md` 1.1/1.2 are silent; `specs/audit-query-api/spec.md`'s Pagination requirement states no ordering at all (only the UI spec says "most recent first"). Specify a total order — `ORDER BY created_at DESC, id DESC` — in Decision 1, in task 1.1, and as a requirement/scenario in `specs/audit-query-api/spec.md`.

3. **The "actor" column has no honest content — resolve before implementation.** The ticket AC requires "human-readable action/resource/**actor**/source/timestamp," but every row returned is by construction the caller's own, and Decision 5's response carries only `actorUserId` and `actorTokenId` as opaque UUID strings. As designed, task 4.1's actor column renders the viewer's own UUID (and, for PAT events, a second opaque token UUID) — not human-readable, and not useful. Decide and record explicitly in `design.md` + `tasks.md` 4.1: either (a) drop the actor column and keep source only, or (b) render "You" plus the token's **name** — noting that (b) requires the response to carry a token name/label, which `AuditEventResponse` as specified in Decision 5 does not, so Decision 5 and the schema would need to change. Do not leave this to the executor to guess.

4. **UI pagination behavior is unspecified.** The backend defaults to `limit=200` and reports `total`, but `specs/audit-events-ui/spec.md` has no requirement about how many rows the view shows or how a user reaches older events, and `tasks.md` §4 has no pagination task. As written an implementer may reasonably build a single unpaginated 200-row dump with silently truncated history. State the intended behavior in the UI spec (a scenario for "more events than one page") and add a corresponding task — or explicitly record "first page only, no controls" as a deliberate v1 decision in `design.md` so it is a choice rather than an omission.

### Non-blocking notes

- `design.md` Decision 6 has an unclosed parenthesis and a run-on that makes the sentence hard to parse — worth a cleanup pass since this is the decision the honesty requirement rests on.
- Decision 5 echoes `metadata` (raw `JsValue`) straight to the client. Since every row is the caller's own, this is not a cross-tenant leak, but a one-line note in `design.md` acknowledging that HEL-477 instrumentation's metadata is surfaced verbatim would be worth having on record.
- `specs/audit-query-api/spec.md`'s 401 scenario is good; consider also asserting that a valid PAT (not just a session) can call the endpoint, since `AuthDirectives` supports both and the UI/PAT distinction is central to this ticket's rendering.
