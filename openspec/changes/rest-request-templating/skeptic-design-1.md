### Verdict: REFUTE

The design is strong in its adversarial core — Decision 4's credential-unreachability claim is genuinely structural (not merely asserted), Decision 6's stale-known-issue re-verification is correct, Decision 3's query-param reasoning is right, and the out-of-scope declarations (repeated keys, run-time overrides, body-as-entity) are honest rather than evasive. Four defects block implementation.

### Change Requests

1. **Flat contradiction on ephemeral-path behavior — an implementer cannot build this as written.** Three artifacts specify three incompatible behaviors for `{{...}}` reaching `buildEphemeralRequest`:
   - `proposal.md:15` — "has no `parameters` store, so any `{{...}}` there **fails loud** by design"
   - `design.md:29-30` — "A `{{...}}` placeholder reaching this path **always fails loud** as 'unresolved'"
   - `tasks.md:17` (3.2) — "verify (**do not implement**) that any `{{...}}` ... is **left as literal text** (EphemeralRestConfig has no interpolation call)"
   
   Fail-loud and literal-passthrough are opposite behaviors, and `specs/rest-api-connector/spec.md:19-22` makes fail-loud an **unconditional** `SHALL` ("It SHALL NOT be silently substituted with an empty string **or passed through literally**"), which tasks 3.2 directly violates. Pick one, make all four artifacts agree, and give it a test in section 4.
   
   Note for whichever is chosen: literal passthrough is the backward-compatible option (a bare `url` containing `{{` today works and would keep working); fail-loud is a behavior change on an existing path and, per tasks 3.2's "do not implement", is not actually being built. If literal passthrough is chosen, `spec.md`'s unresolved-variable Requirement must be scoped to the `connectorId`-resolving path rather than stated unconditionally.
   
   (The *boundary itself* — no `parameters` store on the ephemeral path — is legitimate and well-justified; design.md:30-33's argument that the AC's "authoring-time" coverage is satisfied by `connectorId`-carrying test/preview/refresh is sound. This CR is about the contradiction, not the boundary. But proposal.md:12-13's "one function, called from **both** `buildResolvedRequest` **and** `buildEphemeralRequest`" is false as designed and must be corrected too.)

2. **`parameters` as a non-`Option` payload field with a Scala default will silently break every existing REST source.** proposal.md:24 specifies "`RestApiConfigPayload`/`DataSourceConfigCodec` wire/decode `parameters` (default empty map)" and tasks.md 1.2 just says "Add `parameters` to `RestApiConfigPayload`". Read literally as `parameters: Map[String, String] = Map.empty`, spray-json 1.3.6 **ignores the default** (verified in `ProductFormats.fromField`: defaults are never consulted; only `OptionFormat` tolerates a missing field). Every already-stored `data_sources.config` JSONB blob lacks `parameters`, so `jsonFormat9`'s read throws → `decodeRest` returns `Left("malformed: ...")` → `DataSourceRepository.rowToDomain` substitutes `RestApiConfig(connectorId = "__malformed__")` behind a `warnOnce`. Result: every pre-existing REST source stops fetching, with no exception surfaced and only one log line. This directly destroys spec.md:15-17's "byte-identical to the pre-templating behavior" scenario. Required:
   - Specify in design.md and tasks.md 1.2 that the **payload** field is `parameters: Option[Map[String, String]] = None` (matching all eight existing sibling fields), with `RestApiConfig.parameters: Map[String, String] = Map.empty` on the **domain** side and `.getOrElse(Map.empty)` in `RestApiConfigPayload.toDomain` (`DataSourceProtocol.scala:332-356`).
   - Specify that `fromDomain` (`DataSourceProtocol.scala:357-366`) emits `None` when `parameters.isEmpty`, exactly like the existing `queryParams`/`headers` treatment — otherwise `encodeRest` output changes shape for every source and the "byte-identical" claim fails on the encode side too.
   - Name **both** `jsonFormat8` sites that become `jsonFormat9` (`DataSourceProtocol.scala:391` and `DataSourceConfigCodec.scala:20`) in tasks 1.2; the second is easy to miss.
   - Add a test to section 4: decoding a stored REST config blob **with no `parameters` key** yields a working `RestApiConfig` with empty parameters (this is the regression that CR2 exists to prevent, and 4.6 as written does not cover the decode path).

3. **`URLEncoder.encode` is the wrong encoder for a path segment.** design.md:79 specifies the endpoint helper as "`URLEncoder.encode(value, "UTF-8")`-based". `java.net.URLEncoder` implements HTML form (`application/x-www-form-urlencoded`) encoding, not RFC 3986 path-segment encoding: it encodes a space as `+`, which in a URL **path** is a literal plus character, not a space. A parameter resolving to `New York` would be delivered to the upstream API as the path segment `New+York` — a silently wrong request, not a rejected one. (It also leaves `*` unencoded and encodes `~`.) The unicode half of AC "escaped correctly per context ... unicode" would pass while the ASCII-space case is wrong. Specify RFC 3986 path-segment encoding instead — e.g. build the segment through Pekko's `Uri.Path` / `Uri.Path.Segment` rendering, or post-process `URLEncoder`'s output (`+` → `%20`, and re-encode `*`). Add a test with a space and a `*` in a templated endpoint value to tasks 4.4.

4. **The design commits to a value store that has no write path after create.** Decision 2 (human-resolved) says `parameters` is "set via API/agent alongside the template strings", and tasks 1.3 threads it through `CreateSourceRequest` only. `UpdateDataSourceRequest` is `(name: Option[String])` (`DataSourceProtocol.scala:107`) — the `PATCH /api/sources/:id` route (`DataSourceRoutes.scala:83-86`) cannot touch `config` at all. So a parameter value can only ever be changed by deleting and recreating the source, which makes source-level static parameters materially less useful than Decision 2 implies and pushes real usage toward the deferred run-time overrides (Decision 5). Either add the update path to scope (a `parameters` field on `UpdateDataSourceRequest` + `DataSourceService.update`, with a task and a test) or state it explicitly in Non-Goals as a known limitation with the follow-up named — do not leave it unstated, since Decision 2's escalated resolution reads as though the field is freely settable.

### Non-blocking notes

- **spec.md over-promises on `body`.** The ADDED requirement (spec.md:5-8) says body placeholders are "resolved ... before the outbound request is issued", and the Scenario at 46-49 asserts "the resolved body remains valid JSON". But `body` is never attached to any `HttpRequest` (verified: `RestApiConnectorDriver.scala:137`), and tasks 3.1 interpolates only endpoint/query/headers — 4.7 tests body against the interpolator in isolation. design.md Decision 7 is honest about this; the spec delta is not. Consider rewording the body clauses to the interpolator-level contract HEL-826 will consume. The HEL-826 split itself (Decision 7) is a real, non-colliding boundary — this ticket ships `resolve` + the JSON-escape helper, HEL-826 wires the entity and calls them — no duplicated templating path.
- **JSON body escaping assumes a string context.** `JsString(value).toString` minus its outer quotes is correct for `{"n": "{{x}}"}` but gives no protection for `{"n": {{x}}}` (numeric/structural position), where a resolved value can still break the document. design.md:85-87 states the assumption; worth restating in spec.md's escaping Requirement (line 33-34's "cannot break out of its JSON string context" already implies it, but the assumption is load-bearing enough to name).
- **`parameters` is plaintext in `data_sources.config` JSONB** and is echoed back by `DataSourceResponse.fromDomain` via `SecretRedaction.redact` with `HasSecrets[RestApiConfigPayload] = HasSecrets(Set.empty)` (`DataSourceProtocol.scala:375`) — i.e. no redaction. Nothing stops a user or agent from putting an API key in `parameters`, where it is stored unencrypted and returned by every source read path. The credential-unreachability work (Decision 4) is airtight for the *Connector's* credential but creates an adjacent plaintext store the design never characterizes. Worth one sentence saying `parameters` is explicitly not secret storage (and, if cheap, a doc/comment on the field).
- proposal.md:44's claim that widening `queryParams` would affect "the frontend" is unsupported — `grep -rn "queryParams" frontend/src` returns zero hits. Harmless to the decision (the out-of-scope call stands on the backend churn alone), but the justification overstates.
- tasks 4.2 (prove the run-time pipeline path resolves identically "not just argued from shared code") is exactly the right instinct and the strongest single item in the test plan — keep it.
