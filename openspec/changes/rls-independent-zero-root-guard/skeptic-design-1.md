## Skeptic Report — design gate (round 1, skeptic-design-1.md)

### What I verified (with evidence)

- Read `ticket.md`, `proposal.md`, `design.md`, `tasks.md`, `specs/pipeline-zero-root-db-guard/spec.md` in the worktree change dir.
- Read `V99__prevent_zero_root_pipelines.sql` and `V40__fix_rls_policy_function_recursion.sql` in full.
- **Mechanism (D1) is sound.** `V34__*.sql:17-18` creates `helio_privileged` as `CREATE ROLE helio_privileged BYPASSRLS NOLOGIN`, and `:27` `GRANT helio_privileged TO current_user` (so the migrating role may `ALTER ... OWNER TO` it). Postgres decides RLS bypass on the *effective* user id, which `SECURITY DEFINER` switches to the function owner, and `has_bypassrls_privilege` is a direct role attribute — so a `helio_privileged`-owned `SECURITY DEFINER` body reads with RLS disabled. This is byte-for-byte V40's shipped, production-proven shape. **Re-owning IS sufficient.**
- **FORCE RLS premise confirmed, not assumed:** `V35:29` / `V94:1309` / `V98:330` force RLS on `pipelines`; `V98:349` forces it on `pipeline_roots`. The vacuity diagnosis is real.
- **D2's ordering claim holds.** `CREATE OR REPLACE FUNCTION` requires ownership of the existing function; after `ALTER FUNCTION ... OWNER TO helio_privileged` the migrating role is no longer owner and the replace would fail with `must be owner of function`. Replace-then-re-own is correct.
- **D3 grant reasoning is sound** and correctly asserts rather than assumes.
- Read `DataSourceService.delete` (`backend/src/main/scala/com/helio/services/sources/DataSourceService.scala:579-607`) and `DataSourceRepository.soleRootDependentPipelines` (`.../sources/DataSourceRepository.scala:228-239`) to test the false-positive claim in D6. This is where the plan breaks (CR2 below).

### Verdict: REFUTE

Three blocking defects. The fix mechanism is right; the *proof* plan is self-contradictory, and the change's behavioural blast radius is mis-scoped.

### Change Requests

1. **Tasks 3.7 and 3.7a demand two mutually exclusive outcomes from the SAME reverted state — the proof plan cannot be executed as written.** 3.7a says "in the SAME reverted state as 3.7". In that state the function still carries `SET row_security = off` (only the `OWNER TO` line is reverted), so the body's read is *not* silently empty — Postgres raises `query would be affected by row-level security policy`, SQLSTATE `42501`. That is exactly what 3.7a wants, and it makes 3.7's required red ("the guard did not raise", or the post-state `roots=0`) **unreachable**. Worse, 3.7 explicitly instructs the executor to classify a `permission denied` red as a WRONG-reason red, "record it, discard it, fix the harness" — `42501` is `insufficient_privilege`, i.e. the tripwire firing correctly would be discarded as harness breakage and the executor would thrash against a phantom. Split into two distinct mutation states and say so in D5:
   - **3.7 (fix mutation):** revert the `OWNER TO` line **AND** remove `SET row_security = off`. Expected red: silent non-firing — no raise, post-state `roots=0`. This is the only configuration that reproduces the original defect and therefore the only one that proves the re-own is load-bearing.
   - **3.7a (tripwire mutation):** revert the `OWNER TO` line, **keep** `SET row_security = off`. Expected red: loud, SQLSTATE `42501`, message `query would be affected by row-level security policy`.
   Update 3.7's wrong-reason list accordingly: `permission denied` on `pipelines`/`pipeline_roots` (a missing `GRANT SELECT`) is still a wrong reason, but `42501 / query would be affected by row-level security policy` must be named as *the expected right-reason red for 3.7a*, not lumped in as harness noise.

2. **The plan does not test the one behavioural divergence the fix actually creates on the live user path, and a design Risk bullet asserts something false about it.** After V100 the trigger reads with `BYPASSRLS`; `DataSourceRepository.soleRootDependentPipelines` (the HEL-987 pre-check) still runs under `ctx.withUserContext`, i.e. RLS-scoped. Their visibility now differs. In any case where a `pipeline_roots` row points at the caller's data source but the `pipelines` row is not visible to the caller under `helio_can_access_pipeline` (revoked grant, cross-user sharing, ownerless/legacy row — the very "cross-user grant-revocation variant" the proposal's Non-goals waves away as "whatever this fix closes incidentally"), the sequence is: pre-check returns empty → `deleteFileF` **deletes the backing file first** (`DataSourceService.delete:588-599`) → the delete then hits the now-BYPASSRLS trigger and raises → the race-path `recover` maps it to a generic 409. Net: a delete that previously **succeeded** now fails, *after* irreversibly destroying the source's file. That is a real new false positive with data loss, on the shipped user path, and D6 does not cover it — 3.3 only tests the GUC-set **owner**, and 3.4/3.5 only test structural cases with the GUC unset. Required: (a) add a gate exercising a delete where the trigger can see a pipeline the pre-check cannot (GUC set to a caller who is not the pipeline's owner / has no grant), asserting the intended outcome explicitly; (b) state in design and V100's header whether the pre-check must be widened (e.g. a privileged read) to stay consistent with the trigger, or explicitly accept the divergence with the file-deletion ordering addressed; (c) **correct the false claim** in design.md Risks — "it returns no data to the caller beyond the pipeline ids in the error message, which the caller already necessarily referenced". After this fix the caller may be handed the id of a pipeline they never referenced and cannot see. Either scope that disclosure honestly or suppress the ids on the cross-tenant path. This ticket exists because a migration header asserted something that was not true; do not ship a second one.

3. **The mutation checks edit V100 after it may already be applied to the shared dev database — the known Flyway-checksum incident, re-armed.** Task 1.7 boots against the shared dev DB with V100 applied; 3.7/3.7a then mutate V100's SQL body. Once the dev DB has recorded a checksum for V100, any subsequent boot with a different V100 body fails validation (`Database.initApp` uses Flyway defaults — the design itself establishes this, and it is the whole basis of the `v100-header-only` ruling). Add explicit sequencing constraints to design + tasks: all mutation work runs **only** against EmbeddedPostgres in the new spec, never against the dev database; task 1.7's dev-DB boot check runs **last**, against the final frozen V100 body; and if a mutated V100 ever reaches the dev DB, the recovery step (`flyway repair` / drop the row) is named in the task rather than discovered mid-run.

### Non-blocking notes

- D2's stated threat model is slightly overstated: after the re-own, a future migration running as `DB_USER` **cannot** `CREATE OR REPLACE` this function at all (it would fail with `must be owner`), so the "silently re-created under `DB_USER`" path realistically requires `DROP` + `CREATE` (or an explicit re-own). The tripwire still has value — worth stating the mechanism precisely in V100's header rather than implying a replace could quietly change ownership.
- Task 1.1's probe runs against "a scratch harness"; consider making it literally the new `V100ZeroRootGuardNonSuperuserSpec` fixture at an earlier commit, so the vacuity proof and the regression gate provably exercise the same fixture rather than two hand-built ones that could differ.
- Nothing asserts the trigger is still attached to `pipeline_roots` after the `CREATE OR REPLACE` (it is, same OID) — 3.2 covers it behaviourally, so this is a note only.
