## Goals / Non-Goals

**Goals:** close the case-variant Owner claim; make Owner reachable only via verified Google sign-in (or a manual DB grant); remove the literal address from deploy config and from the live files this change touches; fail loudly on pre-existing duplicates.

**Non-Goals:** refusing unverified Google sign-in for non-owner accounts, and account linking between Google and password accounts (HEL-1856 — this change covers only HEL-1856's "unverified Google email can match the owner allowlist" bullet); password-signup email verification (HEL-1715); editing `infra/.env.deploy.example` or any `.env*` (the driver fixed the example in a separate PR); rewriting git history; any prod action; any frontend change.

## Decisions

**D1 — One shared normaliser.** Add `EmailNormalizer.normalize(raw: String): String = raw.trim.toLowerCase(java.util.Locale.ROOT)` (one object, e.g. `com.helio.domain.auth` or `com.helio.services.auth`; executor picks, one definition only). Trim semantics are fixed ONCE as Java `String.trim`: strip every leading/trailing char in U+0000..U+0020 (space, tab, CR, LF, other C0 controls). The migration (D2) implements the identical class in SQL as `lower(regexp_replace(email, '^[\x01-\x20]+|[\x01-\x20]+$', '', 'g'))` (Postgres text cannot hold U+0000, so `\x01` is the effective lower bound) — the executor proves equivalence with a migration-spec case using a tab/newline-padded duplicate. Callers: `RequestValidation.validateRegisterRequest` and `validateLoginRequest` return the request with the normalised email (normalise first, then validate format, so `"  A@B.co "` is valid); registration additionally rejects (400) an email that still contains any whitespace or control character after normalisation, so no such address is stored from now on; `AuthService.completeOAuth` normalises `profile.email`; `UserTierConfig.isOwnerEmail` and `fromEnv` use it for both sides; `UserRepository.findByEmail` filters on `lower(email) === normalize(input)` (Slick `_.email.toLowerCase`) so it hits the new functional index and still matches a row inserted by a raw writer. `Locale.ROOT` avoids the Turkish dotless-i trap. Lower-casing equivalence is claimed for ASCII only: Java `toLowerCase(Locale.ROOT)` and Postgres `lower()` (collation-dependent) may differ on some non-ASCII letters the format regex admits. That residue is harmless here: uniqueness and lookups are both decided by Postgres `lower(email)` over the stored value, and after D3 no lowercasing mismatch can grant Owner (Owner needs a Google-verified email). Alternative rejected: normalising only in the repository — the allowlist check and the stored value must use the same form, and the ruling asks for one normaliser at the entry points.

**D2 — Migration `V148__users_email_lower_unique.sql`.** Order: (1) a `DO` block counts groups of the D1 SQL normal form (`lower(regexp_replace(email, '^[\x01-\x20]+|[\x01-\x20]+$', '', 'g'))`) with `count(*) > 1`; if any, `RAISE EXCEPTION` with a message naming HEL-1852/V148, the number of colliding groups, that no rows were changed, and that duplicates must be resolved manually first (no addresses in the message — it lands in Cloud Logging). (2) `UPDATE users SET email = <same normal form> WHERE email <> <same normal form>`. (3) `ALTER TABLE users DROP CONSTRAINT users_email_key` (no `IF EXISTS`: a drifted name must fail loudly). (4) `CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email))`. One Flyway transaction, so a failure in any step leaves the table untouched. Must run as the non-superuser `helio` role in prod (see MISTAKES.md "RLS policies never run in dev or CI"; the existing `FlywayNonSuperuserMigrationSpec` must stay green). Alternative rejected: `citext` — new extension, wider blast radius.

**D3 — Owner only via verified Google.** Password register always inserts `free`. Password login no longer promotes (delete `promoteIfAllowlisted`; `finishLogin` receives the user as stored). Google sign-in: `ownerEligible = profile.emailVerified && profile.email.isDefined && tierConfig.isOwnerEmail(normalisedEmail)`, computed once in `AuthService.completeOAuth` and passed to `upsertGoogleUser` as a `Boolean` (the repository no longer takes `UserTierConfig`). New user: `owner` iff eligible, else `free`. Returning user: promoted iff eligible and not already `owner`; never demoted. The fallback `google:<sub>@helio.invalid` address is never eligible.

**D4 — `email_verified` parsing.** `GoogleProfile` gains `emailVerified: Boolean`. The reader maps `JsBoolean(true)` and `JsString("true")` to `true`; missing, `false`, or any other shape to `false`. Never throws for that field.

**D5 — Register race returns 409.** The register insert maps a Postgres unique violation (SQLState `23505`) to `ServiceError.Conflict("email already registered")`, so a concurrent case-variant register is 409, not 500. The Google insert path keeps today's behaviour on collision (HEL-1856's linking rule); the executor confirms with a test that a Google first sign-in colliding with an existing password row's email (case-variant) is rendered by the callback's existing "unexpected internal failure" handling, not an unhandled 500 body, and records the result.

**D6 — Secret wiring.** `cd-backend.yml`: drop `HELIO_OWNER_EMAILS=...` from `--update-env-vars`; append `HELIO_OWNER_EMAILS=helio-owner-emails:latest` to `--update-secrets`; update the adjacent comment. `infra/deploy-backend.sh`: drop it from `--set-env-vars`, append to `--set-secrets`, and drop any now-unused required-variable check for `HELIO_OWNER_EMAILS` in that script (inspect the script only, never the env files). `BetaAccessService` keeps reading `tierConfig.ownerEmails` (the env var name is unchanged; only its source changes). Cloud Run refuses to change an existing variable from a literal to a secret in one update, so the release checklist (D9) adds a one-time owner step before tagging: preferred atomic form `gcloud run services update helio-backend --region=us-west1 --project=helio-493120 --remove-env-vars=HELIO_OWNER_EMAILS --update-secrets=HELIO_OWNER_EMAILS=helio-owner-emails:latest`, with the two-step form (remove, then add) as fallback; both marked unverified (C8: no gcloud calls). During a two-step window the allowlist is unset: harmless for tiers (promote-only) but beta-access notifications return 503.

**D7 — Guard.** New `scripts/check-deploy-env-no-emails.mjs` + `.selftest.mjs`, `package.json` scripts `check:deploy-env-no-emails[:selftest]`, wired into `ci.yml`'s job beside `check:cloud-run-cpu` (CI only, NOT `.husky/pre-commit` — same reasoning as ci.yml's own comments; avoids the gate-chain requirements). It fails if any `--update-env-vars`/`--set-env-vars` flag VALUE (scoped to that value only — `--service-account=helio-backend-sa@...` legitimately contains `@`) in `cd-backend.yml`'s non-comment `flags:` or `deploy-backend.sh`'s non-comment `gcloud run deploy` contains an `@`-address token or a `HELIO_OWNER_EMAILS=` entry, fails if either path's secrets flag (`--update-secrets`/`--set-secrets`) does not map `HELIO_OWNER_EMAILS=helio-owner-emails:latest` (a silent drop of the allowlist is also caught), and fails (never vacuously passes) if either file or flag is missing. The selftest proves it red on a fixture with `owner@example.test` in the env-vars flag.

**D8 — Fixtures and docs.** Test fixtures that obtained Owner by password-registering an allowlisted email switch to an explicit tier grant (`updateTier`/direct SQL), the "manual DB grant" path the ticket allows. Each such edit is a direct consequence of D3, listed in the executor report. The real address in `GoogleOAuthRoutesSpec` becomes `owner@example.test`. CLAUDE.md: edit only the `HELIO_OWNER_EMAILS` table row. `docs/secrets-inventory.md`: a `helio-owner-emails` section (what, where, accessor SA, rotation = add a version + redeploy).

**D9 — Release checklist.** A new `release-checklist.md` in the change dir (source for the PR body's "Before release" section), in the ruling's order: (a) create Secret Manager secret `helio-owner-emails` (value entered interactively, never on a command line that lands in shell history); (b) grant `helio-backend-sa@helio-493120.iam.gserviceaccount.com` `roles/secretmanager.secretAccessor` on that secret; (c) the exact read-only duplicate-check SQL, using the SAME normal-form expression as V148's `DO` block, so a clean result guarantees V148 will not raise (it returns normal form + count only, no other columns); (d) the exact read-only Owner-tier listing SQL — `id, email, created_at, google_id IS NOT NULL AS has_google, password_hash IS NOT NULL AS has_password` for `tier = 'owner'`, ordered by `created_at` — with a note that a password-only Owner row is the attack's signature and must be confirmed or demoted by hand; (e) the one-time literal-to-secret switch (D6), marked unverified; (f) then tag. It also states which part of HEL-1856 this covers (unverified Google email can no longer match the owner allowlist) and which it leaves (refusing unverified Google sign-in for non-owner accounts; the account-linking rule and its 500), that git history still holds the address (rewrite out of scope), and that `infra/.env.deploy.example` is handled by the driver with the owner.

**D10 — Whole-tree address scrub (owner ruling, added mid-run).** Every tracked file in the current tree that contains the real owner address (including historical `openspec/changes/archive/**` files) has each occurrence replaced with `owner@example.com`; history is not rewritten. The list is re-derived with `git grep -lF -i` over a shell variable holding the value (never printed, never written anywhere, `unset` afterwards), excluding `.env*` paths. `GoogleOAuthRoutesSpec` keeps its allowlist-match coverage by using the placeholder on both sides. The D7 guard is widened: it also fails on any email-shaped token in `.github/workflows/*.yml` or the `deploy-backend.sh` gcloud invocation whose domain is not `example.com`/`example.test`/`example.org` and that is not on a small explicit allowlist of non-personal addresses (service accounts, GitHub noreply). The real value is never embedded in the guard.

## Risks / Trade-offs

- [Prod holds case-duplicates] → V148 aborts the deploy's migration step loudly; release is gated on the owner's duplicate check (PR "Before release").
- [An attacker already holds a case-variant Owner account in prod] → not demoted by this change; the PR's "Before release" lists the one-time Owner-tier listing (ticket AC) so the owner can fix it by hand.
- [Literal-to-secret type switch fails the first CD deploy] → one-time manual step in "Before release".
- [Owner's own password login stops promoting] → existing Owner rows keep Owner; a fresh environment needs one verified Google sign-in or a manual grant.
- [Google sign-in for an address that case-matches an existing password account now collides] → previously it silently created a duplicate; behaviour on collision is HEL-1856's linking rule.
- [Fixture edits mask a defect] → evaluator checks each fixture edit maps to D3.

## Migration Plan

Deploy V148 with the code. Rollback: the index can be dropped and `users_email_key` re-added; lowercasing is not reversed (no information needed). Release order (owner): create `helio-owner-emails`, grant `helio-backend-sa` secretAccessor, run the duplicate check and the Owner listing on prod, perform the one-time literal-to-secret switch, then tag.
