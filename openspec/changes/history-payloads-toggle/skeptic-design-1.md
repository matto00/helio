### Change Requests

1. **Correct the false RLS premise (design.md Context bullet 9, D1 last two sentences, Risks bullet 2).** `users` carries no RLS (`V88__user_tier.sql:9-10`), and a pipeline editor grantee can read the pipeline row on the RLS pool (`V39:79-81`). Keep the decision (privileged pool, one batched query, called only with pipeline ids of Outputs already authorized for this caller), but give the real reasons:
   - it matches `ownerLimit` and the repository's privileged-only contract (its class doc);
   - the payload writer reads the same join the same way, so the flag and the writer cannot disagree;
   - it stays correct for an owned Output whose pipeline grant was revoked (GET /api/outputs).

   Restate the safety property as "authorization happens before the lookup", not "RLS would block it". Reword the Risks bullet. "RLS-only defect invisible locally" is not the risk being mitigated, and the cross-tier route test cannot detect an RLS defect anyway, because dev and CI run BYPASSRLS (MISTAKES.md §"RLS policies never run in dev or CI"). Otherwise a false "users has RLS" claim will flow into code comments and the spec.

2. **Resolve the D5 / spec ambiguity about what Save sends when unavailable or unchanged.** D5 says the sheet seeds state from `config.historyPayloads === true` and always adds "an explicit boolean" on update. It also says that when unavailable "the stored value is re-sent unchanged". These conflict whenever the stored config has no `historyPayloads` key (or has `null`). The seed is then `false`, and Save writes `historyPayloads: false`. That changes the stored config, while the spec's unavailable requirement says "Saving SHALL NOT change the stored `historyPayloads` value", and task 4.2 tests "never changes the stored value". An implementer can read this two ways (semantic equivalence vs. literal preservation), and the test can be written either way. Pick one and state it in D5, the spec and 4.2. Recommended: omit the key from the PATCH config unless the toggle is enabled and its state differs from the seeded value. The shallow merge (`OutputService.mergeConfig`) then preserves whatever is stored (absent, null or a stale `true`) byte-for-byte. Keep the "true or false" persistence wording for a user-changed enabled toggle.

3. **Remove the conditional in D2 and state the decision.** `OutputRoutes` already takes `historyService: Option[OutputHistoryService] = None` (`OutputRoutes.scala:30`). Decide:
   - the new dependency's exact shape (e.g. `payloadAvailability: Option[(NodePayloadHistoryRepository, PayloadHistoryConfig)] = None` or equivalent);
   - that `ApiRoutes.scala:940` passes `Some(resolvedNodePayloadHistoryRepo, payloadHistoryConfig)`;
   - that test fixtures without it omit the field.

   Then reconcile this with ticket.md's "present on every Output REST route response": add a 4.1 assertion that the production-wired route (built through `ApiRoutes`, not a bare `OutputRoutes` fixture) emits the key at all 5 sites. Otherwise a missed wiring that omits the field everywhere still passes, and the frontend fails closed silently.

4. **D6 anchor placement and acceptance signal.** The "Beta access" `<h2>` lives in `SettingsPage.tsx` (the `<section>` wrapping `<BetaAccessSection />`), not inside `BetaAccessSection`. An `id` on `BetaAccessSection`'s root scrolls the heading just out of view. Put `id="beta-access"` on that `<section>` in `SettingsPage.tsx`, or state why not. Also note that the four sections above it (Preferences, Agent memory, Security, PATs) render loading placeholders and then content, so a mount-time `scrollIntoView` can land short after layout shift. Say when the scroll fires. In 4.4, add an acceptance signal: after clicking "Request Beta access" and Settings settling (`e2e/support/settingsReady.ts` exists), the "Beta access" heading is in the viewport. "Link to Settings" alone does not prove the spec's "leads to Settings' Beta access section".

### Non-blocking notes

- 4.1 lists "free/beta owners" for the route spec. The ticket's additional acceptance asks for free, beta *and owner* plus cross-tier. 1.1's repository spec covers owner, so this is met overall, but adding an owner-tier case at route level is cheap.
- A beta/owner *viewer* who edits their own Output on a free-owned shared pipeline sees "Free stores run summaries only / Request Beta access", and the link lands on "You have Beta access." (`BetaAccessSection.tsx:26-30`). This follows from owner rulings Q1/Q3, so it is not a change request. The executor may want a test that pins it, so nobody later "fixes" it back to `User.tier` (C1).
- D2 says "Patch-set apply/preview also call it". There are six such sites (listed above). That is harmless, but the enumeration helps the executor confirm none was meant to change.
- An Output's `config` can still carry a client-sent `historyPayloadsAvailable` key (config is not key-whitelisted). The spec scenario only constrains the top-level field, which is correct. The frontend must read the top-level field only (D3 already says so).
